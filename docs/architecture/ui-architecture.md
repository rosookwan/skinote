작성 2026-09-23(같은 날 검토 반영). 고침 2026-09-24: 사장님 답 — 왼쪽 레일 없앰 확정(1절), 리프트권 반납 도장 · 보증금 칸 · 반납 창의 부분 반납(6-2 · 6-4 · 6-5), 하루 기준 시각 06:00과 마감 화면 첫 줄(7절). 같은 날 다시 고침: **채택한 둘째 판 시안**([docs/design/screens-v2](../design/screens-v2/spec.md))에 맞춰 반납 창(6-2, V1), 접수 확정 창(4-5 · 6-4, V4), 확인 창 높이(5절), 기사 업무 판의 말(6-3 · 6-5, V7), 구역 버튼 수(4-4 · 5절)를 고치고 새 접수 · 한 번에 수납 · 마감 · 가게 규칙을 새 절로 더했다(6-6 ~ 6-9). **배치가 클라우드 중심으로 바뀌어**(README ADR-19) 카운터도 오프라인에서 같은 코드로 그린다(5절 `ConnectionStrip`, 7절 `LocalClient`). 같은 날 셋째 검토를 반영했다: 카운터 장부도 연결 띠 자리를 늘 비워 둠(4-3), 끊긴 반납 창은 권을 처음에 고르지 않음(6-2), 끊긴 카운터의 권 지급 · 바꿔 드림 · 적재(6-2), 배달의 `못 전함` 동작 행(6-5), 온라인 · 오프라인 넘기기 지연과 '결과 확인 중'(7절), 관리자 콘솔은 따로 된 주소(1 · 7절), 카운터 판이 바뀌는 때(7절). **같은 날 넷째 고침: 화면 문구를 대화형 말에서 짧은 업무 용어로 바꿨다**(README D6, 기준은 [docs/design/wording.md](../design/wording.md)): 이 문서가 인용한 화면 글(버튼 · 이름표 · 알림 · 예시)을 그 표의 말로 고쳤고, 설계 설명 문장과 식별자는 그대로다. 새 React 앱(`apps/pos`)의 화면을 **설정으로 그리는** 구조다. 방향은 C(종이 대여 장부와 도장)를 바탕으로, A의 '지금' 줄, B2의 남은 일 목록, A3의 ▲▼ 순서 바꾸기를 섞는다(docs/53, 시안 [`docs/design/redesign-mockups.html`](../design/redesign-mockups.html)). 자료 쪽 표는 [`schema.sql`](../../packages/schema/schema.sql) 2.6절, 품목 능력 값과 속성은 [catalog-and-pricing.md](catalog-and-pricing.md).

## 0. 한눈에

- 옛 화면은 거의 모든 것을 코드에서 갈랐다: 리프트권 분기 20곳 이상, 한글 상태 이름을 정렬 기준으로 사용, 화면 크기 구간을 12곳 넘게 숫자로, 메뉴 · 설정 탭 · 할인 종류 · 스키장 템플릿을 코드 배열로. 남겨 쓸 만한 것은 카드 · 줄 · 타일 공통 부품, 글자 맞추기 엔진(parts · items · words · alts), 높이로 나누는 쪽 넘김, 크기 토큰, 규칙 검사기였다.
- 새 화면은 **세 층의 설정**으로 그린다. ① 코드: 기기 크기 규칙(DeviceProfile), 부품, 코드 키 어휘(sys 표), ② 매장 데이터: 품목 종류 표시, 도장 단계, 장부 칸 · 탭 · 바닥줄 · 동작, 메뉴, 상태 문구, 사용 기능, ③ 기기: 잰 크기와 역할로 고른 등급.
- 새 품목 종류 · 새 도장 · 새 장부 칸 · 새 속성은 **행을 더하면** 화면과 인쇄에 나온다. 앱이 새 기본 설정을 가져오면 이미 쓰던 매장에도 들어간다(2절). 코드를 고치는 것은 새 그리기 방식이나 새 계산 규칙이 필요할 때뿐이다.
- **넘치는 것을 모두 한 모델로 다룬다**(4-4): 장부 칸만이 아니라 탭, 메뉴, 바닥줄 숫자, 결제 칸, 결제 수단, 옆 동작, 속성 자리도 우선순위와 '넘칠 때'가 있다. 같은 계산이 개발 시험, 설정을 바꾸는 명령(서버), 화면(기기)에서 돈다.
- 크기 규칙은 기계가 검사한다: 매장 기기 등급은 글자 16px 이상, 누르는 곳 52px 이상(기사 기기 56px), 말줄임표 없음, 반쯤 잘린 줄 없음, 스크롤 대신 쪽 넘김.

## 1. 방향과 바뀌는 결정

| 화면 | 바탕 | 섞는 것 |
|---|---|---|
| 오늘 할 일 | C1 오늘 대여 장부(한 줄 한 팀, 지급 · 반납 · 수납 도장 칸, 색인 탭) | A1의 '지금' 노란 줄(시각순 줄 사이에 지금 시각 표시), 야간 수거 준비 안내 |
| 접수 확인 | C2 대여 접수증(품목마다 지급 · 반납 동그라미) | B2 남은 일 목록(화면 이름 `처리 현황`: 완료 초록 체크, 지금 할 일 주황, 큰 버튼은 늘 다음 한 가지) |
| 차량 화면 | C3 야간 수거 목록(수거 도장과 시각, 끝 4자리 숫자판, 차량 재고) + 배달 목록 · 업무 판 · 현장 수납 · 권 추가(6-5) | A3 ▲▼ 순서 변경, 긴급 고정 줄 |

- **왼쪽 메뉴(레일)를 없앤다**(사장님 확정 2026-09-24: '필요 없으면 없애도 된다'). 모든 화면은 위쪽 머리줄과 장부의 색인 탭만 쓰고, 어느 화면에도 레일이 없다. 옛 저장소의 docs/35 1절(레일 96~112px, 메뉴 9개)과 docs/42 부록 A(레일 문구 · 선택자)는 옛 앱(포스 v4)을 적은 문서라 스키노트를 묶지 않는다: 고칠 필요 없이 그대로 두고, 스키노트의 기준은 이 문서와 AGENTS.md 화면 규칙 9번이다. 화면 지도는 3-6.
- 관리 화면(설정, 재고 · 정비, 거래처, 직원)은 머리줄의 `관리`로 들어가고 거기서는 카드 목록을 쓴다(docs/38의 카드 규칙). 관리 화면도 `pos` 등급(16px)이다.
- 기사 화면은 **촘촘한 줄 목록과 쪽 넘김**을 지킨다(사용자 결정 2026-09-17). C3가 이미 그렇다.
- 빨강은 '늦었다'에만 쓴다(N8). 반납 때 받기로 한 정상적인 미수는 검정 글자다. 끝난 도장은 **도장 주홍**(`seal`, 빨강과 다른 색 토큰)이다(3-2).
- 화면마다 주황 주 버튼은 '지금 가장 자주 하는 일' 하나다(N7): 오늘 할 일에서는 낮에 `새 접수`, 마지막 반납 타임 뒤에는 `마감`. 접수증에서는 다음 할 일 하나(`다음 처리`).
- 날짜는 `오늘 · 내일 · 모레` 글자로 쓰고 같은 날짜를 두 번 쓰지 않는다(N14).

## 2. 세 층의 설정

| 층 | 어디 | 무엇 | 누가 바꾸나 |
|---|---|---|---|
| 코드 | `packages/ui` · `packages/layout` · `packages/contract` | DeviceProfile 값, 부품, 칸 맞춤 계산과 글자 폭 표, 코드 키 어휘(화면 · 틀 · 칸 그리기 · 도장 규칙 · 상태 · 동작 · 확인 창 · 조건 · 색 · 맞춤 · 넘칠 때 · 입력 방식 …, 모두 `sys_*` 표), 문구 표(언어별), 화면 기본 설정(`ui-defaults.json`, 판 번호) | 앱 배포 |
| 매장 데이터 | 매장 파일 레지스트리 | `item_kinds`의 표시 값, `stamp_steps` · `item_kind_stamp_steps`, `ledger_views` · `ledger_view_columns` · `ledger_view_column_steps` · `ledger_view_tabs` · `ledger_view_metrics` · `ledger_view_primary_actions` · `ledger_view_actions`, `menu_entries`, `status_terms`, `label_translations`, `attribute_placements`, `print_templates`, `shop_features`, `payment_sections` · `payment_methods` | 설정 명령(권한), 매장 개설 시드, 기본 설정 반영 |
| 기기 | 브라우저 | 잰 화면 크기 + 역할로 고른 등급, 기기별 알림 소리, 마지막으로 연 탭(`localStorage`, 없어도 동작) | 자동 |

- **코드 키는 모두 외래 키다.** 매장 데이터 · 템플릿 · 가져오기가 `fold_into = 'tema'`, `command = 'stock.isue'`, `tone = 'red'`(늦지 않은 상태에), `condition = 'vehicle_pikup'`을 쓰면 데이터베이스가 거절한다. 칸이 채워야 할 연결(도장 단계 · 속성 · 동작)은 `sys_column_renderers.binding_key`가 정하고 설정 명령과 검증기가 맞춰 본다. 합쳐 들어갈 칸은 같은 화면의 칸이어야 한다(자기 참조 FK). 도장의 명령 · 확인 창 · 되돌리기는 `sys_actions` 한 행으로 묶인다.
- **시스템 기본값과 매장이 바꾼 값을 나눈다.** 화면 설정 행마다 `origin_key`(system · template · shop), `default_rev`(그 행을 쓴 기본 설정 판), `customized_at`(매장이 시스템 행을 바꾼 때)이 있다. 매장을 만들 때 `ui-defaults.json`의 행을 시스템 행으로 넣는다. **앱이 새 기본 설정 판을 가져오면** 마이그레이션 실행기의 `ui_defaults.apply(rev)`가:
  1. 매장에 없는 시스템 행을 넣는다(기능이 꺼져 있어도 넣는다 — 나중에 켜면 탭 · 칸 · 상태 문구가 바로 있다).
  2. 매장이 바꾸지 않은 시스템 행(`customized_at IS NULL`)을 새 값으로 고친다(예: 반납 일정 칸 최소 폭 수정).
  3. 매장이 바꾼 행은 그대로 두고 `config_changes`와 `확인 필요`(`새 화면 설정 3개 · 매장 변경 항목 유지`)에 올린다.
  4. 결과를 `ui_default_applications`에 적는다.
- 매장 문구가 없는 상태 · 도장 키는 `sys_status_keys.default_label`(또는 문구 표)로 보인다. 키 글자 그대로나 빈칸이 보이는 일은 없다.
- 설정이 바뀌면 `shops.config_rev`가 오르고, 기기는 동기화 때 설정을 다시 받는다.
- **시즌 1의 화면 설정은 공급자(개발자)만 바꾼다.** 설정 명령(`registry.update`)으로 바꾸고 서버가 4-2의 맞춤 검사를 돈다. 매장 관리자가 칸 · 탭 · 메뉴를 고치는 편집 화면은 시즌 뒤에 만든다(이름 · 짧은 이름 · 켜기 · 순서 정도부터). 그 전까지 관리 화면은 포스 v4를 써도 된다(README 열린 질문 6).

## 3. 레지스트리

### 3-1. 품목 종류의 표시

`item_kinds`의 `label`, `unit_label`, `tone_key`(`sys_tones`), `icon_key`(`sys_icons`), `sort`, `picker_placement_key`(`sys_picker_placements`: tile · grouped · hidden), `stock_metric_label`, `feature_key`, 그리고 `item_kind_stamp_steps`(어떤 도장을 어떤 순서로, 어떤 조건에서 — 조건은 `sys_conditions`). 화면은 종류 key를 보지 않고 이 값들만 쓴다. 새 종류는 고르기 화면에 타일로, 접수증에 줄로, 장부 품목 칸에 이름으로, 차량 요약에 `stock_metric_label`로 저절로 나온다.

지급 · 반납 · 교환 확인 창은 종류 key가 아니라 **재고 방식**(`tracking_key`)으로 모양을 고른다: `unit` = 장비(스티커 번호)를 고름(이 팀이 가진 번호 버튼), `count` = 규격마다 −/+ 수량, `none` = 수량만(칸 없음). 그래서 새 수량 품목(고글)도 따로 만든 창 없이 된다. 반납 창은 처음에 이 팀이 가진 것을 **모두 골라 두고** 안 가져온 것만 빼게 한다(6-2, 둘째 판 시안 V1).

### 3-2. 도장 단계(StampStep)

| 열 | 뜻 |
|---|---|
| `key`, `label`, `short_label`, `stamp_text`, `checklist_label` | 칸 제목(지급), 좁은 칸 제목, 도장 글자(지급 · `수거 21:42`), 처리 현황 문구(장비 지급) |
| `rule_key` | 칸 상태를 계산하는 규칙(`sys_stamp_rules`, 코드) |
| `action_key` | 동그라미를 누르면: 확인 창 → 명령 → 되돌리기, 한 묶음(`sys_actions`). 규칙의 범위(줄 · 접수 · 업무)와 맞는지 설정 명령이 확인 |
| `required_permission_key`, `feature_key` | 권한이 없거나 기능이 꺼지면 칸이 사라짐 |
| `urgency_out`, `urgency_back` | 나가는 쪽 · 들어오는 쪽 긴급 순위(ASCII 키의 숫자 순위. 한글 이름으로 정렬하던 옛 방식을 없앰) |
| `tone_key`, `shows_time` | 색(`sys_tones`), 도장에 시각 표시(칸 최소 폭이 여기서 나옴) |

**칸 상태는 일곱 가지**(`sys_stamp_states`): `todo`(빈 동그라미, 검정), `partial`(`부분`: 스키 4 중 2 지급, 주황 테두리), `done`(**도장 주홍**의 도장), `na`(`—`: 반납 없는 권), `blocked`(회색 자물쇠 `대기`: 앞 단계가 남음 — 발권 전 지급), `scheduled`(파란 '예정': 다른 팀 결제 예정 · 후불), `delegated`(보라 '차량 22:00', 읽는 이름 `차량 담당`: 차량이 수거할 반납이라 카운터 반납 동그라미가 없음, N6). 도장 주홍(`seal`)은 규칙 검사기가 '빨강'으로 세지 않는 별도 토큰이고, 경고에 쓰지 않는다. 빨강(`red`, `late_only`)은 늦은 것에만 쓴다.

**팀 한 줄로 모으기**(`sys_stamp_rollups`): 장부는 한 줄이 한 팀이지만 지급 · 반납은 품목 줄 단위다. 칸마다 모으는 법을 정한다: `worst_of` — 해당 없음(na)은 빼고 가장 덜 된 상태, 끝과 할 일이 섞이면 `partial`. `first_open` — 칸이 단계 사슬(`ledger_view_column_steps`: 적재 → 지급)에 묶였으면 사슬에서 **아직 끝나지 않은 첫 단계**를 보인다. 그래서 차량 배달 팀의 지급 칸은 먼저 `적재`로, 적재가 끝나면 `지급`으로 보인다(N1).

계산은 도메인 패키지의 순수 함수(`deriveStamp(rule, line, order)`)이고 서버와 오프라인 기기가 같은 코드로 읽기 모델에 넣는다. 화면은 계산하지 않는다. `blocked` 칸을 누르면 막고 있는 단계의 확인 창이 첫 줄 `{누른 단계} 불가 · {기다리는 단계} 대기`(`반납 불가 · 지급 대기`)와 함께 열리거나, 그럴 수 없으면 그 한 줄(`지급 불가 · 발권 대기`)이 뜬다. 끝난 도장은 `지급 · 김영희 팀` / `지급 완료 · 09:26`, 다른 팀이 낼 돈의 `예정` 도장은 `이정호 팀 결제 예정`과 `직접 수납 · 60,000원`(알림 창 제목은 단계 이름 + 팀).

도장은 **확인 창을 거친 뒤에만** 찍힌다(docs/53). 오프라인 기사 기기는 확인한 도장을 `전송 대기` 점선으로 보여 주고, 서버가 적용하면 실선이 된다.

### 3-3. 상태 문구(StatusTerm)

`status_terms(domain_key, key, locale, label, tone_key, rank)`. `(domain_key, key)`는 `sys_status_keys`(코드가 가진 상태 값)만 가리킬 수 있고, 색은 `sys_tones`만. 화면은 `in_use`, `awaiting_load` 같은 키만 비교하고 문구 · 색 · 순위는 이 표에서 가져온다. 매장 문구가 없으면 `sys_status_keys.default_label`. 카드와 줄에는 상태 하나와 '다음 처리' 한 줄만 쓴다.

### 3-5. 화면 정의(ScreenDef · LedgerView)

`ledger_views`: 경로(`screen_key` → `sys_screens`), 틀(ledger · slip · checklist · collection_list · driver_list), 기기 등급, **바탕 화면**(`base_view_id`: 등급 판은 바탕의 칸 · 탭 · 숫자를 물려받고 적은 것만 덮음), **한 줄의 단위**(`row_grain_key`: 팀 · 품목 줄 · 업무 · 강습 · 장비), 묶음과 보조 묶음(`group_by_key`, `subgroup_by_key` — 보조는 제목이 아니라 줄 안의 이름표), 정렬(`sort_key`), 지금 줄 기준(`now_line_field`, 시각인 정렬 키만), ▲▼(`reorderable`, 한 묶음 안에서만), 긴급 먼저(`pin_urgent`), 기능과 켜짐 여부. 조건별 주 버튼은 `ledger_view_primary_actions`(순서대로 첫 번째로 맞는 조건: `after_last_return_slot` → `close_day`, `always` → `new_order`), 옆 동작은 `ledger_view_actions`(조건: 교환 가능, 연장 가능 …, 우선순위, 넘칠 때). 탭은 `ledger_view_tabs`(이름, 서버 필터와 값, 개수 표시, 기능), 바닥줄은 `ledger_view_metrics`(숫자와 값: '차량 재고'). 한 화면에 제목은 하나다.

**등급 판의 폴백:** 등급에 맞는 판이 없으면 `pos_narrow` → `pos`, `driver_phone` → `driver_tablet` 순으로 찾는다. 875 · 907 폭도 대부분 `pos` 판 하나를 4-2의 계산으로 맞춘다.

코드의 화면 틀은 이 행을 받아 그린다. 틀이 정하는 것은 배치(장부 표, 접수증 모양, 목록 + 숫자판)와 부품이고, 무엇을 몇 칸에 어떤 순서로 보일지는 행이 정한다.

### 3-6. 화면 지도와 메뉴(MenuEntry)

레일을 없앤 뒤 어디로 가는지:

| 가는 곳 | 어떻게 |
|---|---|
| 오늘 대여 장부(홈) | 머리줄 왼쪽 `장부`(로고). 어느 화면에서든 한 번 |
| 수령 · 반납 · 미수 · 차량 · 강습 목록 | 장부의 색인 탭(날마다 쓰는 목록은 탭) |
| 접수증 | 장부 줄, 머리줄 `끝 4자리 찾기`(N10), 알림 |
| 새 접수 · 마감 | 바닥줄의 주황 주 버튼(시각에 따라 하나) |
| 수거 목록(카운터), 리프트권 발권, 확인 필요, 사이즈 요청 | 메뉴 칸(`menu_entries`) — 등급의 칸 수를 넘으면 `더 보기` 판(쪽 넘김) |
| 설정, 재고 · 정비, 거래처, 직원, 기기, 백업 | 머리줄 오른쪽 `관리`(늘 끝, `pinned_end`). 매장 설정의 색인 탭 `운영 규칙`에서 리프트권 반납 · 리프트권 보증금 · 리프트권 결제 · 당일 취소 환불 · 영업일 기준 시각(하루 기준 시각)을 고른다(카드 목록, 권한 `settings.manage`, 6-9). `백업` 카드는 복구 점검 결과 한 줄과 가게 보관용 내보내기 켜기(deployment 6절) |

- `menu_entries(workspace_key, key, label, short_label, screen_key, seq, priority, overflow_key, feature_key, feature_on, permission_key, device_class_key, pinned_end)`. `screen_key`는 `sys_screens`(경로 모양 · 틀 · 값 스키마)라 없는 화면을 가리킬 수 없다. '리프트권'(강습 꺼짐)과 '리프트권·강습'(강습 켜짐)은 `feature_on`만 다른 두 행이다(docs/52).
- 머리줄에 들어가는 메뉴 칸 수는 등급마다 정해져 있다(`menuCapacity`, 3-7). 넘치면 `pinned_end`가 아니고 우선순위가 낮은 것부터 `더 보기`로 간다.
- **돌아가기:** 화면을 열 때 온 곳(화면 · 쪽 · 고른 줄)을 브라우저 기록 상태에 넣고, 접수증의 `‹ 장부`는 그 쪽 그 줄로 돌아간다(N9). 경로가 있으므로 오프라인에서 새로 고쳐도 그 화면 그 쪽이 열리고, 데스크톱 포장 앱도 경로로 연다. 매장 앱에는 `/admin` 경로가 없다(관리자 콘솔은 따로 된 주소의 따로 된 앱, deployment 3절).

### 3-7. 기기 등급(DeviceProfile, 코드)

크기 규칙은 **여기 한 곳**에 있고, 부품과 규칙 검사기가 이 값을 읽는다.

| 등급 | 크기(검사 크기) | 글자 | 누르는 곳(쪽 넘김 버튼 포함) | 주 버튼 | 머리 · 제목·탭 · 바닥 | 장부 한 줄 | 칸 수: 메뉴 · 탭 · 빠른 결제 수단 · 한 쪽 결제 칸 | 강조색 |
|---|---|---|---|---|---|---|---|---|
| `pos` | 1024×600 ~ 1366×768 (1024×600, **1024×569, 1024×529**, 1024×768, 1366×768) | ≥ 16px | ≥ 52px | 56px | 60 · 60 · 72 | 52px | 3 · 6 · 4 · 3 | 주황 |
| `pos_narrow` | 907×648, 875×600 | ≥ 16px | ≥ 52px | 56px | 60 · 60 · 72 | 52px | 2 · 5 · 4 · 3 | 주황 |
| `driver_tablet` | 1024×520 ~ 1280×720 (1024×520, 1024×600, 1280×720) | ≥ 16px | ≥ 56px | 72px | 60 · 56 · 80 (+ 연결 띠 32) | 60px | 2 · 4 · 3 · — | 보라 |
| `driver_phone` | 360×640 (390×740, 412×780) | ≥ 16px | ≥ 56px | 64px, 가로 전체 | 56 · 56 · 72 (+ 연결 띠 32) | 64px(두 줄) | 1 · 3 · 2 · — | 보라 |
| `print` | A4 794px(96dpi, 여백 뺌), 영수증 80 mm, 스티커 80×50 | 인쇄 틀 | — | — | 틀 | 틀 | — | 흑백 |
| `admin`(**플랫폼 관리자 콘솔만**) | 1440×810(맥북) | ≥ 14px | ≥ 40px | 44px | 64 · 56 · 64 | 44px | — | 남색 |

- 등급은 **잰 화면 크기와 역할로** 고른다(옛 코드는 역할만 보았다). 카운터 직원이 태블릿을 쓰면 `pos_narrow` 규칙, 기사가 휴대폰을 쓰면 `driver_phone`.
- 16px 규칙의 예외는 `admin` 등급 하나뿐이고, 그것은 공급자의 플랫폼 관리자 콘솔(따로 된 주소 · 접근 제한)이다. 매장 사장님이 쓰는 관리 화면은 `pos` 등급(16px)이다. 검사기는 등급의 값을 읽으므로 따로 예외 목록이 없다.
- 제목 · 탭 줄은 docs/42와 같이 60px이다(예전 이 문서의 56px를 고침). 기사 기기는 56px.
- docs/42는 휴대폰 누르는 곳을 52px로 적었지만, 장갑 낀 손(N11)을 생각해 기사 기기는 모두 56px로 올린다. 기사 기기의 쪽 넘김 버튼도 56px다.
- 시안에서 규칙에 어긋난 곳은 구현 때 고친다: 기사 바닥줄 64px → 80px, 기사 주 버튼 60px → 72px, 도장 동그라미 48px는 그림일 뿐 누르는 곳은 칸 전체(≥ 52px), 이름의 `nowrap` → 글자 맞추기(휴대폰은 두 줄).
- **설치한 PWA의 실제 높이:** Windows에서 설치한 PWA는 제목 표시줄(약 31px)이 남고 작업 표시줄이 있으면 1024×600 화면의 실제 영역은 1024×529~569다. 그래서 검사 크기에 1024×569 · 1024×529를 넣고, 모든 계산은 잰 높이로 한다. 카운터 PC는 작업 표시줄 자동 숨김을 권하고, 시즌 뒤 데스크톱 포장 앱은 전체 화면(키오스크)으로 연다.

### 3-8. 사용 기능

`shop_features`가 꺼진 기능은 메뉴, 탭, 장부 칸, 고르기 타일, 확인 창 줄, 도장 칸에서 **사라진다.** 회색 비활성 버튼으로 남기지 않는다(docs/52). 자료는 지우지 않는다. 설정 행마다 `feature_key`와 `feature_on`이 있어서 화면 틀은 기능 목록 하나만 보면 된다. 지점마다 기능을 덮어쓸 수 있다(`scope_key`).

### 3-9. 문구 표와 언어

화면 문구(이름, 단위, 쪽 표시 `1 / 3쪽`, 버튼 이름)는 문구 표(`packages/ui/strings.<locale>.ts`, 기본 `ko-KR`)에 두고 키로 부른다. 시험이 기대는 고정 문구(docs/42 부록 A)는 표에 `fixed: true`로 표시해 바꾸면 CI가 알린다. 매장 데이터의 이름(`label`)은 매장이 바꿀 수 있고, 다른 언어는 `label_translations`(표 · 행 · 칸 · 언어)에 둔다. 저장된 문장(확인 필요, 알림)은 문구 틀 키와 값을 함께 두어 다른 언어로 다시 그린다. **말은 사장님이 바로 읽는 짧은 업무 용어다**(2026-09-24, README D6): 버튼 · 이름표 · 탭은 이름씨로 쓰고 문장 끝(`~합니다` · `~주세요` · `~하기` · `~드림`)을 쓰지 않는다. 동작 버튼은 동작 이름 + 수 · 금액(`반납 처리 · 5개`, `수납 처리 · 120,000원`), 남길 알림은 `사실 · 할 일` 한 줄(`처리 실패 · 재시도 필요`)이다. 한 개념은 한 말이고(수령 · 반납 · 수거 · 배달 · 수납 · 결제 · 미수 · 일정 · 완료 · 지연 …), 화면에 `약속`을 쓰지 않는다. 말의 기준은 [docs/design/wording.md](../design/wording.md)이고, 새 말은 그 표에 먼저 넣는다.

### 3-10. 속성(매장이 정하는 칸)의 입력과 보이는 모양

사용자의 핵심 요구 — 품목 · 칸을 행으로 늘리는 것 — 는 속성이 **어떻게 입력되고 어떻게 보이는지**까지 정해야 끝난다.

- **입력 방식**(`attribute_definitions.input_widget_key`, 없으면 형식의 기본): `int` · `measurement` · `money` → 숫자판, `option` → 선택 격자(쪽 넘김: pos 3×3, pos_narrow 3×3, 태블릿 4×2, 휴대폰 2×3 — 부츠 220~300 5mm 간격 17개는 두 쪽), `bool` → 사용 · 미사용, `time` → 시각 버튼, `date` → 달력, `text` → 글자(화면 키보드 `HangulKeyboard`, 5절). 글자 입력 판은 우리 화면 키보드가 아래에서 올라오는 판이고 편집 칸이 없어 운영체제 자판이 뜨지 않는다. 화면 높이가 줄지 않으므로 그동안 쪽 넘김을 다시 계산하지 않는다.
- **보이는 모양**(`display_format_key`): 그대로, 숫자 + 단위(`265mm`), 금액, 시각, 오늘 · 내일, 선택지 이름. 좁은 자리에는 `short_label`(`객실`).
- **자리**는 두 가지로 나뉜다. 입력폼 · 문서(사이즈 입력폼, 접수 화면, 준비표, 팀 스티커, 접수증, 영수증, 기사 업무 판)는 `attribute_placements`(등급별, 순서, 우선순위, 넘칠 때, 맞춤), **표 모양 화면**(대여 장부, 수거 목록, 기사 목록 줄)은 `ledger_view_columns`의 `attribute` 칸이다. 한 칸이 두 곳에 있지 않다. 표 모양 화면에 속성을 더하려면 칸 행을 더하고, 설정 명령이 그 화면의 줄 단위가 그 속성의 주인을 가질 수 있는지(`sys_row_grain_entities`)와 맞춤(4-2)을 확인한다.
- **어디서 묻나**(`item_kind_attributes.usage_key`): 규격 축(`variant_axis`)은 고르기 화면에서 규격 격자로, 줄 속성은 접수 화면의 그 줄에서, 사람 속성은 사이즈 입력폼 · 준비표에서, 장비 속성은 재고 화면에서.
- **고르기 화면**(새 접수 2단계): 타일 수는 등급마다(pos 3×3, 태블릿 4×2, 휴대폰 2×3), 넘치면 쪽. `grouped` 종류는 타일 하나 뒤에 권종 창. 수량 품목(`count`)의 규격은 −/+ 격자.

## 4. 크기 규칙과 맞추기

### 4-1. 규칙(기계가 검사)

1. 글자는 매장 기기 등급(pos · pos_narrow · driver_tablet · driver_phone)에서 16px 이상(알림 점 하나만 예외). 등급의 값은 DeviceProfile 한 곳에서 읽는다.
2. 누르는 곳은 등급의 최소(52px, 기사 기기 56px) 이상. 도장 칸은 칸 전체가 누르는 곳. 쪽 넘김 버튼도 같다.
3. 말줄임표(`…`) 없음. 덜 중요한 부분이 통째로 빠지고, 품목 목록은 `외 N종`으로 끝난다.
4. 스크롤 영역 대신 잰 높이로 쪽을 나눈다. 한 쪽에는 온전한 줄 · 카드만. 쪽 표시는 바닥줄에.
5. 한 화면에 주황 주 버튼 하나, 빨강(`late_only` 색)은 늦은 것에만. 도장 주홍은 빨강이 아니다.

### 4-2. 칸 폭 정하기

장부 판의 폭 `W`를 잰다(`ResizeObserver`, 묶어 넣은 글꼴을 읽은 뒤에도 다시). 칸 폭은 em이고 등급의 기본 글자 크기(16px)와 실제 글꼴로 px로 바꾼다. 글꼴은 Pretendard 부분 글꼴을 앱에 묶어 PWA가 미리 받아 둔다(Malgun Gothic으로 바뀌어 폭이 달라지는 일이 없게). 브라우저 확대(110 · 125%)는 CSS px 폭이 줄어든 것으로 똑같이 계산한다.

```text
layout(columns, W):
  보일 칸 = 기능 · 권한으로 거른 칸
  반복:
    if Σ preferred ≤ W:  남는 폭을 weight 비율로 나눔 → 끝
    if Σ min ≤ W:        모자란 폭을 (preferred − min) 비율로 줄임 → 끝
    아니면 다음 하나를 한다(가능한 첫 번째):
      a) drop_priority가 가장 높은 칸을 뺀다. fold_into가 있으면 그 칸 안에 합쳐 그린다:
         prefix면 앞부분으로('09:10 · 김민수 · 0025'), 받는 칸의 최소 폭 += fold_min_share
         second_line이면 줄 높이가 두 줄을 허락할 때 둘째 줄로(휴대폰)
      b) 같은 collapse_group의 도장 칸들을 한 칸(다음 할 단계, 최소 폭 = 가장 긴 도장 글자)으로 모은다
      c) 두 줄 줄(stacked row: 1줄 팀 · 품목, 2줄 일정 · 금액 · 도장, 줄 높이 88px)로 바꾼다
      d) 그래도 안 되면 `화면 폭 부족` 표시와 [확대 초기화] 버튼
  drop_priority = 0인 칸(팀, 품목, 도장)은 빠지지 않는다(도장은 모일 수는 있다)
```

- **글자 맞추기의 우선순위:** parts 모드의 조각은 우선순위가 있다. 팀 칸은 이름과 끝 4자리는 빠지지 않고, 합쳐 들어온 시각 앞부분이 먼저 빠진다(끝 4자리는 모든 화면이 팀을 찾는 열쇠다, N10). 긴 단체 이름('한국대학교 스키동아리')은 이름 안에서 낱말을 줄인다(words).
- **도장 칸의 최소 폭**은 설정이 아니라 도장 글자에서 나온다: `shows_time` 도장('수거 21:42')은 5.5em(88px), 글자만('지급')은 4em(64px). 설정의 최소 폭이 그보다 작으면 설정 명령이 거절한다.

오늘 대여 장부의 칸 설정과 크기별 결과(판 좌우 여백 30px씩, em × 16 = px):

| 칸 | 제목 | 그리기 | 최소 | 원함 | 비율 | 빠짐 | 합침(모양 · 넓힘) | 모음 | 맞춤 |
|---|---|---|---|---|---|---|---|---|---|
| time | 시각 | time | 4em (64) | 4.125em (66) | 0 | 3 | team (prefix · 4em) | | parts(두 줄: 윗줄 날짜 말 · 종류, 아랫줄 시각) |
| team | 팀 | team | 8.25em (132) | 9em (144) | 1 | 0 | | | parts(이름 · 끝 4자리 고정) |
| items | 품목 | items | 9.5em (152) | 12.25em (196) | 3 | 0 | | | items |
| promise | 반납 일정 | promise | 10.5em (168) | 13.375em (214) | 2 | 0 | | | parts |
| money | 금액 | money | 6.5em (104) | 7.75em (124) | 1 | 0 | | | alts(안 들어가면 두 줄: 윗줄 '미수' · 아랫줄 금액) |
| stamp:issue · stamp:return · stamp:pay | 지급 · 반납 · 수납 | stamp | 4em (64) | 4.25em (68) | 0 | 0 | | stamps | |

- 1024×600: `W = 964`, 원함 합 948 → 그대로, 남는 16px은 비율로.
- 907×648: `W = 847`, 최소 합 812 ≤ 847 → 모자란 101px를 (원함 − 최소) 비율로 줄임. 품목은 `스키 2 · 보드 1 외 1종`.
- 875×600: `W = 815`, 최소 합 812 ≤ 815 → 합치지 않고 줄이기만 한다. 시각 칸(약 64px, 글자 48px — 굵은 '22:00'이 들어가는 폭)이 모든 줄에 따로 남아 정렬 기준이 늘 보인다(시각 칸은 윗줄 날짜 말 · 종류, 아랫줄 시각의 두 줄이다. 다른 날의 줄은 '내일'이 윗줄로 올라가 좁아도 시각이 빠지지 않는다). 금액 칸(104px, 글자 88px)에 '미수 120,000원'(굵은 글자 약 112px)이 들어가지 않으면 두 줄('미수' / '120,000원').
- 시각이 팀 칸 앞으로 합쳐질 때(아래 두 경우)는 팀 최소가 4em 늘어난다(132 → 196): 굵은 16px 글자로 잰 '22:00 · 한동수 · 0034'가 약 174px이라 2.5em(40px)로는 여백을 빼면 들어가지 않았다(2026-09-23 검토).
- 강습이 켜져 `stamp:lesson_done`(4em)이 더해지면: 875 · 907에서 최소 합 876 → 시각을 합쳐도 876 > 815 → 도장 네 칸이 한 칸(`반납 ○`, 5em)으로 모여 700 → 들어감. 전체 도장은 접수증에서 본다.
- 1024×600을 125%로 확대(819 CSS px, 판 759): 812 > 759 → 시각을 합쳐도 812 > 759 → 도장 모음으로 700 → 들어간다. 판이 700px보다 좁아지면 두 줄 줄.

**설정을 바꿀 때마다 같은 계산을 서버가 돈다.** 계산과 글자 폭 측정(묶은 글꼴의 글자 폭 표)은 공유 패키지(`packages/layout`)에 있고, 서버는 모든 설정 명령(칸 · 탭 · 메뉴 · 숫자 · 결제 칸 · 이름 바꾸기)에서 영향을 받는 화면을 그 화면의 모든 대상 크기로 계산한다. 넘치면 한 문장으로 거절한다: '탭 폭 초과 · 6자 이하 또는 짧은 이름 필요'(875 폭 화면의 탭) 이름이 고정 폭 자리에 들어가는 곳에는 짧은 이름(`short_label`)을 받는다. 그래도 기기에서 넘치면(글꼴을 못 읽음 등) 화면은 잘라 내지 않고 위의 c · d 단계로 간다.

### 4-3. 글자 맞추기와 쪽 넘김

- 글자 맞추기 엔진은 옛 `pos-shell.js`의 엔진을 옮기고 조각 우선순위를 더한다. 칸마다, 크기가 바뀔 때마다, 글꼴을 읽은 뒤에 다시 돈다. 맞춤 방식: parts(`22:00 · 설천 주차장 · 차량` → 우선순위 낮은 부분부터 뺌), items(`스키 2 · 보드 1 · 헬멧 3` → `스키 2 외 2종`), words, alts(`미수 120,000` → `120,000`).
- **쪽 넘김은 잰 항목을 순서대로 채운다**(고정 '7줄'이 아님): 줄(52 · 60 · 64 · 88px), 묶음 제목(40px, 다음 줄과 떨어지지 않음), 지금 줄(24px 구분선으로 셈 — 줄을 덮지 않음), 긴급 줄(64px), 안내 띠, 연결 띠. 한 쪽에 들어가는 만큼만 넣고 나머지는 다음 쪽.
  - **연결 띠 자리는 늘 비워 둔다**(채택한 둘째 판 시안 V7의 규칙 (2)를 카운터 장부에도, 셋째 검토): 줄 수는 띠(32px)가 떠 있을 때의 높이로 정하고, 연결되어 있을 때 남는 32px는 줄이 나눠 쓴다(규칙 (1): 줄은 남는 높이를 나눠 쓴다, 최소 = 등급 줄 높이, 최대 = 두 줄 줄 88). 그래서 가게 인터넷이 끊기거나 서버가 느려도 한 쪽의 줄 수와 줄 자리가 바뀌지 않는다. 띠는 넘기기 지연(연속 두 번 실패, 10초 안정, sync 8-1)을 따라 깜빡이지 않는다.
  - 예: 1024×600 포스는 머리 60 + 제목 · 탭 60 + 표 머리 40 + 바닥 72 + 연결 띠 자리 32 = 264, 남는 336px에 52px 줄 6개(312)와 지금 줄(24)까지 들어간다(연결되어 있으면 줄이 56px). 1024×529(설치한 PWA)는 265px에 5개, 지금 줄이 그 쪽에 있으면 4개. 띠 자리를 비우지 않으면 1024×600이 7줄이지만 끊길 때 줄이 한 번 다시 나뉜다 — 어느 쪽으로 할지 사장님께 한 번 보여 드린다(README 열린 질문 31).
  - 묶음 제목은 다음 쪽 첫 줄 위에 다시 나온다(`만선 티롤 앞 · 22:10 (계속)`). 목록 높이가 640px 미만이라 묶음 제목 두 개가 안 들어가면 쪽마다 제목을 한 줄만 두고 시간대를 함께 적는다(docs/42 2-3의 규칙 5를 이어 받음).
- 처음 여는 쪽은 **지금 줄이 있는 쪽**이다. 고른 줄이 있으면 그 줄의 쪽.

### 4-4. 넘치는 목록의 한 모델(capacity)

설정으로 늘어나는 목록은 모두 같은 규칙을 쓴다: 행마다 `priority`(낮은 것부터 밀려남)와 `overflow_key`(`sys_overflow_modes`), 글자가 들어가는 곳은 `fit_mode_key`와 짧은 이름. 등급마다 칸 수(3-7)가 있고, 같은 계산(`packages/layout`)이 개발 시험 · 설정 명령 · 화면에서 돈다.

| 목록 | 넘칠 때 | 등급별 칸 수 · 폭 |

| 바닥줄 숫자 | 합산(`지급 14 · 반납 9` → `지급/반납 14/9`), 그다음 우선순위 낮은 숫자를 뺌 | 폭은 주 버튼 · 쪽 표시를 뺀 나머지 |

### 4-5. 접수 확정 창의 폭과 높이

채택한 둘째 판 시안 V4를 따른다(2026-09-24).

- **폭:** 창 폭 = min(W − 64, 860px), 본문 글 폭 812(1024 기준). 두 줄 칸(104px) = 제목 줄 40(**글만**: 굵은 칸 이름 · 회색 품목 · 오른쪽에 회색 할인 상태(`할인 없음`, `10% 할인 · 225,000원 → 202,500원`) · 결제 예정 · 금액) + 수단 줄 52(빠른 수단 ≤ 4 + `후불` + `기타`, 각 ≥ 110px, 끝에 윤곽 `할인 적용 ›`) + 틈 12(어느 수단 줄이 어느 칸 것인지 갈라 보이게). 수단 줄 폭 = 110 × 5 + 사이 12 × 4 = 598, `할인 적용 ›`(옛 `할인 고르기 ›`의 약 124보다 짧음)를 더해도 812 안이다. 875에서도 창 폭 811이라 들어간다. 간편결제 · 상품권을 더해도 `quick = 0`이면 `기타` 안으로 간다.
- **한 줄 칸(52px):** 수단이 하나뿐인 칸(이 매장의 `리프트권 보증금`: 현금만)은 버튼 없이 한 줄이다(`리프트권 보증금 · 4매 · 매장 기준 1매 5,000원 · 반납 시 반환 · 현금 20,000원`). 수단이 둘 이상이면 두 줄 칸(`후불` 없음).
- **높이:** 제목 56 + 위 여백 12 + 두 줄 칸 × 104 + 한 줄 칸 × 52 + 결제 팀 줄 64 + 받을 금액 줄 40 + 주 버튼 줄 72. 이 매장(장비 · 리프트권 두 줄 칸 + 보증금 한 줄 칸, 강습 꺼짐) = 56 + 12 + 208 + 52 + 64 + 40 + 72 = **504** — 1024×600(창 한도 552) · 1024×569(521) · 1024×529(505) 모두 한 쪽이다. 결제 팀 줄은 `후불`인 칸이 없어도 자리를 지킨다(창 높이가 흔들리지 않음, 5절 `ConfirmDialog`). 한 쪽에 두 줄 칸 셋까지이고, 강습 · 판매 칸이 더해져 넘치면 `다음 칸 ›`으로 쪽을 넘기며 주 버튼은 앞 쪽에서 윤곽 `다음 칸 ›`, 마지막 쪽에서만 돈을 적는다.
- **주 버튼 말:** `접수 확정 · 현금 160,000원`(받을 금액만, 수단 이름과 함께 — 카드 단말에 칠 돈과 돈통에 넣을 돈을 가른다). 수단이 섞이면 `접수 확정 · 카드 225,000원 · 현금 160,000원`, 버튼에 들어가지 않으면 수단별 금액은 `받을 금액` 줄에만 적고 버튼은 합계. 받는 돈이 없으면 `접수 확정`. 보증금은 수납이 아니므로(data-model 4-12) `수납하고`라고 쓰지 않는다(옛 글 '수납하고 접수 확정 · 105,000원'을 고침).
- **받을 금액 줄(40px):** 굵은 `받을 금액` · `현금 160,000원` · `= 리프트권 140,000원 + 보증금 20,000원`(수납과 보증금을 나눠 적음). DeviceProfile(`POS_CONFIRM`, `payerRowPx` 64)은 그대로다.

## 6. C 세 화면과 기사 화면을 설정으로 쓰면

### 6-1. 오늘 대여 장부(포스)

```yaml
ledger_view: day_ledger / pos           # pos_narrow는 따로 두지 않고 이 판을 4-2로 맞춤
  screen: day_ledger                     # /ledger/:date
  label: "{date} 대여 장부"                 # '12월 26일 (토) 대여 장부'
  template: ledger
  row_grain: order
  group_by: time_bucket
  sort: next_due_at
  now_line_field: next_due_at
  primary_actions:                       # 첫 번째로 맞는 조건 (N7)
    - close_day   when after_last_return_slot
    - new_order   when always
  columns: time · team · items · promise · money · stamp:issue(사슬: 적재 → 지급, first_open) · stamp:return · stamp:pay   (4-2 표)
  tabs:    전체(all) · 수령(pickup) · 반납(return) · 미수(unpaid) · 차량(vehicle, 기능 vehicles) · 강습(lessons, 기능 lessons)
  metrics: team_count · issued_count · returned_count · due_total     # '합계 · 18팀 · 지급 14 · 반납 9 · 미수 485,000원'
```

- **시각 칸 = 정렬 기준.** 줄의 시각은 그 팀의 다음 약속(`next_due_at`): 수령 전이면 수령 시각, 이용 중이면 반납 시각이고, 칸에 종류를 짧게 붙인다(`수령 16:00`, `반납 22:00`). 칸이 좁아(64~66px) 한 줄로는 종류가 늘 빠지므로 52px 줄 안에 두 줄로 쓴다: 작은 윗줄 날짜 말 · 종류, 아랫줄 시각. 다른 날의 시각은 날짜 말('내일')을 윗줄 조각으로 따로 두어(시각과 한 조각이면 좁은 칸에서 낱말이 빠져 시각이 사라진다) 좁으면 종류가 먼저 빠지고 `내일` / `09:00`이 남는다. 시각이 팀 칸에 합쳐지면(4-2) 종류가 먼저 빠진다.
- **자리 지키기:** 보고 있는 동안 줄이 자리를 옮기지 않는다. 도장을 찍어 다음 약속이 바뀐 줄, 다른 기기의 변경으로 바뀐 줄은 **쪽을 넘기거나, 화면을 떠났다 오거나, 60초 동안 손을 대지 않았을 때** 제자리로 가고, 그 전에는 제자리에 두고 작은 `순서 변경` 표시를 붙인다(시각 칸 윗줄에 종류 대신 `순서 변경`, 좁으면 `변경`. 그 칸의 옅은 바탕은 줄을 골라도 남는다. 시각이 팀 칸에 합쳐진 좁은 화면에서는 팀 칸 조각). 손가락이 화면에 닿아 있거나 창이 열려 있는 동안 온 새로 고침은 미뤘다가 끝난 뒤 그린다(다른 팀 도장을 잘못 누르지 않게).
- **끝난 팀**(`next_due_at` 없음)은 맨 뒤에 흐리게 둔다(N15). 시안처럼 시각 자리에 두고 싶은 매장은 정렬 키만 바꾼다.
- 처음 여는 쪽은 지금 줄이 있는 쪽.
- 도장 칸: 지급 = 줄들의 `issue` 단계, 차량 배달 약속이 있으면 사슬의 첫 단계 `적재`가 먼저(N1). 반납 = `return` 단계(반납 없는 줄만 있으면 `—`, 차량이 받을 반납이면 보라 `차량 22:00`). 리프트권을 꼭 돌려받는 매장(이 매장)은 권 줄도 반납 단계가 있어 권이 돌아와야 반납 칸이 끝난다. 수납 = 접수의 `order_due_zero`(다른 팀이 낼 몫만 남으면 파란 `예정`, 이 팀이 대신 낼 몫이 남으면 끝이 아님).
- 금액 칸: 미수는 검정, 늦은 미수(지급일이 지났는데 미수)만 빨강. 다른 팀이 낼 금액은 `김OO 팀 결제 예정`. **미수는 늘 이 팀 몫만**이고, 다른 팀 몫까지 받을 팀은 합을 `받을 금액 150,000원`으로 쓴다(넓으면 `미수 90,000원 · 대납 60,000원`). 한 줄 문구가 들어가지 않으면 두 줄(작은 윗줄 `미수` · `받을 금액`, 아랫줄 `120,000원`)로 이름과 원을 함께 지킨다(읽기 모델의 `stacked`).
- 늦음은 읽기 모델의 `due_at` · `late_at` 시각으로 화면이 매분 다시 정한다(7절). 아무도 쓰지 않아도 22:00이 지나면 그 줄이 빨개진다. 처음 여는 쪽(지금 줄의 쪽)보다 앞쪽에 늦은 줄이 있으면 지금 줄 끝에 늦음 색으로 `이전 쪽 지연 5팀`을 적는다(‹를 누르면 본다).
- 줄을 누르면 접수증, 도장 동그라미를 누르면 그 단계의 확인 창.
- 머리줄의 끝 4자리 찾기는 어느 화면에서든 그 팀 접수증을 연다(N10).

### 6-2. 대여 접수증과 처리 현황(포스)

```yaml
ledger_view: order_slip / pos
  screen: order_slip                     # /orders/:orderId
  template: slip
  row_grain: order_line
  columns (품목 표): items(품목) · text(수량) · money(금액) · stamp:load(조건 vehicle_pickup) · stamp:issue · stamp:return   # 도장은 모음 'stamps'
  fields: 날짜 · 구분(접수 경로) · 대표자 · 연락처 · 인원  + 자리 'slip'인 속성(객실 등)
  primary: next_step                     # 주황은 늘 다음 할 일 하나('다음 처리')
  actions (ledger_view_actions): pay · change_promise · exchange(교환 가능) · extend(연장 가능) · cancel(부분 취소 가능) · early_return · print · call
```

**폭과 높이(설정 명령과 시험이 확인):**

| | 1024×600 (W 964) | 875×600 (W 815) | 1024×529 |
|---|---|---|---|
| 오른쪽 판(처리 현황 + 주 버튼 + 옆 동작) | 280px | 280px | 280px |
| 품목 표 | 품목 152 + 수량 56 + 금액 104 + 도장 3 × 64 = 504 (남는 폭은 품목) | 519px 안: 같은 504 | 같음 |
| 위쪽: 머리 60 · 제목 60 · 칸 한 줄 40(날짜 · 구분 · 대표자 · 연락처 · 인원, parts) · 일정 요약 한 줄 32(`수령 16:00 매장 · 반납 22:00 설천 · 1호 차량`, 일정이 줄마다 다르면 `일정 3건 ›`) · 돈 줄 40 · 표 머리 40 · 바닥 72 | 344px | 344px | 344px |
| 품목 줄(52px) 한 쪽 | 4줄 | 4줄 | 3줄 |

- 품목이 더 많으면 품목 표만 쪽을 넘긴다(`품목 1 / 3쪽`). 오른쪽 판은 그대로다.
- **세트:** 세트 줄 한 줄 아래에 구성품 줄을 들여 쓴다. 도장은 구성품 줄에 있고(부츠만 교환 · 반납), 세트 줄의 도장은 `—`. 장부의 품목 요약은 **고르는 단위**(세트 줄과 세트가 아닌 줄)를 센다: `스키 세트 4 · 의류 4 · 헬멧 3 · 리프트권 4`(구성품을 따로 세지 않음).
- **처리 현황(B2의 남은 일 목록)**은 오른쪽 판 위에 붙는다. 만드는 법: 이 접수 줄들의 도장 단계와 접수 단계(`pay`)를 모아 `urgency_out` · `urgency_back` 순으로 줄 세우고, 끝난 단계는 한 줄(`완료 3건 ✓`)로 접고, 첫 todo가 '지금'. 문구는 `checklist_label` + 요약(`장비 지급 · 스키 2 · 보드 1 · 헬멧 3`, `수납 · 120,000원`, `반납 · 오늘 22:00 · 설천 주차장 · 차량 수거`).
- **큰 주황 버튼은 '지금' 단계 하나**: `지급 처리 · 6개 · 3매`(확인 창 주 버튼 `지급 처리 · 6개 · 3매`와 같은 셈, 읽기 모델 `figure.units`), 차량 배달이면 `적재 처리 · 6개`(N1), 수납이 지금이면 `수납 처리 · 120,000원`. 지금이 아닌 수납은 옆 동작의 보통 버튼이다(한 화면 주황 하나). 주황 버튼과 같은 명령(`sys_actions.command_key`)을 하는 옆 동작은 빠진다(`수납 처리`와 `수납`은 둘 다 `payment.take`).
- 처리 현황의 품목은 둘째 줄의 품목 맞춤(`스키 2 · 보드 1 · 헬멧 3 외 1종`)이다: 조각으로 빼면 헬멧 · 권이 말없이 사라진다. 늦은 일(늦은 반납 · 늦은 미수)은 단계 이름에 `지연`을 붙이고 늦음 색이다(`반납 지연 · 오늘 12:00 · 매장`, `수납 지연 · 65,000원`). 일정 요약 줄도 종류 말에 붙인다(`반납 지연 12:00 · 매장`, 시각과 한 조각이라 빠지지 않음).
- **옆 동작**은 `ledger_view_actions`로, 줄의 능력(교환 가능 · 연장 가능 · 부분 취소 가능)이 조건이다. 등급의 칸 수(3 · 2)를 넘으면 `더 보기`. 새 동작(조기 반납 등)은 행 하나다. 수납은 받을 돈이 있을 때(`has_due`), 조기 반납은 내준 장비가 아직 돌아오지 않았을 때(`has_items_out`)만 보인다. 취소 동작의 이름은 `접수 취소`다(창의 `닫기`와 헷갈리지 않게).
- **동작은 종류로 가른다**(`sys_actions.kind_key`): 도장 · 명령은 서버의 확인 창 초안(`confirmDraft`, 아직 없는 일은 서버가 한 문장), 화면은 그 화면(`screen_key`), 기기 동작(전화)은 기기 기능. 자기 창이 따로 있는 동작(수거 실패의 방문 결과 판, 순서 변경)만 화면이 따로 다룬다.
- **품목 표의 칸 값**은 서버가 설정의 칸마다 채운다(품목 이름 · 수량 · 금액 · 도장 · 속성, `SlipLine.cells`). 화면은 칸 값만 그리고, 값이 없는 칸은 빈칸이다(칸을 더해도 다른 칸의 값을 짐작해 넣지 않는다).
- `일정 변경`은 품목 줄의 **수량 일부**의 반납 약속만 바꾼다(N2, 옛 방식은 줄 전체; 채택한 둘째 판 시안 V9). 창(860 × 약 503): 이름표 칸(6em) + 줄 — `변경 품목`(수량 칸 두 줄, 처음에는 모두 0, 둘째 줄 `대여 3개` 또는 일정별 수), `반납 시각`(SlotChooser: `오전타임 후 12:00` · `오후 16:30` · `야간 22:00` · `심야 24:00` · `내일` · `다른 날 ›`; 오늘 지났거나 10분 안인 타임은 자리를 지킨 채 점선 · 회색), `반납 장소`(PlaceChooser: `매장 직접` · `설천 ›` · `만선 ›` · `솔마을 ›` · `꽃마을 ›`), `수거 차량`(`매장 직접`이면 자리만), 요약 두 줄 `변경` · `유지`. 주 버튼 `일정 변경 · 보드 1 · 헬멧 1 · 권 1매`(수량이 0이거나 일정이 그대로면 누를 수 없음). 날을 바꾸면 연장 값이 `변경` 줄과 주 버튼에 붙고(`일정 변경 · 보드 1 · 헬멧 1 · 30,000원`), 리프트권은 하루권이라 날을 옮기지 않는다(`리프트권 당일 한정 · 날짜 변경 불가`). 기사에게 곧바로 닿아야 하는 결정이라 **연결이 필요하다**: 끊긴 카운터에서 누르면 `일정 변경 불가 · 연결 끊김 · 종이 접수증에 기록`(sync 8-2).
- **반납 확인 창과 부분 반납**(2026-09-24, data-model 4-18; 채택한 둘째 판 시안 V1): 창(860 × 440)은 품목 칸이 **늘 보이고 처음에 이 팀이 가진 것이 모두 골라져** 있다. 다 가져왔으면 그대로 누르고, 일부만 가져왔으면 안 가져온 번호만 눌러 뺀다. `모두 반납` / `일부만` 고르기는 두지 않는다: 고르기가 있으면 급할 때 기본값을 세지 않고 눌러 숙소에 있는 보드까지 반납되고 두솔동 수거가 사라진다. 칸 모양은 재고 방식(3-1): 하나씩 세는 품목(스키 · 보드 · 헬멧 · 리프트권)은 이 팀이 가진 **번호 버튼**(`17번` · `18번`, 고른 번호는 남색 바탕 — 돌아온 권이 번호로 적혀 권마다 다시 전달 · 발권처 환불이 됨), 수량 품목(고글)은 −/+(둘째 줄 `대여 6개`), 세지 않는 품목은 칸이 없다. 칸 둘째 줄은 일정별 수(`설천 2 · 두솔동 1`, 일정이 하나면 `설천 2대`; `N개 중`은 헬멧 규격 `중`과 헷갈려 쓰지 않음). 나누는 단위는 품목 줄과 수량이고 사람을 묻지 않는다(현장 접수는 대표자만 적는다). 줄 차례: ① 회색 표시 `전체 선택 · 미반납 번호 해제`(늦은 반납이면 이 자리에 늦음 색 `반납 지연 · 일정 22:00`) ② 품목 칸(한 줄에 둘, 두 줄 112, 품목 줄 6개까지 한 쪽, 넘치면 이 칸만 쪽을 넘김) ③ `미반납: 보드 1 · 헬멧 1 · 권 1매 → 22:00 솔마을 두솔동 수거 예정 · 설천 주차장 수거 취소`(모두 골랐으면 `미반납 없음 · … 수거 취소`) ④ `권 2매 보증금 10,000원 반환 · 매장 기준 1매 5,000원 · 잔여 보증금 5,000원(권 1매)` ⑤ 이름표 `반환 방법` + 이름씨 버튼 `현금` · `미수 차감 · 120,000원 → 110,000원`(처음 고른 것은 규칙의 `refund_default_key`, 받은 수단을 따름: 카드로 받은 매장은 `카드 취소 · 10,000원`, 계좌면 `계좌 반환`; 미수가 없으면 둘째 버튼이 없다). 주 버튼은 `반납 처리 · 스키 2 · 헬멧 2 · 권 2매 · 보증금 10,000원`(모두면 `반납 처리 · 6개 · 3매 · 보증금 15,000원`, 길면 `외 N종`, 모두 빼면 누를 수 없음). 번호를 누르면 ③ ④와 주 버튼 글이 바로 바뀌지만 창 높이는 그대로다(5절 `ConfirmDialog`). 명령은 반납 하나(`stock.direct_return`, `lines: [{ lineId, quantity, assetIds }]`)와 보증금 돈 하나(`deposit.return`, `dependsOn`, `expect` = 보관 중 보증금 · 받을 돈). 창 높이 440은 1024×600(552) · 1024×569(521) · 1024×529(505) 모두 안이다. 보증금을 맡지 않은 매장 · 권이면 ④ ⑤가 없다(창이 96 짧게 열리고 연 동안 그대로). 번호 스티커가 없는 품목은 그 줄만 −/+ 수량(README 열린 질문 29). 끊긴 카운터에서도 이 창은 되고 도장은 점선이다(sync 8-2). 다만 **끊긴 카운터(LocalClient)가 그리거나, 그 접수의 사본이 마지막 연결 뒤 다른 기기에서 바뀌었을 수 있으면 보증금이 걸린 번호(권)는 처음에 고르지 않은 채 연다**: ① 회색 표시가 `연결 끊김 · 다른 카운터 반납 가능 · 실물 번호만 선택`이 되고, ④ 보증금 줄은 누른 번호 수만큼만 셈한다(옛 사본의 '전부'에는 다른 카운터에서 이미 돌아온 권이 있을 수 있어 보증금이 두 번 나가지 않게, sync 8-7). 장비는 전처럼 모두 골라 둔다(이미 돌아온 장비를 다시 골라도 `superseded`로 끝나고 돈이 움직이지 않음). 창 높이는 그대로다.
- **끊긴 카운터의 지급 · 권 · 교환 · 적재**(sync 8-2): 지급 창의 번호 고르기는 사본상 다른 곳(다른 팀)에 있는 번호도 고를 수 있게 두고 한 줄 경고 `기록상 김민수 팀 대여 번호 · 실물 확인 후 지급`을 보인다(손에 든 것을 봤으므로; 연결되면 서버가 일어난 순서로 맞춘다). 권 줄의 지급 칸은 끊긴 동안 `권 지급 처리`(`stamp.ticket_hand_out`)가 되어 매장 권 재고에서 번호를 고르게 한다(배정 + 지급 한 명령; 발권 도장은 연결을 기다림). 옆 동작 `교환`은 끊긴 동안 `즉시 교환` 창(돌려받는 번호 · 주는 번호, 확인 창 `swap`)을 연다(만들기 전에는 한 줄 `교환 불가 · 연결 끊김 · 종이 접수증에 기록`). 차량 배달 줄의 적재 도장은 끊겨도 된다(`stock.load`).
- 차량이 받기로 한 반납(보라 `차량 22:00`)을 카운터에서 누르면 먼저 한 줄(`1호 차량 수거 예정 · 22:00`)과 `매장 반납 처리`가 뜨고, 그것이 같은 반납 창을 연다. 매장에서 먼저 받은 수량은 차량 업무에서 빠진다(`elsewhere_quantity`).
- 돈 줄: `청구 225,000원 · 수납 105,000원(계좌이체 12/24) · 보증금 15,000원 · 미수 120,000원`과 수납 도장. 보증금(맡고 있는 금액)은 청구 · 미수에 넣지 않고 따로 적는다. 수납 도장은 상태를 글로 쓴 글자 도장이다(`수납 완료` · `부분 수납` · `수납 예정`, 미처리면 점선 `수납`): 24px 동그라미 색만으로는 완료 · 부분 · 미처리가 갈리지 않는다. 다른 팀 몫까지 받는 팀은 굵은 글이 `받을 금액 150,000원`이고 앞 글에 `미수 90,000원 · 대납 60,000원`.

### 6-3. 야간 수거 목록(기사 태블릿 · 휴대폰)

```yaml
ledger_view: collection_list / driver_tablet
  screen: driver_list                    # /driver/:date
  label: "오늘 야간 수거 목록"
  template: driver_list
  row_grain: task
  group_by: return_slot                  # 반납 타임이 제목
  subgroup_by: place                     # 장소는 줄 안의 이름표(N3); ▲▼는 한 반납 타임 안에서
  sort: manual_route                     # 긴급 → 순위 → 일정 시각 → 업무 id
  reorderable: 1                         # ▲▼ (N12, 자기 차량만)
  pin_urgent: 1
  primary_actions: [receive_to_shop]     # '매장 입고 · 14개' (보라, 72px)
  columns: stamp:collect(수거 + 시각; 체크 칸과 하나) · team(이름 · 끝 4자리) · items · action:call
  metrics: collected_count · pending_count · remaining_count · vehicle_load   # '완료 4 · 전송 대기 8 · 잔여 3' / '차량 재고 스키 14 · 보드 3 · 의류 2 · 헬멧 6'

ledger_view: collection_list / driver_phone   (base: driver_tablet)
  columns: stamp:collect 5.5em · team 11.5em(items는 둘째 줄: fold_mode second_line) · action:call 3.5em   # 88 + 184 + 56 = 328 = 360 − 32
```

- **수거 칸 하나:** 예전의 '체크 칸'과 수거 도장은 같은 단계라 한 칸이다. 비었으면 누르는 동그라미, 누르면 수거 확인 창 → `stock.collect`, 수거하면 `수거 21:42`(전송 대기 중이면 점선).
- **전화는 동작 칸**(`action` 그리기)이지 글자 칸이 아니다.
- **줄을 고르면** 바닥줄 자리에 동작 줄이 나온다: `▲ · ▼ · 맨 위로 · 수거 실패 · 전화`(각 56px 이상). 길게 누르기는 쓰지 않는다(장갑, 고령). `수거 실패`는 방문 결과 판(`사유`: `고객 부재 / 장소 변경 / 물품 미준비` → `재방문`: `오늘 / 내일 / 날짜` → `16:30 / 17:00 / 직접 입력`, 모두 버튼)을 연다(N11). 실패 버튼의 말은 **업무 종류로** 바뀐다(채택한 둘째 판 시안 V7): 수거는 `수거 실패`(수거 칸과 짝), 배달은 `배달 실패`(배달 칸과 짝)이고, 판의 셋째 사유도 수거 `물품 미준비` · 배달 `기타`다. 까닭 목록은 읽기 모델(`visitReasons`)이 업무 종류로 거른다.
- 맨 위 긴급 줄: `긴급 · 21:50 꽃마을 들국화 · 오승민 · 0039 · 조기 반납` + 전화. 카운터가 누르면 기사 기기에 알림(요청됨 → 도착 → 확인).
- 묶음 제목: `22:00 반납 · 4 / 8`, 장소는 줄 안에 `설천 주차장`. 다음 묶음이 다음 쪽이면 `22:10 반납 · 0 / 2 · 다음 쪽`.
- **높이(1024×520 태블릿):** 머리 60 + 제목 · 탭 56 + 바닥 80 = 196 → 목록 324px. 긴급 줄 64 + 묶음 제목 40을 빼면 220px → 60px 줄 3개(docs/42의 '3줄@1024×520'과 같음). 오프라인이면 연결 띠 32px를 더 빼고 다시 센다. 긴급 줄 · 묶음 제목이 없으면 5개.
- **숫자판:** 높이 600px 이상 태블릿은 오른쪽 판(제목 40 + 표시 56 + 4 × 56 키 + 차량 재고 48 ≈ 400px), 1024×520과 휴대폰은 `끝 4자리` 버튼으로 아래에서 올라오는 판. 손님이 다가오면 끝 4자리 → 그 줄로 이동 · 강조.
- **휴대폰(360×640):** 머리 56 + 제목 · 탭 56 + 바닥 72 = 184 → 456px(오프라인이면 424), 64px 두 줄 줄 6개(긴급 줄이 있으면 5개).
- 오프라인이면 연결 띠 `연결 끊김 · 전송 대기 3`, 수거한 줄은 점선 도장. 목록은 기기에서 같은 코드로 그린다(sync 문서 8-1).
- **날짜:** 목록의 날짜는 서버가 준 영업일이다. 하루 기준 시각이 06:00이라(이 매장, data-model 3-3) 자정을 넘긴 야간 수거는 새벽 6시까지 그날 목록 그대로이고, 6시가 지나도 **끝나지 않은 어제 업무는 끝나거나 옮겨질 때까지** 목록에 남는다.
- 카운터의 `수거 목록` 화면(N3)은 같은 설정을 바탕(`base_view_id`)으로 하는 `pos` 판이고, 같은 설정의 `print` 판으로 A4 인쇄(`collection_list_a4`)한다. 팀마다 포스트잇 한 줄: `김민수 팀 · 010-…-0025 · 스키 4 · 헬멧 2 · 반납 오늘 22:00 설천 주차장`.
- **구현(체험판, `apps/pos` · 2026-09-23):** 기사 화면은 `#/driver/:date`(넓은 화면에서 `?device=phone`이면 360×640 틀 안에 휴대폰 등급으로), 카운터 수거 목록은 `#/collections/:date`(`#/collection/:date`도 같은 화면). 정한 것:
  - 탭은 `전체 · 잔여 · 완료`(개수 표시). 긴급으로 고정된 줄은 그 반납 타임 맨 위에 있고 ▲ · ▼ · 맨 위로가 막힌다(순서는 고정이 풀린 뒤에 바꾼다). ▲ · ▼의 기준 업무는 지금 보이는 목록(탭)의 이웃이다.
  - 줄의 장소 이름표는 팀 이름 · 끝 4자리 뒤 남는 폭에만 들어간다: 온전한 이름 → 짧은 이름(`subgroupShortLabel`: 숙소는 장소 '들국화', 그 밖은 구역 '설천') → 빼기. 그래서 팀 칸이 남는 폭을 가장 많이 받는다(태블릿 판 `team` 원함 14em · 비율 3, `items` 원함 12em · 비율 1): 숫자판 옆 판이 있는 1024×600과 카운터 875에서도 온전한 이름이 들어간다. 휴대폰(팀 칸 184px)은 이름표 여백을 줄여 짧은 이름(세 글자까지)이 들어간다. 규칙 검사기가 모든 기사 · 카운터 크기에서 줄마다 이름표가 있는지 본다.
  - 긴급 줄은 장소가 가장 중요하다: 좁으면 메모('조기 반납') → 시각(묶음 제목에 있다) → 장소는 짧은 이름으로 줄었다가 마지막에 빠진다(조각의 `short`). 휴대폰: `긴급 · 들국화 · 오승민 · 0039`.
  - 늦은 줄이 있는 반납 타임은 묶음 제목도 늦음 색과 `지연`(`16:30 반납 · 지연 · 0 / 2`): 기사 목록에서 시각이 적힌 곳은 묶음 제목뿐이다.
  - 한 쪽에 묶음 제목을 합치면(4-3, 목록 높이 640px 미만) 제목이 넘칠 때 개수 → 짧은 이름('16:30 · 21:50 · 22:00') → '16:30 외 2' 순으로 통째로 바꾸고, 그 쪽의 줄은 팀 칸 앞에 반납 타임을 붙인다('16:30 · 김민재 · 0021'). **휴대폰은 팀 칸이 좁아 붙일 자리가 없으므로 묶음 제목을 합치지 않는다**(DeviceProfile `combineHeadingsBelowPx` 0).
  - 동작 줄의 동작은 설정 행 그대로(순서 동작 `move_*` 포함, 행을 지우거나 우선순위를 바꾸면 따른다)이고, 줄의 능력(`LedgerRow.conditions`)으로 거르며, 누를 수 없는 것(수거한 줄의 수거 실패, 묶음 첫 · 끝 줄의 ▲ · ▼, 긴급으로 고정된 줄의 순서)은 서버가 준 까닭(`disabledActions`)과 함께 회색이다. 끝에는 늘 `닫기`가 있어 고르기를 끝내고 바닥줄(쪽 넘김 · 매장 입고)로 돌아간다(지금 탭을 다시 눌러도 끝난다). 폭이 모자라면 ① 가장 낮은 동작(`시간순 정렬`) ② 그림 있는 버튼의 낱말 ③ 낮은 동작부터 순으로 줄인다: 휴대폰은 `▲ · ▼ · 수거 실패 · 전화(그림) · 닫기`.
  - `시간순 정렬`은 이 차량의 직접 바꾼 순서를 모두 지우므로 확인 창(`시간순 정렬 · 1호 차량`, 요약 `수동 순서 삭제 · 시간순 정렬`)을 거친다.
  - 기사 머리줄은 좁으면 차량 이름표가 먼저 비켜(더 보기 판 제목 `더 보기 · 1호 차량`) `끝 4자리` · `더 보기` 낱말을 지킨다(AppHeader 5절).
  - 주 버튼 `매장 입고 · N개`(좁으면 `입고 · N개`)는 차량 재고가 없으면 회색(`입고 대상 없음`), 연결이 끊겼으면 누를 때 `입고 불가 · 연결 끊김`(sync 8-4). 카운터 판의 주 버튼은 `수거 목록 인쇄`(인쇄는 아직 `수거 목록 인쇄 준비 중` 알림).
  - 카운터에서 수거 칸을 누르면 도장 대신 한 줄(`1호 차량 수거 예정`)과 `접수증`. 이 표시 · 동작은 서버가 도장 칸에 붙인다(`StampCell.pressNote`, 차량 담당 도장 · 전송 대기 도장도 같음): 화면은 기기 역할이나 단계 키로 문장을 고르지 않는다. `긴급 요청`은 카운터 수거 목록의 동작 줄과 접수증의 옆 동작(조건 `has_open_tasks`)에서 확인 창(`긴급 요청 · 박준호 팀`)을 거쳐 보낸다(`task.pin`, 같은 업무 두 번은 `긴급 요청 완료`).
  - 수거 실패(방문 결과 판)의 사유는 읽기 모델(`visitReasons`, 매장의 `reason_codes`)에서, 시각 버튼은 목록의 반납 타임 시각(고른 날짜의 그 시각이 지금부터 10분 뒤 이후인 것, 세 개까지)과 `직접 입력`(시 · 분 숫자판)이다. 날짜 · 시각은 매장 시간대의 절대 시각으로 바꿔 지금과 견준다: 자정을 넘긴 야간 수거에서 영업일 '오늘'의 22:00은 이미 지난 시각이다. 약속을 옮기는 것은 서버 몫이다.

### 6-4. 접수 확정 창(N4 · N19)

채택한 둘째 판 시안 V4(2026-09-24). 새 접수의 단계 ③ `결제`이고 제목은 `결제 · 이민호 팀`.

- 폭 · 높이는 4-5. 두 줄 칸: `장비 · 스키 4 · 의류 3 · 헬멧 1 · 할인 없음 · 225,000원` / `카드 · 현금 · 계좌이체 · 후불 · 기타 · 할인 적용 ›`. 제목 줄은 글만이고 할인은 수단 줄 끝의 `할인 적용 ›`(그 칸 할인 묶음의 작은 창, 한 묶음에 하나)로 고른다.
- **첫 선택:** 결제 칸의 기본 수단 · 시점(장비 카드, 리프트권 현금). 선입금 방식(`prepayment_mode`)은 **구분이 전화 예약일 때만** 리프트권 칸을 전액으로 미리 고른다(catalog 11). 이미 받은 선입금은 제목 줄에 실제 상태(`12/24 선입금 105,000원 · 미수 없음`)로 적고 다 받은 칸은 한 줄이다. 현장 접수는 선입금 안내가 없고 리프트권 칸에서도 `후불`을 고를 수 있다. 구분은 새 접수 ②의 `예약 · 수령일 ›`로 정한다(6-6).
- `후불` → 그 칸 금액이 옅은 먹이 되고 결제 팀 줄이 보인다: 이름표 `장비 225,000원 · 결제 팀`, 고르기 `이민호 · 0042`(이 팀도 이름 · 끝 4자리로 — `이 팀`은 옆의 `이정호`와 붙어 '이 씨 팀'으로 읽힘) · `이정호 · 0032` · `다른 팀 찾기 · 끝 4자리`. 다른 팀을 고르면 그 칸 제목 줄에 파란 `이정호 팀 결제 예정`. 결제 팀 줄은 `후불`인 칸 **모두**에 걸리고 이름표가 그 칸들을 적는다(한 칸만 다른 팀이 내게 하려면 그 칸의 `기타` 판의 `다른 팀 결제`). 자기 접수는 다른 팀으로 고를 수 없다.
- **받을 금액 줄:** `받을 금액` · `현금 160,000원` · `= 리프트권 140,000원 + 보증금 20,000원`. 모든 칸이 `후불`이고 보증금 칸이 없으면 `받을 금액 없음`.
- **주 버튼:** `접수 확정 · 현금 160,000원`(받을 금액만, 수단 이름과 함께; 섞이면 `접수 확정 · 카드 225,000원 · 현금 160,000원`; 받을 금액이 없으면 `접수 확정`). 보증금은 수납이 아니므로 `수납하고`를 쓰지 않는다(옛 글을 고침). 전화 예약 접수와 `일행 · 장비 추가`도 같은 창이고 주 버튼만 `추가 확정 · N원`.
- **보증금 칸**(보증금 규칙의 결제 칸, 이 매장 `리프트권 보증금`): 수단이 하나(이 매장 현금만)라 버튼 없는 한 줄 52 `리프트권 보증금 · 4매 · 매장 기준 1매 5,000원 · 반납 시 반환 · 현금 20,000원`(할인 · `후불` 없음 — 보증금은 권을 주기 전에 받는 돈). 매장이 수단을 둘 이상 두면 두 줄 칸(`후불` 없음)이고, 반환할 때(6-2)는 받은 수단을 따른다. 매장 값이라는 것이 보이게 쓴다(`매장 기준 …`). 보증금을 받지 않는 매장, 입금 시점이 `지급 시`인 매장은 이 칸이 없다(자리는 비워 두고, 지급 창이 묻는다).
- 다른 카운터가 이 팀 카드 결제 중이면 수단 버튼 대신 '카드 결제 중 · 카운터 1'. 카드 결과를 모르면 창 안의 단계: '단말기 승인 확인 [승인번호 입력] [미승인]'.
- **끊긴 카운터에서:** 같은 창으로 현장 접수를 확정한다(`order.create`, 제한 `walk_in_cached_quote`: 기기의 게시 판 값, 미리 정한 할인만, 결제 팀은 이 팀만). 제목에 `임시 접수 번호 2-01`이 붙고, `다른 팀 찾기`와 카드 단말 연동 요청은 누르면 `연결 끊김 · 연결 후 가능` 한 줄이다(sync 8-6).

- **구현(체험판, 2026-09-25):** `components/CheckoutDialog.tsx`(읽기 모델 `checkoutSheet`, 명령 `order.create` + `expect.quoteHash`), 창 860 × 504(전화 예약은 보증금 칸이 없어 452), 연 동안 그대로. 돈은 칸마다 한 건(plan 8절 D42), 결제 팀 줄의 추천 · 찾기(D44), 체험 할인은 묶음마다 `10% 할인` 하나(D39). 카드 단말 단계 · 끊긴 카운터의 임시 접수 번호 · `일행 · 장비 추가` · 예약금은 아직이다(D38 · D45).

- **카드는 행에서 나온다(ADR-05):** `○○ 반납` 카드는 반납 정책을 고를 수 있는 종류마다(값 = `return_policy_key`), `○○ 보증금` 카드는 보증금 규칙마다(`deposit_rules`). 이 매장은 둘 다 리프트권 하나라 두 장이고, 장비 보증금을 두는 매장은 카드가 한 장 늘 뿐 코드는 그대로다.
- 카드와 말: `리프트권 반납` — `반납 필수`(required) · `반납 선택 · 반납 시 기록`(optional; `none`은 리프트권 카드에 내지 않음), 표시 `반납 필수 · 리프트권 반납 후 완료` / `리프트권 보증금` — `보증금`: `사용` · `미사용` · 값 버튼 `1매 5,000원 ›`(윤곽, 금액 숫자판; `미사용`이면 사라지고 `보증금 미사용`), `입금 시점`: 두 줄 `접수 시` / `미입금: 지급 시` · `지급 시`, `미반납 시`: `보증금 몰수`(keep) · 두 줄 `분실금 청구` / `보증금 공제`(charge_loss, 좁으면 한 줄 `차액 청구`, 고르면 `1매 35,000원 ›`) / `리프트권 결제 · 전화 예약` — `선입금 전액` · `예약금`(고르면 `팀당 50,000원 ›`) · `당일 결제` / `당일 취소 환불`(한 줄) — `환불` · `환불 없음` / `영업일 기준 시각` — `00:00` · `03:00` · `06:00` · `직접 입력`(00:00~11:59), 예시 `27일 00:15 반납 → 26일 장부` · `27일 07:00 반납 → 27일 장부`, 표시 `마감 후 기록 · 다음 마감 반영`.
- 카드에 없는 규칙 값(받는 수단 — 결제 칸 설정, 돌려드리는 법의 기본, 며칠 뒤)은 시작 값 그대로이고 결제 칸 설정은 `요금 · 할인` 탭(이번 판에서 그리지 않음).
- 바닥줄: `‹ 관리` · `변경 3건 · 다음 기록부터 적용` · 주 버튼 `저장 · 3건`(변경이 없으면 `변경 없음`, 누를 수 없음). 저장 확인 창은 전 → 후 목록과 `다음 기록부터 적용 · 지난 기록 · 접수 유지`. 저장하지 않고 떠나면 `미저장 변경 3건` + `저장 안 함` · `저장 · 3건`. 두 기준 시각 사이에는 기준 시각 저장이 거절된다(`변경 불가 · 06:00 이후 가능`, data-model 3-3). 서버가 모든 화면 · 대상 크기에서 칸이 들어가는지 계산한다(4-2).
- 설정은 연결이 필요하다(끊긴 카운터에서는 `설정 변경 · 연결 후 가능`).

- **구현(체험판, 2026-09-25):** 관리는 `screens/ManageScreen.tsx`(카드 `매장 설정` · `마감`, 바닥줄 `‹ 장부`), 매장 설정은 `screens/ShopSettingsScreen.tsx`(경로 `#/manage/settings/:tab`, 운영 규칙만 만들고 다른 탭은 `준비 중인 화면`). 운영 규칙은 읽기 모델 `shopRules`(카드 · 바뀐 곳 전 → 후 · 바닥줄 · 거절 까닭)와 명령 `setting.set`이고, 카드(`RuleCard`)는 통째로 칸 · 쪽에 나눈다(`packCards`, 1024×569 · 529 두 쪽, 좁은 포스 한 칸, plan 8절 D78). `분실금 청구`의 값은 제 줄(D79), 저장 · 떠날 때 창(D80), 기준 시각을 바꾸면 지난 기록은 옛 기준으로 센다(D81), 보증금 `미사용`이어도 맡은 보증금은 반환한다(D82), 금액 · 시각 숫자판의 범위는 읽기 모델이 준다(D83).

## 7. 화면과 도메인의 연결

```ts
// packages/contract — 화면과 서버가 함께 쓰는 형식
export interface DomainClient {
  config(): Promise<UiConfig>;                         // 레지스트리 · 사용 기능 · 문구 · config_rev (기기가 아는 키만)
  ledgerView(viewKey: string, params: ViewParams): Promise<LedgerViewResult>;   // 설정으로 그리는 모든 목록
  query<Q extends QueryName>(name: Q, params: QueryParams[Q]): Promise<QueryResult[Q]>;   // 틀이 따로인 것(확정 창 초안 등)
  command(envelope: AnyCommandEnvelope): Promise<CommandOutcome>;   // 종류로 가르는 봉투. 보내지 못하면 DomainError('NETWORK'),
                                                                     // 보냈는데 답을 잃으면 outcome 'unknown'(결과 확인 중)
  subscribe(onChange: (head: { epoch: string; rev: number; configRev: number }) => void): () => void;
  connection(): ConnectionState;                       // 온라인 · 전송 대기 수 · 마지막 연결(바뀌면 subscribe로 알림)
  pending(): Promise<PendingCommand[]>;                // 전송 대기 목록(오프라인)
}
// LedgerViewResult = { asOfRev, epoch, serverTime, currentBusinessDate, groups, rows: [{ id, cells: { [column_key]: Cell },
//                      stamps, dueAt, lateAt, rank }], metrics, page }
// 따로 있는 조회: orderSlip(orderId) · confirmDraft(orderDraft) · reviewList() · vehicleLoad(vehicleId)
export interface PlatformBridge {                      // PWA와 데스크톱 포장 앱이 각자 구현
  print(job: PrintJobRef): Promise<PrintOutcome>;      // 서버(끊기면 기기의 같은 코드)가 그린 문서를 인쇄 도우미 · 브라우저로 내보내기만
                                                       // (끊긴 동안은 같은 PC 도우미의 localhost 창구로; printedLocally, sync 9절)
  openDrawer(): Promise<void>;                         // 같은 PC 도우미의 localhost 창구
  cardTerminal(intentId: string): Promise<void>;       // 카드 단말 도우미에 요청 id를 넘김(결과는 도우미가 서버에 알림)
  playAlert(kind: string): void;
  wakeLock(on: boolean): void;
  saveFile(name: string, data: Blob): Promise<void>;
  app(): { version: string; contract: number; updateReady: boolean; applyUpdate(): void };
}
```

- **목록은 하나의 조회로 그린다.** `ledgerView(viewKey, params)`가 화면 설정(칸 · 탭 · 숫자 · 묶음 · 줄 단위)을 읽어 줄마다 칸 값(`cells[column_key]`: 속성 값, 도장 상태, 맞춤 조각)을 서버가 만든다. 새 장부 화면('미반납 목록', '강습 시간표')이나 새 속성 칸은 설정 행이고 서버 SQL을 고치지 않는다. 속성 칸은 그 줄 단위가 가질 수 있는 주인만(`sys_row_grain_entities`의 조인 길).
- 읽기 모델은 서버(또는 오프라인 기기의 같은 코드)가 만든다. 도장 상태, 처리 현황, 늦음의 기준 시각(`due_at` · `late_at`), 표시 문구 키가 이미 들어 있다. 화면은 그리기만 하고, 늦음은 **서버 시각 차이로 고친 지금 시각**과 `late_at`을 매분 비교해 칠한다. '오늘'은 서버가 준 `currentBusinessDate`다: 하루 기준 시각(이 매장 06:00, data-model 3-3)을 넣은 영업일이라 27일 01:00에도 26일 장부가 열린다. 마감 화면의 제목줄 기준 띠는 그 기준을 한 줄로 보인다(`현재 27일 00:40` · `26일 장부 · 기준 06:00 · 00:15 정하늘 · 0041 반납 포함`, 6-8; 자정을 넘긴 마감 화면만 날짜를 숫자로 쓴다). 끊긴 기기는 마지막으로 받은 서버 시각 차이와 기준 시각으로 '오늘'을 정한다(sync 8-8). 화면은 날짜를 스스로 계산하지 않는다.
- **확인 창은 연 때의 `asOfRev`를 명령의 basis로 보낸다**(sync 문서 2절). 창을 연 동안 새 rev가 와도 basis는 바뀌지 않고, 돈 결정은 `expect`(받을 돈 등)를 함께 보낸다: 서버가 준 초안(`ConfirmDraftView.expect` · `dependsOn`)을 창이 열릴 때 초안에 넣는다. 돈 명령(`MONEY_COMMANDS`: `payment.take`, 환불)은 `expect`가 없으면 서버가 거절한다(`EXPECT_REQUIRED`).
- **초안의 요청번호:** 창을 열 때 새로 만든다. 창이 열린 채 새로 고침한 뒤 같은 창을 다시 열면, 저장된 초안이 아직 보내지 않았고(`sentAt` 없음) basis가 같을 때만 그 번호를 다시 쓴다(`reusableDraft`). 보낸 초안의 번호는 새 창(새 의도)에 쓰지 않는다: 같은 번호면 서버가 옛 결과를 돌려주어 새 도장이 말없이 사라진다. 창을 닫거나 화면을 떠나면 저장된 초안을 지운다.
- **형식:** 명령 봉투 · 초안은 종류로 가르는 합(`AnyCommandEnvelope` · `AnyCommandDraft`)이라 종류와 본문이 어긋난 명령은 형식 검사에서 막힌다(`ConfirmCommand` = `{ type, payload }`).
- **실패의 약속:** 조회(`config` · `ledgerView` · `query`)는 실패하면 `DomainError`(코드 `NOT_FOUND` · `NETWORK` · `UNKNOWN_VIEW`)로 거절하고, `command`는 업무 결과(거절 · 충돌 포함)를 `CommandOutcome`으로 돌려준다. **보내지 못한 것**(연결이 없었음)만 `NETWORK`로 거절하고, **보냈는데 답을 잃은 것**(서버에서는 적용됐을 수 있음)은 `outcome: 'unknown'`(결과 확인 중)이다: 요청번호를 놓지 않고, 오프라인 허용 명령은 같은 봉투로 보냄 대기에, 온라인 전용 명령은 창에 `연결 끊김 · 결과 확인 중`을 띄우고 새 요청을 막은 채 연결되면 같은 봉투를 다시 보내 결과를 받는다(sync 8-1). 화면은 다시 읽기가 실패해도 가진 읽기 모델을 지우지 않고(잠시 뒤 다시 읽음) 코드로만 가른다(`접수 없음` ↔ `연결 끊김 · 접수증 조회 실패 · 자동 재시도`). 보내지 못하면 '처리 중'을 풀고 한 줄(`전송 실패 · 재전송 필요`).
- **연결 상태와 설정 판:** `DomainClient.connection()`(온라인 · 전송 대기 수 · 마지막 연결)이 계약에 있고 바뀌면 `subscribe`로 알린다(연결 띠 · 매장 입고의 연결 확인). 동기화 머리(`SyncHead`)에 `configRev`가 있어 설정이 바뀌면 기기가 `config()`를 다시 받는다.
- 명령을 보내면 화면은 결과가 올 때까지 그 줄에 `처리 중`을 보이고, 오프라인이면 `전송 대기`로 큐에 넣는다. 이어 붙은 결과는 `ChangeBanner` 한 줄.
- **HttpClient**(운영): 우리 **중앙 서버**의 `/api/v2`(HTTPS 하나의 앱 주소, SSE 알림; README ADR-19, deployment 1 · 2절). 2026-09-26에 만든 것(work/impl-server/plan.md 6절, `apps/pos/src/app`):
  - **모드 고르기(`runtime.ts`):** 앱은 호스트 이름이나 물어본 답으로 짐작하지 않는다. 배포가 서버 판의 `index.html`에만 찍는 표시 `<meta name="skinote-runtime" content="server">`가 있으면 늘 서버 모드이고(세션 `GET api/v2/session`: 200 앱 · 401 등록 · 로그인 · 그 밖은 `연결 끊김` 화면, 5초마다 다시 묻고 체험판으로 가지 않는다), 없으면(GitHub Pages · vite · 미리 보기) 체험판이다. 주소의 `?demo`는 표시가 없는 곳에서만 뜻이 있고(어차피 체험판), 표시가 있는 우리 서버 주소에서는 무시한다: 우리 주소의 `?demo` 링크 · 즐겨찾기 · 설치한 앱으로 카운터가 체험 자료에 접수를 적는 일이 없게(시험 `npm run test:e2e`가 본다). `check:dist`가 빌드에 표시가 없는지 본다.
  - **세션 문(`session.tsx`):** 기기 등록(숫자판으로 12자리, 기기 열쇠 WebCrypto P-256을 IndexedDB에, 비밀 열쇠는 꺼낼 수 없음) → 로그인(한 번 값에 서명 → 직원 타일 → 비밀번호 숫자판, 가린 표시) → HttpClient로 체험판과 같은 `App`. 역할은 기기 종류에서 온다(포스 = 카운터 `#/ledger`, 기사 태블릿 · 휴대폰 = 기사 `#/driver/<오늘>`). 기사 기기는 기사 화면 밖을 열지 않는다. 세션이 끝나면(401) 로그인(`로그인 만료 · 재로그인 필요`), 끊은 기기면 등록으로. 나가기 화면에 `로그아웃`.
  - **HttpClient(`http-client.ts`):** 상대 주소 · 같은 곳 쿠키 · POST는 JSON + CSRF 머리(`SessionInfo.csrf`, 메모리에만). 조회는 모두 `POST api/v2/query`(주소에 끝 4자리 · 이름이 남지 않게). 명령은 연결 없음 · 502 · 503 · 504면 같은 본문을 1 · 2 · 4초 뒤 다시 보내고(서버가 요청번호로 한 번만 적용), 그래도 안 되면 `NETWORK`(창이 초안을 쥐고 `전송 실패 · 재전송 필요`). 알림 연결 하나(rev · configRev가 바뀌면 다시 읽기), 끊긴 동안 머리를 5초(카운터) · 10초(기사)마다, 살아 보여도 30초 조용하면 한 번 묻는다. 서버 모드는 온라인만(보냄 대기 없음, plan §0).
  - **연결 상태:** 기사 화면은 연결 띠, 카운터는 머리줄 매장 이름 자리의 이름표 `연결 끊김 · 마지막 연결 16:48`(좁으면 `연결 끊김`, `AppHeader connection`). 이름표는 연결 띠와 같은 노랑 바탕이다(회색은 어르신 직원이 놓치기 쉽다; 5절 `ConnectionStrip`의 지금 구현). 연결 상태는 넘기기 지연을 따른다(연속 두 번 실패에 끊김, 10초 안정 뒤 이어짐). 서버에 붙은 기기에는 보냄 대기가 없어(`ConnectionState.sendQueue: false`: 명령은 바로 보내거나 거절된다) 기사 바닥줄의 `전송 대기` 숫자를 그리지 않는다.
  - **서비스 워커:** 범위 안의 `api/` 아래는 저장하지도 감싸지도 않는다(`test:pwa`가 본다). 서버 판의 앱 뼈대는 설치 때 표시와 함께 저장되므로 연결 없이 켜도 체험판이 아니라 `연결 끊김`이다.
  - **시험:** 단위(`apps/pos/test` runtime · http-client · session · device-key), 로컬 앞단(`scripts/lib/local-proxy.mjs`, dist를 주며 index.html에 표시를 찍고 `/api`를 서버로)과 진짜 서버로 브라우저 끝까지(`npm run test:e2e`). 등록 · 로그인 · 연결 끊김 · 로그아웃 화면은 체험판 미리 보기(`#/preview/enroll` · `login` · `offline` · `exit`)로 규칙 검사기가 모든 크기에서 잰다.
- **LocalClient**: 브라우저 Web Worker에서 같은 `packages/store` · `packages/domain`을 SQLite WASM에서 돌린다. 세 곳에 쓴다: ① 체험판(GitHub Pages, 메모리 DB, 체험 매장 `is_test` 시드, `체험 자료 초기화` 버튼), ② **기사 기기의 오프라인 읽기**(OPFS의 범위 자료 + 보냄 대기 겹치기, sync 문서 8-1), ③ **카운터의 오프라인**(2026-09-24, ADR-19: OPFS의 오늘 일할 사본 + 보냄 대기 겹치기; 연결되어 있으면 HttpClient, 요청이 연속 두 번 3초 안에 답을 못 받거나 끊기면 같은 화면을 LocalClient로 그리고, 10초 동안 답이 잘 오면 돌아옴 — sync 8-1 · 8-9). 서버와 같은 코드라 온라인 · 오프라인 · 체험판이 다르게 움직이지 않는다. 보냄 대기 겹치기는 사본에 이미 그 요청번호의 행이 있는 큐 명령을 건너뛰고, 사실 어댑터 명령은 어댑터의 native 앞 단계로 겹친다(옛 처리기는 기기에 없다, sync 8-1). WASM 묶음이 너무 무거우면 체험판은 미리 만든 읽기 모델만 보여 주는 읽기 전용으로 한다(열린 질문). 기사 기기와 카운터의 WASM은 줄일 수 없는 필수다(설치한 PWA가 미리 받아 둠).
- **판이 다른 앱과 서버:** 기기는 자기가 아는 계약 판(`devices.command_contract`)을 알리고, `config()`는 그 판보다 늦게 들어온 sys 키(`sys_*.added_in`)를 쓰는 설정 행을 빼고 준다. 그래도 모르는 그리기 · 틀 · 필터 키가 오면 그 칸 · 탭만 숨기고 오류를 서버에 알린다(화면이 깨지지 않음).
- **업데이트:** 새 판은 받아 두었다가 **열린 창이 없고 보냄 대기가 0일 때만** 적용한다. 하루 종일 창을 닫지 않는 카운터는 **마감 뒤나 05:00 ~ 06:00에 열린 창 · 초안 · 보냄 대기가 없으면 스스로 다시 연다**. 기사 기기는 앱을 켤 때 바뀐다. 그 전에는 머리줄 알림 칸에 '새 버전' 표시. 서버가 먼저 올라가고, 동기화 답의 `minClientVersion`(배포 창에서만 올림)보다 옛 기기는 큐를 다 보낸 뒤 바뀐다(deployment 7절).
- **FixtureClient(임시):** LocalClient가 오기 전까지 체험판(GitHub Pages)은 `apps/pos/src/fixture`의 FixtureClient를 쓴다. 시안과 같은 하루(12월 26일 15:40, 18팀)를 브라우저 `localStorage`에 두고, 서버 대신 읽기 모델(장부 · 접수증 · 수거 목록 · 확인 창 초안 · 끝 4자리 찾기)을 만들어 준다. 규칙은 그 폴더의 `rules.ts` · `stamps.ts`에만 최소한으로 있고 화면은 모른다. 명령은 요청번호로 한 번만 적용한다. `나가기` 화면에서 체험 시계를 앞으로 돌리거나(`+10분` · `+1시간`) 체험 자료를 처음으로 돌린다(`체험 자료 초기화`). LocalClient가 오면 이 폴더를 통째로 없앤다(README 결정 '체험판 전용 가짜 로직은 버림'의 임시 예외).
  - **기기 역할과 연결(체험):** 기사 화면을 여는 동안 FixtureClient는 기사 기기(LocalClient 몫)가 된다. 기사 기기의 `나가기`(`#/exit?from=driver`)에서 연결을 끊으면 오프라인 허용 명령(수거 · 방문 결과 · 순서 · 알림 확인)은 보냄 대기(화면 `전송 대기`)에 쌓이고(결과 `queued`, 기기 쪽 결과라 서버 기록에는 없다), 목록은 대기 명령을 복사본에 겹쳐 그려 수거 도장을 점선으로, 바닥줄을 `완료 · 전송 대기 · 잔여`로 보인다(sync 8-1). 매장 입고처럼 연결이 필요한 명령은 거절한다. 다시 이으면 쌓인 순서대로 기기에서 확인한 시각으로 적용한다. 카운터 화면에는 기사 기기의 대기가 보이지 않는다.
- **설치한 PWA:** `apps/pos`는 설치할 수 있는 앱이다. 빌드 플러그인(`apps/pos/pwa/skinote-pwa.ts`)이 `manifest.webmanifest`(이름 · 짧은 이름 스키노트, `lang` ko, standalone, 색은 디자인 토큰 `--sn-desk`, 마스크 아이콘 포함, 주소는 모두 상대 주소)와 `sw.js`(빌드한 앱 뼈대 · 스크립트 · 스타일 · 묶은 글꼴 · 아이콘을 미리 받는 목록과 내용 해시 판 번호)를 쓴다. 서비스 워커는 운영 빌드에서만 `./sw.js`(범위 `./`)로 등록하므로 GitHub Pages의 하위 경로(`/skinote/`)에서도 그 폴더가 범위다. 화면 열기는 받아 둔 앱 뼈대, 나머지는 받아 둔 파일을 먼저 쓰므로 한 번 연 뒤에는 연결 없이도 열린다. 새 판은 받아 두고 열린 창이 모두 닫히면 바뀐다. 서비스 워커는 `skinote:apply-update` 메시지를 받으면 바로 바꾸지만, 앱에서 이 메시지를 보내는 곳(열린 창이 없고 보냄 대기가 0일 때 · 알림 칸의 '새 버전')은 아직 없다. vite-plugin-pwa는 Vite 8을 적어 두었지만 서비스 워커를 따로 묶는 workbox-build(rollup · babel · terser 한 벌)를 들여오므로 쓰지 않았다.
- **가져오기 경계:** `apps/pos`는 `packages/contract` · `packages/ui` · `packages/layout`만 가져온다(LocalClient Worker 안만 예외). `apps/pos`와 `packages/ui`는 `@skinote/core`와 Node 내장 모듈을 가져오지 않는다. `scripts/check-import-boundary.mts`(`npm run check:imports`, `apps/pos` 시험에도 들어 있음)가 막는다. 옛 스파이크(`apps/pos/src/main.tsx`의 `@skinote/core` 가져오기)는 없앴다.
- 옛 포스 v4(vanilla)는 이관 기간 동안 `/api/v1` 호환 창구(legacy facade)로 새 저장소에서 돌 수 있다. React 화면이 늦으면 그 화면을 대신 쓴다(migration 문서 4절).
- **인쇄:** 인쇄 틀은 화면과 같은 장부 설정 · 속성 자리를 `print` 등급으로 풀어 쓴다(3-7). 중앙 서버가 문서를 한 번 그려 얼리고(`print_jobs.document_json`), 도우미나 브라우저는 `PlatformBridge.print`로 내보내기만 한다. 끊긴 카운터는 같은 코드로 기기에서 그려 브라우저 인쇄나 같은 PC의 도우미로 찍고(임시 접수 번호가 든 접수증), 인쇄 기록(`print.request`)은 보냄 대기로 간다. 화면에 새 칸을 더하면 인쇄에도 나온다.
- **화면의 안전 규칙:** 매장 앱과 콘솔 모두 엄격한 CSP(`script-src 'self'`, 인라인 스크립트 없음, `object-src 'none'`, `frame-ancestors 'none'`)와 Trusted Types를 쓴다. 매장이 넣은 글(손님 이름, 메모, 장소 메모)과 설정 · 인쇄 틀은 **HTML이 아니라 형식 있는 값으로만** 그린다(`dangerouslySetInnerHTML`을 쓰지 않음; 인쇄 틀 `layout_json`도 값만). 세션은 HttpOnly 쿠키라 화면 코드가 토큰을 만지지 않는다(deployment 3절).
- 관리자 콘솔은 같은 부품을 `admin` 등급으로 쓰는 별도 앱이고 **따로 된 주소**(매장 앱과 다른 출처, 접근 제한 · 하드웨어 키 2단계 인증)에서만 열린다. 매장 앱에는 `/admin` 경로가 없고 체험판에도 넣지 않는다(deployment 3절).

## 8. 시험

- 촬영 크기: 포스 1024×600, **1024×569, 1024×529**, 1024×768, 1366×768, 907×648, 875×600, 그리고 1024×600의 **110% · 125% 확대** · 기사 태블릿 1024×520, 1024×600, 1280×720 · 기사 휴대폰 360×640, 390×740, 412×780 · 관리자 1440×810 · 인쇄 A4 · 80 mm · 80×50.

  - 실행: `npm run build` 뒤 `npm run rules -w @skinote/pos`(루트 `npm run test:rules`). `apps/pos/scripts/check-ui-rules.mjs`는 빌드하지 않고 `dist`를 vite preview(5183, `--strictPort`)로 띄운다. 매장 기기 등급(`SHOP_DEVICE_CLASS_KEYS`)마다 DeviceProfile의 `checkSizes`를 돌고, 등급은 `pickDeviceClass`로 가른다(카운터 경로: 처음 화면 · 장부 · 모든 접수증 · 없는 접수 · 카운터 수거 목록 · 나가기, 기사 경로: 처음 화면 · 수거 목록 · 휴대폰 모양으로 보기 · 기사 나가기). 화면마다 탭과 쪽을 넘기고 도장 · 주 버튼 · 옆 동작 · 머리줄 메뉴 · 동작 줄을 눌러 확인 창 · 알림 창 · 숫자판 · 아래 판(더 보기 · 방문 결과 · 차량 재고)을 모두 열어 잰다. 그 뒤 도장을 찍고(지급 · 수납 · 수거 · 매장 입고 · 수거 실패 · 긴급 요청 · 연결 끊김) 체험 시계를 21시 · 22시 뒤로 돌려 다시 잰다.
  - 재는 것(`apps/pos/scripts/ui-rules-measure.mjs`, 페이지 안에서 돈다): 최소 글자 · 누르는 곳은 검사 크기의 등급과 화면이 고른 등급(`data-device`) 중 엄한 값, 페이지와 요소의 가로 넘침 · 화면 밖, 글 조각이 담긴 상자나 자르는 조상 밖으로 나간 글자, 말줄임표 글자 · `text-overflow` · 줄 수 자르기, 페이지 스크롤 · 스크롤 영역 · 스크롤 상자 안의 목록 · 반쯤 잘린 줄, 창(또는 화면)마다 주 버튼 하나와 그 색이 등급 강조색인지, `.tone-late` · `.is-late` 밖의 빨강(늦음 토큰과 빨강 쪽 색상, 글자 · 바탕 · 테두리 · 그림자 · 그림), 영어 글자, 화면이 고른 등급. 창이 열려 있으면 그 창 안만 잰다.
  - 찍은 화면은 `work/screens/rules/`(경로 · 크기마다 한 장 이상, 창은 제목마다 첫 장과 어긋난 장)와 `report.json`. 하나라도 어긋나면 끝 코드 1.
- 규칙 검사기의 내용 검사: 장부의 끝나지 않은 줄마다 시각이 보이는지(좁은 포스 포함), 수거 목록의 줄마다 장소 이름표가 있는지, 동작 줄의 `닫기`가 고르기를 끝내는지, `시간순 정렬`이 확인 창을 거치는지.
- 화면 시험(Playwright)은 단위 시험 명령(`npm test`)에 넣지 않는다(브라우저가 필요). 루트 `npm run check`와 CI(`.github/workflows/ci.yml`)는 빌드 뒤 `check:dist`(브라우저 없이 체험판 빌드의 상대 주소 · PWA 범위 · 넣지 않는 것 확인, `scripts/check-dist.mjs`), `test:pwa`, `test:rules`를 차례로 돈다. Pages 배포(`pages.yml`)는 브라우저 없이 빌드와 `check:dist`만 돈다. 앞 단계의 `test:ui`(`scripts/check-screens.mjs`: 빌드한 앱을 vite preview로 열어 포스 검사 크기마다 장부 · 접수증 · 확인 창 · 숫자판 · 긴급 요청 · 카운터 수거 목록 · 나가기를, 기사 검사 크기(1024×520 · 1024×600 · 1280×720 · 360×640, 누르는 곳 56px)마다 수거 목록 · 줄 고르기 · 순서 · 수거 실패 · 수거 도장 · 끝 4자리 · 긴급 · 차량 재고 · 매장 입고 · 연결 끊김을 눌러 가며 찍고 규칙을 잰다. 창이 열려 있으면 그 창 안만 잰다)와 `test:pwa`(`scripts/check-pwa.mjs`: 하위 경로 `/skinote/`로 띄워 manifest · 서비스 워커 · 미리 받은 파일, 브라우저 오프라인과 서버를 멈춘 뒤에도 열리는지, 개발 서버에서는 등록하지 않는지)가 있다. `test:ui`는 규칙 검사기와 겹쳐 `check` · CI에는 넣지 않았다. 검사 크기 · 최소 글자 · 누르는 곳은 DeviceProfile에서, 늦음 빨강은 토큰에서 읽는다.
- **설정 시험:** 모든 `ledger_view`와 모든 목록(탭 · 메뉴 · 숫자 · 결제 칸 · 옆 동작 · 속성 자리)이 모든 대상 크기에서 4-2 · 4-4 계산으로 들어가는지 — 개발 시험(기본 설정)과 **설정 명령마다 서버에서**(매장 설정). 기본 설정 판을 올린 뒤 옛 매장 파일에 `ui_defaults.apply`를 돌려 없던 탭 · 칸 · 상태 문구가 생기는지.
- **오프라인 시험:** 같은 자료로 서버와 기기의 `driverList` · 도장 · 바닥줄 숫자가 같은지, S6을 오프라인 중 앱 다시 시작까지 넣어 돌리는지. 카운터도 같다(2026-09-24): 같은 자료로 서버와 기기의 `dayLedger` · 접수증 · 확정 창 초안이 같은지, **연결 띠가 떠도 쪽 수와 줄 자리가 바뀌지 않는지**(띠 자리를 비워 둠, 4-3), 느린 회선에서 띠가 깜빡이지 않는지(넘기기 지연), 연결을 기다리는 버튼이 자리를 지키고 한 줄 표시(`… · 연결 후 가능`)를 보이는지, 끊긴 반납 창이 권을 처음에 고르지 않는지, 답을 잃은 명령이 '결과 확인 중'이 되는지, S18(두 카운터가 함께 끊김 · 그사이 서버 되살리기, sync 8-11)을 돌려 두 번 세는 것 · 버린 것이 0인지. 규칙 검사기는 카운터 경로도 연결 끊김 상태로 한 번 더 잰다.
- **자리 지키기 시험:** 도장을 찍은 줄과 다른 기기의 변경이 보고 있는 쪽의 줄 자리를 바꾸지 않는지(쪽을 넘기거나 60초 뒤에만).
