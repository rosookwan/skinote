# 스키노트 기반 설계

작성 2026-09-23. 고침 2026-09-24: 사장님 답 다섯 가지를 '정한 것'(D1–D5)으로 옮기고 ADR-18(보증금)을 더했다. 같은 날 화면 문구를 대화형 말에서 짧은 업무 용어로 바꾸기로 하고(D6, 기준 [docs/design/wording.md](../design/wording.md)) 설계 문서가 인용한 화면 글을 고쳤다. 같은 날 **배치를 클라우드 중심으로 바꿨다**(ADR-19, 새 문서 [deployment.md](deployment.md)): 장부 원본은 우리 중앙 서버에, 카운터도 기사처럼 오프라인 사본과 보냄 대기로 일한다. ADR-02 · 10 · 11 · 12와 D4를 그에 맞춰 고쳤고(바뀐 곳에 '바뀜' 표시), 채택한 둘째 판 시안([docs/design/screens-v2](../design/screens-v2/spec.md))의 화면 말을 D1 · D2 · D5와 다른 문서에 맞췄다. 스키노트(한국 스키 렌탈샵 POS, 첫 매장 · 무주)가 여러 해 동안 **데이터베이스를 다시 만들지 않고** 새 품목 · 새 칸 · 새 장소 · 새 매장 · 새 기능을 더할 수 있게 정한 기반이다. 세 가지 설계안(A 관계형 우선, B 이벤트 소싱, C 묶음 + JSON)을 세 심사가 평가했고, 이 설계는 **A를 바탕으로 B와 C의 좋은 점을 더하고 심사가 찾은 치명적 약점을 모두 고친** 최종안이다. 같은 날 네 관점(다시 만들기 사냥 · 돈과 재고 · 동시 수정과 오프라인 · 화면 확장)의 공격적 검토 93건을 받아 반영했다(맨 끝 '검토 반영 기록'). **클라우드 중심으로 바꾼 뒤 같은 날 셋째 검토 78건**(끊김 · 보안 · 운영 · 일관성)을 받아 반영했다: 큐에서 온 명령은 적어 두는 사실이고(ADR-10), 카운터도 끊긴 채 적재 · 권 주기 · 바꿔 드림을 하며, 마감은 보낼 기록이 남은 모든 기기를 기다리고, 되살리기는 두 길 · 새 VM 연습이며(ADR-12), 관리자 콘솔은 따로 된 주소, 열쇠를 나누고(ADR-02), 혼합은 시즌 1 대안이 아니다(ADR-19).

## 결정 기록

### ADR-01 표가 진실이다
- **결정:** 모든 업무 사실은 형식이 정해진 STRICT 표의 행이다. 작업 기록(`events`)은 감사, 5분 복구 구간, 옛 엔진과의 대조에 쓰고, 평소에는 그것으로 상태를 다시 만들지 않는다.
- **이유:** 앞으로 이 코드를 고칠 사람과 AI 에이전트가 평범한 SQL로 이해할 수 있고, 돈 · 재고 규칙을 데이터베이스가 직접 지킬 수 있다. 측정한 성능도 충분하다.
- **버린 것:** B의 이벤트가 진실 · 투영은 버릴 수 있는 구조(모든 옛 이벤트 모양의 변환기를 영원히 유지, 투영 재구축 중 쓰기 멈춤, 저장된 진실에 데이터베이스 제약이 거의 없음). C의 JSON 본문 묶음(관계가 JSON 안에 있어 외래 키가 없고, 장부 행까지 제자리 변환).

### ADR-02 control과 shop, 두 데이터베이스
- **결정:** 계정 · 세션 · 로그인 기록 · 요금제 · 라이선스 · 스키장 템플릿 · 플랫폼 사용 내역 · 백업 목록 · 매장별 epoch · 매장을 알기 전의 길 찾기(링크 토큰, 업체 번호, 콜백 받은편지함)는 `control.sqlite`, 매장이 가진 모든 것은 `shop-<id>.sqlite`. 두 파일 사이 외래 키는 없고, 매장 행은 계정을 행위자 키(`staff:<id>`)와 이름 스냅샷으로만 가리킨다. 라이선스는 공급자가 Ed25519로 서명한 토큰이다. 계정은 전역 ULID, 로그인은 `(영역, 이름)`, 사용 내역 사슬은 파일마다, 템플릿 · 요금제는 고정 id다. PostgreSQL에서는 control과 매장 표가 다른 스키마다.
- **바뀜(2026-09-24, ADR-19):** 두 파일 모두 **우리 중앙 서버**에 있다(처음 결정은 매장 PC 한 폴더). 라이선스는 매장 서버가 아니라 **중앙 서버가 세션을 열 때마다 확인**하고, 기기에는 서명된 짧은 기기 라이선스 표를 주어 오프라인에서도 앱의 공개 키로 확인하게 한다(유예 14일, deployment 5절). 키를 다시 매기지 않는 규칙(전역 계정 ULID, 영역, 사슬 id, 고정 id)은 그대로 두며, 이제는 PostgreSQL · 여러 서버로 옮기기와 혼합 매장을 위한 것이다(control의 쓰는 쪽은 늘 중앙 하나, 혼합 매장의 작은 PC는 그 매장 조각의 읽기 전용 사본). 콜백 받은편지함은 NAT 뒤의 매장 PC 때문이 아니라 매장을 알기 전에 길을 찾으려고(그리고 혼합 매장을 위해) 두고, 기기 등록 번호의 길 찾기(`enrollment_routes`)도 여기 둔다. **셋째 검토(같은 날):** 운영 서버가 인터넷에 붙어 세션마다 서명하므로 **열쇠를 두 층으로** 나눴다: 오프라인 루트 키(개발자의 하드웨어 키 · 금고)가 라이선스 증서와 '기기 표 서명 키'의 인증서에 서명하고, 서버는 자주 바꾸는 기기 표 키만 가진다(`licence_signing_keys.purpose_key` · `certified_by`, 연습 서버는 `test_only` 키). 기기 쪽 확인은 화면 안내용이고 이미 일어난 오프라인 기록은 라이선스 때문에 거절하지 않는다.
- **이유:** 매장 파일을 따로 옮기거나(매장별 파일, 혼합 매장, PostgreSQL) 계정을 지워도 장부가 깨지지 않는다. 표를 고쳐도 라이선스가 풀리지 않는다(서명). 행 보안 아래의 공유 표에서도 문자 · 결제 콜백과 손님 링크가 매장을 찾는다.
- **버린 것:** A의 한 파일 안 계정 FK(매장별 분리 때 수백 개 FK가 깨짐, 서명 없는 라이선스 행). 서명 없는 라이선스(B · C).

### ADR-03 매장 경계와 '같은 접수'를 데이터베이스가 보증
- **결정:** 모든 매장 표는 `shop_id`로 시작하는 키와 복합 외래 키를 쓴다. 접수에 딸린 행은 `(shop_id, order_id, x_id)`로 참조해 같은 접수임을 보증하고, 규격 · 선택지 · 속성 대상 · claim의 장비 · 돈통의 마감 범위도 같은 방식으로 맞춘다. 0001 뒤에 생기는 참조는 복합 FK가 있는 새 연결 · 확장 표를 먼저 쓰고(이동 · claim · 업무 · 조정 · 거래처 거래 · 재고 위치의 새 출처는 반드시), 꼭 열로 더해야 하면 `sys_soft_references`에 적어 검증기가 매일 확인한다.
- **이유:** 다른 매장 · 다른 팀의 행에 붙는 실수를 코드가 아니라 데이터베이스가 막는다. SQLite는 열을 더할 때 복합 FK를 달 수 없으므로 그 빈틈을 숨은 트리거가 아니라 눈에 보이는 목록과 검증기로 메운다.
- **버린 것:** A의 테넌시 트리거(열마다 기억해서 만들어야 하는 숨은 SQLite 전용 규칙). C의 `location_kind/location_id` 같은 다형 참조(FK 검사 불가, 잘못된 차량 id가 조용히 남음).

### ADR-04 DDL에 닫힌 목록이 없다
- **결정:** 코드가 뜻을 아는 값은 `sys_*` 표(마이그레이션만 넣음, FK 대상), 매장이 바꾸는 값은 레지스트리. 화면 설정이 가리키는 코드 키(화면 경로, 칸 그리기, 맞춤, 정렬 · 묶음, 색, 조건, 상태 값, 동작 · 확인 창, 입력 방식)도 모두 sys 표 FK다. 동작 값(부호, 배타, 묶임, 기사 허용, 오프라인 허용, 자동 재시도, 환불 대상 필요, 현금 여부)은 형식 있는 열이고, 규칙이 되는 값은 행에 복사해 복합 FK로 원본과 맞춘다. `CHECK`는 바뀌지 않는 규칙(0/1, 부호, 범위, 계산식)에만 쓴다. 유일성은 모두 이름 있는 인덱스로 적는다.
- **이유:** 새 값은 INSERT이고, 규칙을 바꿀 때 표를 다시 만들 필요가 없다. 표 안 `UNIQUE`는 나중에 풀 수 없지만 인덱스는 바꿀 수 있다(예: 강습 여러 회차).
- **버린 것:** `CHECK (x IN (…))` 목록. B의 `code_lists`(FK 대상이 될 수 없음). C의 `meta` JSON 안 동작 값(검사 불가).

### ADR-05 동작은 능력 값에서, 리프트권과 강습은 평범한 품목
- **결정:** 코드는 `fulfillment_mode_key`, `tracking_key`, `return_policy_key`, `ticketed`, `ends_same_day`, `extendable`, `exchangeable`, `requires_time_slot` 같은 값을 보고, `'liftTicket'` · `'ski'` · 한글 이름을 비교하지 않는다. 줄은 만들 때 계열 · 재고 방식 · 반납 정책을 복사한다.
- **이유:** 옛 코드의 리프트권 분기 약 30곳과 스키 · 보드 고정 교환을 없애고, 강습 줄이 접수를 영원히 열어 두는 문제를 없앤다. 새 종류는 행 추가다.
- **버린 것:** 분류 글자로 가르기. 종류마다 다른 표.

### ADR-06 ID · 돈 · 시간
- **결정:** 모든 새 id는 전역 ULID(기기가 미리 만들 수 있음; 서버가 만드는 id는 요청에서 정해짐), 옛 id는 매장 코드 접두어(`shop1.ski`). 돈은 정수 원, 비율은 basis point, 부호는 어휘 표. 시각은 UTC, 매장마다 시간대와 영업일 기준 시각. 온라인 명령의 발생 시각은 서버가 받은 시각, 큐 명령은 서버 시각 − 기기의 단조 시계 나이. 돈 · 재고 · 청구 기록마다 `occurred_at` · `recorded_at` · `business_date`(일어난 날) · `posting_date`(세는 마감일, 마감 범위마다의 기준선)를 저장하고 다시 계산하지 않는다.
- **정한 값(2026-09-24, D2):** 이 매장과 스키 매장의 기본 기준 시각은 06:00이다. 자정을 넘긴 야간 반납 · 마감은 전날 영업일이다.
- **이유:** 통신이 끊긴 차량도 기록을 만들 수 있고, 매장 파일을 합치거나 다른 매장으로 장비를 보내도 id가 겹치지 않으며, 틀린 기기 시계가 날짜를 옮기지 않고, 야간 기준 시각을 나중에 정해도 지난 기록이 움직이지 않으며, 마감 뒤 들어온 돈 · 청구도 원래 날짜를 잃지 않고 닫힌 날 사이로 새지 않는다.
- **버린 것:** KST 고정. A의 늦은 기록이 `business_date`를 다음 날로 덮어쓰는 방식.

### ADR-07 추가만 하는 장부를 데이터베이스가 지킨다
- **결정:** 장부 50개 표(돈, 배분, 보증금 장부, 조정, 세금 문서, 현금, 넘기기 · 확인, 이동, 이동 줄, 되돌리기 연결, 품목 바꾸기, 상태 변경, 취소 · 연장, 마감 · 다시 열기 · 합계 · 인계, 거래처 거래 · 정산, 설정 판, 템플릿 판, 기기 로그인, 보관 목록 · 확인 등)에 **0001의 열 목록으로** 수정을 막는 트리거(`BEFORE UPDATE OF …`)와 삭제를 막는 트리거를 둔다(생성 스크립트가 만들고 CI가 확인). 나중에 더한 열은 마이그레이션이 채운 뒤 '한 번만' 트리거를 단다. 자유 글 칸은 `(지움)`으로 가리기만 된다. 연결마다 `recursive_triggers = ON`이라 `INSERT OR REPLACE`도 막힌다. 청구 쪽도 같다: 품목 줄의 가격 · 수량 · 날짜 · 스냅샷은 고정, 접수 · 줄 · 약속 · 장비 · 업무 행은 지워지지 않는다. 장부 행에 있던 바뀌는 칸은 따로 뺐다: 되돌리기는 `stock_movement_reversals`, 마감 잠금은 `business_days`, 현금 확인은 `cash_transfer_confirmations`, 할인 변경은 새 적용 행. 작업 기록은 추가 전용 확인 행이 있는 시즌 보관 범위만 지울 수 있다. 장부 행에는 개인정보가 없다.
- **이유:** 약속이 아니라 규칙이 되어야 코드에 버그가 있어도 돈 기록이 안전하다. 옛 처리기를 새 표 위에서 돌릴 때 번역이 빠진 곳도 바로 드러난다.
- **버린 것:** A의 '관례로만 추가'.

### ADR-08 장비 claim은 차선(lane)으로
- **결정:** claim 종류마다 차선(preparation · transport · disposition · composition · ticket_window)이 있고, 배타 차선마다 살아 있는 claim은 하나다(`exclusive_key = asset_id || '|' || lane_key` + CHECK + 부분 유일 인덱스). 그 위에 **장비마다 살아 있는 묶임(`asset_bindings`: 어느 접수 · 권 공용 창 · 환불 · 대여) 하나**가 있고, 묶임 차선의 claim은 모두 그 장비의 묶임에 걸린다(복합 FK). 종류와 차선, 차선과 배타 · 묶임 값이 맞는지도 FK로 확인한다. 물건이 실제로 옮겨진 사실은 계획(claim)보다 이긴다: 이동은 늘 적고 부딪힌 계획을 `displaced_by_fact`로 푼다.
- **이유:** 준비한 장비에 차량 적재 claim을 걸 수 있으면서, 같은 장비를 두 차량이 잡거나 **차선이 달라도 두 접수에 약속하는** 일(A 접수 준비 + B 접수 적재, 내일 손님 권의 발권처 환불)은 데이터베이스가 막는다. 새 차선은 행이다.
- **버린 것:** A의 배타 칸 하나(준비와 적재가 부딪힘). B의 `claim_group`(차선 값 확인 없음).

### ADR-09 돈: 실제 돈 한 건 + 배분 + 현금 이동 하나
- **결정:** `payments` 한 행 = 카드 한 번 · 현금 한 번, `payment_allocations`가 여러 접수 · 줄로 나눈다(옮길 때는 음수 배분 + 사유, 수량도 같은 부호). `payment_groups`(결제 자리), `payment_intents` + `payment_intent_allocations` + `order_checkout_locks`(카드 · PG, 한 팀에 열린 결제 하나), `payment_promises`(결제 팀 · 시점 · 선입금; 내는 팀 쪽에도 보임), `cash_movements`(마감이 현금을 읽는 단 한 곳). **돈 종류마다 현금 장부는 하나**(거래처 · 강습팀 · 발권처 환불 돈은 거래처 정산만). 환불 대상 · 보증금 · 돈통 · 조정 부호는 복사본 + FK + CHECK로 데이터베이스가 지킨다. 보증금의 매수는 보증금 장부가 센다(ADR-18). 카드 승인번호는 유일하지 않으므로 거절 대신 확인 필요. 세금은 수납이 아니라 줄의 분류와 세금 문서(ADR-17).
- **이유:** 여섯 가족 한 번 결제에서 승인번호가 한 건으로 맞고 모든 팀 미수가 0이 된다. 차량 지갑 · 발권처 환불금 · 거래처 현금이 모두 한 곳에서 **한 번씩만** 세어진다. 실제로 받은 카드 돈이 유일성 규칙 때문에 기록되지 못하는 일이 없다.
- **버린 것:** C의 접수마다 결제 행(승인번호를 한 행에만 둘 수 있는 문제). 옛 '결제 하나 = 접수 하나'.

### ADR-10 동시 수정: 충돌 키, 사실은 거절하지 않음
- **결정:** 결정을 바꾸는 명령(intent)은 **확인 창이 그린 읽기 모델의 `{epoch, rev}`**를 보내고, 서버가 명령에서 만든 충돌 키(바꾸는 키 + 그 결정이 기대는 돈 · 수량의 읽은 키)가 그 뒤 바뀌지 않았고 `expect`(받을 돈 등)가 맞으면 자동으로 이어 붙인다(달라진 것은 한 줄 띠로). 일어난 사실(fact)은 버전을 보지 않고 불변식만 보며, 사실 안의 결정 부분만 intent처럼 본다. 앞뒤가 안 맞으면 `확인 필요`가 그 일을 일으킨 기기 · 화면에 `사실 · 할 일` 한 줄로 가고(급한 것은 열린 창 안의 단계), 관리자 목록은 쌓인 것이다. 방문 순서는 업무마다 한 행의 분수 순위(기준 업무로 보내고 나중 결정이 이김), 긴급 요청은 업무마다 하나.
- **이유:** 진짜로 같은 결정을 두 사람이 바꾸거나 결정의 바탕이 바뀌었을 때만 충돌이 난다(`이 팀 120,000원 수납 완료 · 다른 카운터`). 고령 직원은 기술 용어 없는 짧은 한 줄과 버튼 두 개만 본다.
- **바뀜(2026-09-24, ADR-19):** 처음에는 카운터가 매장 LAN으로 늘 연결된다고 보아 늦게 오는 사실은 기사 기기의 것뿐이었다. 이제 **카운터도 오프라인에서 사실을 쌓는다**(지급 · 반납 · 돈 · 보증금, 셋째 검토에서 적재 · 권 지급 · 즉시 교환). 규칙은 같다: 사실은 거절하지 않고, 두 카운터가 함께 끊겨 생긴 겹침(같은 팀 돈 두 번, 같은 장비 두 팀)은 확인 필요로 보인다(sync 8-7). 오프라인에서 쌓을 수 있는 intent는 **새 묶음을 만드는 것**(새 현장 접수 · 이 팀이 내는 열린 접수의 품목 추가)뿐이고 기존 결정을 바꾸는 intent는 연결이 있어야 한다(sync 8-2, `sys_offline_commands`). **셋째 검토(같은 날): 큐에서 온 명령은 등급과 상관없이 '적어 두는 사실'이다**(sync 8-12): epoch · basis · 충돌 키 · 30일 · `expect` · 마감한 날 · dependsOn 실패로 돌려보내지 않고 판단 부분(견적 · 할인 · 결제 팀 · 권한 · 라이선스)만 확인 필요로 올린다. 끊긴 동안 서버를 되살려 epoch가 바뀌어도 끊긴 새 접수와 옛 expect의 돈이 버려지지 않고, 끝내 적용할 수 없는 새 접수는 최소 접수로 적어 딸린 돈 · 지급이 붙을 곳을 남긴다. 온라인으로 바로 보낸 intent만 전처럼 충돌을 받는다. 같은 매장의 여러 기기가 다시 붙을 때는 재고 사실을 일어난 순서로 적용하고, 이동마다 보류한 사실을 다시 판단한다(sync 8-3).
- **버린 것:** 옛 매장 전체 버전. C의 접수 전체 버전(다른 줄 약속끼리 충돌). A의 순위 행 다시 쓰기.

### ADR-11 멱등과 작업 기록
- **결정:** `command_log`는 받은 모든 명령을 영원히 남기고 결과 본문만 90일 뒤 비운다. **멱등 키는 요청번호 하나**(행위자는 데이터: 큐 명령은 기기가 서명한 그때의 직원). 요청번호는 확인 창이 열릴 때 만들어 모든 재시도에 쓰고, 지문은 종류 · 판 · 본문만. `(device_id, device_seq)`는 유일하기만 하고 빈 번호를 찾는다. `dependsOn`은 돈을 멈추지 않는다. 시스템 명령은 정해진 요청번호. `events`는 서버가 정한 값이 모두 든 정본 명령(개인정보 · 자유 글 없음), 넣은 장부 행의 해시, 개인정보의 약속값과 해시 사슬(보관 파일 경계에 앞뒤 해시)을 가지고, 개인정보와 자유 글은 `event_pii`(30일)에 따로 둔다.
- **이유:** 늦게 온 재시도, PIN을 바꾼 뒤의 재시도, 기사가 바뀐 휴대폰의 큐도 두 번 적용되지 않고 원래 사람의 기록으로 남는다. 한 명령이 사라져도 그 기기가 멈추지 않는다. 돈 다툼에서 **표의 행까지** 고치지 않았음을 보일 수 있고, 개인정보를 지워도 사슬이 깨지지 않는다.
- **바뀜(2026-09-24, ADR-19):** 서명된 큐 명령 · 보낸 기록(`sent`, 서버가 정한 값 포함) · 기기 번호 빈 곳 찾기가 **카운터에도** 똑같이 있다. 셋째 검토: 보냈는데 답을 잃은 명령은 요청번호를 놓지 않고 같은 봉투로 결과를 받으며(`결과 확인 중`, sync 8-1), 지문은 개인정보를 참조로 바꾼 정본의 매장 비밀 키 HMAC이고, 막은 기기에서 막은 뒤 도착한 명령과 쓰기 프로세스를 죽인 명령은 보류(`held`)해 사람이 넣을 때 적용한다. 카운터가 끊긴 채 받은 새 접수는 기기 번호가 앞자리인 **임시 접수 번호**(`임시 1-12`, `orders.provisional_receipt_no`)를 가지고, 서버가 받을 때 최종 접수 번호를 주며 임시 번호는 남는다(sync 8-6). 끊긴 동안의 PIN 전환은 `device.sign_in` 큐 명령이 `device_sign_ins`가 된다. 작업 기록 구간은 LAN이 아니라 두 번째 저장소로 1분마다 간다(ADR-12).
- **버린 것:** A의 30일 멱등 · NULL 행위자. C의 거절 미기록. B의 이벤트 진실 위 해시 사슬(보관 파일을 넘는 검증이 무거움 → 앞뒤 해시로 해결).

### ADR-12 백업과 복구
- **결정(2026-09-24 ADR-19로 고침, 같은 날 셋째 검토로 다시 고침):** `synchronous = FULL`. 중앙 서버의 모든 파일(매장 파일 + control)을 **커밋마다 몇 초 안에 다른 구역 저장소로 WAL 복제**(복제 도구의 자기 세대 + WAL, 7일 안 아무 초로나 되살림), **1분마다 작업 기록 구간**(바뀐 행의 after-image 포함, 해시 사슬)을 **다른 회사의 한국 저장소**로(필수; 개인정보 부분은 따로 된 객체로 35일), **날마다 `VACUUM INTO` 스냅샷**(35일), 주 · 시즌 끝 스냅샷은 손님 정보를 지운 사본, **새 VM에 되살리는 연습**(개장 전 두 번, 시즌 중 매주 자동; 그 스크립트가 재해 절차). 모든 사본은 올리기 전에 **매장마다의 공개 키로 암호화**하고(서버에는 공개 키만), 저장소는 객체 잠금으로 지울 수 없게 한다. **되살리는 길은 둘이고 섞지 않는다:** ① PITR = 복제 도구의 세대 + WAL, ② `VACUUM INTO` 스냅샷(그 자체가 되살리는 지점) + 구간의 **after-image 적용**(처리기 코드가 바뀌어도 같은 결과). 원본의 WAL을 `VACUUM INTO` 사본 위에 적용할 수는 없다. 되살린 뒤: 새 epoch + **지금까지 쓴 가장 큰 rev** 위로 1,000,000 도약 + 사람이 읽는 번호 건너뛰기(+500, 기기 번호 +10) + 기기들이 7일 보낸 기록을 **그때 서버가 정한 값과 함께** 다시 보냄(서버를 잃었으면 값 그대로, 잘못된 배포를 되돌렸으면 계산 값을 다시 계산) + 재시도 없는 채널은 사람이 확인 + 목표 시각 뒤의 손님 정보 지우기 · 기기 등록을 다시 적용. RPO는 서버 쪽 5초 이하(기기가 보낸 것은 0 — 기기 안의 기록이 지워지지 않는 한). RTO는 **알림을 받은 때부터** 서버 한 대 1시간(VM만 죽으면 볼륨을 새 VM에 붙여 30분), 지역 · 업체 전체는 근거가 생길 때까지 '하루 안'(deployment 6절, sync 10절).
- **이유:** 서버가 통째로 망가져도 잃는 것은 아직 복제되지 않은 몇 초이고 그것도 기기가 다시 보낸다. 매장에 백업 장치가 없어 불 · 도난 · 매장 PC 고장이 자료 사고가 아니다. 다시 보낸 명령이 다른 번호 · 다른 id를 받거나 문자 · 카드가 두 번 나가는 일이 없고, 복구를 두 번 해도 잃은 rev 번호로 만든 옛 id가 다시 쓰이지 않는다. 두 길(물리 WAL과 논리 구간)이고 두 회사에 나눠 두어 한 도구 · 한 업체 계정의 사고에 함께 무너지지 않는다. 서버가 뚫려도 백업을 읽거나 지울 수 없다. 연습이 곧 재해 절차라 혼자인 개발자가 한밤에 순서를 떠올릴 필요가 없다.
- **처음 결정(2026-09-23, 매장 PC 서버 전제 — ADR-19로 바뀜):** 커밋마다 몇 초 안에 작업 기록 구간을 LAN의 다른 기기(카운터 2)로 흘려 보내고, 5분마다 두 번째 디스크 · USB, 묶이는 대로 원격, 1시간마다 전체 백업 48개. 복구 규칙(epoch · rev_floor · 번호 건너뛰기 · 기기의 다시 보냄 · after-image)은 그대로 이어받았다.
- **버린 것:** C의 밤 한 번 백업 · 큐를 확인 목록으로만. A의 큐만 다시 보내기(받았다고 답한 뒤 잃은 명령을 복구 못 함). 매장 PC · USB · LAN 복사(ADR-19).
- **이 매장(D4):** 사장님 답은 '추천대로'. 추천이 클라우드로 바뀌어 D4를 고쳤다(가게에 드리는 말, 아래 D4).

### ADR-13 확장은 추가로만, 매장 칸은 형식 있는 속성 행
- **결정:** 확장 방법 E1–E12(레지스트리 행, `sys_*` 행 + 코드, 속성, 빈 값 허용 열 + 채우기 + 한 번만 트리거, 새 표, 설정 판, 기능, 화면 설정 + 기본 설정 반영, 인덱스, 속성 → 열 올리기, JSON 문서 새 판, 새 모양이 필요하면 `*_v2` 표 + 뷰). 매장이 정하는 칸은 주인별 값 표 10개(주문, 줄, 일행, 고객, 상품, 규격, 장비, 업무, 장소, 거래처)에 형식 있는 값으로, 여러 값은 `value_seq`. 마이그레이션은 앞으로만, CI 검사가 금지 문장을 막고, 허용되는 트리거는 정해진 네 모양뿐이다. **'빈 예약 표는 다시 만든다'는 예외는 없앴다**(매장 파일마다 따로 마이그레이션해 확인할 수 없고, 예약 표가 이미 FK 대상이므로). 대신 강습 · 보증금 · 지점 · 카드 단말 · 알림 표의 키를 0001에서 정했다.
- **이유:** 객실 번호 같은 새 칸은 코드 없이 행으로 생기고, 선택지 · 대상이 FK로 검사된다. 핵심이 되면 열로 올린다.
- **버린 것:** C의 JSON `attrs` · `body`(형식 검사와 FK가 없음, 제자리 변환). 대상 id가 다형인 일반 EAV 표 하나.

### ADR-14 옮기기: 두 줄기와 멈춤 기준
- **결정:** 저장은 첫날부터 새 표. 검증된 옛 처리기는 codec과 facade로 새 표 위에서 **그대로** 돌고(legacy 줄기; 사실 명령은 native 사실 어댑터 뒤에서 — 맞는 부분만 적용하고 거절하지 않음, 옛 명령마다 자기 명령 종류 행과 충돌 키), 12월 우선순위 · 돈 · 마감 · 차량 업무 · 계정 · 동기화는 native로 새로 쓴다. 표현 규칙과 codec 왕복 시험이 두 줄기를 맞춘다. 222개 시험은 그대로(모드 A)와 새 표 위(모드 B)에서 돈다. 11월 연습 기간에 새 서버(우리 중앙 서버, ADR-19)로 바꾸고 옛 엔진은 그림자 대조. G1(11/6)을 못 넘으면 옛 서버로 시즌(F1, 운영 준비는 4 ~ 5주차에 미리), G2(12/1)에 화면만 모자라면 포스 v4를 `/api/v1`로(F2). 가게 인터넷은 예비 회선 자동 넘어가기가 개장 조건이고, 혼합(매장 작은 PC가 쓰는 쪽)은 시즌 1 대안이 아니다(셋째 검토, ADR-19).
- **이유:** 10주 안에 약 400 KB의 옛 규칙을 다시 쓰는 대신, 옛 기능 전부가 2주차부터 새 저장소에서 돌고 12월 일은 새 기능에만 쓴다. 직원은 11월에 실제 새 시스템으로 연습한다.
- **버린 것:** A의 10주차 한 번에 바꾸기(모든 묶음 재작성). B의 7주차 기준 이벤트 저장소 + 옛 id 흉내 다리 + 옛 엔진 주 서버 그림자. 판정 3의 '옛 처리기는 대조용으로만' — facade를 운영에 쓰되 LOAD_PLAN 측정, 성능 기준, 대안으로 범위를 묶었다.

### ADR-15 화면은 설정으로 그린다
- **결정:** C 장부를 바탕으로 A 지금 줄, B2 남은 일 목록, A3 ▲▼를 섞고 왼쪽 레일을 없앤다(사장님 확정 2026-09-24, D3; 화면 지도는 ui 3-6). 코드(DeviceProfile, 부품, 코드 키 어휘, 칸 맞춤 계산) · 매장 데이터(도장 단계, 장부 칸 · 탭 · 바닥줄 · 동작, 메뉴, 상태 문구, 기능) · 기기(잰 크기 + 역할) 세 층. 시스템 기본 설정은 판이 있고 앱이 올라가면 이미 쓰던 매장에도 반영된다(매장이 바꾼 행은 그대로). 칸 폭은 em, 넘치는 목록은 모두 한 모델(우선순위 · 넘칠 때), 같은 계산이 설정 명령에서도 돈다. 화면은 `DomainClient`의 설정으로 그리는 조회 하나(`ledgerView`)로 서버에 붙고, 체험판과 **기사 기기 · 카운터의 오프라인 화면**(카운터는 2026-09-24 ADR-19부터)은 같은 저장소 코드를 브라우저의 SQLite WASM에서 돌린다. 인쇄도 같은 설정.
- **이유:** 새 종류 · 새 도장 · 새 칸 · 새 속성이 행으로 화면과 인쇄에 나오고, 1024×600부터 875×600(설치한 PWA의 1024×529, 125% 확대 포함)까지 말줄임 없이 칸이 빠지고 합쳐지고 모인다. 체험판과 오프라인 기사 화면이 운영과 다르게 움직이지 않는다.
- **버린 것:** 화면마다 코드로 가르기(옛 v4). 체험판 전용 가짜 로직. 처음 한 번 복사하고 끝나는 기본 설정.

### ADR-16 한 사업자의 여러 위치는 한 파일의 지점, 하루는 마감 범위마다 닫는다
- **결정:** 두 번째 가게 · 따로 닫는 건물은 같은 매장 파일의 지점(`branches`)과 마감 범위(`closing_scopes`, 기본 `main`)다. `business_days` · 마감 · 기준선 · 돈 · 재고 장부 행이 모두 범위를 가지고, 돈통의 범위와 같아야 한다(복합 FK). 설정 · 기능 · 달력도 범위마다 덮어쓸 수 있다. 서로 다른 사업자는 늘 다른 테넌트이고, 다른 테넌트로 물건을 보낼 때는 양쪽 이동이 전역 `transfer_ref`를 나눠 가진다.
- **이유:** 18:00에 닫는 지점과 23:00에 닫는 본점이 서로의 마감을 막지 않는다. 두 파일을 한 파일의 지점으로 합쳐도 키를 다시 매기지 않는다. 채워진 뒤에는 바꿀 수 없는 `business_days` · 마감의 키를 지금 정했다.
- **보류한 것:** 사업자 단위의 공유 고객 · 적립(가맹)은 필요해질 때 control의 새 표(E5)로.

### ADR-17 세금은 줄에서, 세금 문서는 따로
- **결정:** 품목 종류 · 상품의 세금 분류(`sys_tax_categories`), 줄의 분류 · 공급가 · 부가세 스냅샷, 수납에 붙는 추가 전용 `tax_documents`(현금영수증 · 세금계산서)와 개인정보인 신원은 따로(`tax_document_identities`).
- **이유:** 한 카드가 과세 대여 · 대행 리프트권 · 면세 강습을 함께 낼 수 있어 수납 한 행의 부가세 칸은 틀린 단위이고, 추가만 하는 장부에 한 번 쓰면 고칠 수도 없다.
- **버린 것:** S14 예시였던 `payments.tax_amount`.

### ADR-18 보증금은 매장이 고르는 규칙과 매수로 세는 장부(2026-09-24)
- **결정:** 돌려받아야 하는지(종류의 `return_policy_key`)와 보증금을 맡는지(`deposit_rules`)를 매장이 따로 고른다. 보증금 규칙은 종류 전체나 상품 하나를 대상으로 매당 금액 · 받는 때 · 결제 칸 · 돌려드리는 법의 기본 · 안 돌아올 때 · 며칠 뒤 · 효력 기간을 가진다. 맡은 보증금은 **팀 · 규칙마다 보관 하나**(규칙 값 복사)이고, 돈은 `deposit_*` 수납 한 건, **매수는 추가만 하는 보증금 장부**(`deposit_entries`: 줄 · 매수 · 권 · 돌려받은 이동 줄)가 센다. 장부 줄은 같은 보증금 · 맞는 종류의 돈과, 그 품목 줄을 옮긴 이동 줄만 가리킬 수 있다(복합 FK). 안 돌아온 권은 폐기 이동과 `보증금 몰수`(`deposit_forfeit`, 현금이 움직이지 않음)로, 뒤늦게 돌아오면 `몰수 취소`(`deposit_restore`) 뒤 `보증금 반환`으로 적는다. 보증금은 청구 · 매출이 아니다.
- **이유:** 이 매장은 권 보증금이 있어 권을 꼭 돌려받지만 다른 스키장은 아닐 수 있다(사장님 답). 부분 반납(3매 중 2매)에서 돌아온 매수만 돌려드리고, 어른 권 · 어린이 권 두 줄의 보증금을 한 번에 돌려드려도 돈 한 건이며, 마감이 '보증금 보관 중 · 리프트권 1매 · 5,000원'을 매수까지 보인다. 규칙 값을 복사하므로 시즌 중 금액을 바꿔도 이미 맡은 팀에는 말한 금액대로 돌려드린다.
- **버린 것:** 종류 · 상품의 능력 값 열로 두기(둘째 판 시안 명세의 제안: 두 표에 열이 여럿 늘고 금액의 효력 날짜 · 돌려드리는 법이 없다). 줄마다 보관 하나(두 줄을 한 번에 돌려드릴 때 돈이 두 건). 수납 행에 매수 열(보증금 아닌 돈에는 뜻이 없고 돌려받은 이동과 이을 수 없다).

### ADR-19 배치: 클라우드 중심(2026-09-24)
- **결정:** 모든 매장의 장부 원본은 **우리가 운영하는 중앙 서버(한국 안의 클라우드)**에 둔다. 매장마다 SQLite 파일 하나와 공용 `control.sqlite`를 중앙 서버가 가지고, 매장 파일마다 쓰는 쪽은 하나다(쓰기 프로세스가 매장마다 명령을 하나씩). 카운터 포스(설치한 PWA) · 기사 태블릿 · 휴대폰은 HTTPS로 붙고 SSE로 바뀜을 받는다. 인터넷 · 우리 서버가 끊겨도 기기는 **자기 안의 사본(같은 저장소 코드, SQLite WASM)과 서명된 보냄 대기**로 일한다: 기사에게 설계한 것을 카운터에도 쓴다. 카운터가 끊긴 채 할 수 있는 일은 사실(지급 · 반납 · 돈 · 보증금)과 새 묶음(새 현장 접수 · 품목 추가, 임시 접수 번호)이고, 기존 결정을 바꾸는 일은 연결을 기다린다(`sys_offline_commands`, sync 8-2). 라이선스 확인(세션마다 중앙, 기기에는 서명된 표와 오프라인 유예 14일), 자동 백업(다른 구역으로의 WAL 복제 · 다른 회사로의 작업 기록 구간 · 스냅샷 · 새 VM 되살리기 연습), 기사 기기 연결, 업데이트, 원격 지원을 모두 중앙에서 한다. PostgreSQL은 되살리기 시간 · 자동 절체 · 매장 사이 기능이 필요해질 때 옮긴다(deployment 2-1). 자세한 것은 [deployment.md](deployment.md).
- **이유:** 개발자는 혼자이고 가게에서 멀리 떨어져 일한다: 매장마다 서버 PC · USB · 랜선 복사 · 업데이트 · 백업을 돌볼 수 없다. 여러 매장에 팔려면 라이선스 · 업데이트 · 백업 · 지원이 한 곳에 있어야 한다. 기사 휴대폰은 산에서 LTE로 붙으므로 매장 PC 서버라도 중앙 중계가 필요했다. 매장 하드웨어가 망가지거나 불 · 도난이 나도 장부가 안전하다. 카운터 오프라인은 이미 설계한 기사 오프라인의 같은 코드라 새 구조가 아니다. 표와 자료 구조는 그대로이고 바뀐 것은 파일이 있는 곳과 기기가 붙는 길이다.
- **버린 것:** **매장 PC 서버**(처음 설계: 매장 PC에 두 파일, LAN으로 카운터 2에 복사, USB, 매장 서버가 라이선스 확인 — ADR-02 · 12, D4, 열린 질문 14): 혼자서 지원할 수 없고, 기사 중계가 따로 필요하며, 매장이 늘수록 설치 · 지원이 늘고, 매장 하드웨어 사고가 곧 자료 사고였다. **처음부터 혼합**(매장 PC가 쓰는 쪽 + 중앙 복제): 두 곳의 쓰는 쪽을 오가는 복잡함과 매장 하드웨어 · 지원 부담이 그대로이고, 첫 매장은 인터넷 + 예비 회선 + 카운터 오프라인으로 충분할 것으로 본다(G2에서 잰다). **처음부터 공용 PostgreSQL**: 오프라인 사본(SQLite)과 서버가 다른 방언이 되고, 옮기기 · 운영이 10주 일정에 더해진다.
- **혼합을 내놓는 때(시즌 뒤):** 가게 인터넷을 성수기에 재어(1주차부터 잰 기록) 영업 중 30분 넘는 끊김이 한 주에 한 번 넘거나 짧은 끊김이 잦고, 예비 회선 자동 넘어가기로도 메워지지 않고, 카운터 오프라인으로 모자라다고 사장님이 판단하고, 작은 PC · 설치 · 지원 비용을 받아들이고, 공개 주소의 PWA가 LAN 서버를 부르는 문제 · 쓰는 쪽 옮기기 · 기사 중계를 스파이크로 풀었을 때. 그 매장의 작은 PC가 쓰는 쪽이 되고 중앙은 복제본 · 라이선스 · 기사 중계를 맡는다(`tenants.data_location`, deployment 1-3). **셋째 검토로 고침:** 혼합(F3)은 시즌 1 대안이 아니다(결정 시점이 개장 3일 전이고 만들 수 없는 구조였다). 시즌 1의 가게 인터넷 대비는 **예비 회선 자동 넘어가기(듀얼 WAN 공유기 + LTE, 개장 조건)** + 카운터 오프라인 + 끊긴 동안 결정을 적는 종이 양식이다(migration 4 · 6-1절).
- **바꾼 것:** ADR-02(파일이 있는 곳, 라이선스 확인), ADR-10(카운터도 늦게 오는 사실, 오프라인 intent는 새 묶음만), ADR-11(카운터의 보냄 대기 · 보낸 기록 · 임시 접수 번호, 오프라인 PIN), ADR-12(백업의 곳과 방법), ADR-15(카운터 오프라인 화면), D4(가게에 드리는 백업 계획), 열린 질문 9 · 14. 스키마(0001 안, 더하기만): `sys_offline_commands`, `orders.provisional_receipt_no`, `devices.short_no`, `licences.offline_grace_days` · `expiry_grace_days`, 확인 필요 종류 `asset_elsewhere` · `deposit_over_returned` · `revoked_device_record`. 셋째 검토(같은 날, 0001 안): `enrollment_routes`, `support_access_grants`, `sys_offline_limits`, `pii_access_log`, 라이선스 키 · 되살리기 연습 · 매장 끝내기 · 기기 등록 · 작업 기록 구간의 칸, 카운터 오프라인 명령 셋, 확인 필요 종류 여섯, 동작 셋(목록은 맨 끝 '검토 반영 기록').

## 정한 것(2026-09-24 사장님 답)

사장님이 2026-09-24에 답한 다섯 가지(D1–D5)와 같은 날 사용자가 요청한 화면 문구 변경(D6)이다. 열린 질문의 번호는 다른 문서가 가리키므로 그 자리에 '정함'만 남겼다.

### D1. 리프트권은 꼭 돌려받는다 · 권 보증금(매장이 고름)
- **답:** 리프트권은 꼭 돌려받아야 한다(리프트권 보증금이 있어서). 다른 스키장은 그렇지 않을 수 있으니 이것도 고르게.
- **정한 것:** 반납 정책은 매장이 고른다(관리 → 매장 설정 → 운영 규칙 `리프트권 반납`: `반납 필수` = `required` · `반납 선택 · 반납 시 기록` = `optional`). 이 매장은 `required`. 보증금도 매장이 고른다(운영 규칙 `리프트권 보증금`: `사용` · `1매 5,000원 ›` / `미사용`, `입금 시점`, `미반납 시`). 이 매장의 시작 값: **1매 5,000원(이 매장 값)** · 입금 시점 `접수 시 / 미입금: 지급 시`(그때 못 받은 전화 예약은 지급 창이 먼저 물음) · 돌려받으면 매수만큼 현금(미수가 있으면 반납 창의 `반환 방법`에서 `미수 차감`을 고를 수 있음) · 미반납 시 `보증금 몰수`(`keep`, 반납 약속일 다음 영업일의 마감이 정리). 다른 고르기는 입금 시점 `지급 시`(`at_issue`), 미반납 시 `분실금 청구 / 보증금 공제`(`charge_loss`). 카드의 자리는 채택한 둘째 판 시안 V8이고 말은 D6이다(처음 설계 글의 '안 돌려받음 · 주면 끝', '지급할 때', '보증금에서 뺌', '분실 값 따로 받음'을 V8의 말로 고쳤고, V8의 말은 D6에서 다시 고침. 열린 질문 25는 D6으로 정함).
- **구조:** 보증금 규칙 `deposit_rules`, 팀 · 규칙마다 보관 `deposits`, 매수를 세는 보증금 장부 `deposit_entries`(장부), 돈 종류 `deposit_forfeit` · `deposit_restore`, 명령 `deposit.keep` · `field.deposit_return`(ADR-18). 부분 반납은 돌아온 매수만 돌려드리고, 마감은 '보증금 보관 중'을 매수와 함께 보인다. 권 줄에도 반납 약속 · 반납 도장이 있다.
- **문서:** catalog 3 · 11 · 11-1 · 15, data-model 4-4 · 4-12 · 4-13 · 4-18 · S16, ui 6-2 · 6-4 · 6-5, sync 4-2 · 8-2, migration 3-6. 남은 것: 열린 질문 16 · 17 · 18.

### D2. 자정을 넘긴 반납은 전날 장부 — 하루 기준 새벽 6시
- **답:** 자정을 넘었어도 전날 반납으로 쳐야 한다.
- **정한 것:** `shops.business_day_cutoff = '06:00'`(설계 이름 '하루 기준 시각', 화면 말은 운영 규칙 카드 `영업일 기준 시각`: `00:00` · `03:00` · `06:00` · `직접 입력`, D6). 스키 매장의 기본값도 06:00(매장 개설 시드; 열의 기본 00:00은 기술 값). 새벽 6시보다 이른 기록은 전날 영업일이다: 27일 00:15 반납 · 00:40 마감 → 26일 장부, 27일 07:00 대여 → 27일. 바꾸면 그다음 기록부터이고 지난 기록은 그대로다(ADR-06). 두 기준 시각 사이의 시각에는 바꾸지 못한다. 마감 화면의 제목줄 기준 띠가 `현재 27일 00:40` · `26일 장부 · 기준 06:00 · 00:15 정하늘 · 0041 반납 포함`을 보인다(둘째 판 시안 V6). 새벽 6시 전에 마감한 뒤 들어온 반납 · 돈은 다음 열린 날의 마감이 센다(기준선, 카드의 표시 `마감 후 기록 · 다음 마감 반영`).
- **문서:** data-model 3-3 · 4-13 · S17, ui 7, catalog 3, migration 3-6.

### D3. 왼쪽 메뉴 레일은 없앤다
- **답:** 왼쪽 메뉴 줄은 필요 없으면 없애도 된다.
- **정한 것:** 어느 화면에도 레일이 없다. 머리줄(장부 · 끝 4자리 · 메뉴 칸 · 알림 · 관리 · 나가기)과 종이의 색인 탭만 쓴다(ui 1 · 3-6, AGENTS.md 화면 규칙 9). 옛 저장소의 docs/35 1절과 docs/42 부록 A는 옛 앱(포스 v4)을 적은 문서라 스키노트를 묶지 않는다. 고치지 않고 그대로 둔다.

### D4. 백업은 추천대로 — 클라우드로 바뀐 추천(2026-09-24 고침)
- **답:** 백업은 추천대로.
- **고친 까닭:** 사장님이 답한 뒤 같은 날 개발자가 배치를 **클라우드 중심**으로 바꿨다(ADR-19). 그래서 '추천'의 내용이 바뀌었다: 가게에 서버 PC · USB · 랜선 복사를 두지 않고, 우리 중앙 서버가 백업을 한다. 처음 D4(매장 PC · USB · 카운터 2)는 버렸다. 사장님께 새 계획을 한 번 말씀드리고 답이 그대로인지 확인한다(열린 질문 19).
- **정한 것:** ADR-12(sync 10절, deployment 6절). 가게에 드리는 말로 적으면:

| 무엇 | 어디에 | 언제 | 누가 보나 |
|---|---|---|---|
| 방금 한 일(접수 · 도장 · 돈 하나하나) | 우리 **중앙 서버**(한국)에 바로 적히고, 몇 초 안에 **다른 구역의 보관함**에 한 벌 더, 1분 안에 **다른 회사의 보관함**에 또 한 벌 | 늘, 몇 초 안 | 따로 볼 것 없음. 복사가 멈추면 공급자 휴대폰이 울리고, 오래 멈추면 관리 화면 `백업` 카드에 `백업 지연` |
| 인터넷이 끊겼을 때 한 일 | 먼저 예비 회선(LTE)으로 저절로 넘어간다. 넘어가지 못하면 그 카운터 · 기사 기기 안(`전송 대기`, 카운터는 인쇄 도우미에도 한 벌), 연결되면 중앙으로 | 연결되는 대로 | 화면 위 띠 `연결 끊김 · 전송 대기 3` |
| 하루 전체 복사본(가게마다 다른 열쇠로 잠금: 보관함 회사도, 우리 서버도 열 수 없음) | 다른 구역 보관함(지울 수 없게 잠금) | 날마다 새벽 4시 | 35일치. 월요일 것은 손님 이름 · 전화를 지운 사본으로 26주, 시즌 끝 것은 5년(세무 확인) |
| 되살리기 연습 | 매번 새로 만든 연습 서버에 매장 자료를 되살려 숫자가 맞는지, 몇 분 걸렸는지 봄(그 순서가 곧 실제 사고 때의 순서) | 개장 전 두 번(사장님과 한 번), 시즌 중 매주 월요일 새벽 4시 30분(시즌 첫 달 안에 켬) | 관리 화면 `백업` 카드 한 줄(`복구 점검 통과 · 월요일 04:30 · 12분`). **사장님이 월요일 아침에 한 번 본다.** 실패하면 공급자가 알림을 받고 그날 고친다 |
| 가게 보관용 장부 사본 | 카운터 PC의 폴더에 잠근 파일(여는 열쇠는 사장님의 복구 열쇠 종이에만) | 날마다 마감 뒤 | 손님 이름 · 전화를 뺀 장부 사본은 **기본으로 켬**(공급자가 없어져도 사장님이 자기 장부를 가짐). 손님 정보까지 담은 파일은 사장님이 켤 때만 — 열린 질문 22 |

- **잃을 수 있는 것:** 우리 서버가 통째로 망가져도 아직 복사되지 않은 몇 초. 그 몇 초의 일도 카운터 · 기사 기기가 7일 동안 기억했다가 다시 보낸다. 가게 인터넷이 끊기면 잃는 것이 없다(기기에 쌓였다가 간다) — **그 PC의 브라우저 자료를 지우지 않는 한**(끊긴 동안 띠에 `전송 대기 · 전원 유지`가 뜨고, 인쇄 도우미가 한 벌 더 가진다). 카드는 단말기 기록과 카드사 정산으로 맞춘다.
- **서버가 멈추면:** 카운터와 기사 기기는 끊긴 것처럼 계속 일한다(지급 · 반납 · 수납 · 보증금 · 새 현장 접수). 공급자가 **알림을 받은 때부터 1시간 안에** 새 서버로 되살리는 것이 목표다(밤에는 다음 개장 1시간 전까지). 데이터 센터 전체가 멈추는 드문 경우는 다른 회사의 보관함으로 하루 안에 되살린다.
- **공급자에게 기대는 것:** 이 방식은 가게 서버를 없앤 대신 공급자(개발자 한 사람)에게 기댄다. 그래서 공급자가 며칠 연락이 안 될 때를 위해 되살리기 열쇠 · 비상 라이선스 연장 · 한 쪽짜리 절차를 봉투에 넣어 둘째 사람에게 맡기고(누구로 할지는 열린 질문 33), 가게에는 장부 사본과 할 일 한 장을 드린다(deployment 12절).
- **사람이 할 일:** 매일은 없다. 월요일 아침 `백업` 카드 한 번. 가게에 둘 것은 **예비 회선이 저절로 넘어가는 공유기(듀얼 WAN + LTE 요금제)**다: 개장 조건이다(휴대폰 테더링처럼 손으로 바꾸는 것은 대신하지 못함, 열린 질문 23). 서버 PC · USB는 필요 없다. 개장 전 주(10주차)에 공급자가 사장님과 함께 인터넷 선을 뽑고 두 시간 일해 보기와 되살리기를 보여 드린다.
- 설정 `backup_policy`의 새 기본값: `wal_keep_days 7`, `daily_keep_days 35`, `journal_pii_keep_days 35`, `weekly_scrubbed_keep_weeks 26`, `season_scrubbed_keep_years 5`, 연습 월요일 04:30, `owner_export_scrubbed true`(손님 정보를 뺀 장부 사본), `owner_export false`(손님 정보 포함). 가게가 바꾸는 것은 두 내보내기뿐이다. 관리 화면의 `백업` 카드는 7주차 백업 · 복구와 함께 그린다(roadmap).

### D5. 부분 반납 · 조기 반납은 지금 구조로 된다
- **질문:** 일괄 반납 말고 나중에 부분 반납 같은 것도 다 더할 수 있나?
- **답:** 된다. 반납 · 약속 · 수납 · 보증금이 처음부터 **품목 줄과 수량** 단위이고 사람 단위가 아니다(현장 접수는 대표자만 적는다). 더할 것은 화면(반납 창에서 가져온 번호 · 수량만 고르기, 일정 변경의 품목 수량)뿐이고 새 표 · 마이그레이션이 필요 없다. 조기 반납 · 교환이 같은 접수의 줄 · 약속만 가리키도록 복합 FK 두 곳을 이번에 채웠다(data-model 4-18, 4-10).
- **채택한 화면(둘째 판 시안 V1 · V9):** 반납 창에는 `모두 반납` / `일부만` 고르기가 없다. 품목 칸이 늘 보이고 처음에 이 팀이 가진 것이 **모두 골라져** 있어서, 다 가져왔으면 그대로 누르고 아니면 안 가져온 번호만 눌러 뺀다(하나씩 세는 품목은 번호 버튼, 수량 품목은 −/+). 고르기가 있으면 급할 때 기본값을 세지 않고 눌러 숙소에 있는 보드까지 반납되기 때문이다(ui 6-2).

### D6. 문구는 업무 용어로(2026-09-24)
- **요청(사용자):** '할인 고르기, 받을 돈 정하기, 약속 정하기, 약속 바꾸기 등, 약속이라는 단어도 … 실제 시스템에서 사용하긴 별로 … 전체적인 화면 문구 변경'. 글만 바꾸고 배치 · 크기는 그대로 둔다. 힉스필드 그림은 다시 뽑지 않는다.
- **정한 것:** 화면 글은 포스 · 가게의 짧은 업무 용어로 쓰고 한 개념은 한 말이다. 기준은 [docs/design/wording.md](../design/wording.md) 하나다(원칙 1절, 기준표 1-2, 영역별 표 3절). 버튼 · 이름표 · 탭은 이름씨로 쓰고 문장 끝(`~합니다` · `~주세요` · `~하기` · `~드림`)을 쓰지 않는다. 동작 버튼은 동작 이름 + 수 · 금액이다(`반납 처리 · 5개`, `수납 처리 · 120,000원`, `접수 확정 · 현금 160,000원`). 남길 알림은 `사실 · 할 일` 한 줄이다(`강지은 팀 45,000원 수납 완료 · 다른 카운터`, `처리 실패 · 재시도 필요`). 화면에 `약속`을 쓰지 않는다(`수령 일정` · `반납 일정`, 동작 `일정 변경`). 도장 그림은 남기고 버튼은 `지급 처리` · `반납 처리` · `수납 처리`다.
- **주요 말:** `받기` · `돌려주기` → `수령` · `반납`, `받을 돈` → `받을 금액`, `나중에` → `후불`, `다른 수단` → `기타`, `할인 고르기` → `할인 적용`, `빨리 확인` → `긴급`(사용자가 전에 정한 말을 바꿈), `받음` · `못 받음` · `못 전함` → `수거` · `수거 실패` · `배달 실패`, `차에 있는 것` → `차량 재고`, `보냄 대기` · `마지막 맞춤` → `전송 대기` · `마지막 연결`, `돌려드림` → `반환`, `보증금에서 뺌` · `보증금 안 돌려드림` → `보증금 몰수`, `셀 돈` → `현금 점검`, `가게 규칙` → `운영 규칙`, `전날 장부로 치는 시각` → `영업일 기준 시각`(`06:00`), `한 번에 수납` → `일괄 수납`.
- **사용자가 볼 것:** wording.md 5절의 결정 25가지(리드 예시와 다르게 고른 말, 사용자가 전에 정한 말을 바꾼 곳, 19~25는 반영 뒤 2차 검토에서 정한 말). 다른 말을 고르면 wording.md를 먼저 고치고 4절의 곳을 한 번에 고친다.
- **문서:** 설계 문서가 인용한 화면 글을 이 표의 말로 고쳤다(ui-architecture 3-9 · 4 · 5 · 6 · 7 · 8절, data-model, catalog, sync, deployment, migration-plan, 이 README의 ADR-10 · 18, D1 · D2 · D4 · D5, 용어, 열린 질문). 설명 문장의 개념 말(약속 = `line_promises`, 보냄 대기 = 기기 큐, 되살리기 연습 …)은 그대로이고 화면 말은 '용어' 표에 함께 적었다. 아래 '검토 반영 기록'은 그날의 기록이라 옛 말 그대로 둔다. AGENTS.md 문구 규칙은 사람이 확인하고 고친다(열린 질문 30 ⑤). 코드 · 설정 · 시드 · 시안 · 시험 · 검사기는 wording.md 4절대로 한 묶음으로 고친다.
- **정해진 열린 질문:** 25(`보증금 몰수` 한 말), 28(`수령` · `반납`).

## 열린 질문

번호는 다른 문서가 가리키므로 바꾸지 않는다. 답을 받은 것은 '정함'으로 남긴다.

1. **리프트권 반납 정책** — 정함(2026-09-24, D1): 매장이 고른다. 이 매장은 required + 권 보증금.
2. **야간 영업일 기준 시각** — 정함(2026-09-24, D2): 06:00. 자정을 넘긴 반납은 전날 장부.
3. **개인정보 보관 기간:** 손님 이름 · 전화를 몇 년 뒤 지울지(기본 3년으로 둠)와 거래 기록 보관 의무를 세무 담당과 확인.
4. **실제 운영 자료:** ski-rent-ops 운영 서버에 실제 손님 자료가 있는지, 몇 건인지(가져오기 크기).
5. **왼쪽 레일 없애기** — 정함(2026-09-24, D3): 없앤다. 옛 저장소 docs/35 · docs/42는 스키노트를 묶지 않으므로 개정하지 않는다.
6. **시즌 1 관리 화면:** 설정 · 재고 · 거래처 관리 화면을 포스 v4로 두어도 되는지(관리자만 씀). 화면 설정(칸 · 탭 · 메뉴)은 시즌 1 동안 공급자만 설정 명령으로 바꾸기로 했다(ui 문서 2절) — 사장님이 직접 고칠 일이 있는지.
7. **체험판:** SQLite WASM 묶음 크기가 Pages 체험판에 괜찮은지. 안 되면 읽기 전용 체험판. 기사 기기와 **카운터**(ADR-19)의 오프라인 화면은 같은 WASM이 필수다.
8. **기사 휴대폰 누르는 곳:** docs/42의 52px 대신 56px(장갑)로 올리는 것.
9. **원격 백업 위치와 담당** — 정함(2026-09-24, D4), 같은 날 ADR-19로 바뀜: 백업은 우리 중앙 서버가 다른 구역 · 다른 회사의 보관함으로 한다. 되살리기 연습 결과는 사장님이 월요일 아침에 관리 화면에서 보고 실패는 공급자가 고친다. 업체 고르기는 질문 20.
10. **라이선스 과금 단위, 사용 내역 보관 기간, 관리자 인증 방식:** docs/45에 남은 결정.
11. **개장일:** 10주차 계획의 끝(12/4)과 멈춤 기준 G2(12/1)가 실제 개장일에 맞는지.
12. **남은 확인 질문지 23개:** 답이 오면 설정 · 레지스트리 값으로 반영(대부분 구조 변경 없음).
13. **세금 분류:** 리프트권을 대행(수수료만 매출)으로 볼지, 강습이 면세인지, 현금영수증 · 세금계산서를 스키노트에서 낼지, 안 돌아온 권의 '몰수 보증금'(`deposit_forfeit`)을 매출로 볼지(세무 담당). 종류 값과 설정만 바뀐다(ADR-17).
14. **서버 PC** — 필요 없어짐(2026-09-24, ADR-19): 매장에 서버 PC를 두지 않는다. 장부는 중앙 서버에 있고 카운터는 오프라인 사본으로 끊김을 견딘다. 인터넷이 정말 나쁘면 나중에 혼합(매장 작은 PC)을 고른다(deployment 1-3).
15. **카운터 PC 화면:** 작업 표시줄 자동 숨김을 해도 되는지(설치한 PWA의 실제 높이 1024×569). 안 되면 1024×529로 설계한 쪽 수가 기준이 된다.
16. **수거 현장의 권 보증금:** 차량이 권을 받을 때 기사가 그 자리에서 차량 지갑으로 돌려드리나, 미수에서 빼나, 다음에 매장에서 돌려드리나? 구조는 셋 다 된다(`field.deposit_return` · `deposit_apply` · 보관 중으로 넘김). 둘째 판 시안은 기사가 돌려드린다고 그렸다.
17. **안 돌아온 권:** `보증금 몰수`로 끝인가(시작 값), `분실금 청구 / 보증금 공제`인가? 언제 정리하나 — 반납 약속일 다음 영업일의 마감(시작 값 `unreturned_after_days = 1`)인가, 사람이 정할 때까지 두나(비움)?
18. **전화 예약의 권 보증금:** 선입금과 함께 계좌이체로 받나, 권을 줄 때 받나(시작 값: 입금 시점은 `접수 시 / 미입금: 지급 시`, 못 받았으면 지급 창이 먼저 묻는다)? 보증금을 현금으로만 받나(둘째 판 시안의 가정)?
19. **바뀐 백업 계획 설명(사장님):** '백업은 추천대로'라고 답한 뒤 추천이 클라우드로 바뀌었다(D4 고침). 가게에 서버 PC · USB 없이 중앙 서버가 백업한다는 것, 예비 회선 자동 넘어가기 공유기가 개장 조건이라는 것, 공급자 한 사람에게 기대는 만큼 둘째 사람 봉투와 장부 사본을 둔다는 것을 말씀드리고 답이 그대로인지 확인한다.
20. **호스팅 업체(공급자, 1주차):** 한국 안의 업체 하나와 두 번째 저장소(가능하면 다른 회사)를 고른다(deployment 4절). 요금은 계약 전에 요금표로 확인한다.
21. **도메인(공급자, 1주차):** 앱 주소 하나와 연습 주소(deployment 3절).
22. **가게 보관용 내보내기(사장님):** 둘로 나눠 묻는다. ① **손님 이름 · 전화를 뺀 장부 사본**을 날마다 마감 뒤 카운터 PC에 둘지 — 시작 값은 켬(공급자가 없어져도 자기 장부를 가짐). ② **손님 정보까지 담은 파일**도 둘지 — 시작 값은 끔. 둘 다 사장님의 복구 열쇠 종이(개인 키)로만 열리고 공급자 · PC를 만지는 사람은 열 수 없다(공개 키로 잠금, deployment 6-6). ②를 켜면 그 PC가 손님 정보를 담게 되므로 PC 잠금이 더 중요해진다.
23. **예비 회선 자동 넘어가기(사장님, 개장 조건):** 셋째 검토로 '권함'에서 **필수**로 바꿨다. 듀얼 WAN 공유기와 LTE 요금제를 사서(비용) 가게 인터넷이 끊기면 몇 초 안에 저절로 넘어가게 한다(4 ~ 5주차 설치, G2에서 선을 뽑아 확인). 휴대폰 테더링처럼 사람이 바꾸는 것은 대신하지 못한다. 가게 인터넷은 1주차부터 재고, 그 기록은 시즌 뒤 혼합을 정하는 근거다(혼합 F3는 시즌 1 대안에서 뺐다).
24. **개인정보 · 세무 전문가 확인:** deployment 10-6의 열여덟 가지(모으는 근거, 처리 위탁 계약, 안전성 조치, 보관 기간 · 파기와 백업 사본이 사라지는 때, 유출 알림, 손님 요청 창구, 해외 서비스, 세무 보관 기간, 원격 지원 때 자료 보기, 위치정보, 만 14세 미만 일행, 재위탁, 계약 끝의 반환 · 파기, 기사 개인 휴대폰, 직원 개인정보, 개인정보 읽기 기록, 가게 보관용 파일, 지운 사본이 가명정보인지). 법률 자문은 이 문서가 하지 않는다.
25. **'보증금에서 뺌'의 말** — 정함(2026-09-24, D6): 운영 규칙 카드 · 마감 미리 보기(`… · 마감 시 몰수`) · 접수증과 마감 인계의 버튼(`deposit.keep`) · 사용 내역 · 어휘 이름을 모두 `보증금 몰수`(되돌림 `몰수 취소`) 한 말로. `몰수`가 센 말이면 다른 안은 `보증금 귀속`(wording.md 결정 10).
26. **오늘 일할 사본의 암호화(공급자, 1주차 확인):** 카운터 · 기사 기기의 OPFS SQLite를 암호화 빌드로 둘 수 있는지. 안 되면 사본을 꼭 필요한 것만 두고 기기 잠금을 요구한다(deployment 10-1).
27. **끊겼을 때 돈 · 보증금 받는 카운터(사장님):** 가게 인터넷이 끊기면 두 카운터가 서로의 수납 · 보증금 · 반납을 못 본다. 끊긴 동안 **돈과 보증금은 카운터 한 곳에서만**, **한 팀은 처음 받은 카운터에서** 받기를 운영 규칙으로 둘지(sync 8-7). 설계는 겹쳐도 두 번 세지 않고 확인 필요로 보이지만, 손님이 떠난 뒤에는 돌려받기 어렵다.
28. **가져가는 것 · 돌려주는 것의 말(사장님, 둘째 판 시안 질문 8)** — 정함(2026-09-24, D6): `수령` · `반납`으로 맞춘다(접수증 일정 줄 `수령 16:00 · 매장 · 반납 22:00 · …`, 기사의 가져옴은 `수거`).
29. **번호 스티커(사장님, 둘째 판 시안 질문 9):** 스키 · 보드 · 헬멧에 번호 스티커가 있나, 리프트권은 권마다 번호를 적나? 반납 창은 돌아온 번호를 누르게 그렸다(V1). 번호가 없는 품목은 그 줄만 −/+ 수량으로 세고 서버가 그 팀 것 중에서 고른다.
30. **AGENTS.md 고치기(사람 확인, 셋째 검토):** 에이전트는 AGENTS.md를 고치지 않았다. 사람이 확인하고 넣을 네 줄: ① '체험판과 비밀'에 '운영 자료와 화면 캡처는 GitHub(이슈 · PR · 커밋) · AI 도구 · 해외 서비스에 넣지 않는다. 지원 기록은 비공개 곳에' (deployment 8절), ② 같은 절의 '관리자 콘솔은 … 운영 서버의 숨은 주소에서만 연다'를 '따로 된 주소 + 접근 제한(IP 허용 · VPN · mTLS 중 하나, 하드웨어 키 2단계 인증)'으로 (deployment 3절), ③ '먼저 읽을 것' 표에 '배치 · 서버 · 라이선스 · 백업 · 개인정보 → deployment.md' 줄, ④ '자료와 SQL'의 허용 목록에 '`sys_event_types` · `sys_movement_routes`의 `offline_allowed = 1` UPDATE(0 → 1만)'(data-model 7-2, lint가 이미 허락함). ⑤(2026-09-24, D6) '문구 규칙'의 가게 말 목록과 막히는 일의 말 모양을 D6 · wording.md 1절로: 목록의 `빨리 확인` · `받음` · `못 받음` · `차에 있는 것` · `보냄 대기`를 `긴급` · `수거` · `수거 실패` · `차량 재고` · `전송 대기`로, '쉬운 한 문장과 버튼 두 개'를 '`사실 · 할 일` 한 줄과 버튼 두 개'(예 `이 팀 120,000원 수납 완료 · 다른 카운터`)로, 동작 버튼 모양(`반납 처리 · 5개`)과 wording.md를 가리키는 줄을 더함(준비한 고침: 커밋하지 않는 작업 폴더의 `work/wording/AGENTS-wording.patch`, `git apply --check` 통과).
31. **카운터 장부의 연결 띠 자리(사장님께 보여 드림):** 띠 자리를 늘 비워 두면 가게 인터넷이 끊겨도 줄이 움직이지 않지만 1024×600 한 쪽이 7줄에서 6줄이 된다(연결되어 있을 때는 줄이 조금 커짐). 비워 두지 않으면 7줄이지만 끊길 때 쪽이 한 번 다시 나뉜다. 설계는 비워 두는 쪽이다(ui 4-3).
32. **첫 매장의 기사 휴대폰(사장님):** 업무용으로 지급할지, 기사 개인 휴대폰을 쓸지. 개인 휴대폰이면 화면 잠금을 강제할 수 없고 퇴사 때 지우기 절차가 필요하다(deployment 10-5, 전문가 확인 14).
33. **둘째 사람(공급자):** 공급자가 연락이 안 될 때 쓸 봉투(백업을 푸는 열쇠, 호스팅 계정 복구 수단, 비상 라이선스 연장, 한 쪽 절차서)를 누구에게 맡길지와 쓰는 조건(deployment 12절).
34. **첫 매장의 라이선스 강제(공급자):** 첫 매장은 시범이라 기기 표 · 오프라인 유예 · 기간 끝 제한을 강제로 켜지 않는다(두 번째 매장 전에 켬). 첫 매장과의 계약에 그렇게 적어도 되는지.

## 검토 반영 기록

아래 표는 그날의 기록이다. 2026-09-24 ADR-19로 배치가 클라우드 중심이 되어 LAN 복제 · 서버 PC를 말하는 줄(M9 · C4의 '반영' 내용, 열린 질문 14)은 중앙 서버의 WAL 복제와 기기의 보낸 기록으로 바뀌었다(복구 규칙 자체는 그대로).

2026-09-23, 공격적 검토 93건(높음 26 · 중간 49 · 낮음 18)을 네 관점에서 받았다: 다시 만들기 사냥(R), 돈과 재고(M), 동시 수정 · 오프라인 · 동기화(C), 화면 확장(U). 모두 설계 파일을 고쳐 **반영**했다. 일부만 미룬 것은 R3의 '사업자 단위 공유 고객 · 적립' 하나이고(필요할 때 control의 새 표로 더할 수 있어 다시 만들 일이 없다), 여러 방법 중 하나를 고른 것은 결정 칸에 적었다. 고친 뒤 `schema.sql`을 다시 실행해 FK 853묶음 문제 0, 표 안 UNIQUE · 목록형 CHECK 0, 동작 시험 88개 통과, 다섯 시즌 쓰기 0.58–0.64 ms를 확인했다.

### 2026-09-24 셋째 검토: 클라우드 중심 문서(끊김 O · 보안 S · 운영 P · 일관성 K)

클라우드 중심(ADR-19)으로 바꾼 문서에 네 관점의 공격적 검토 78건(높음 20 · 중간 37 · 낮음 21)을 받았다. 모두 확인했고(문서 · 스키마 · 실행기 · lint를 직접 읽음; 실행기가 모르는 마이그레이션을 읽기 전용으로 여는 것, `VACUUM INTO` 사본에 WAL을 이어 붙일 수 없는 것, `deposits_order_rule` 유일 인덱스, lint의 `SYS_UPDATE`, 끊긴 카운터가 권을 줄 명령이 없는 것 등), **통째로 기각한 것은 없다.** 73건은 그대로 반영했고, 5건은 반영하되 한 부분을 미루거나 앞선 결정대로 두었다(O12 가게 LAN 중계는 시즌 뒤 · O14 기사 태블릿의 적재는 보류 · S7 기사 세션 줄이기는 보류 · K8 보증금 어휘 이름은 D1대로 둠 · P1 실행기의 '뒤로 호환' 표시는 1주차). AGENTS.md는 에이전트가 고치지 않았고 넣을 네 줄을 열린 질문 30에 적었다(S3 · S14 · K5 · K19). 0001은 아직 배포 전이라 스키마는 0001 안에서 더했다: control 30표(`enrollment_routes` · `support_access_grants`), shop 269표(`sys_offline_limits` · `pii_access_log`, 코드 어휘 68), 외래 키 891묶음 문제 0, 목록형 `CHECK` 0, `npm test`(core 222 · schema 235 · contract 46 · layout 42 · ui 72 · pos 44) · `npm run lint` 통과. 이 검토의 중심 결정은 **큐에서 온 명령은 등급과 상관없이 적어 두는 사실**(sync 8-12)이다.
