# 동시 수정 · 오프라인 · 백업과 복구

작성 2026-09-23(같은 날 검토 반영). 카운터 두 대, 차량 세 대, 휴대폰 기사가 동시에 일하고, 산속에서 통신이 끊기고, 매장 PC가 고장 나도 기록이 한 번씩만 정확히 남게 하는 규칙이다. 표 정의는 [`schema.sql`](../../packages/schema/schema.sql) 2.16 · 2.17절, 원칙은 [data-model.md](data-model.md).

## 0. 한눈에

- 옛 시스템은 명령마다 매장 전체 JSON을 읽고 복사하고 다시 썼고(주문 600건에서 82 ms, 5.2 MB), 매장 전체 버전 하나를 비교해서 **어느 기기든 한 번 쓰면 다른 모든 기기의 다음 명령이 충돌**했다. 작업 기록과 멱등 기록은 JSON 안에 영원히 쌓였다.
- 새 방식: 표가 진실, 쓰기는 파일마다 하나씩(한 건 약 0.6 ms), 충돌은 **같은 결정을 두 사람이 바꿀 때, 또는 결정의 바탕이 된 돈 · 수량이 그사이 바뀌었을 때만**. 일어난 사실(돈, 물건 이동, 방문 결과)은 기기가 늦게 보내도 거절하지 않는다. 사실과 부딪힌 계획은 사실이 이기고, 앞뒤가 안 맞으면 그 일을 일으킨 사람 앞에(급하면 그 화면 안에서) 쉬운 한 문장으로 보인다.
- 모든 명령은 **요청번호 하나**로 한 번만 적용된다(누가 로그인해 보냈는지와 상관없이). 요청 기록은 지우지 않는다.
- 백업은 커밋마다 몇 초 안에 LAN의 다른 기기로 흘려 보내는 작업 기록 구간, 1시간마다 전체, 밤마다 원격, 매주 자동 복구 시험. 복구는 구간에 담긴 **바뀐 행의 이후 모습(after-image)**을 그대로 적용하고, rev는 지금까지 쓴 가장 큰 rev 위로 뛰며, 기기들이 최근 7일 보낸 명령을 **서버가 정했던 값과 함께** 다시 보낸다.

## 1. 쓰기 순서

```text
POST /api/v2/commands (또는 :batch)
 1  세션 → 계정 → 직원(staff_members) → 매장, 역할, 권한(범위 · 한도), 기기, 차량(vehicle_assignments)
    큐에 쌓였던 명령: 봉투의 서명된 행위자(recordedBy)를 기기 키로 확인하고, 그 사람이 occurred_at에
    그 기기에 로그인해 있었는지 device_sign_ins로 본다. 맞으면 그 사람이 행위자, 보낸 세션은 submitted_by
 2  봉투 검사: (type, commandVersion)의 허용 키 목록. 옛 판이면 upcaster로 올림. 너무 옛 판이면 UPGRADE_REQUIRED
    (오프라인 허용 명령의 upcaster는 큐 보관 기간보다 오래 둔다)
 3  BEGIN IMMEDIATE            -- SQLite: 파일마다 쓰기 하나. PostgreSQL: shop_counters('rev') FOR UPDATE
 4  command_log(shop, request_id) 찾기
      있음 · 같은 지문 → 저장한 결과를 돌려줌(결과가 90일 지나 비었으면 events로 다시 만듦), 아무것도 안 씀
      있음 · 다른 지문 → 처음 결과를 돌려주고 idempotencyMismatch 표시 + integrity_findings(클라이언트 버그)
      dependsOn 중 실패 · 멈춘 것이 있으면 → 돈이 아니면 'blocked', 돈(is_money)이면 멈추지 않음(8-3)
 5  명령이 선언한 묶음만 불러옴(id로). 매장 전체를 읽지 않음
 6  intent면 충돌 키 확인(4절: 바꾸는 키 + 읽은 키). fact면 불변식만, 사실 안의 '결정' 부분은 intent처럼
 7  처리기 실행: native(순수 함수: 불러온 묶음 + 명령 + 문맥 → 쓸 행, outbox, 알림, 확인 필요, 결과)
               adapter(사실 어댑터: 지금 위치를 먼저 보고 맞는 부분만 옛 execute()에 넘기고 나머지는
                       superseded · needs_review; 옛 오류는 결과 상태로 바꿈 — 사실을 거절하지 않음)
               legacy(옛 execute()를 표에서 채운 옛 모양 상태 위에서 실행, intent만 → 바뀐 요소를 codec으로 행으로)
 8  행 쓰기, rev = shop_counters.rev + 1 (shop_instance.rev_floor 위), created_rev · updated_rev, 행 version + 1
    서버가 만드는 id · 번호는 요청에서 정해짐(data-model 3-1): 같은 명령을 다시 보내도 같은 값
 9  건드린 묶음의 투영을 장부에서 전부 다시 계산
10  events(개인정보 없는 정본 명령 + 결과 + 넣은 장부 행의 해시 + pii_commitment + 사슬 해시), event_pii,
    intent_marks, change_log(범위별, 옛 범위 · 새 범위 모두), command_log, outbox, notifications, review_items
11  COMMIT → 작업 기록 구간을 LAN의 다른 기기로 흘려 보냄(10-1) → SSE로 {epoch, rev} 알림, outbox 작업자 깨움
    처리기가 예외로 끝나도 rollback 뒤 따로 command_log에 rejected · retryable · INTERNAL을 적는다(8-3)
```

- 미리 보기(dry run, 옛 `prepareMove`)는 3~9단계를 savepoint 안에서 하고 되돌린 뒤 결과만 돌려준다. 기사 기기가 보냄 대기 명령을 목록에 겹쳐 그릴 때도 같은 방식이다(8-1).
- 처리기는 순수 함수라 테스트에서 표 없이도 돈다. SQL은 저장소 패키지(`packages/store`)에만 있다.
- 한 명령 = 한 트랜잭션 = 한 rev = 작업 기록 한 줄.

## 2. 명령 봉투

```json
{
  "type": "promise.change",
  "commandVersion": 1,
  "requestId": "01JF3Q8W2Z6N9XK4T7B5R1C0DM",
  "deviceSeq": 1287,
  "ageMs": 0,
  "clockAnchor": "boot-7f3a",
  "basis": { "epoch": "01JF0…", "rev": 48213 },
  "expect": { "dueAmount": 0 },
  "dependsOn": [],
  "recordedBy": { "staffId": "01JE…", "sessionId": "01JF…", "signature": "…" },
  "replay": null,
  "payload": {
    "orderId": "01JF3P…", "lineId": "01JF3P…", "quantity": 2,
    "promise": { "methodKey": "vehicle_collection", "placeId": "01JD…", "returnSlotId": "01JC…", "vehicleId": "01JB…" }
  }
}
```

- 매장, 역할, 권한, `recorded_at`, 영업일, rev는 **봉투에서 받지 않는다.** 세션과 서버가 정한다. 행위자도 온라인 명령은 세션에서 정한다. 큐에 쌓였던 명령만 `recordedBy`(그 일을 한 순간 기기에 로그인한 직원, 기기의 내보낼 수 없는 키로 서명)를 쓰고, 서버는 서명과 `device_sign_ins`를 확인한다. 세션이 끝났거나 계정이 정지됐어도 **등록된 기기가 서명한 사실은 받아 적고** `확인 필요`에 올린다(권한 없음으로 버리지 않음). 취소된 기기도 `revoked_at` 전에 서명한 사실은 받는다.
- `requestId`: 기기가 만든 ULID. **확인 창이 열릴 때 만들어 초안과 함께 저장하고, 다시 보낼 때마다 같은 것을 쓴다**(두 번 누르기, '처리 중'에 또 누르기, 창이 열린 채 새로 고침한 뒤 같은 창을 다시 열 때). 단 **한 번 보낸 초안의 번호는 새 창에 쓰지 않는다**(초안에 `sentAt`을 적는다): 같은 도장을 나중에 다시 여는 것은 새 의도이고, 옛 번호로 보내면 서버가 옛 결과를 돌려주어 새 도장이 말없이 사라진다. 저장된 초안은 basis가 같을 때만 다시 쓴다. 시스템 명령은 정해진 모양(`outbox:<id>:<attempt>:<status>`, `import:<run>:<collection>:<id>`, `verifier:<run>:<check>`, `inbound:<id>`)이라 작업자를 다시 돌려도 중복이 없다.
- `deviceSeq`: 기기마다 1부터 오르는 번호. `(device_id, device_seq)`는 **유일하기만** 하고 순서는 강제하지 않는다. 서버는 높은 물 표시와 빈 번호 목록을 가지고, 빈 번호가 `seq_gap_alert_minutes`(30분)보다 오래 비면 `확인 필요`('1호차 기록 3건이 오지 않았습니다')를 올린다. 순서가 필요한 것은 `dependsOn`이 말한다. 한 기기에서 포스를 두 창으로 열어도 보내는 쪽은 하나(Web Locks로 뽑힌 창)다.
- 시각: 온라인 명령은 `occurred_at = recorded_at`. 큐 명령은 `ageMs`(만든 뒤 지난 단조 시계 ms)와 `clockAnchor`(부팅 · 세션 id)를 보내고 서버가 `recorded_at − ageMs`로 정한다. 기준을 잃었을 때만 기기 벽시계 + 시계 차이를 쓰고 `time_source_key = 'wall_clock'`으로 표시한다(data-model 3-3).
- `basis`: **확인 창이 그린 읽기 모델의 `as_of_rev`와 그 epoch**(동기화 커서가 아님). 창이 열린 동안 SSE가 새 rev를 가져와도 basis는 창을 연 때 값이다. 다른 epoch의 basis는 늘 '자료를 복구했습니다. 다시 확인해 주세요'로 돌려보낸다.
- `expect`: 돈 결정의 바탕이 된 숫자(받을 돈, 환불할 돈, 예상 현금). 서버가 지금 값과 비교해 다르면 충돌(4-2). 확인 창은 서버가 준 초안의 `expect`를 창이 열릴 때 초안에 넣는다. 돈 명령(`payment.take` · 환불)은 `expect`가 없으면 거절한다(`EXPECT_REQUIRED`): 받을 돈을 보지 않은 수납이 적용되지 않게.
- 충돌 키는 **봉투에 없다.** 서버가 `(type, payload)`에서 만든다(계약 패키지의 함수 하나, 클라이언트와 공유). 옛 클라이언트가 키를 덜 보내 충돌을 비켜 가는 일이 없다.
- `dependsOn`: 오프라인에서 이어진 명령(권 추가 → 그 권의 현장 수납).
- `replay`: 복구 뒤 다시 보낼 때만. 서버가 처음에 정했던 값(만든 id, 접수 번호, 묶음 번호, `posting_date`, 견적, 받은 rev)을 그대로 싣는다(10-2).
- `commandVersion`: 명령 모양의 판. 서버는 바로 전 판의 upcaster를 가지고, 오프라인 허용 명령은 큐 보관 기간(7일)보다 오래된 판까지 받는다. 서버를 먼저 올리고 기기를 나중에 올린다.
- 응답: `{ outcome, requestId, rev, asOfRev, epoch, versions, rebased, changes, canonical, result }`. `canonical`은 서버가 정한 값(10-2에서 다시 쓰려고 기기가 `sent`에 보관). 거절이면 `{ code, message, current }`(지금 상태를 함께 보내 화면이 무엇이 바뀌었는지 보여 줌).

`events.command_json`에는 **서버가 정한 값이 모두 들어간 정본 명령**(만든 id들, 접수 번호, `occurred_at`, 영업일, `posting_date`)을 적는다. 이름 · 전화와 **모든 자유 글(메모, 사유, 장소 메모)**은 참조로만 쓰고 값은 `event_pii`에 두며, 사슬은 그 약속값(`pii_commitment`)만 덮는다. 결과에는 명령이 넣은 장부 행마다 정본 해시가 있어 사슬이 표의 행까지 덮는다(밤마다 검증기가 다시 계산).

## 3. 명령의 세 등급

| 등급 | 예 | 확인 | 충돌 때 |
|---|---|---|---|
| **fact**(이미 일어난 일) | 수납 · 환불 · 현장 수납, 현금 입출금 · 넘김 · 넘김 확인, 적재 · 지급 · 전달 · 받음 · 매장 입고 · 매장 반납, 방문 결과, 강습 끝, 발권처 환불 시도, 사이즈 입력, 카드 · 문자 결과 | 물건 위치 · 잔량 · 돈 불변식. 버전은 보지 않음 | **거절하지 않음.** 맞는 부분만 적용(`partially_applied`), 이미 된 일은 `superseded`(쓰는 것 없음), 앞뒤가 안 맞으면 `needs_review`. **물건이 실제로 옮겨진 사실은 늘 이동으로 적고**, 부딪힌 계획(claim)은 `displaced_by_fact`로 끝내며 확인 필요는 그 계획에 단다. 돈은 늘 기록 |
| **intent**(앞으로의 결정) | 약속 바꾸기 · 나누기, 업무 옮기기, 취소, 가격 직접 입력, 할인, 연장, 결제할 팀 정하기, **카드 결제 요청**, 설정 · 레지스트리 편집, 마감 | 충돌 키(바꾸는 키 + 읽은 키) · `expect` · 행 버전 | 겹치면 `VERSION_CONFLICT`와 지금 값. 안 겹치면 자동으로 이어 붙임(`rebased: true`) — 단 돈 intent는 그 접수의 돈이 바뀌었으면 이어 붙이지 않음 |
| **commutative**(순서만 바뀌는 일) | 방문 순서 ▲▼ · 맨 위로 · 시간순, 빨리 확인 · 풀기, 알림 확인, 인쇄 요청 | 없음(순서 바꾸기는 기준 업무 + 결정 시각) | 서버가 지금 순서에 맞춰 풀어 적용. 더 오래된 순서 바꾸기가 늦게 오면 짐(4-5) |
| **system** | outbox 결과, 받은편지함 결과, 가져오기, 검증기 고침, 기기 로그인 | 정해진 요청번호 | 멱등 |

**사실 안의 결정.** 사실 명령 중에는 결정을 함께 싣는 것이 있다(방문 결과의 '내일 다시', 현장 권 추가의 가격, 현장 수납의 줄 배분). 서버는 관찰한 부분(방문했다, 돈을 받았다, 권을 건넸다)은 늘 적고, 결정 부분만 intent처럼 충돌 키로 본다. 그사이 카운터가 그 업무의 일정(`task:<id>:schedule`)을 바꿨으면 방문 결과는 적되 일정은 덮지 않고 `확인 필요`에 올린다. 순번 열(`task_visits.seq` 등)은 기기가 아니라 서버가 적용할 때 매긴다.

명령 종류마다 등급과 시즌 1 처리 엔진은 `sys_event_types`에 있고, 계약 패키지가 같은 값을 코드로 내보낸다. CI는 모든 intent 명령이 충돌 키 함수를 가졌는지, 모든 오프라인 허용 명령과 fact가 native나 adapter인지, 코드에 등록된 엔진이 시드와 같은지 검사한다.

## 4. 버전과 충돌

### 4-1. 세 가지 번호

| 번호 | 쓰임 |
|---|---|
| 행 `version` | 레지스트리 · 설정 편집. 본 버전과 다르면 그 행만 `VERSION_CONFLICT` |
| 충돌 키(`intent_marks`) | 결정과 그 결정이 기대는 값. rev마다 어떤 키가 바뀌었는지 기록 |
| `{epoch, rev}` | 동기화 커서, 읽기 모델이 그려진 시점(`as_of_rev`). 잠금 조건이 아님 |

### 4-2. 충돌 키와 자동 이어 붙이기

충돌 키는 "누가 무엇을 결정했나"와 "그 결정이 무엇을 보고 했나"의 단위다.

| 키 | 쓰는 명령(표시를 남김) | 읽는 명령(기준 뒤 바뀌었으면 충돌) |
|---|---|---|
| `line:<id>:return_promise` · `line:<id>:pickup_promise` | 약속 바꾸기 · 나누기, 연장, 조기 반납 | 같음 |
| `line:<id>:quantity` | 취소, 줄 추가 · 수량 | 약속 나누기, 교환 |
| `line:<id>:price` | 가격 직접 입력, 할인 변경 | 취소(환불 금액) |
| `order:<id>:contact` · `order:<id>:payer` · `order:<id>:price_list` | 대표자 · 연락처, 결제할 팀, 요금표 | — |
| `order:<id>:money` | **돈 사실**(수납 · 환불 · 현장 수납 · 배분 옮기기), 청구가 바뀌는 명령 | 취소 · 환불 결정, 결제할 팀 정하기, 할인, 수납 창의 '받을 돈' |
| `order:<id>:checkout` | 카드 결제 요청 · 결과 · 확인 | 같은 팀의 카드 · 현금 수납 |
| `task:<id>:schedule` · `task:<id>:vehicle` | 업무 날짜 · 시각, 차량 옮기기 | 방문 결과의 '다시 가기' 부분 |
| `drawer:<id>:cash` | 그 돈통의 현금 사실 | 마감(예상 현금) |
| `closing:<scope>:<date>` | 마감 · 다시 열기 | 늦은 사실의 기준선 계산 |
| `registry:<table>:<id>` | 레지스트리 행 편집(행 버전과 같이) | — |

intent 명령이 오면 서버는 `SELECT 1 FROM intent_marks WHERE shop_id = ? AND conflict_key IN (바꾸는 키 + 읽은 키) AND rev > basis.rev LIMIT 1`을 보고(측정 0.001 ms), `expect`가 있으면 지금 값과 비교한다.

- 둘 다 없으면: 기기가 본 뒤로 **이 결정도, 이 결정이 기댄 값도 바뀌지 않았다.** 다른 칸이 바뀌었더라도(다른 줄의 약속, 지급) 지금 상태 위에서 그대로 적용하고 `rebased: true`와 달라진 것 한 줄(`changes`)을 돌려준다. 화면은 새로 그린 뒤 **한 줄 띠**로 보여 준다: '그사이 헬멧 1개가 추가되어 합계가 125,000원입니다.'
- 있으면: 진짜 충돌이다. `VERSION_CONFLICT`와 그 rev의 작업 기록(누가, 언제, 무엇으로)을 돌려준다. 돈 intent의 문장은 무엇이 바뀌었는지를 말한다: **'그사이 이 팀이 120,000원을 냈습니다. 다시 확인해 주세요.'**
- 마감은 `expect`에 돈통별 예상 현금을 싣는다. 미리 보기 뒤에 현금이 하나라도 들어왔으면 마감은 이어 붙지 않고 다시 세게 한다(얼린 마감에 틀린 차액이 남지 않음).
- `basis.rev`가 `intent_marks` 보관 기간(30일)보다 오래됐으면 행 버전으로 비교하지 않고 **새로 보고 다시 하라는 충돌**을 돌려준다(투영 열 변경이 가짜 충돌을 만들거나 진짜 충돌을 놓치지 않게).

투영 열(잔액, 진행 수량)이 바뀌는 것은 충돌 키를 남기지 않는다. 돈이 바뀐 사실은 `order:<id>:money` 표시로만 남아 **돈을 보고 한 결정**만 충돌시킨다. 그래서 수납 때문에 약속 변경이 충돌하는 일은 여전히 없다.

### 4-3. 고령 직원과 기사에게 보이는 모습

- 충돌 창은 한 문장과 두 버튼이다: **"다른 기기에서 이 품목의 반납 약속을 바꿨습니다. 지금: 오늘 22:00 설천 주차장 · 1호 차량 (카운터 2, 15:40)"** → `[그대로 두기]` `[내가 고른 것으로 바꾸기]`. 두 번째를 누르면 새 `basis`로 다시 보낸다. 몇 분 안에 다른 사람이 정한 것을 바꾸면 그 사람 기기에 '15:40에 정한 반납 약속을 카운터 1이 바꿨습니다'(`decision_overridden`)가 간다.
- 기술 용어(버전, 충돌, rev)는 화면에 나오지 않는다.
- fact는 충돌 창을 띄우지 않는다. `확인 필요`는 종류마다 **무게와 보일 곳**이 있다(`sys_review_kinds.routing_key`):
  - `dialog_step`(막는 단계): 카드 결과 모름, 카드가 한 번 더 승인됨, 보낼 차량 기록이 남은 마감 — 지금 열린 결제 · 마감 창 안에서 먼저 답해야 다음으로 간다.
  - `origin_device`(일으킨 기기의 그 화면): 기사 목록 줄에 '매장에서 이미 받음', 받은 수 확인, 같은 돈 두 번?, 순서가 바뀜, 내 결정이 바뀜.
  - `order_banner`: 더 받은 돈, 분실 금액 확인 — 그 접수증 위 띠.
  - `manager`: 쌓인 것의 목록(관리자). 버튼 두 개(`확인`, `기사님 기록으로 바꾸기`)로 끝내고, 누르는 순간 서버가 불변식을 다시 확인한다(`review.resolve`도 basis를 가짐; 몇 시간 뒤 그사이 다시 빌려 간 장비를 되돌리지 않음).
- 기사 목록은 명령마다 결과를 줄에 보인다: 실선 도장(적용), '매장에서 이미 받음'(superseded), '확인 필요'(needs_review). 기사가 '12팀 다 받았다'고 잘못 믿지 않는다.

### 4-5. 방문 순서와 빨리 확인

- ▲ · ▼ · 맨 위로는 '이 업무를 저 업무 앞 · 뒤로'(기준 업무)로 보내고, 서버가 **지금** 순서에서 순위를 계산한다. 캐시가 오래된 기사 기기의 ▲도 엉뚱한 자리에 떨어지지 않는다.
- 경로의 첫 손 이동은 그 경로(차량 · 날짜)의 모든 업무에 순위를 한 명령으로 쓴다. 그 뒤로 새로 생긴 업무는 약속 시각으로 순위 사이에 들어간다. 같으면 (순위, 약속 시각, 업무 id). 순위 키는 BINARY로 비교한다(PostgreSQL `COLLATE "C"`).
- 같은 업무를 두 사람이 옮기면 **나중에 일어난 쪽**(고친 `occurred_at`, `decided_at`)이 이긴다. 두 시간 오프라인이던 기사의 옛 ▲가 늦게 와서 카운터의 새 순서를 덮지 않는다. 진 쪽 기기에 '순서가 바뀌었습니다 (카운터 1, 22:05)'.
- 오프라인의 '시간순 되돌리기'도 같은 규칙이라 그 뒤 카운터가 정한 순서를 지우지 않는다.
- 업무 옮기기는 같은 트랜잭션에서 `route_positions`의 차량 · 순위를 다시 쓴다.
- 빨리 확인은 멱등이다: 두 카운터가 같은 초에 누르면 둘째는 '이미 됨'. 알림 출처 키는 `pin:<고정 id>`라 나중에 같은 업무를 다시 고정할 수 있다.

## 5. 동기화(받기)

- `GET /api/v2/sync?after=<rev>.<seq>&epoch=<epoch>&limit=500` → `{ epoch, rev, seq, reset, changes: [{ rev, seq, entity, id, op, row }], more, serverTime, currentBusinessDate }`. 커서는 `(rev, seq)`라 한 rev가 500줄을 넘어도(재고 들이기, 템플릿 적용, 요금표 게시) 쪽 사이에서 줄을 건너뛰지 않는다.
- 서버는 `change_log`에서 이 기기의 범위 행을 커서 뒤부터 읽고(인덱스 `(shop_id, scope_key, rev)`, 측정 0.23 ms), **지금 행**을 역할에 맞게 잘라서 보낸다.
  - `store`: 카운터 · 관리자, 전체 행.
  - `vehicle:<id>`: 그 차량의 업무, 업무 품목, 방문 순서, 빨리 확인, 알림, 차량 재고, 차량 지갑 잔액, 그 범위의 읽기 모델을 기기에서 다시 만드는 데 필요한 행, 그리고 **작은 접수 카드**(접수 번호, 팀 이름, 전화, 품목 요약, 미수 금액 읽기 전용 — `driver_sees_due_amount` 설정). 다른 팀의 돈 기록은 보내지 않는다.
  - `money`: 돈 권한이 있는 기기.
  - `public`: 손님 사이즈 입력폼(자기 요청만).
- **범위는 표마다 하나의 함수로 정한다**: 행의 주인 묶음(업무, 접수)에서 범위를 계산하고, 쓰기 때 **옛 범위와 새 범위 모두**에 `change_log`를 남긴다. 업무를 1호차에서 2호차로 옮기면 그 업무, 업무 품목, 방문 순서, 빨리 확인, 알림, 업무 속성, 접수 카드가 `vehicle:van-1`에는 `tombstone`, `vehicle:van-2`에는 `upsert`로 같은 rev에 들어간다. 카운터 수납이 `orders.due_amount`를 바꾸면 그 접수에 열린 업무가 있는 모든 차량 범위에 접수 카드 `upsert`가 간다. 시험: `change_log`를 범위 캐시에 다시 적용한 결과 = 범위로 직접 뽑은 결과(속성 시험).
- 속성 값(`*_attribute_values`)과 가격 내역은 주인 묶음의 행으로 함께 보낸다.
- `reset: true`: epoch가 다르거나(복구), 커서가 보관 기간(60일)보다 오래됐거나, 앱의 스키마 판이 달라 기기가 모르는 행이 생겼거나, **기기의 범위가 바뀐 경우**(휴대폰 기사가 다른 차량을 맡음, 역할 · 권한이 바뀜). 기기는 캐시를 버리고 `GET /api/v2/bootstrap?scope=`(오늘 일하는 데 필요한 것: 열린 접수, 오늘 업무, 레지스트리, 설정)을 받고 **보낼 줄(큐)은 그대로 둔다**.
- SSE `/api/v2/stream`은 `{epoch, rev}` 알림만 보낸다. 기기는 알림을 받으면 위 요청을 한다. SSE가 끊기면 포스는 5초, 기사 기기는 10초마다 묻는다. 바뀐 것이 없으면 인덱스 한 번 보고 끝난다(옛 방식은 2초마다 4.7 MB 전체 스냅샷).
- 응답의 `serverTime`으로 기기는 시계 차이를 재고, 화면은 그것으로 '지금' 줄과 늦음을 매분 다시 그린다(ui 문서 7절). `currentBusinessDate`는 매장 시간대와 기준 시각으로 서버가 정한 영업일이다. 기기가 자기 날짜로 '오늘'을 정하지 않는다.

## 6. 멱등과 보관

- 키: `(shop_id, request_id)`. 행위자는 키가 아니라 데이터다(ULID와 정해진 시스템 요청번호는 전역으로 유일). PIN으로 바꾼 다음 사람이 같은 명령을 다시 보내도, 기사가 바뀐 휴대폰이 큐를 보내도 두 번 적용되지 않고 원래 행위자로 남는다.
- 지문: `{type, commandVersion, payload}`의 sha256. basis · 시각 · 기기 번호는 넣지 않는다(다시 보낼 때 SSE 때문에 basis가 바뀌어도 같은 명령). 개인정보는 해시 안에만 있다. 저장한 봉투를 **바이트 그대로** 다시 보내는 것이 원칙이다.
- 결과 상태: `applied`, `partially_applied`, `superseded`, `needs_review`, `rejected`, `blocked`, `conflict`. 모두 `command_log`에 남는다.
- `rejected` 중 **다시 해 볼 만한 것**(`retryable = 1`: 마감한 날, 잠깐 잠김, `SQLITE_BUSY`, 처리기 예외 `INTERNAL`, 기능 꺼짐)은 같은 요청번호로 다시 오면 새로 판단한다. 영구 거절(형식 오류)은 저장한 거절을 돌려준다. 권한 없음은 큐에 있던 서명된 사실이면 거절이 아니라 기록 + 확인 필요다.
- **돈 사실의 부드러운 중복 확인:** 같은 접수 · 금액 · 수단 · 행위자가 2분 안에 두 번이면 둘 다 적되 `확인 필요`('같은 돈이 두 번 들어왔나요?', `possible_duplicate_money`)를 일으킨 기기에 띄운다. 같은 단말 · 승인번호 · 금액 · 날짜의 카드 두 건은 `possible_duplicate_card`.
- 결과 본문(`result_json`)은 90일 뒤 비우고 행은 남긴다(작업 기록 보관 기간 동안, 그 뒤 시즌 보관 파일로). 기기 큐는 7일이 지나도 버리지 않으므로(8-5) 중복은 요청번호로 언제나 잡힌다. 본문이 빈 요청이 다시 오면 `events`에서 응답을 다시 만든다.
- 오프라인에서 만든 행의 id(ULID)를 다른 요청번호로 다른 내용과 함께 보내면 `ID_CONFLICT`.
- outbox의 멱등 키는 만든 요청에서 정해지고 업체(문자 · 카드)가 지원하면 함께 보낸다. 결과를 모르면 사람에게 보이고 자동으로 다시 보내지 않는다(9절).

## 7. 기기와 세션

- **기기 등록:** 관리자가 `기기 등록`에서 종류 · 이름 · 차량을 고르면 8자리 일회용 번호(15분)가 나온다(`device_enrollment_codes`, 해시로 저장). 새 기기에서 번호를 넣으면 기기 id(ULID)와 WebCrypto 키 쌍(내보낼 수 없는 키)이 만들어지고 `devices` 행이 생긴다. 이때 `navigator.storage.persist()`를 요청하고, 거절되면 그 기기는 오프라인 기록을 할 수 없다고 보이고(`offline_capable = 0`, '이 기기는 오프라인 기록을 보관할 수 없습니다') 버튼을 온라인에서만 연다. 기기 수는 라이선스 한도로 센다.
- **기사 세션:** 유휴 시간이 길다(14일, 설정). 산에서 두 시간 끊겨도 다시 로그인하지 않는다. 로그인 · PIN 바꾸기마다 `device_sign_ins` 한 행.
- **기기 취소:** `devices.status_key = revoked`면 새 세션이 바로 끊긴다. 취소 전에 그 기기 키로 서명된 사실은 계속 받는다(고장 난 줄 알았던 태블릿의 큐를 잃지 않음).
- **카운터 PIN:** 등록된 카운터 기기에서는 직원이 4~6자리 PIN으로 바로 바뀐다(`accounts.pin_hash`, 5번 틀리면 잠금). 누가 했는지가 기록마다 정확히 남고, 고령 직원이 긴 비밀번호를 치지 않아도 된다. 바뀌기 전에 보낸 명령의 재시도는 원래 사람의 것이다(6절).
- **권한 확인:** 모든 명령에서 권한 + 범위 + 한도(할인 금액)를 본다. 기사의 `own_vehicle` 범위는 **일이 일어난 시각**의 업무 배정(`task_reassignments` 역사)으로 본다. 한도를 넘는 할인은 관리자 PIN을 받아 그 관리자를 승인자로 기록한다.

## 8. 오프라인(기사 기기)

### 8-1. 기기에 두는 것과 그리는 법

- **범위 자료:** 자기 범위의 행을 SQLite WASM(OPFS)에 받아 둔다. 서버와 **같은 `packages/store` · `packages/domain`**을 기기의 Web Worker에서 돌려 수거 목록 · 배달 목록 · 도장 · 남은 수 · 차에 있는 것을 **같은 읽기 모델 코드로** 만든다(LocalClient와 같은 길, 스키마는 그 범위의 표만). 앱을 오프라인에서 껐다 켜도 목록이 그려진다.
- **보냄 대기 겹치기:** 큐의 명령을 같은 native 처리기로 savepoint 안에서 적용해 읽기 모델을 만들고 되돌린다. 화면에 따로 계산하는 코드가 없다. 대기 중인 도장은 점선이고, 바닥줄 숫자는 대기를 따로 센다: **'받음 4 · 대기 8 · 남음 3'**(끝난 것처럼 보이지 않고, 남은 수도 틀리지 않음).
- 시험: 같은 자료로 서버의 `driverList`와 기기의 `driverList`가 똑같아야 하고, S6을 오프라인 중 앱 다시 시작까지 넣어 돌린다.
- IndexedDB `queue`: 보낼 명령(요청번호, 기기 번호, 만든 뒤 지난 시간, 서명된 행위자, basis, dependsOn, 본문, 상태: 대기 · 보내는 중 · 적용 · 이미 됨 · 확인 필요 · 거절 · 멈춤).
- IndexedDB `sent`: 서버가 받았다고 답한 명령, 그 rev, **서버가 정한 값(`canonical`)**, 7일 보관(복구 때 다시 보냄, 10절).
- 모두 등록 때 만든 내보낼 수 없는 기기 키로 암호화한다. 옛 방식의 "한 칸짜리 저장, 그게 풀릴 때까지 다음 일 못 함"은 없어진다.
- 오프라인 상태는 머리줄이 아니라 **자기 띠**('연결 끊김 · 보냄 대기 3 · 마지막 맞춤 21:40')로 보이고, 목록 높이 계산에 들어간다(ui 문서 6-3).

### 8-2. 오프라인에서 할 수 있는 일

`sys_event_types.offline_allowed = 1`이고 `sys_movement_routes.offline_allowed = 1`인 것만: 차량 받음(`stock.collect`), 차량에서 전달(`stock.deliver`), 방문 결과(`task.visit`), 현장 수납(`field.collect`), 차량 예비권으로 권 추가(`field.add_ticket`), 발권처 환불 시도(`vendor_refund.attempt`), 자기 차량 순서 바꾸기(`route.move`, `route.reset`), 알림 확인(`notification.ack`). 모두 native이거나 사실 어댑터 뒤의 옛 처리기(`adapter`)다. 카운터가 정하는 일(가격, 취소, 약속 변경, 할인, 업무 옮기기)은 오프라인이면 **버튼이 보이지 않는다**.

권 추가의 가격은 기기가 가진 요금표 판으로 계산해 `price_list_version_id` · 견적 금액 · `quote_hash`를 함께 보낸다. 서버는 그 판이 `occurred_at`에 효력이 있던 게시 판이면 그 값을 그대로 받고(`price_source_key 'offline_quote'`), 아니면 기기 값으로 적고 `확인 필요`를 올린다. 조용히 다시 계산하지 않는다(받은 돈과 청구가 어긋나지 않게).

매장 PC가 서버이므로 카운터는 매장 안 네트워크로 늘 연결된다. 인터넷이 끊겨도 카운터 일은 멈추지 않는다. 매장 PC 자체가 멈추면 종이(준비표 · 수거 목록 · 대여 장부 인쇄)로 일하고, PC가 돌아오면 입력한다.

### 8-3. 다시 연결되면

`POST /api/v2/commands:batch`로 기기 번호 순서대로(한 번에 50개까지) 보낸다. 서버는 **하나씩 각자의 트랜잭션**으로 적용하고 결과를 하나씩 돌려준다. 처리기가 예외로 끝나거나 `SQLITE_BUSY`면 되돌린 뒤 `rejected · retryable · INTERNAL`을 따로 적어 그 기기 번호가 비어 남지 않게 한다. 거절된 명령은 그것에 `dependsOn`한 **돈이 아닌** 명령만 멈춘다(`blocked`). 돈(`is_money`) 명령은 앞선 명령이 실패해도 멈추지 않는다.

순서의 기준: 차량 범위 확인은 `occurred_at`의 업무 배정으로, 장비의 '지금 위치'는 적용 순서(`created_rev`)로 본다. 이미 더 뒤의 이동이 적용된 장비에 그보다 먼저 일어난 이동이 늦게 오면, 그 이동은 **역사로만** 적고(`late_fact = 1`) 지금 위치를 옮기지 않는다.

| 기록 | 서버 판단 | 결과 |
|---|---|---|
| 장비 받음(ski-001, 김민수 팀에서 1호차로) | ski-001이 아직 김민수 팀 위치 | 적용 |
| 같은 기록인데 그사이 카운터가 매장 반납으로 받음 | 이미 매장 | `superseded`('매장에서 이미 받음'), 이동 없음 |
| 같은 기록인데 ski-001이 2호차 적재 계획에 잡혀 있음 | 계획보다 사실 | **이동 적용**, 2호차 계획 `displaced_by_fact`, 확인 필요는 계획에(`plan_displaced`) |
| 같은 기록인데 기록상 ski-001이 2호차에 있음 | 앞뒤가 안 맞음 | `needs_review`, 이동 없음(두 차량 중 어디인지 사람이 봄) |
| 수량 품목 4개 받음, 손님에게 2개 남음 | 2개만 맞음 | 2개 적용 + `partially_applied` + `확인 필요`('4개를 받았다고 했지만 남은 것은 2개') |
| 21:55 받음, 그런데 카운터가 22:10에 그 업무(T5)를 2호차로 옮김 | 21:55에는 1호차 업무였음 | **적용**, 2호차의 T5는 취소하고 2호차 기기에 알림(`task_moved_meanwhile`) |
| 21:00 1호차가 ski-001 전달(오프라인), 22:00 손님이 카운터에 직접 반납 | 카운터의 매장 반납은 '손에 든 것을 봄' | 22:00 매장 반납은 출발지가 기록과 달라도 **적용**(`skipped_hop`), 23:40에 온 21:00 전달은 `late_fact`로 역사만 — ski-001은 매장에 있다 |
| 현장 수납 35,000원 | 돈은 거절하지 않음 | 적용. 그사이 카운터에서 받았으면 과수납으로 보이고 `확인 필요`('더 받은 돈') |
| 현장 수납인데 그날 마감됨 | 마감한 날 | 적용, `business_date` = 받은 날, `posting_date` = 기준선, `확인 필요`('마감 뒤 들어온 돈'), 다음 마감 인계에 `late_entry` |
| 권 추가인데 차에 그 권이 없음 | 권을 줄 수 없음 | 권 줄 · 이동은 `needs_review`, dependsOn한 현장 수납은 **돈이라서 그대로 기록** — 배분할 줄이 없으므로 접수 전체 배분(`allocation_fallback`)으로 |
| 방문 결과(고객 부재, '내일 다시')인데 그사이 카운터가 일정을 바꿈 | 관찰은 사실, 일정은 결정 | 방문 결과 적용, 일정은 덮지 않고 `확인 필요` |
| 방문 결과(고객 부재)인데 업무가 이미 끝남 | 사실은 기록 | 적용 + `확인 필요`('취소된 업무') |
| 순서 바꾸기 | 순서만 | 4-5의 규칙(기준 업무, 나중에 일어난 쪽) |

같은 요청번호는 한 번만 적용되고, 모든 장비 이동은 장비의 지금 위치와 마지막 이동을, 모든 돈은 id와 배분 규칙을 확인하므로 **두 번 세는 일이 없다.** 시험: 오프라인 허용 돈 명령은 모든 dependsOn이 실패해도 `payments` 행을 남긴다.

### 8-5. 큐를 잃지 않는 규칙

- 큐의 사실은 **나이 때문에 버리지 않는다.** 7일이 지난 것은 관리자에게 알리고 보낸다.
- 두 판 넘게 서버가 올라가도 오프라인 허용 명령의 모양은 upcaster로 받는다(그 명령들의 모양은 되도록 바꾸지 않는다).
- 서버는 기기 번호의 빈 곳으로 잃어버린 명령을 찾는다(2절). iPhone PWA처럼 저장소가 지워질 수 있는 기기는 등록 때 `persist()`가 거절되면 오프라인 기록을 끈다.

## 9. 바깥으로 나가는 일(outbox)

명령 트랜잭션 안에서 `outbox` 행을 쓰고, 커밋 뒤 작업자가 실행한다. 결과는 정해진 요청번호의 시스템 명령으로 기록한다(작업자를 다시 돌려도 한 번).

**잡기 규칙:** 작업자는 바깥을 부르기 **전에** 따로 커밋하는 트랜잭션으로 행을 잡는다(`in_flight`, `attempts + 1`, `outbox_attempts` 한 행, `locked_until`). 시작할 때와 잡은 시간이 지났을 때: 재시도 없는 채널(문자 · 카드)의 `in_flight`는 `unknown` + `확인 필요`, 재시도하는 채널은 `failed` + 뒤로 미룸. 그래서 '보냈는데 결과를 적기 전에 꺼짐'은 두 번 보내지 않고 사람에게 간다. PostgreSQL은 `FOR UPDATE SKIP LOCKED`.

| 채널 | 동작 | 자동 재시도 | 결과를 모를 때 |
|---|---|---|---|
| `sms` | 업체로 보냄. 시간이 중요한 틀은 `not_after`(예: 출발 문자는 20분) | **안 함** | `unknown` → `확인 필요`('문자가 갔는지 모름, 필요하면 전화'). `not_after`가 지나면 `expired` |
| `card_terminal` | 카드 단말 도우미 · PG에 요청 전달(요청 id = 요청에서 정해진 id) | **안 함** | `unknown` → 결제 창 안의 막는 단계. 승인번호 입력(`payment.intent_resolve`)이나 단말 조회로 맞춤. 다시 긁기 전에 반드시 조회 |
| `print` | 인쇄 도우미 또는 브라우저 | 함 | `dispatched`(보냄)와 `confirmed`(직원이 확인)를 나눔. 도우미는 인쇄 작업 id로 중복을 걸러 응답을 잃어도 두 번 찍지 않음 |
| `webhook` | 외부 알림 | 함 | 실패 기록 |
| `backup_upload` | 백업 · 작업 기록 구간을 원격에 올림 | 함 | 관리자 대시보드 경고 |

- **카드 단말 도우미는 기기다.** 자기 승인 기록(작은 로그)을 가지고 결과를 자기 기기 명령으로 알린다. epoch가 바뀌면(복구) 그 로그를 다시 알리고, 날마다 VAN 정산 파일과 수납을 맞춘다. 인쇄 도우미도 기기다.
- **바깥에서 오는 결과**(문자 전달 결과, PG 콜백)는 control의 받은편지함에서 매장 서버가 가져가 `inbound:<id>` 시스템 명령으로 기록한다(data-model 2-3).
- `shops.is_test = 1`(체험 · 연습 매장)이면 모든 채널이 모의 대상으로 가고 `suppressed`로 끝난다. 연습 로그인이 손님에게 문자를 보내는 일이 없다.

| 연결 설정 | 늘 | WAL, `synchronous = FULL`(정전에도 커밋한 돈이 남음), `busy_timeout = 5000`, `foreign_keys = ON`, `recursive_triggers = ON` |
| **작업 기록 구간**(작업 기록 + `event_pii` + 명령 기록 + 바뀐 행의 after-image) | **커밋마다 몇 초 안에** | 같은 LAN의 다른 기기(카운터 2 또는 작은 도우미)로 흘려 보냄(`lan_peer`). 5분마다 묶어 두 번째 디스크 · USB에, 묶이는 대로 원격 대기열에(`journal_exports`, 앞뒤 해시, epoch). 관리 화면에 복제 지연을 보인다 |
| control 파일의 복구 기록 | 같음 | `control_changes`(바뀐 행의 after-image)를 같은 방식으로 내보냄(`control_journal_exports`). 1시간 사이에 만든 기사 계정 · PIN을 잃지 않음 |
| 전체 백업(`VACUUM INTO`: 읽기 한 번의 스냅샷) | 1시간마다(영업이 뜸한 때를 골라), 48개 순환. 배포와 마이그레이션 **바로 뒤**에도 한 번 | 매장 PC의 다른 폴더 |
| 암호화 원격 복사 | 밤마다 + 구간은 묶이는 대로 | 원격 저장소(`backup_upload`) |
| 마이그레이션 · 가져오기 전 | 그때마다 | `pre_migration` · `pre_import` |
| 복구 시험 | 매주 자동 | 임시 파일에 복구 → `integrity_check` → 검증기 → 행 수 비교 → 구간 이어 붙이기 → `restore_drills` |

`node:sqlite`의 `backup()`은 다른 연결이 쓰면 처음부터 다시 하므로 성수기에 끝나지 않을 수 있다. 그래서 `VACUUM INTO`(한 번의 읽기 스냅샷)를 쓰거나, `backup()`을 쓰는 연결에서 한가할 때 한다. 모든 백업은 control의 `backups`에 sha256, epoch, `max_rev`, 그때 작업 기록 해시와 함께 목록으로 남고, `tenant_epochs.max_rev_seen`을 올린다.

**실제 복구 지점(RPO):** 카운터 1이 서버 PC에서 도는 기본 배치에서도, 잃을 수 있는 것은 **LAN의 다른 기기로 아직 흘러가지 않은 몇 초**뿐이다. 서버 PC와 LAN의 받는 기기가 함께 망가지면 두 번째 디스크 · USB의 마지막 5분 묶음까지, 불 · 도난이면 원격의 마지막 묶음까지다. 그 사이의 기록 중 다른 기기(카운터 2, 차량)가 보낸 것은 그 기기들이 다시 보내고, 카드는 단말 도우미의 로그와 VAN 정산으로 맞춘다. 가장 안전한 배치는 서버를 카운터가 아닌 PC에서 돌리는 것이다(열린 질문).

### 10-2. 복구 순서

1. 가장 최근의 확인된 전체 백업을 새 파일로 복구한다(옛 파일은 건드리지 않고 옆에 둔다). 백업은 늘 같은 앱 · 스키마 판의 구간이 뒤따르는 것을 고른다(배포 · 마이그레이션 직후 백업이 있으므로).
2. 그 백업의 `max_rev` 뒤의 작업 기록 구간을 rev 순서로 이어 붙인다. 각 구간의 첫 `prev_hash`가 앞 구간의 마지막 `hash`와 같은지 확인한다(사슬이 끊기면 거기서 멈추고 관리자에게 알림). **적용은 구간에 담긴 after-image를 그대로 쓰는 것**이다: 같은 행이 같은 id · 같은 번호로 생기고, 처리기 코드가 그사이 바뀌었어도(핫픽스) 결과가 달라지지 않는다. 처리기를 다시 돌리는 것은 확인용이며 `events.handler_version`이 다르면 하지 않는다.
3. `shop_instance`와 control `tenant_epochs`에 새 epoch를 쓴다: `restored_up_to_rev`(이어 붙인 마지막 rev), `rev_floor` = **지금까지 이 매장에서 쓴 가장 큰 rev**(`tenant_epochs.max_rev_seen`, 모든 epoch의 `backups.max_rev` · `journal_exports.to_rev`, 기기가 알린 가장 큰 rev 중 최댓값) + 1,000,000. 복구를 두 번 하거나 더 옛 백업으로 돌아가도 이미 쓴 rev · 그 rev로 만든 옛 id가 다시 나오지 않는다.
4. 사람이 읽는 번호를 건너뛴다: 접수 번호 · 묶음 번호 계산기를 범위마다 +500 올린다(잃은 구간에서 이미 종이에 찍혔을 수 있는 번호를 다른 팀이 받지 않게).
5. 복구 뒤 만들어지는(다시 적용 · 다시 보냄) outbox 행은 `replayed = 1`이고, 재시도 없는 채널(문자 · 카드)은 `unknown`에서 시작해 스스로 나가지 않는다. 사람이나 단말 조회가 정한다.
6. `platform_audit_log`에 복구를 적는다.
7. 서버를 켠다. 모든 응답에 새 epoch가 실린다. 다른 epoch의 basis를 가진 intent는 '자료를 복구했습니다. 다시 확인해 주세요'를 받는다. 기기들은:
   - 캐시를 버리고 bootstrap을 받는다.
   - `sent` 기록(7일)에서 **서버가 준 rev가 `restored_up_to_rev`보다 큰 명령**을 같은 요청번호로, **`replay`에 그때 서버가 정한 값(`canonical`: 만든 id, 접수 번호, 묶음 번호, `posting_date`, 견적, 받은 rev)을 실어** 다시 보낸다. 카운터 포스도 같은 `sent` 기록을 가진다. 카드 · 인쇄 도우미도 자기 기록을 다시 알린다.
   - 그다음 아직 못 보낸 큐를 보낸다.
8. 서버는 다시 보낸 명령을 짧은 창(기본 2분) 동안 모아 **원래 rev 순서로** 적용하고, `replay`의 값을 그대로 예약해 쓴다(같은 접수 번호, 같은 id). 이미 그 값을 다른 것이 가졌으면(다른 기기가 먼저 보낸 다른 팀) 새 값을 쓰고 `확인 필요`('복구 뒤 접수 번호 261226-041이 다른 팀에 쓰였습니다 — 종이 접수증을 확인해 주세요', `receipt_no_clash`). 이미 들어간 것이면 `duplicate`, 잃어버린 것이면 새로 적용된다. 적용할 수 없는 것만 `확인 필요`('복구 뒤 다시 받음')로 간다.
9. 복구 기기의 기기 번호는 복구된 높은 물 표시 위의 것을 모두 받는다(구간에 없던 거절 · 충돌 행 때문에 빈 번호가 영원히 남지 않게).

### 10-3. 복구 시험이 확인하는 것

`PRAGMA integrity_check`, `foreign_key_check`, 검증기 전체(투영 · 현금 출처 · 해시 사슬 · 장부 행 해시), 행 수가 백업 목록의 값과 같은지, 구간 이어 붙이기가 끝까지 되는지, 다시 보낸 명령이 같은 id · 번호로 들어가는지. 실패하면 관리자 콘솔 대시보드와 매장 관리 화면에 빨간 알림.

## 11. 여러 매장과 PostgreSQL

- 매장 PC: 파일마다 쓰기 하나(`BEGIN IMMEDIATE`). 한 건이 약 0.6 ms라 100개가 몰려도 약 60 ms에 끝난다.
- SaaS SQLite: 매장마다 파일 하나, 매장끼리 서로 막지 않는다(옛 구조는 모든 매장이 쓰기 잠금 하나를 나눔).
- SaaS PostgreSQL: 쓰기 트랜잭션마다 `SELECT value FROM shop_counters WHERE shop_id = $1 AND counter_key = 'rev' FOR UPDATE`. 매장별로만 줄을 세우고 커밋 순서 = rev 순서라 읽는 쪽이 rev를 건너뛰지 않는다. 행 보안 정책으로 `shop_id`를 한 번 더 막는다. 한 매장만 복구할 때는 새 스키마에 그 매장의 구간 after-image를 다시 적용해 만든 뒤 바꿔 끼운다(data-model 9절).
- 오래 걸리는 일: 검증기 · 보고서 · 백업 스냅샷은 별도 읽기 연결의 작업 스레드에서 한다(WAL이라 읽기가 쓰기를 막지 않음). **쓰는 긴 일**(시즌 보관의 지우기, 검증기의 고침)은 읽기 연결이 아니라 쓰기 경로로, 잘게 나눠서 한다: 지우기는 한 트랜잭션에 2,000줄씩 영업 시간 밖에, 사이마다 쓰기 잠금을 놓는다. 검증기의 고침은 정해진 요청번호의 시스템 명령(`verifier.repair`)이라 rev와 변경 목록이 남고 기기에도 간다. `SQLITE_BUSY`는 다시 해 볼 만한 거절이고 기기 번호를 쓰지 않는다.
