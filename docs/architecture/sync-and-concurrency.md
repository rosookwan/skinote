# 동시 수정 · 오프라인 · 백업과 복구

작성 2026-09-23(같은 날 검토 반영). 고침 2026-09-24: 보증금 충돌 키(4-2), 수거 현장의 보증금 돌려드림을 오프라인 허용(8-2), 이 매장의 백업 배치는 README '정한 것' D4(10-1). **같은 날 다시 고침: 배치가 클라우드 중심으로 바뀌었다(ADR-19, [deployment.md](deployment.md)).** 장부 원본은 우리 중앙 서버에 있고, 카운터도 기사처럼 오프라인 사본과 보냄 대기로 일한다(8절: 8-2 기기 종류마다의 목록, 8-6 ~ 8-11 카운터), 기기 등록 · 라이선스 · PIN은 중앙을 거치며(7절), 백업은 다른 곳의 저장소로의 WAL 복제 · 스냅샷 · 되살리기 연습이다(10절). **같은 날 셋째 검토(끊김 · 보안 · 운영 · 일관성, README '검토 반영 기록') 반영:** 큐에서 온 명령은 등급과 상관없이 적어 두는 사실이다(8-12: 끊긴 새 접수 · 옛 기준의 돈이 돌려보내지지 않음), 카운터도 적재 · 권 주기 · 바꿔 드림을 끊긴 채 한다(8-2), 여러 기기가 다시 붙을 때는 일어난 순서로 적용하고 이동마다 보류한 사실을 다시 판단한다(8-3), 두 카운터 겹침의 규칙을 넓혔다(8-7), 답을 잃은 명령은 요청번호를 놓지 않는다(8-1), 마감은 보낼 기록이 남은 모든 기기를 기다린다(8-2 · 8-4), 막은 기기는 서버가 받은 때로 가른다(7절), 되살리기는 두 길이다(10절: 복제 도구의 세대 + WAL, 스냅샷 + 구간). **같은 날 넷째 고침:** 이 문서가 정한 화면 글(충돌 창 · 확인 필요 · 연결 띠 · 연결을 기다리는 버튼 · 기기 등록)을 짧은 업무 용어의 `사실 · 할 일` 모양으로 바꿨다(README D6, [docs/design/wording.md](../design/wording.md)). 설명 문장의 개념 말(약속 · 보냄 대기 · 되살리기 …)은 그대로다. 카운터 두 대, 차량 세 대, 휴대폰 기사가 동시에 일하고, 산속이나 가게에서 통신이 끊기고, 우리 서버가 고장 나도 기록이 한 번씩만 정확히 남게 하는 규칙이다. 표 정의는 [`schema.sql`](../../packages/schema/schema.sql) 2.16 · 2.17절, 원칙은 [data-model.md](data-model.md).

## 0. 한눈에

- 옛 시스템은 명령마다 매장 전체 JSON을 읽고 복사하고 다시 썼고(주문 600건에서 82 ms, 5.2 MB), 매장 전체 버전 하나를 비교해서 **어느 기기든 한 번 쓰면 다른 모든 기기의 다음 명령이 충돌**했다. 작업 기록과 멱등 기록은 JSON 안에 영원히 쌓였다.
- 새 방식: 표가 진실, 쓰기는 파일마다 하나씩(한 건 약 0.6 ms), 충돌은 **같은 결정을 두 사람이 바꿀 때, 또는 결정의 바탕이 된 돈 · 수량이 그사이 바뀌었을 때만**. 일어난 사실(돈, 물건 이동, 방문 결과)은 기기가 늦게 보내도 거절하지 않는다. 사실과 부딪힌 계획은 사실이 이기고, 앞뒤가 안 맞으면 그 일을 일으킨 사람 앞에(급하면 그 화면 안에서) 쉬운 한 문장으로 보인다.
- 모든 명령은 **요청번호 하나**로 한 번만 적용된다(누가 로그인해 보냈는지와 상관없이). 요청 기록은 지우지 않는다.
- 모든 기기(카운터 · 기사)는 인터넷으로 중앙 서버에 붙고, 끊기면 자기 사본과 보냄 대기로 일한다. 카운터는 지급 · 반납 · 적재 · 권 지급 · 즉시 교환 · 수납 · 보증금 · 새 현장 접수(임시 접수 번호) · 품목 추가 · 인쇄를 오프라인에서 하고, 기존 결정을 바꾸는 일(약속 · 취소 · 연장 · 할인 · 마감)은 연결을 기다린다(8-2). 큐에서 온 명령은 이미 일어난 일이라 도착해서 돌려보내지 않는다(8-12).
- 백업은 커밋마다 몇 초 안에 다른 구역 저장소로 가는 WAL 복제, 1분마다 다른 회사 저장소로 작업 기록 구간, 날마다 스냅샷, 새 VM에 되살리는 연습(10절). 복구는 두 길이다: 복제 도구의 세대 + WAL을 아무 초로나(PITR), 또는 스냅샷에 구간의 **바뀐 행의 이후 모습(after-image)**을 이어 붙임. rev는 지금까지 쓴 가장 큰 rev 위로 뛰며, 기기들이 최근 7일 보낸 명령을 **서버가 정했던 값과 함께** 다시 보낸다.

## 1. 쓰기 순서

```text
POST /api/v2/commands (또는 :batch)
 0  처리 중 기록: (매장, 요청번호)를 쓰기 프로세스 밖의 작은 기록(서버 디스크의 파일)에 적고 끝나면 지운다. 다시 시작할 때
    남아 있으면 그 요청은 프로세스를 죽인 명령이다: 실행하지 않고 held + command_held, 개발자를 깨움(11절)
 1  세션 → 계정 → 직원(staff_members) → 매장, 역할, 권한(범위 · 한도), 기기, 차량(vehicle_assignments)
    큐에 쌓였던 명령: 봉투의 서명된 행위자(recordedBy)를 기기 키로 확인하고, 그 사람이 occurred_at에
    그 기기에 로그인해 있었는지 device_sign_ins로 본다. 맞으면 그 사람이 행위자, 보낸 세션은 submitted_by
    그 기기가 막혀 있으면(서버가 revoked_at 뒤에 받음) 적용하지 않고 held + revoked_device_record(7절)
 2  봉투 검사: (type, commandVersion)의 허용 키 목록. 옛 판이면 upcaster로 올림. 너무 옛 판이면 UPGRADE_REQUIRED
    (오프라인 허용 명령의 upcaster는 큐 보관 기간보다 오래 둔다; 큐 명령의 형식 오류는 서버의 upcaster · 고침 길로, 8-12)
 3  BEGIN IMMEDIATE            -- SQLite: 파일마다 쓰기 하나. PostgreSQL: shop_counters('rev') FOR UPDATE
                               -- 연 파일의 shops.id가 세션의 매장인지 트랜잭션마다 다시 봄(다르면 멈추고 알림)
 4  command_log(shop, request_id) 찾기
      있음 · 같은 지문 → 저장한 결과를 돌려줌(결과가 90일 지나 비었으면 events로 다시 만듦), 아무것도 안 씀
      있음 · 다른 지문 → 처음 결과를 돌려주고 idempotencyMismatch 표시 + integrity_findings(클라이언트 버그)
      dependsOn 중 실패 · 멈춘 것이 있으면 → 큐에서 온 명령은 멈추지 않음(적용 + 확인 필요, 8-12),
                                          온라인 명령은 돈이 아니면 'blocked', 돈(is_money)이면 멈추지 않음(8-3)
 5  명령이 선언한 묶음만 불러옴(id로). 매장 전체를 읽지 않음
 6  intent면 충돌 키 확인(4절: 바꾸는 키 + 읽은 키)과 expect. fact면 불변식만, 사실 안의 '결정' 부분은 intent처럼
    큐에서 온 명령(기기 종류의 오프라인 목록에 있고 기기가 서명함)은 등급과 상관없이 '적어 두는 사실':
    epoch · basis · 충돌 키 · 30일 · expect로 돌려보내지 않고, 판단 부분(견적 판 · 할인 · 결제 팀 · 권한 ·
    라이선스)만 확인 필요로(8-12)
 7  처리기 실행: native(순수 함수: 불러온 묶음 + 명령 + 문맥 → 쓸 행, outbox, 알림, 확인 필요, 결과)
               adapter(사실 어댑터: 지금 위치를 먼저 보고 맞는 부분만 옛 execute()에 넘기고 나머지는
                       superseded · needs_review; 옛 오류는 결과 상태로 바꿈 — 사실을 거절하지 않음)
               legacy(옛 execute()를 표에서 채운 옛 모양 상태 위에서 실행, intent만 → 바뀐 요소를 codec으로 행으로)
 8  행 쓰기, rev = shop_counters.rev + 1 (shop_instance.rev_floor 위), created_rev · updated_rev, 행 version + 1
    서버가 만드는 id · 번호는 요청에서 정해짐(data-model 3-1): 같은 명령을 다시 보내도 같은 값
 9  건드린 묶음의 투영을 장부에서 전부 다시 계산
10  events(개인정보 없는 정본 명령 + 결과 + 넣은 장부 행의 해시 + pii_commitment + 사슬 해시), event_pii,
    intent_marks, change_log(범위별, 옛 범위 · 새 범위 모두), command_log, outbox, notifications, review_items
11  COMMIT → (복제 도구가 WAL을 몇 초 안에 다른 구역 저장소로, 1분마다 작업 기록 구간을 다른 회사 저장소로, 10-1; 커밋은 기다리지 않음)
    → SSE로 {epoch, rev} 알림, outbox 작업자 깨움
    처리기가 예외로 끝나도 rollback 뒤 따로 command_log에 rejected · retryable · INTERNAL을 적는다(8-3). 끝나면 0의 기록을 지움
```

- 미리 보기(dry run, 옛 `prepareMove`)는 3~9단계를 savepoint 안에서 하고 되돌린 뒤 결과만 돌려준다. 기사 기기가 보냄 대기 명령을 목록에 겹쳐 그릴 때도 같은 방식이다(8-1).
- 처리기는 순수 함수라 테스트에서 표 없이도 돈다. SQL은 저장소 패키지(`packages/store`)에만 있다.
- 한 명령 = 한 트랜잭션 = 한 rev = 작업 기록 한 줄.

## 2. 명령 봉투

```json
{
  "type": "promise.change",
  "commandVersion": 1,
  "requestId": "01JF3Q8W2Z6N9XK4T7B5R1C0DM",
  "deviceSeq": 1287,
  "ageMs": 0,
  "clockAnchor": "boot-7f3a",
  "basis": { "epoch": "01JF0…", "rev": 48213 },
  "expect": { "dueAmount": 0 },
  "dependsOn": [],
  "recordedBy": { "staffId": "01JE…", "sessionId": "01JF…", "signature": "…" },
  "replay": null,
  "payload": {
    "orderId": "01JF3P…", "lineId": "01JF3P…", "quantity": 2,
    "promise": { "methodKey": "vehicle_collection", "placeId": "01JD…", "returnSlotId": "01JC…", "vehicleId": "01JB…" }
  }
}
```

- 매장, 역할, 권한, `recorded_at`, 영업일, rev는 **봉투에서 받지 않는다.** 세션과 서버가 정한다. 행위자도 온라인 명령은 세션에서 정한다. 큐에 쌓였던 명령만 `recordedBy`(그 일을 한 순간 기기에 로그인한 직원, 기기의 내보낼 수 없는 키로 서명)를 쓰고, 서버는 서명과 `device_sign_ins`를 확인한다. 세션이 끝났거나 계정이 정지됐어도 **등록된 기기가 서명한 큐 명령은 받아 적고** `확인 필요`에 올린다(권한 없음으로 버리지 않음; 계정 정지 · PIN 바꿈 뒤의 오프라인 로그인은 `unverified_sign_in`, 7절). **막은 기기**는 기기가 말한 시각이 아니라 **서버가 받은 때**로 가른다: `revoked_at` 전에 도착한 것은 보통 명령이고, 그 뒤에 도착한 그 기기의 명령은 말한 시각과 상관없이 적용하지 않고 보류(`held`)해 관리자가 `반영`을 눌러야 적용한다(`revoked_device_record`, 7절). 고친 앱이 `ageMs`를 크게 보내 기록을 '막기 전'으로 옮길 수 없다.
- **서명이 덮는 것:** `(shop_id, device_id, deviceSeq, requestId, type, commandVersion, payload 해시, ageMs, clockAnchor, recordedBy.staffId)`. `occurred_at`은 서버가 정하는 값이라 서명에 넣지 않는다. 같은 기기에서 `deviceSeq`는 큰데 고친 시각이 앞인 기록은 `clock_suspect`다.
- `requestId`: 기기가 만든 ULID. **확인 창이 열릴 때 만들어 초안과 함께 저장하고, 다시 보낼 때마다 같은 것을 쓴다**(두 번 누르기, '처리 중'에 또 누르기, 창이 열린 채 새로 고침한 뒤 같은 창을 다시 열 때). 단 **한 번 보낸 초안의 번호는 새 창에 쓰지 않는다**(초안에 `sentAt`을 적는다): 같은 도장을 나중에 다시 여는 것은 새 의도이고, 옛 번호로 보내면 서버가 옛 결과를 돌려주어 새 도장이 말없이 사라진다. 저장된 초안은 basis가 같을 때만 다시 쓴다. 시스템 명령은 정해진 모양(`outbox:<id>:<attempt>:<status>`, `import:<run>:<collection>:<id>`, `verifier:<run>:<check>`, `inbound:<id>`)이라 작업자를 다시 돌려도 중복이 없다.
- `deviceSeq`: 기기마다 1부터 오르는 번호. `(device_id, device_seq)`는 **유일하기만** 하고 순서는 강제하지 않는다. 서버는 높은 물 표시와 빈 번호 목록을 가지고, 빈 번호가 `seq_gap_alert_minutes`(30분)보다 오래 비면 `확인 필요`('1호 차량 기록 3건 미수신 · 해당 기기 전송 필요', `device_gap`)를 올린다. 순서가 필요한 것은 `dependsOn`이 말한다. 한 기기에서 포스를 두 창으로 열어도 보내는 쪽은 하나(Web Locks로 뽑힌 창)다.
- 시각: 온라인 명령은 `occurred_at = recorded_at`. 큐 명령은 `ageMs`(만든 뒤 지난 단조 시계 ms)와 `clockAnchor`(부팅 · 세션 id)를 보내고 서버가 `recorded_at − ageMs`로 정한다. 기준을 잃었을 때만 기기 벽시계 + 시계 차이를 쓰고 `time_source_key = 'wall_clock'`으로 표시한다(data-model 3-3).
- `basis`: **확인 창이 그린 읽기 모델의 `as_of_rev`와 그 epoch**(동기화 커서가 아님). 창이 열린 동안 SSE가 새 rev를 가져와도 basis는 창을 연 때 값이다. 온라인으로 바로 보낸 intent만 basis를 본다: 다른 epoch의 basis는 '자료 복구 · 재확인 필요'로 돌려보낸다. **큐에서 온 명령은 basis를 보지 않는다**(8-12: 끊긴 동안 서버를 되살려 epoch가 바뀌어도 끊긴 새 접수가 돌려보내지지 않음).
- `expect`: 돈 결정의 바탕이 된 숫자(받을 돈, 환불할 돈, 예상 현금). 확인 창은 서버가 준 초안의 `expect`를 창이 열릴 때 초안에 넣는다. 돈 명령(`payment.take` · 환불)은 `expect`가 없으면 거절한다(`EXPECT_REQUIRED`): 받을 돈을 보지 않은 수납이 적용되지 않게. **온라인으로 바로 보낸 돈 명령만** 지금 값과 달라 충돌을 돌려받는다(4-2, 창 안의 `제외 후 수납`). **큐에서 온 돈 사실**(`payment.take` · `deposit.take` · `deposit.return` · `field.*`)의 `expect`는 참고 값이다: 끊긴 두 카운터의 expect는 처음부터 옛 값이므로, 늘 적용하고 차이는 `overpaid` · `deposit_over_returned` · `possible_duplicate_money`로 올린다(8-12).
- 충돌 키는 **봉투에 없다.** 서버가 `(type, payload)`에서 만든다(계약 패키지의 함수 하나, 클라이언트와 공유). 옛 클라이언트가 키를 덜 보내 충돌을 비켜 가는 일이 없다.
- `dependsOn`: 오프라인에서 이어진 명령(권 추가 → 그 권의 현장 수납, 카운터의 새 접수 → 그 접수의 수납 · 보증금 · 지급). 큐에서 온 명령은 앞 명령이 끝내 적용되지 못해도 멈추지 않는다(8-12). 온라인 명령만 돈이 아니면 `blocked`.
- 오프라인 카운터의 새 접수(`order.create`)는 본문에 기기가 매긴 **임시 접수 번호**(`provisionalReceiptNo`, `'1-12'`)를 싣는다. 서버는 받는 순간 최종 접수 번호를 주고 임시 번호를 그 접수에 남긴다(8-6).
- `replay`: 복구 뒤 다시 보낼 때만. 서버가 처음에 정했던 값(만든 id, 접수 번호, 묶음 번호, `posting_date`, 견적, 받은 rev)을 그대로 싣는다(10-2). 서버는 되살린 까닭에 따라 두 방식으로 쓴다: `restore_lost`(서버를 잃음)는 모든 값을 그대로, `restore_bad_deploy`(잘못된 배포로 값이 틀림)는 이름 값(id · 접수 번호 · 묶음 번호 · 임시 번호)만 두고 계산 값(견적 · `posting_date`)은 고친 처리기로 다시 계산해 달라진 것을 `recomputed_after_restore`로 올린다.
- `commandVersion`: 명령 모양의 판. 서버는 바로 전 판의 upcaster를 가지고, 오프라인 허용 명령은 큐 보관 기간(7일)보다 오래된 판까지 받는다. 서버를 먼저 올리고 기기를 나중에 올린다.
- 응답: `{ outcome, requestId, rev, asOfRev, epoch, versions, rebased, changes, canonical, result }`. `canonical`은 서버가 정한 값(10-2에서 다시 쓰려고 기기가 `sent`에 보관)과 **기기가 제안한 id를 서버가 바꿔 읽은 대응**(예: 끊긴 두 카운터가 같은 팀 보증금 보관을 각자 만들었을 때 둘째의 제안 id → 첫째 보관 id, 8-7)이다. 기기는 뒤 명령의 제안 id를 이 대응으로 바꿔 보내고, 서버도 같은 기기의 뒤 명령에 있는 제안 id를 바꿔 읽는다. 거절이면 `{ code, message, current }`(지금 상태를 함께 보내 화면이 무엇이 바뀌었는지 보여 줌).

`events.command_json`에는 **서버가 정한 값이 모두 들어간 정본 명령**(만든 id들, 접수 번호, `occurred_at`, 영업일, `posting_date`)을 적는다. 이름 · 전화와 **모든 자유 글(메모, 사유, 장소 메모)**은 참조로만 쓰고 값은 `event_pii`에 두며, 사슬은 그 약속값(`pii_commitment`)만 덮는다. 결과에는 명령이 넣은 장부 행마다 정본 해시가 있어 사슬이 표의 행까지 덮는다(밤마다 검증기가 다시 계산).

## 3. 명령의 세 등급

| 등급 | 예 | 확인 | 충돌 때 |
|---|---|---|---|
| **fact**(이미 일어난 일) | 수납 · 환불 · 현장 수납, 현금 입출금 · 인계 · 인계 확인, 적재 · 지급 · 배달 · 수거 · 매장 입고 · 매장 반납, 권 지급(배정 포함), 즉시 교환(카운터 교환), 방문 결과, 강습 완료, 발권처 환불 시도, 사이즈 입력, 카드 · 문자 결과 | 물건 위치 · 잔량 · 돈 불변식. 버전은 보지 않음 | **거절하지 않음.** 맞는 부분만 적용(`partially_applied`), 이미 된 일은 `superseded`(쓰는 것 없음), 앞뒤가 안 맞으면 `needs_review`. **물건이 실제로 옮겨진 사실은 늘 이동으로 적고**, 부딪힌 계획(claim)은 `displaced_by_fact`로 끝내며 확인 필요는 그 계획에 단다. 돈은 늘 기록 |
| **intent**(앞으로의 결정) | 일정 변경 · 나누기, 업무 차량 변경, 취소, 가격 직접 입력, 할인, 연장, 결제 팀 · 시점, **카드 결제 요청**, 설정 · 레지스트리 편집, 마감 | 충돌 키(바꾸는 키 + 읽은 키) · `expect` · 행 버전 | 겹치면 `VERSION_CONFLICT`와 지금 값. 안 겹치면 자동으로 이어 붙임(`rebased: true`) — 단 돈 intent는 그 접수의 돈이 바뀌었으면 이어 붙이지 않음. **큐에서 온 새 접수 · 품목 추가는 여기가 아니라 8-12**(적어 두는 사실) |
| **commutative**(순서만 바뀌는 일) | 방문 순서 ▲▼ · 맨 위로 · 시간순, 긴급 요청 · 해제, 알림 확인, 인쇄 요청 | 없음(순서 바꾸기는 기준 업무 + 결정 시각) | 서버가 지금 순서에 맞춰 풀어 적용. 더 오래된 순서 바꾸기가 늦게 오면 짐(4-5) |
| **system** | outbox 결과, 받은편지함 결과, 가져오기, 검증 보정, 기기 로그인 | 정해진 요청번호 | 멱등 |

**사실 안의 결정.** 사실 명령 중에는 결정을 함께 싣는 것이 있다(방문 결과의 `재방문 내일`, 현장 권 추가의 가격, 현장 수납의 줄 배분). 서버는 관찰한 부분(방문했다, 돈을 받았다, 권을 건넸다)은 늘 적고, 결정 부분만 intent처럼 충돌 키로 본다. 그사이 카운터가 그 업무의 일정(`task:<id>:schedule`)을 바꿨으면 방문 결과는 적되 일정은 덮지 않고 `확인 필요`에 올린다. 순번 열(`task_visits.seq` 등)은 기기가 아니라 서버가 적용할 때 매긴다.

명령 종류마다 등급과 시즌 1 처리 엔진은 `sys_event_types`에 있고, 계약 패키지가 같은 값을 코드로 내보낸다. CI는 모든 intent 명령이 충돌 키 함수를 가졌는지, 모든 오프라인 허용 명령과 fact가 native나 adapter인지, 코드에 등록된 엔진이 시드와 같은지 검사한다.

## 4. 버전과 충돌

### 4-1. 세 가지 번호

| 번호 | 쓰임 |
|---|---|
| 행 `version` | 레지스트리 · 설정 편집. 본 버전과 다르면 그 행만 `VERSION_CONFLICT` |
| 충돌 키(`intent_marks`) | 결정과 그 결정이 기대는 값. rev마다 어떤 키가 바뀌었는지 기록 |
| `{epoch, rev}` | 동기화 커서, 읽기 모델이 그려진 시점(`as_of_rev`). 잠금 조건이 아님 |

### 4-2. 충돌 키와 자동 이어 붙이기

충돌 키는 "누가 무엇을 결정했나"와 "그 결정이 무엇을 보고 했나"의 단위다.

| 키 | 쓰는 명령(표시를 남김) | 읽는 명령(기준 뒤 바뀌었으면 충돌) |
|---|---|---|
| `line:<id>:return_promise` · `line:<id>:pickup_promise` | 일정 변경 · 나누기, 연장, 조기 반납 | 같음 |
| `line:<id>:quantity` | 취소, 줄 추가 · 수량 | 약속 나누기, 교환 |
| `line:<새 id>:*`(새 줄의 약속 · 수량 · 가격) | 새 접수(`order.create`), 품목 추가(`order.add`): 새 줄의 키만 남긴다. 청구가 바뀌므로 `order:<id>:money`도 남긴다 | 없음(새 줄은 다른 결정에 기대지 않음: 품목 추가는 `order:<id>:money`를 읽지 않는다) |
| `line:<id>:price` | 가격 직접 입력, 할인 변경 | 취소(환불 금액) |
| `order:<id>:contact` · `order:<id>:payer` · `order:<id>:price_list` | 대표자 · 연락처, 결제 팀, 요금표 | — |
| `order:<id>:money` | **돈 사실**(수납 · 환불 · 현장 수납 · 배분 옮기기), 청구가 바뀌는 명령 | 취소 · 환불 결정, 결제 팀 · 시점, 할인, 수납 창의 `받을 금액` |
| `order:<id>:checkout` | 카드 결제 요청 · 결과 · 확인 | 같은 팀의 카드 · 현금 수납 |
| `task:<id>:schedule` · `task:<id>:vehicle` | 업무 날짜 · 시각, 차량 옮기기 | 방문 결과의 재방문 부분 |
| `deposit:<id>` | 보증금 돈 사실(`보증금 입금` · `보증금 반환` · `미수 차감` · `보증금 몰수` · `몰수 취소`; `미수 차감`은 `order:<id>:money`도 남김). 보증금 명령은 보관을 id가 아니라 **(접수, 규칙)**으로 찾는다(팀 · 규칙마다 보관 하나, 8-7) | `보증금 몰수`(`deposit.keep`), 마감의 보증금 정리(미리 보기 뒤 권이 돌아왔으면 이어 붙지 않음), 반납 창의 반환할 보증금(`expect`, 온라인만 충돌) |
| `drawer:<id>:cash` | 그 돈통의 현금 사실 | 마감(예상 현금) |
| `closing:<scope>:<date>` | 마감 · 다시 열기 | 늦은 사실의 기준선 계산 |
| `registry:<table>:<id>` | 레지스트리 행 편집(행 버전과 같이) | — |

intent 명령이 오면 서버는 `SELECT 1 FROM intent_marks WHERE shop_id = ? AND conflict_key IN (바꾸는 키 + 읽은 키) AND rev > basis.rev LIMIT 1`을 보고(측정 0.001 ms), `expect`가 있으면 지금 값과 비교한다.

- 둘 다 없으면: 기기가 본 뒤로 **이 결정도, 이 결정이 기댄 값도 바뀌지 않았다.** 다른 칸이 바뀌었더라도(다른 줄의 약속, 지급) 지금 상태 위에서 그대로 적용하고 `rebased: true`와 달라진 것 한 줄(`changes`)을 돌려준다. 화면은 새로 그린 뒤 **한 줄 띠**로 보여 준다: '헬멧 1개 추가 · 합계 125,000원'
- 있으면: 진짜 충돌이다. `VERSION_CONFLICT`와 그 rev의 작업 기록(누가, 언제, 무엇으로)을 돌려준다. 돈 intent의 표시는 무엇이 바뀌었는지를 말한다: **`이 팀 120,000원 수납 완료 · 다른 카운터`**.
- 마감은 `expect`에 돈통별 예상 현금을 싣는다. 미리 보기 뒤에 현금이 하나라도 들어왔으면 마감은 이어 붙지 않고 다시 세게 한다(얼린 마감에 틀린 차액이 남지 않음).
- `basis.rev`가 `intent_marks` 보관 기간(30일)보다 오래됐으면 행 버전으로 비교하지 않고 **새로 보고 다시 하라는 충돌**을 돌려준다(투영 열 변경이 가짜 충돌을 만들거나 진짜 충돌을 놓치지 않게).

투영 열(잔액, 진행 수량)이 바뀌는 것은 충돌 키를 남기지 않는다. 돈이 바뀐 사실은 `order:<id>:money` 표시로만 남아 **돈을 보고 한 결정**만 충돌시킨다. 그래서 수납 때문에 약속 변경이 충돌하는 일은 여전히 없다.

### 4-3. 고령 직원과 기사에게 보이는 모습

- 충돌 창은 한 줄과 두 버튼이다: **`다른 기기 반납 일정 변경 · 현재 오늘 22:00 설천 주차장 · 1호 차량(카운터 2, 15:40)`** → `[유지]` `[내 선택 적용]`. 두 번째를 누르면 새 `basis`로 다시 보낸다. 몇 분 안에 다른 사람이 정한 것을 바꾸면 그 사람 기기에 `15:40 결정 반납 일정 · 카운터 1 변경`(`decision_overridden`)이 간다.
- 기술 용어(버전, 충돌, rev)는 화면에 나오지 않는다.
- fact는 충돌 창을 띄우지 않는다. `확인 필요`는 종류마다 **무게와 먼저 보일 곳**이 있다(`sys_review_kinds.routing_key`). 관리자 목록은 보일 곳과 상관없이 **열린 확인 필요를 모두** 보인다(쌓인 것):
  - `dialog_step`(막는 단계): 카드 결과 모름, 카드가 한 번 더 승인됨, 보낼 기록이 남은 기기(차량 `van_unsynced` · 카운터와 그 밖 `device_unsynced`)의 마감 — 지금 열린 결제 · 마감 창 안에서 먼저 답해야 다음으로 간다.
  - `origin_device`(일으킨 기기의 그 화면): 기사 목록 줄에 '매장 반납 완료', `수거 수량 확인`, `중복 수납 의심`, `순서 변경`, `결정 변경`.
  - `order_banner`: `초과 수납`, `분실금 확인`, `보증금 초과 반환` — 그 접수증 위 띠.
  - **연결 끊김 중 중복 처리:** 큐를 다 보낸 기기에는 그 기기의 큐 명령이 일으킨 확인 필요(`target_device_id` = 그 기기: `초과 수납` · `장비 위치 불일치` · `보증금 초과 반환` · `중복 수납 의심` · `연결 끊김 중 접수 확인`)를 모은 한 화면 `연결 끊김 중 중복 처리 N건`을 한 번 띄운다. 보일 곳이 접수증 띠인 것도 여기에 모인다: 그 팀이 차량 수거로 반납하면 카운터가 그 접수증을 다시 열 일이 없고, 손님이 아직 매장 가까이 있을 때 전화로 확인해야 하기 때문이다.
  - `manager`: 쌓인 것의 목록(관리자). 버튼 두 개(`확인`, `기사 기록 적용`)로 끝내고, 누르는 순간 서버가 불변식을 다시 확인한다(`review.resolve`도 basis를 가짐; 몇 시간 뒤 그사이 다시 빌려 간 장비를 되돌리지 않음).
- 기사 목록은 명령마다 결과를 줄에 보인다: 실선 도장(적용), '매장 반납 완료'(superseded), '확인 필요'(needs_review). 기사가 '12팀 다 받았다'고 잘못 믿지 않는다.

### 4-5. 방문 순서와 긴급 요청

- ▲ · ▼ · 맨 위로는 '이 업무를 저 업무 앞 · 뒤로'(기준 업무)로 보내고, 서버가 **지금** 순서에서 순위를 계산한다. 캐시가 오래된 기사 기기의 ▲도 엉뚱한 자리에 떨어지지 않는다.
- 경로의 첫 손 이동은 그 경로(차량 · 날짜)의 모든 업무에 순위를 한 명령으로 쓴다. 그 뒤로 새로 생긴 업무는 약속 시각으로 순위 사이에 들어간다. 같으면 (순위, 약속 시각, 업무 id). 순위 키는 BINARY로 비교한다(PostgreSQL `COLLATE "C"`).
- 같은 업무를 두 사람이 옮기면 **나중에 일어난 쪽**(고친 `occurred_at`, `decided_at`)이 이긴다. 두 시간 오프라인이던 기사의 옛 ▲가 늦게 와서 카운터의 새 순서를 덮지 않는다. 진 쪽 기기에 `방문 순서 변경됨(카운터 1, 22:05)`.
- 오프라인의 `시간순 정렬`도 같은 규칙이라 그 뒤 카운터가 정한 순서를 지우지 않는다.
- 업무 차량 변경은 같은 트랜잭션에서 `route_positions`의 차량 · 순위를 다시 쓴다.
- 긴급 요청은 멱등이다: 두 카운터가 같은 초에 누르면 둘째는 `긴급 요청 완료`. 알림 출처 키는 `pin:<고정 id>`라 나중에 같은 업무를 다시 고정할 수 있다.

## 5. 동기화(받기)

- `GET /api/v2/sync?after=<rev>.<seq>&epoch=<epoch>&limit=500` → `{ epoch, rev, seq, reset, changes: [{ rev, seq, entity, id, op, row }], more, serverTime, currentBusinessDate }`. 커서는 `(rev, seq)`라 한 rev가 500줄을 넘어도(재고 입고, 템플릿 적용, 요금표 게시) 쪽 사이에서 줄을 건너뛰지 않는다.
- 서버는 `change_log`에서 이 기기의 범위 행을 커서 뒤부터 읽고(인덱스 `(shop_id, scope_key, rev)`, 측정 0.23 ms), **지금 행**을 역할에 맞게 잘라서 보낸다.
  - `store`: 카운터 · 관리자, 전체 행. 카운터의 오프라인 사본은 그중 '오늘 일할 것'만 받는다(8-1).
  - `vehicle:<id>`: 그 차량의 업무, 업무 품목, 방문 순서, 긴급 요청, 알림, 차량 재고, 차량 지갑 잔액, 그 범위의 읽기 모델을 기기에서 다시 만드는 데 필요한 행, 그리고 **작은 접수 카드**(접수 번호, 팀 이름, 전화, 품목 요약, 미수 금액 읽기 전용 — `driver_sees_due_amount` 설정). 다른 팀의 돈 기록은 보내지 않는다.
  - `money`: 돈 권한이 있는 기기.
  - `public`: 손님 사이즈 입력폼(자기 요청만).
- **범위는 표마다 하나의 함수로 정한다**: 행의 주인 묶음(업무, 접수)에서 범위를 계산하고, 쓰기 때 **옛 범위와 새 범위 모두**에 `change_log`를 남긴다. 업무를 1호차에서 2호차로 옮기면 그 업무, 업무 품목, 방문 순서, 긴급 요청, 알림, 업무 속성, 접수 카드가 `vehicle:van-1`에는 `tombstone`, `vehicle:van-2`에는 `upsert`로 같은 rev에 들어간다. 카운터 수납이 `orders.due_amount`를 바꾸면 그 접수에 열린 업무가 있는 모든 차량 범위에 접수 카드 `upsert`가 간다. 시험: `change_log`를 범위 캐시에 다시 적용한 결과 = 범위로 직접 뽑은 결과(속성 시험).
- 속성 값(`*_attribute_values`)과 가격 내역은 주인 묶음의 행으로 함께 보낸다.
- **판이 다른 기기:** 서버는 기기가 알린 스키마 판 · 계약 판(`device_sync_cursors.schema_seen`, `devices.command_contract`)에 맞춰 sync · bootstrap에서 **그 기기가 모르는 표 · 열 · sys 키를 빼고** 보낸다(설정 행에만 있던 규칙을 모든 행으로 넓힘). 그래서 서버가 열을 더해도 옛 앱의 사본이 깨지지 않고 reset도 걸리지 않는다.
- `reset: true`: epoch가 다르거나(복구), 커서가 보관 기간(60일)보다 오래됐거나, **기기의 범위가 바뀐 경우**(휴대폰 기사가 다른 차량을 맡음, 역할 · 권한이 바뀜)뿐이다. 기기는 캐시를 버리고 `GET /api/v2/bootstrap?scope=`(오늘 일하는 데 필요한 것: 열린 접수, 오늘 업무, 레지스트리, 설정)을 받고 **보낼 줄(큐)은 그대로 둔다**.
- **카운터의 오늘 일할 사본**(8-1)은 `store` 범위를 받되, 사본 밖 묶음(오늘 일할 사본에 없는 접수: 40일 전 미수 팀 등)의 행은 버린다(그 접수가 없어 넣을 수도 없다). 그 접수를 열면 서버에서 읽고, 끊겨 있으면 `연결 후 조회 가능` 한 줄이다. 새로 사본 범위에 든 묶음(새 약속 · 새 미수)은 묶음째 받는다. 범위 속성 시험에 카운터 사본을 넣는다.
- SSE `/api/v2/stream`은 `{epoch, rev}` 알림만 보낸다. 기기는 알림을 받으면 위 요청을 한다. SSE가 끊기면 포스는 5초, 기사 기기는 10초마다 묻는다. 바뀐 것이 없으면 인덱스 한 번 보고 끝난다(옛 방식은 2초마다 4.7 MB 전체 스냅샷).
- 응답의 `serverTime`으로 기기는 시계 차이를 재고, 화면은 그것으로 '지금' 줄과 늦음을 매분 다시 그린다(ui 문서 7절). `currentBusinessDate`는 매장 시간대와 기준 시각으로 서버가 정한 영업일이다. 기기가 자기 날짜로 '오늘'을 정하지 않는다.

## 6. 멱등과 보관

- 키: `(shop_id, request_id)`. 행위자는 키가 아니라 데이터다(ULID와 정해진 시스템 요청번호는 전역으로 유일). PIN으로 바꾼 다음 사람이 같은 명령을 다시 보내도, 기사가 바뀐 휴대폰이 큐를 보내도 두 번 적용되지 않고 원래 행위자로 남는다.
- 지문: `{type, commandVersion, payload}`의 정본에서 이름 · 전화 · 자유 글을 참조로 바꾼 뒤 **매장 비밀 키의 HMAC**(소금 없는 sha256이면 010-xxxx-xxxx 1억 개를 대입해 번호를 되찾을 수 있다). basis · 시각 · 기기 번호는 넣지 않는다(다시 보낼 때 SSE 때문에 basis가 바뀌어도 같은 명령). 저장한 봉투를 **바이트 그대로** 다시 보내는 것이 원칙이다.
- 결과 상태: `applied`, `partially_applied`, `superseded`, `needs_review`, `rejected`, `blocked`, `conflict`. 모두 `command_log`에 남는다.
- `rejected` 중 **다시 해 볼 만한 것**(`retryable = 1`: 온라인 intent의 마감한 날, 잠깐 잠김, `SQLITE_BUSY`, 처리기 예외 `INTERNAL`, 기능 꺼짐)은 같은 요청번호로 다시 오면 새로 판단한다. 영구 거절(형식 오류)은 저장한 거절을 돌려준다. 권한 없음은 큐에 있던 서명된 사실이면 거절이 아니라 기록 + 확인 필요다. 큐에서 온 명령은 마감한 날이어도 기준선으로 적는다(8-12).
- **돈 사실의 부드러운 중복 확인**(둘 다 적고 `possible_duplicate_money`를 띄움; 규칙은 이것 하나이고 8-7도 이것을 쓴다):
  - 온라인: 같은 접수 · 금액 · 수단 · 행위자가 2분 안에 두 번이면 일으킨 기기에.
  - **큐에서 온 돈**(수납 · 현장 수납 · 보증금): 같은 접수에 같은 금액이거나 **합이 청구를 넘고**, 같은 끊김 구간 안이거나 같은 영업일에 **서로 다른 기기**에서 왔으면 행위자 · 수단과 상관없이 — 두 기기 모두와 관리자 목록에(`target_device_id`마다 한 줄). 추운 밤 꺼진 기사 휴대폰의 큐가 다음 날 와서 태블릿으로 다시 적은 현장 수납과 겹치는 경우도 이것이 잡는다.
  - 같은 단말 · 승인번호 · 금액 · 날짜의 카드 두 건은 `possible_duplicate_card`.
- 기사가 차량의 다른 기기로 로그인할 때, 그 차량의 다른 기기가 마지막으로 알린 뒤 소식이 없고 보낼 기록이 있다고 알렸으면 `1호 차량 휴대폰 미전송 기록 가능 · 휴대폰 전송 필요`를 보인다(다시 적어 두 번 세지 않게).
- 결과 본문(`result_json`)은 90일 뒤 비우고 행은 남긴다(작업 기록 보관 기간 동안, 그 뒤 시즌 보관 파일로). 기기 큐는 7일이 지나도 버리지 않으므로(8-5) 중복은 요청번호로 언제나 잡힌다. 본문이 빈 요청이 다시 오면 `events`에서 응답을 다시 만든다.
- 오프라인에서 만든 행의 id(ULID)를 다른 요청번호로 다른 내용과 함께 보내면 `ID_CONFLICT`.
- outbox의 멱등 키는 만든 요청에서 정해지고 업체(문자 · 카드)가 지원하면 함께 보낸다. 결과를 모르면 사람에게 보이고 자동으로 다시 보내지 않는다(9절).

## 7. 기기와 세션

- **기기 등록(중앙을 거침, 두 단계):** 관리자가 `기기 등록`에서 종류 · 이름 · 차량을 고르면 중앙 서버가 일회용 번호(15분)를 준다. 번호는 헷갈리는 글자(I · O · 0 · 1)를 뺀 12자(`K7Q4-MX29-PRT3`)이거나 그 QR이다. 해시는 매장 파일(`device_enrollment_codes`)과 control의 길 찾기 표(`enrollment_routes`, 전역 유일)에 함께 적는다: 새 기기는 앱 주소 하나에서 번호만 넣으므로 중앙이 이 표로 매장을 찾는다(두 매장에 같은 번호가 살아 있을 수 없다). 번호 넣기는 주소(IP)마다 · 전체로 시도 횟수를 제한하고 틀릴수록 늦추며 `login_attempts`(방법 `enrollment`)에 남긴다.
  - 번호를 넣어도 기기는 바로 붙지 않는다: **번호를 만든 관리 화면**에 `새 기기 등록 요청 · 윈도우 · 크롬 · 방금`이 뜨고 그 자리에서 눌러야 붙는다. 전화로 번호를 불러 줘도 멀리 있는 사람의 기기는 붙지 않는다. 번호 화면에는 `이 번호 공개 금지 · 공급자도 묻지 않음`이 있다.
  - 공급자가 관리자 콘솔에서 만든 번호(`origin_key 'supplier'`)는 사장님이 매장 관리 화면에서 허락해야 붙고, 기기 목록에 `공급자 기기`로 보인다(`devices.enrolled_by_supplier`). 붙으면 사장님 알림 칸과 공급자에게 알리고, 기기 목록에 등록한 사람과 시각을 보인다.
  - 붙을 때 중앙이 라이선스의 기기 수를 확인하고, 기기 id(ULID)와 WebCrypto 키 쌍(내보낼 수 없는 키)이 만들어지고 `devices` 행과 **기기 번호**(`short_no`, `shop_counters('device_short_no')`에서 매김 — 매장 안에서 다시 쓰지 않음, 오프라인 임시 접수 번호의 앞자리, 8-6)가 생긴다. 이때 `navigator.storage.persist()`를 요청하고, 거절되면 그 기기는 오프라인 기록을 할 수 없다고 보이고(`offline_capable = 0`, '이 기기 연결 끊김 기록 불가') 버튼을 온라인에서만 연다. 카운터 PC는 설치한 PWA라 보통 허락된다.
- **로그인(인터넷에 열린 서버):** 매장 직원의 비밀번호 로그인은 **등록된 기기에서만** 받는다(요청에 기기 키 증명). 등록 안 된 곳(집 노트북)에서는 사장님 · 관리자만, 2단계 인증과 함께 받는다. 잠금은 계정 전체가 아니라 (계정, 기기 또는 주소)마다 늘어나는 지연이라, 남이 틀린 비밀번호를 잇달아 보내 성수기 저녁에 가게 계정을 잠글 수 없다. 등록된 카운터의 PIN 잠금은 따로다. 세션 토큰은 HttpOnly · Secure · SameSite=Strict 쿠키이고 요청마다 기기 키 증명(DPoP 같은 방식)에 묶여, 토큰만 새어서는 다른 곳에서 쓸 수 없다. SSE도 같은 쿠키로 인증하고 주소에 토큰을 싣지 않는다. 민감 동작(자료 내보내기, 기기 등록 허락, 직원 추가, 고객 정보 삭제, 원격 지원 허용)은 비밀번호를 다시 묻고 `platform_audit_log`에 적고 사장님께 알린다. 옛 접근 파일의 토큰은 가져오지 않는다(전환 때 모든 기기를 다시 등록, migration 5-1).
- **라이선스:** 세션을 열 때마다 중앙이 라이선스를 확인하고 **기기 라이선스 표**(서명, `refresh_by` = 받은 때 + 14일)를 준다. 표는 운영 서버의 **기기 표 서명 키**(자주 바꿈)가 서명하고, 그 키는 오프라인에 둔 **루트 키**가 인증한다(앱에는 루트 공개 키만, deployment 5-1). 기기는 그 표로 오프라인에서도 일하고, **14일이 지나면 그 기기에서 새 접수 · 품목 추가만 멈추고, 지급 · 반납 · 수납 · 보증금 · 인쇄는 계속된다**(deployment 5-2 · 5-5 · 6-5와 같은 문장). 기기 쪽 확인은 화면 안내용이지 강제가 아니다(고친 앱은 넘을 수 있다). 그래서 서버는 **이미 일어난 오프라인 기록을 라이선스 때문에 거절하지 않는다**: 라이선스가 끝난 뒤 시각의 새 접수도 받아 적고 `licence_lapsed_record`에 올려 청구 · 연락에 쓴다(8-12). 라이선스가 막는 것은 **온라인에서 새로 시작하는 일**(새 접수 버튼, 설정, 새 기기, 새 직원)뿐이다. 시즌 1(첫 매장, 시범)에는 기기 표 · 오프라인 유예 · 기간 끝 제한의 강제를 켜지 않고 세션 때 중앙 확인과 기기 막기만 쓴다. 강제는 두 번째 매장 전에 켠다(migration 6절).
- **기사 세션:** 유휴 시간이 길다(14일, 설정). 산에서 두 시간 끊겨도 다시 로그인하지 않는다. 대신 **앱 잠금**: 휴대폰은 뒤로 갔다가 5분, 태블릿은 30분 뒤 돌아오면 PIN을 묻는다(`offline_policy.app_lock_minutes`, 기기의 확인 값이라 끊겨도 된다). 잃어버린 휴대폰의 자료는 deployment 5-4 · 10-5. 로그인 · PIN 바꾸기마다 `device_sign_ins` 한 행.
- **기기 막기(취소):** `devices.status_key = revoked`면 새 세션이 바로 끊기고, 다시 연결되면 기기 안의 사본 · 보낸 기록 · 라이선스 표를 지운다. **가르는 기준은 서버가 받은 때다**(2절): `revoked_at` 전에 도착한 그 기기의 명령은 보통 명령이다. 그 뒤에 도착한 명령은 기기가 말한 시각과 상관없이 적용하지 않고 보류(`command_log.status_key = 'held'`)해 장비 위치 · 잔액 · 돈통 예상 어디에도 넣지 않는다. 관리자 목록의 `revoked_device_record`('사용 중지 기기(…) 기록 N건 보류 · 확인 후 반영')에서 `반영`을 누르면 그때 적용하고(고장 난 줄 알았던 태블릿의 정상 기록도 이 버튼으로 살린다), `미반영`이면 기록만 남는다. 끊긴 동안 기기는 자기가 막힌 줄 모르므로, 그만둔 직원이 가져간 태블릿에서 보낸 '수거'가 장비 위치를 바꾸지 못하게 하려는 것이다.
- **카운터 PIN:** 등록된 카운터 기기에서는 직원이 4~6자리 PIN으로 바로 바뀐다(`accounts.pin_hash`: 서버 비밀(pepper)의 HMAC 위에 느린 해시, 5번 틀리면 잠금). 고령 직원이 긴 비밀번호를 치지 않아도 된다. PIN은 **사람을 편하게 바꾸는 장치이지 강한 잠금이 아니다**: 기록은 기기 기준이고 PIN은 그 기기에서 누가 했는지를 적는다. 바뀌기 전에 보낸 명령의 재시도는 원래 사람의 것이다(6절).
  - **끊긴 동안:** 그 매장의 **카운터 역할 직원 모두**의 PIN 확인 값(기기마다 다른 소금, 느린 해시, 기기 키로 암호화)을 매장의 모든 카운터 기기에 동기화해 둔다: 평소 카운터 1에서만 일하던 직원이 줄이 길어 카운터 2로 옮겨도 자기 이름으로 일한다. 기사 기기에는 그 차량 기사의 것만 둔다. **관리 권한(설정 · 직원 · 기기 · 마감 넘기기 · 다시 열기 · 한도 넘는 할인 승인)을 가진 역할(사장님 · 관리자)의 확인 값은 기기에 두지 않는다**: 끊긴 동안 그 사람은 PIN으로 들어오지 못하고(이미 로그인해 있으면 카운터 권한으로만 계속), 그런 승인은 원래 연결이 필요한 일이며 온라인에서 PIN이 아니라 **비밀번호나 휴대폰 확인**으로 받는다. 켜진 PC의 확인 값을 풀어 PIN을 알아내도 돈 통제를 풀 수 없게 하려는 것이다.
  - 계정 정지 · PIN 변경 · 역할 변경은 다음 동기화에서 기기의 확인 값을 바로 지운다. 바꾼 사실은 `device.sign_in`(오프라인 허용)으로 쌓였다가 연결되면 `device_sign_ins`가 된다. 서버는 늦게 온 `device.sign_in`을 **그 확인 값이 그 기기에 내려간 적이 있고, `occurred_at` 전에 정지 · PIN 변경 · 역할 변경이 없었을 때만** 보통 로그인으로 받는다. 아니면 그 로그인과 그 뒤 명령을 적되 `unverified_sign_in`('미확인 로그인')에 올린다. 끊긴 동안 나간 현금(보증금 돌려드림, 보증금 더 돌려드림)은 마감 미리 보기에 `연결 끊김 중 현금 출금 · 담당자`로 따로 보이고 관리자 확인을 받는다(data-model 4-13). 중앙의 `pin_hash`는 기기로 보내지 않는다(deployment 5-6).
- **권한 확인:** 모든 명령에서 권한 + 범위 + 한도(할인 금액)를 본다. 기사의 `own_vehicle` 범위는 **일이 일어난 시각**의 업무 배정(`task_reassignments` 역사)으로 본다. 한도를 넘는 할인은 관리자가 **비밀번호나 휴대폰 확인**으로 승인해 그 관리자를 승인자로 기록한다(PIN이 아님).

## 8. 오프라인(기사 기기와 카운터)

클라우드 중심(ADR-19)에서는 모든 기기가 인터넷으로 중앙 서버에 붙는다. 가게 인터넷이 끊기거나, 산에서 휴대폰 망이 끊기거나, 우리 서버가 멈추면 기기는 **자기 안의 사본과 보냄 대기**로 일한다. 처음에는 기사 기기를 위해 설계했고(8-1 ~ 8-5), 같은 코드를 카운터도 쓴다(8-6 ~ 8-11). 도착한 큐 명령을 서버가 어떻게 적는지는 8-12다. 기기끼리는 직접 이야기하지 않으므로 끊긴 동안 카운터 1과 카운터 2도 서로의 기록을 보지 못한다(8-7). 예외는 같은 카운터 PC의 인쇄 · 카드 도우미로, 그 PC의 앱과 `localhost`로 이야기한다(인쇄 · 돈통 열기 · 보냄 대기 한 벌, 8-5 · 9절). 가게 LAN으로 두 카운터를 잇는 중계는 시즌 1에 만들지 않는다(deployment 1-2).

### 8-1. 기기에 두는 것과 그리는 법

- **범위 자료:** 자기 범위의 행을 SQLite WASM(OPFS)에 받아 둔다. 서버와 **같은 `packages/store` · `packages/domain`**을 기기의 Web Worker에서 돌려 수거 목록 · 배달 목록 · 도장 · 남은 수 · 차량 재고를 **같은 읽기 모델 코드로** 만든다(LocalClient와 같은 길, 스키마는 그 범위의 표만). 앱을 오프라인에서 껐다 켜도 목록이 그려진다.
- **카운터의 오늘 일할 사본**(`store` 범위의 일부, 부트스트랩이 고름, 5절): 레지스트리 · 설정 · 화면 설정 · 사용 기능 전부(작다), 오늘부터 이레 안에 효력이 있는 게시된 요금표 판, 직원(이름 · 역할 · 권한)과 기기 이름, **카운터 역할 직원의 PIN 확인 값**(7절), 돈통, 그리고 접수는 **열린 접수 전부 + 오늘 · 내일 · 모레(`offline_policy.counter_days_ahead` 2) 약속이 있는 접수 + 최근 30일(`counter_due_lookback_days`)의 미수가 남은 접수**와 그 줄 · 약속 · 수납 · 배분 · 보증금 · 차량 업무(읽기만) · 매장에 있는 장비와 그 팀이 가진 장비, **매장의 권 재고(예비권)와 권 공용 창의 배정 claim**(권 지급, 8-2). 지난 기록 · 작업 기록 · 다른 날 마감은 두지 않는다. 한 매장 성수기 하루에 수 MB다.
- **온라인과 오프라인 사이:** 카운터는 **연결되어 있으면 서버가 만든 읽기 모델**을 그리고(`HttpClient`, 지난 기록 · 보고서까지), 요청이 **연속 두 번**(`offline_policy.fallback_after_failures`) 3초 안에 답을 못 받거나 연결이 끊기면 같은 화면을 **기기의 사본에서 같은 코드로** 그린다(`LocalClient`). 돌아올 때는 **10초 동안**(`fallback_recover_seconds`) 답이 잘 올 때 돌아온다: 서버가 느릴 뿐인 토요일에 3초마다 온라인 · 오프라인이 뒤집혀 버튼이 켜졌다 꺼졌다 하지 않게. 두 길이 같은 코드라 화면이 바뀌지 않는다. 사본은 SSE 알림과 동기화로 늘 따라온다.
- **답을 잃은 명령('결과 확인 중'):** 한 번이라도 보낸 명령은 요청번호를 놓지 않는다. 보내지 못한 것(연결이 없었음)과 **보냈는데 답을 잃은 것**(서버에서는 적용됐을 수 있음)을 가른다. 오프라인 허용 명령은 같은 요청번호 · 같은 봉투로 큐에 들어간다(서버에서 이미 적용됐으면 멱등으로 처음 결과가 돌아옴). 온라인 전용 명령(환불 · 일정 변경 …)은 창에 `연결 끊김 · 결과 확인 중`을 띄우고 **새 요청을 막은 채**, 연결되면 같은 봉투를 다시 보내 결과를 받는다. 그래서 직원이 종이에 적었다가 새 요청번호로 다시 해 환불이 두 건이 되거나, 자기 약속 변경과 부딪혀 `다른 기기 반납 일정 변경 · …` 창이 뜨지 않는다(ui 7절 실패의 약속).
- **보냄 대기 겹치기:** 큐의 명령을 같은 native 처리기로 savepoint 안에서 적용해 읽기 모델을 만들고 되돌린다. 화면에 따로 계산하는 코드가 없다. **사본에 이미 그 요청번호의 행이 있는 큐 명령**(동기화가 서버의 결과를 가져온 것: 수납 · 접수 · 이동 행은 `request_id`를 가짐)은 건너뛴다: 큐 150건을 보내는 동안(`전송 중 · 잔여 12`) 접수증에 두 번 받은 것처럼 보이거나 같은 id 때문에 겹치기가 깨지지 않게. **사실 어댑터 명령**(지급 · 반납 · 적재 · 수거 · 배달, `engine_key 'adapter'`)은 어댑터의 **native 앞 단계**(장비마다 적용할 수 있는지 판단 + 이동 행 만들기)로 겹친다: 옛 처리기(`@skinote/core`)는 기기에 없다. 서버의 어댑터도 같은 앞 단계가 만든 행을 옛 `move()`의 결과와 견주고, 다르면 `integrity_findings`에 적는다(migration 3-2). 대기 중인 도장은 점선이고, 바닥줄 숫자는 대기를 따로 센다: **'완료 4 · 전송 대기 8 · 잔여 3'**(끝난 것처럼 보이지 않고, 남은 수도 틀리지 않음).
- 시험: 같은 자료로 서버의 `driverList`와 기기의 `driverList`가 똑같아야 하고, S6을 오프라인 중 앱 다시 시작까지 넣어 돌린다. 어댑터 명령은 기기의 앞 단계 결과와 서버의 어댑터 결과가 같아야 한다(6주차).
- IndexedDB `queue`: 보낼 명령(요청번호, 기기 번호, 만든 뒤 지난 시간, 서명된 행위자, basis, dependsOn, 본문, 상태: 대기 · 보내는 중 · 결과 확인 중 · 적용 · 이미 됨 · 확인 필요 · 거절 · 멈춤).
- IndexedDB `sent`: 서버가 받았다고 답한 명령, 그 rev, **서버가 정한 값(`canonical`)**, 7일 보관(복구 때 다시 보냄, 10절). 이름 · 전화 · 자유 글 원문은 서버가 받았다고 답한 뒤 24시간(`offline_policy.sent_pii_hours`)만 두고, 그 뒤는 참조로 바꾼 모양만 둔다(서버 쪽 RPO는 몇 초라 그보다 오래 둘 까닭이 없다).
- 모두 등록 때 만든 내보낼 수 없는 기기 키로 암호화한다. 옛 방식의 "한 칸짜리 저장, 그게 풀릴 때까지 다음 일 못 함"은 없어진다. 오늘 일할 사본(OPFS의 SQLite)을 암호화 빌드로 둘 수 있는지는 1주차에 확인한다(deployment 10-1). 암호화해도 켜진 브라우저는 키를 쓸 수 있으므로, 잃어버린 기기를 위해 아래 스스로 지우기와 앱 잠금(7절)이 따로 있다.
- **스스로 지우기:** 마지막으로 서버와 맞춘 뒤 기사 기기는 24시간, 카운터는 72시간(`offline_policy.pii_wipe_hours`)이 지나면 사본의 이름 · 전화 · 메모를 지우고 끝 4자리만 남긴다(큐의 사실은 그대로 보낸다). 끝난 업무의 작은 접수 카드는 그날 기준 시각(06:00)에 기기에서 지운다. 기사 목록 줄에는 번호를 적지 않고 `전화` 버튼으로 걸며, 끊긴 산에서도 걸 수 있게 오늘 열린 업무의 번호만 사본에 둔다(deployment 10-5).
- 오프라인 상태는 머리줄이 아니라 **자기 띠**('연결 끊김 · 전송 대기 3 · 마지막 연결 21:40')로 보이고, 목록 높이 계산에 들어간다(ui 문서 6-3). 카운터도 같은 띠다(8-9).

### 8-2. 오프라인에서 할 수 있는 일(기기 종류마다)

기기 종류마다 **`sys_offline_commands`에 행이 있는 명령만** 보냄 대기에 쌓는다(2026-09-24, ADR-19). 행마다 기기가 쌓기 전에 확인하는 제한(`limit_key` → `sys_offline_limits`)이 있을 수 있다. `sys_event_types.offline_allowed = 1`은 그 합(어느 기기든 쌓을 수 있음)이고 시험이 둘을 맞춘다. 뒤 마이그레이션이 오프라인 허용을 넓힐 때는 새 행과 함께 두 표시를 0 → 1로만 올린다(lint가 그 UPDATE만 허락, data-model 7-2). 물건이 움직이는 명령은 `sys_movement_routes.offline_allowed = 1`인 경로만이다(카운터의 지급 매장 → 손님, 매장 반납 손님 → 매장, 적재 매장 → 차량과 차량 경로). 모두 native이거나 사실 어댑터 뒤의 옛 처리기(`adapter`)다.

- **왜 이 선:** 끊긴 동안 되는 것은 **이미 일어난 사실**(물건이 손을 옮김: 지급 · 반납 · 적재 · 권 지급 · 즉시 교환, 돈이 오감)과 **새 묶음을 만드는 일**(새 접수 · 새 품목 줄: 새 id라 다른 사람의 결정과 부딪히지 않음)뿐이다. 기존 약속 · 청구 · 날을 바꾸는 결정은 다른 카운터나 기사가 그 결정에 기대고 있을 수 있어서 곧바로 닿아야 한다. 기사가 받으러 갈 약속을 카운터가 끊긴 채 바꾸면 기사는 모른 채 엉뚱한 곳에 간다. 끊긴 채 쌓인 명령은 도착해서 돌려보내지 않는다(8-12): 손님은 이미 장비 · 권을 들고 갔고 돈은 돈통에 있다.
- **권 지급(끊긴 카운터):** 권 줄의 도장 단계는 평소 `발권(배정) → 지급`이고 배정(`ticket.allocate`)은 결정이라 연결이 필요하다. 끊긴 카운터에서는 권 줄의 지급 칸이 `권 지급 처리`(`stamp.ticket_hand_out`)가 되어 **매장 권 재고에서 번호를 골라** 배정 claim(권 공용 창)과 지급 이동을 한 명령으로 적는다(차량의 `field.add_ticket`과 같은 모양). 사본의 권 공용 창으로 사용 창이 겹치는 번호는 고를 수 없다. 서버에서 그 번호가 그사이 다른 곳에 배정됐으면 이동은 적고 부딪힌 배정을 `displaced_by_fact`로, 다른 손님 손에 있으면 `asset_elsewhere`(8-3). 그래서 보증금 장부의 매수 줄, 반납 창의 번호 버튼, 발권처 환불이 번호 단위로 맞는다.
- **즉시 교환:** 지급 뒤 30분 안에 '부츠가 꽉 낀다'며 돌아오는 손님이 가장 흔하다. 끊긴 카운터의 교환 버튼은 `즉시 교환` 창(돌려받는 번호 · 주는 번호 또는 규격 · 수량)을 열고 한 명령으로 적는다: 서버에서는 교환(`exchanges`, 방법 매장) 하나와 반납 · 지급 이동(손에 든 것을 본 기록 `skipped_hop`)이다. 값은 바뀌지 않는다(값이 다르면 연결 뒤 `price_correction`). 이것을 만들기 전(6주차 밀리는 순서)에는 교환 버튼이 `교환 불가 · 연결 끊김 · 종이 접수증에 기록`을 보인다.
- **돈은 막지 않는다.** 손님이 돈을 내면 끊겨도 적는다. 받은 쪽이 그사이 바뀌었으면 연결된 뒤 확인 필요로 보인다(8-7).
- **현금영수증:** 끊긴 동안 현금 손님이 요청하면, 카드 단말기가 현금영수증을 낼 수 있는 매장은 단말기에서 내고 수납 창에 승인번호를 적는다(`payment.take` 본문 `cashReceipt`: 승인번호 · 번호 종류, 번호 자체는 개인정보라 `event_pii`). 스키노트가 내는 매장은 수납 본문에 `cashReceiptRequested`(번호 종류 · 번호는 `event_pii`)를 싣고, 연결된 뒤 서버가 발행을 이어 간다(outbox, 결과는 `tax_document.issue`). 어느 쪽이든 잊히지 않는다.
- 카운터에서 연결을 기다리는 버튼은 **자리 그대로 두고**(줄이 흔들리지 않게), 누르면 한 줄과 `닫기`가 뜬다: `일정 변경 불가 · 연결 끊김 · 종이 접수증에 기록` · `마감 · 연결 후 가능`. 기사 화면은 시즌 1처럼 카운터가 정하는 일의 버튼이 없다.

권 추가 · 오프라인 새 접수 · 품목 추가의 가격은 기기가 가진 요금표 판으로 계산해 `price_list_version_id` · 견적 금액 · `quote_hash`를 함께 보낸다. 서버는 그 판이 `occurred_at`에 효력이 있던 게시 판이면 그 값을 그대로 받고(`price_source_key 'offline_quote'`), 아니면 기기 값으로 적고 `확인 필요`를 올린다. 조용히 다시 계산하지 않는다(받은 돈과 청구가 어긋나지 않게, 8-12).

### 8-3. 다시 연결되면

`POST /api/v2/commands:batch`로 기기 번호 순서대로(한 번에 50개까지) 보낸다. 서버는 **하나씩 각자의 트랜잭션**으로 적용하고 결과를 하나씩 돌려준다. 처리기가 예외로 끝나거나 `SQLITE_BUSY`면 되돌린 뒤 `rejected · retryable · INTERNAL`을 따로 적어 그 기기 번호가 비어 남지 않게 한다. 큐에서 온 명령은 앞선 명령이 끝내 적용되지 못해도 **멈추지 않고** 적용 + 확인 필요다(8-12). 온라인 명령만 돈이 아니면 `blocked`이고, 돈(`is_money`)은 멈추지 않는다.

카운터의 늦은 사실도 같은 규칙과 아래 표로 판단한다(두 카운터가 함께 끊긴 경우는 8-7).

**여러 기기가 함께 다시 붙을 때:** 같은 매장의 여러 기기가 겹치는 끊김 뒤에 다시 붙으면(가게 인터넷, 우리 서버 멈춤) 서버는 짧은 창(`offline_policy.reconnect_window_seconds`, 2분, 복구의 다시 받는 창과 같은 방식) 동안 그 기기들의 **재고 사실**을 모아 `occurred_at` 순서로 적용한다. 그래서 카운터 1의 16:10 반납과 카운터 2의 16:25 다시 빌려줌이 어느 카운터가 먼저 보냈는지와 상관없이 같은 결과가 된다. 창이 지난 뒤에 온 사실은 도착 순서로 적용하고, **이동이 적용될 때마다 그 장비에 열린 `asset_elsewhere` · `needs_review` 재고 사실이 있으면 다시 판단한다**: 더 이른 반납이 늦게 와서 앞뒤가 맞게 되면(그 장비에 그보다 뒤의 이동이 없을 때) 보류했던 지급을 적용해 지금 위치를 옮기고 확인 필요를 닫는다.

순서의 기준: 차량 범위 확인은 `occurred_at`의 업무 배정으로, 장비의 '지금 위치'는 적용 순서(`created_rev`)로 본다. 이미 더 뒤의 이동이 적용된 장비에 그보다 먼저 일어난 이동이 늦게 오면, 그 이동은 **역사로만** 적고(`late_fact = 1`) 지금 위치를 옮기지 않는다.

| 현장 수납 35,000원 | 돈은 거절하지 않음 | 적용. 그사이 카운터에서 받았으면 과수납으로 보이고 `확인 필요`('초과 수납') |
| 현장 수납인데 그날 마감됨 | 마감한 날 | 적용, `business_date` = 받은 날, `posting_date` = 기준선, `확인 필요`('마감 후 수납'), 다음 마감 인계에 `late_entry` |
| 현장 보증금 반환인데 그 권은 이미 매장에서 받았고 보관이 모자람 | 돈은 거절하지 않음 | 맡은 만큼은 보증금에서(`deposit_out`), 넘친 돈은 **그 차량 지갑의 현금 출금**(현금 입출금, 사유 `보증금 초과 반환`)과 `deposit_over_returned`(`{drawer}` = 1호 차량 지갑). 수거 이동은 `superseded`. 8-7과 같은 규칙이라 보관 금액이 0 아래로 가지 않는다 |
| 권 추가인데 차에 그 권이 없음 | 권을 줄 수 없음 | 권 줄 · 이동은 `needs_review`, dependsOn한 현장 수납은 **돈이라서 그대로 기록** — 배분할 줄이 없으므로 접수 전체 배분(`allocation_fallback`)으로 |
| 방문 결과(고객 부재, `재방문 내일`)인데 그사이 카운터가 일정을 바꿈 | 관찰은 사실, 일정은 결정 | 방문 결과 적용, 일정은 덮지 않고 `확인 필요` |
| 방문 결과(고객 부재)인데 업무가 이미 끝남 | 사실은 기록 | 적용 + `확인 필요`('취소된 업무') |
| 끊긴 카운터의 새 접수 · 품목 추가 | 적어 두는 사실 | 8-12 |
| 순서 변경 | 순서만 | 4-5의 규칙(기준 업무, 나중에 일어난 쪽) |

같은 요청번호는 한 번만 적용되고, 모든 장비 이동은 장비의 지금 위치와 마지막 이동을, 모든 돈은 id와 배분 규칙을 확인하므로 **두 번 세는 일이 없다.** 시험: 오프라인 허용 돈 명령은 모든 dependsOn이 실패해도 `payments` 행을 남긴다. 큐의 돈 사실은 `expect`가 옛 값이어도 `payments` 행을 남긴다(수납 · 보증금 돌려드림 · 여러 팀 수납, 8-12). 반납 → 다른 카운터에서 다시 지급을 **도착 순서 두 가지**로 넣어도 결과가 같다.

### 8-5. 큐를 잃지 않는 규칙

- 큐의 사실은 **나이 때문에 버리지 않는다.** 7일이 지난 것은 관리자에게 알리고 보낸다.
- 두 판 넘게 서버가 올라가도 오프라인 허용 명령의 모양은 upcaster로 받는다(그 명령들의 모양은 되도록 바꾸지 않는다).
- 서버는 기기 번호의 빈 곳으로 잃어버린 명령을 찾는다(2절). iPhone PWA처럼 저장소가 지워질 수 있는 기기는 등록 때 `persist()`가 거절되면 오프라인 기록을 끈다.
- **브라우저 자료가 지워질 때:** `persist()`는 저장 공간이 모자랄 때 지워지는 것만 막고, 직원이 Chrome '인터넷 사용 기록 삭제(쿠키 및 사이트 데이터)'를 누르거나 청소 프로그램 · PC 다시 설치로 지우는 것은 막지 못한다. 그러면 큐 · `sent` · 기기 키 · 임시 번호 순번이 함께 사라지고, 서버가 모르는 기기 번호(끊긴 동안 만든 것)는 빈 번호 찾기에도 걸리지 않는다. 그래서 카운터에서는:
  - 카운터 PC에 이미 있는 **인쇄 도우미**(설치 프로그램, 기기)가 앱의 큐를 `localhost`로 받아 **암호화한 추가 전용 파일**에 한 벌 더 둔다(앱의 기기 키로 서명된 봉투 그대로). 기기를 다시 등록하면 그 파일에서 큐를 되살려 보낸다: 서명은 옛 기기 키 그대로이고, 옛 기기가 막히지 않았으면 보통 큐 명령으로 받는다.
  - 카운터 PC에는 Chrome 관리 정책으로 이 앱 원본의 사이트 자료 지우기를 막는다(설치 목록, deployment 11절).
  - 끊긴 동안 보냄 대기가 있으면 연결 띠에 `전송 대기 · 전원 유지`를 함께 보인다(8-9).
  - 그래서 '가게 인터넷이 끊기면 잃는 것이 없다'(README D4)는 **기기 안의 기록이 지워지지 않는 한**이다. 도우미의 한 벌이 그 틈을 줄인다.

### 8-6. 카운터의 새 접수와 임시 접수 번호

- 끊긴 카운터에서 새 현장 접수를 확정하면 기기가 **임시 접수 번호**를 매긴다: `기기 번호-순번`(`devices.short_no`와 그 기기가 늘 올리기만 하는 순번). 화면과 종이 접수증에는 `임시 접수 번호 1-12`로 적는다(영어 글자 없음). 순번은 IndexedDB에 먼저 적고(도우미에도 한 벌, 8-5) 나서 인쇄하므로 두 번 쓰이지 않고, 기기 번호는 `shop_counters('device_short_no')`에서 매겨 매장 안에서 다시 쓰지 않으므로(되살리기도 +10 건너뜀, 10-2) **두 카운터 · 두 날 사이에서도 겹치지 않는다**(`orders_provisional_receipt` 유일 인덱스).
- 확정 창 · 명령은 온라인과 같다(`order.create` 하나에 약속 · 결제 약속 · 칸별 수납 · 보증금). 제한은 8-2의 `walk_in_cached_quote`: 현장 접수만, 기기에 있는 게시 판의 값(`offline_quote`), 미리 정한 할인만, 결제 팀은 이 팀이나 후불만. 전화 예약 · 다른 팀 결제 · 가격 직접 입력은 연결된 뒤에 한다.
- **최종 번호가 되는 때:** 연결되면 보냄 대기가 기기 순서대로 가고, 서버가 그 `order.create`를 적용하는 순간 그 영업일의 다음 접수 번호(`261226-031`)를 준다. 임시 번호는 `orders.provisional_receipt_no`에 그대로 남는다. 서버가 정한 값(`canonical`: 접수 id, 최종 번호)이 돌아오면 기기는 화면의 `임시 1-12`를 `261226-031`로 바꾸고 작은 이름표 `임시 1-12`를 남긴다. 최종 번호는 도착 순서라 시각 순서와 다를 수 있다(장부는 시각으로 줄 세우므로 상관없다).
- **종이 접수증은 다시 뽑지 않아도 된다.** 끝 4자리 찾기와 `임시 1-12`로 찾기가 모두 그 팀을 연다. 접수증을 다시 뽑으면 `접수 번호 261226-031 · 임시 1-12`.
- 같은 팀의 수납 · 보증금 · 지급은 그 접수 id를 가리키는 명령으로 이어서 쌓인다(`dependsOn`). 도착한 새 접수 · 품목 추가는 **적어 두는 사실**이다(8-12): 끊긴 동안 서버를 되살려 epoch가 바뀌었든, 그날 마감됐든, 라이선스가 끝났든, 권한 · 견적이 어긋났든 접수와 줄은 늘 적고 어긋난 판단만 확인 필요로 올린다. 그래도 적용할 수 없으면(앱의 버그로 형식이 틀림 등) 서버가 저장된 봉투에서 **최소 접수**(임시 번호 · 대표자 · 줄)를 만들고 `offline_order_unapplied`를 올린다. 그래서 돈 · 보증금 · 지급이 붙을 곳이 늘 있다(`payments`의 배분 · `deposits.order_id`의 FK가 걸리지 않음). 형식 오류는 앱이 다시 보내는 것이 아니라 서버의 upcaster · 고침 길로 처리한다(같은 요청번호에 다른 지문이면 `idempotencyMismatch`로 막히기 때문이다).
- 복구와 상관없다: 임시 번호는 기기가 매기고, 최종 번호는 복구 때 +500 건너뛴다(10-2).

### 8-7. 두 카운터가 함께 끊겼을 때

가게 인터넷이 끊기면 두 카운터가 함께 오프라인이 되고 **서로의 기록을 보지 못한다**(기기끼리 직접 잇지 않음). 연결되면 서버가 아래처럼 맞춘다. 사실은 거절하지 않고, 두 번 세지 않는다. 겹침은 연결된 뒤 그 기기에 `연결 끊김 중 중복 처리 N건` 한 화면으로 모여 보인다(4-3).

| 끊긴 동안 | 연결된 뒤 서버 | 화면 |
|---|---|---|
| 두 카운터가 같은 팀의 돈을 받음(카운터 1 현금 120,000, 카운터 2 카드 120,000; 직원 · 수단이 달라도) | 둘 다 적는다. 그 팀은 더 받은 돈이 생긴다 | 접수증 띠 `초과 수납`(`overpaid`)과 `중복 수납 의심`(`possible_duplicate_money`, 6절의 큐 규칙: 같은 접수에 같은 금액이거나 합이 청구를 넘고 같은 끊김 구간이면 행위자 · 수단과 상관없이, 두 기기와 관리자 목록에) |
| 한 카운터는 반납, 다른 카운터는 그 장비를 다른 팀에 다시 지급 | 재고 사실을 일어난 순서로 적용한다(8-3의 다시 붙는 창과 다시 판단). 반납 → 지급 순서라 둘 다 이동이 된다 | 없음. 반납이 창 밖에 늦게 오면 그사이 지급은 `asset_elsewhere`였다가 반납이 오는 순간 저절로 적용되고 확인 필요가 닫힌다 |
| 같은 장비(스키 17번)를 두 팀에 지급(한쪽은 실제로 없는 것을 적음) | 일어난 순서로 먼저 적용되는 쪽이 이동. 둘째는 이동 없이 `asset_elsewhere` | 둘째 카운터의 그 줄에 `장비 위치 불일치`('스키 17번 기록상 위치 김민수 팀 · …')와 풀이 `17번 이 팀 보유 확인`(누르면 `skipped_hop` 지급) |
| 같은 팀 같은 장비를 두 카운터에서 반납 | 둘째는 `superseded` | 둘째 카운터 줄에 '반납 완료' |
| 같은 팀의 권을 나눠 두 카운터에 돌려줌 | 끊긴 반납 창은 보증금이 걸린 번호를 처음에 고르지 않으므로(아래) 누른 매수만 돌려드린다 | 없음 |
| 같은 권의 보증금을 두 카운터가 돌려드림(그래도 겹침) | 맡은 만큼은 보증금에서, 넘친 돈은 **그 돈통**에서 나간 현금(현금 입출금, 사유 `보증금 초과 반환`)으로 적는다: 돈통 셈이 맞게, 보관 금액은 0 아래로 가지 않음 | 접수증 띠 `보증금 초과 반환`(`deposit_over_returned`, `{drawer}` = 그 돈통)을 두 기기와 관리자 목록에. 손님께 받을지는 사람이 정한다 |
| 같은 팀 보증금을 두 카운터가 따로 받음(여섯 가족이 두 카운터로 나뉘어 권을 받음) | 보증금 명령은 보관을 (접수, 규칙)으로 찾는다: 둘째가 제안한 보관 id는 첫째 보관에 이어 붙이고(매수 줄 둘), 그 대응을 `canonical`로 돌려주며 같은 기기의 뒤 명령(돌려드림)의 제안 id도 바꿔 읽는다 | 없음. 보관 하나에 매수 줄 둘 |
| 각자 새 접수 | 각자 임시 번호(`임시 1-12`, `임시 2-03`), 도착 순서로 최종 번호 | 없음 |
| 한 카운터는 반납 처리, 다른 카운터는 같은 팀에 품목 추가 | 둘 다 적용(새 줄은 새 차수) | 없음 |
| 한 카운터만 끊김, 다른 카운터는 그사이 그 팀 약속을 바꿈 | 반납 사실은 적고 약속은 온라인 쪽이 정한 대로(8-3 표) | 끊겼던 카운터에 확인 필요가 있으면 그 화면에 |

- **끊긴 반납 창은 보증금이 걸린 번호를 처음에 고르지 않는다**(ui 6-2): 반납 창 V1은 처음에 이 팀이 가진 것을 모두 골라 두는데, 끊긴 카운터에서는 그 '전부'가 옛 사본의 보유라 다른 카운터에서 이미 돌아온 권까지 골라진다. 그래서 LocalClient가 창을 그릴 때(또는 그 접수의 사본이 마지막 연결 뒤 다른 기기에서 바뀌었을 수 있을 때) 보증금이 걸린 번호(권)는 고르지 않은 채 열고, 회색 표시를 `연결 끊김 · 다른 카운터 반납 가능 · 실물 번호만 선택`으로 바꾸며, 보증금 줄은 **누른 번호 수만큼만** 셈한다. 장비는 전처럼 모두 골라 둔다(이미 돌아온 장비를 다시 골라도 `superseded`로 끝나 돈이 나가지 않는다). 기사 휴대폰의 수거 창도 끊긴 동안은 권 보증금 줄을 누른 권 수로만 센다(ui 6-5).
- 수납 창은 끊긴 동안 한 줄을 더 보인다: `연결 끊김 · 다른 카운터 수납 미표시 · 손님께 확인`(카운터 기기가 둘 이상인 매장만).
- **끝 4자리 찾기가 빈 결과이면**(다른 카운터에서 끊긴 채 받은 손님은 이 카운터 사본에 없다): `연결 끊김 중 다른 카운터 접수 가능 · 임시 번호 앞자리 = 접수 카운터`. 고령 직원이 새 접수를 또 만들어 한 가족에 접수 · 보증금 보관이 둘 생기지 않게.
- **운영 규칙(끊김이 길 때):** 끊긴 동안 **한 팀은 처음 받은 카운터에서**, **돈과 보증금은 카운터 한 곳에서** 받기를 권한다(운영 규칙으로 둘지는 README 열린 질문 27). 두 번 받기 · 두 번 지급 · 보증금 초과 반환은 모두 두 카운터가 같은 LAN에 있는데도 서로 모른다는 데서 나온다. 가게 LAN으로 두 카운터의 큐를 서로 보여 주는 중계(도우미가 읽기 전용으로)는 시즌 뒤에 본다(deployment 1-2). 시즌 1은 예비 회선 자동 넘어가기로 끊김 자체를 줄인다(deployment 11절, migration 6-1 G2).

### 8-9. 고령 직원에게 보이는 모습(카운터)

- **연결 띠**(32px, 머리줄 아래): 왼쪽 `연결 끊김 · 전송 대기 3 · 마지막 연결 15:40`, 오른쪽 `사용 가능 · 지급 · 반납 · 수납 · 새 접수`(권 지급을 만들기 전에는 `사용 가능 · 장비 지급 · 반납 · 수납 · 새 접수`). 전송 대기가 있으면 한 줄 더 `전송 대기 · 전원 유지`(8-5). 다시 이어지면 `전송 중 · 잔여 12`, 다 보내면 띠가 사라진다. 기술 말(서버, 동기화)을 쓰지 않는다. 빨강이 아니다.
- **띠 자리는 늘 비워 둔다**(채택한 둘째 판 시안 V7의 규칙을 카운터에도, ui 4-3): 장부의 줄 수는 띠가 떠 있을 때의 높이로 정하고, 연결되어 있을 때 남는 32px는 줄이 나눠 쓴다(줄이 조금 커짐). 그래서 띠가 뜨고 사라져도 한 쪽의 줄 수와 줄 자리가 바뀌지 않는다(1024×600 한 쪽 6줄, 1024×529 5줄). 띠는 8-1의 넘기기 지연(연속 두 번 실패, 10초 안정)을 따라 깜빡이지 않는다.
- 끊긴 동안 찍은 도장은 **점선 도장**(`전송 대기`), 서버가 적용하면 실선이 된다. 접수증 머리의 번호 자리는 `임시 접수 번호 1-12`.
- 연결을 기다리는 버튼은 자리 그대로이고, 누르면 한 줄 표시 + `닫기`(8-2). 돈 · 반납 버튼은 늘 된다.
- 연결된 뒤 확인할 것이 생기면 `연결 끊김 중 중복 처리 N건` 한 화면이 한 번 뜨고(4-3), 그 뒤로는 머리줄 알림 칸의 `확인 필요 2`와 그 접수증 띠로 보인다.

### 8-10. 카드 단말기

- 카드 단말기는 **자기 회선**(유선 · LTE)으로 카드사와 이야기하므로 우리 서버 · 가게 인터넷과 상관없이 승인된다. 이 매장은 단말 연동(`card_terminal` 기능)을 쓰지 않으므로 직원이 단말기에서 승인한 뒤 포스에 `카드`와 금액(원하면 승인번호 8자리)을 적는다. 끊긴 동안도 똑같다(`payment.take`, 오프라인 허용 사실). 현금영수증은 8-2.
- 연동을 켠 매장: 카드 결제 요청(`payment.intent_request`)은 결정이라 연결이 필요하다. 끊기면 단말기를 따로 써서 승인하고 위처럼 포스에 적는다. 카드 도우미가 단말과 직접 이야기하는 매장은 도우미의 승인 기록이 연결된 뒤 알려진다(9절).
- 날마다 단말기 · 카드사(VAN) 정산과 수납을 승인번호 · 금액 · 시각으로 맞춘다(9절). 오프라인에서 적은 카드가 빠지거나 두 번 적혔으면 여기서 드러난다.
- 단말기 자체의 회선이 끊기면 그것은 카드사 쪽 일이다: 현금이나 계좌이체로 받는다.

### 8-12. 큐에서 온 명령은 적어 두는 사실

끊긴 기기가 쌓은 명령은 이미 일어난 일이다: 손님은 장비와 권을 들고 갔고, 돈은 돈통에 있고, 종이 접수증이 찍혔다. 그래서 **큐에서 온 명령**(그 기기 종류의 오프라인 목록 `sys_offline_commands`에 있고 기기가 서명한 봉투)은 등급(`class_key`)과 상관없이 **적어 두는 사실**로 다룬다.

- **건너뛰는 것:** epoch(끊긴 동안 서버를 되살려도), basis와 충돌 키(`intent_marks`), 30일 규칙, `expect`의 비교, 마감한 날(기준선의 `posting_date`로 적고 `late_entry`), dependsOn의 실패(앞 명령이 끝내 안 돼도 멈추지 않음). 이것들로 돌려보내지 않는다.
- **판단 부분만 확인 필요로:** 견적 판(그 판이 `occurred_at`에 효력이 없던 게시 판이면 기기 값으로 적고 확인 필요), 할인, 결제 팀(제한을 벗어났으면), 권한(권한 없는 직원이 받은 접수), 라이선스(기간이 끝난 뒤의 기록은 `licence_lapsed_record`), 기기 로그인(`unverified_sign_in`). 관찰한 부분(접수 · 줄 · 돈 · 이동)은 늘 적는다.
- **돈의 `expect`는 참고 값:** 끊긴 두 카운터의 expect는 처음부터 옛 값이다. 늘 적용하고, 차이는 `overpaid` · `deposit_over_returned` · `possible_duplicate_money`로 올린다. 보증금은 맡은 만큼 + 넘친 현금 출금(8-7)이라 보관 금액이 0 아래로 가지 않는다. `data-model` 4-18의 '보증금 명령만 실패'는 온라인에서 창이 막을 때만이다. 온라인으로 바로 보낸 돈 명령은 전처럼 expect가 틀리면 충돌을 받는다(창 안의 `제외 후 수납`, ui 6-7).
- **새 접수 · 품목 추가:** 접수와 줄은 늘 적는다(마감한 날이면 차수의 `posting_date`가 기준선, `late_entry`). 끝내 적용할 수 없으면 저장된 봉투에서 최소 접수(임시 번호 · 대표자 · 줄)를 만들고 `offline_order_unapplied`를 올린다(8-6). 그러면 dependsOn한 지급 · 수납 · 보증금이 붙을 곳이 늘 있다: 손님 손에 있는 장비가 장부에서 매장에 있는 것으로 남거나, 수납이 붙을 접수가 없어 INTERNAL 재시도만 끝없이 도는 일이 없다. 품목 추가는 새 줄의 키와 `order:<id>:money`만 남기고 아무것도 읽지 않는다(4-2).
- **형식이 틀린 봉투**(앱의 버그)는 앱이 다시 보내게 하지 않고(같은 요청번호에 지문이 다르면 `idempotencyMismatch`로 막힌다) 서버의 upcaster · 고침 길(`verifier.repair` 같은 시스템 명령)로 처리한다. 그동안 그 봉투는 `command_held`로 관리자 목록에 보인다.
- **예외 둘:** 막은 기기에서 `revoked_at` 뒤에 도착한 명령은 적용하지 않고 보류한다(7절). 쓰기 프로세스를 죽인 명령도 보류한다(1절 0단계). 둘 다 사람이 `반영`을 눌러야 적용한다.
- 온라인으로 바로 보낸 intent는 전처럼 epoch · basis · 충돌 키 · expect를 본다(2 · 4절). 큐 규칙은 끊긴 기기가 쌓은 것에만 쓴다.
- 시험(S18, 8-11): 끊긴 동안 되살려 epoch가 바뀜 + 새 접수 + 수납 + 지급 + 보증금, 마감 뒤 도착, 권한 없는 직원, 라이선스 끝난 뒤 시각의 새 접수 + 수납(둘 다 적용되고 확인 필요 1건), expect가 옛 값인 큐 명령 셋(수납 · 보증금 돌려드림 · 여러 팀 수납)이 모두 `payments` 행을 남기는지. 기준은 두 번 셈 0 · 버린 것 0.

## 9. 바깥으로 나가는 일(outbox)

명령 트랜잭션 안에서 `outbox` 행을 쓰고, 커밋 뒤 작업자가 실행한다. 결과는 정해진 요청번호의 시스템 명령으로 기록한다(작업자를 다시 돌려도 한 번).

**잡기 규칙:** 작업자는 바깥을 부르기 **전에** 따로 커밋하는 트랜잭션으로 행을 잡는다(`in_flight`, `attempts + 1`, `outbox_attempts` 한 행, `locked_until`). 시작할 때와 잡은 시간이 지났을 때: 재시도 없는 채널(문자 · 카드)의 `in_flight`는 `unknown` + `확인 필요`, 재시도하는 채널은 `failed` + 뒤로 미룸. 그래서 '보냈는데 결과를 적기 전에 꺼짐'은 두 번 보내지 않고 사람에게 간다. PostgreSQL은 `FOR UPDATE SKIP LOCKED`.

| 채널 | 동작 | 자동 재시도 | 결과를 모를 때 |
|---|---|---|---|
| `sms` | 업체로 보냄. 시간이 중요한 틀은 `not_after`(예: 출발 문자는 20분) | **안 함** | `unknown` → `확인 필요`('문자 발송 결과 미확인 · 필요 시 전화'). `not_after`가 지나면 `expired` |
| `card_terminal` | 카드 단말 도우미 · PG에 요청 전달(요청 id = 요청에서 정해진 id) | **안 함** | `unknown` → 결제 창 안의 막는 단계. 승인번호 입력(`payment.intent_resolve`)이나 단말 조회로 맞춤. 다시 긁기 전에 반드시 조회 |
| `print` | 인쇄 도우미 또는 브라우저 | 함 | `dispatched`(보냄)와 `confirmed`(직원이 확인)를 나눔. 도우미는 인쇄 작업 id로 중복을 걸러 응답을 잃어도 두 번 찍지 않음. 끊긴 동안 기기에서 이미 찍은 문서는 outbox를 만들지 않음(아래) |
| `webhook` | 외부 알림 | 함 | 실패 기록 |
| `backup_upload` | 혼합 매장(나중)의 작은 PC가 작업 기록 구간을 중앙에 올림. 클라우드 매장은 복제 도구와 작업 프로세스가 올리므로 쓰지 않음 | 함 | 관리자 대시보드 경고 |

- **카드 단말 도우미는 기기다.** 자기 승인 기록(작은 로그)을 가지고 결과를 자기 기기 명령으로 알린다. epoch가 바뀌면(복구) 그 로그를 다시 알리고, 날마다 VAN 정산 파일과 수납을 맞춘다. 인쇄 도우미도 기기다. 둘 다 카운터 PC의 작은 프로그램이고 중앙 서버에서 일을 받는다(SSE).
- **같은 PC의 로컬 창구:** 도우미는 그 PC의 앱에 `localhost` 창구(Chrome의 사설망 접근 확인 머리를 답하고, 요청은 그 PC 앱의 기기 키로 서명)를 연다: 인쇄, 돈통 열기, 보냄 대기 한 벌(8-5). 가게 인터넷이 끊기면 카운터가 기기 안에서 그린 문서를 이 창구로 영수증 프린터에 바로 찍는다(브라우저 인쇄 창을 매번 거치지 않음, ui 7절 `PlatformBridge`).
- **끊긴 동안 이미 찍은 문서:** 그 `print.request` 본문에 `printedLocally: true`와 도우미의 인쇄 작업 id를 싣는다. 서버는 `print_jobs`를 `dispatched` 없이 `confirmed`로 적고 outbox를 만들지 않는다. 도우미는 인쇄 작업 id로 한 번 더 거른다. 연결이 돌아온 바쁜 카운터에서 끊긴 동안의 접수증 45장이 다시 쏟아지지 않는다.
- **바깥에서 오는 결과**(문자 전달 결과, PG 콜백)는 중앙 서버가 직접 받는다. 콜백 주소는 업체마다 추측할 수 없는 경로이고, 업체 IP 허용 목록과 **업체 서명(HMAC) 검증**을 통과한 것만 control의 받은편지함(`inbound_events`)에 두며(실패하면 `unroutable`, 적용하지 않음), 돈 결과는 콜백을 믿지 않고 **업체 API로 다시 조회한 뒤** 기록한다. 그 매장의 쓰는 쪽이 `inbound:<id>` 시스템 명령으로 기록한다(data-model 2-3). 받은 본문에 수신 번호가 있을 수 있어 가져간 뒤 30일에 비운다(`payload_purged_at`). 혼합 매장(시즌 뒤)은 작은 PC가 가져간다.
- 문자 outbox의 `payload_json`(수신 번호 · 본문)과 업체 응답은 결과가 난 뒤 30일(`retention.outbox_payload_days`)에 수신 번호 · 본문을 비운다(행과 결과는 남음, deployment 10-5).
- `shops.is_test = 1`(체험 · 연습 매장)이면 모든 채널이 모의 대상으로 가고 `suppressed`로 끝난다. 연습 로그인이 손님에게 문자를 보내는 일이 없다.

## 10. 백업과 복구

### 10-1. 백업

2026-09-24 클라우드 중심(ADR-19)으로 바뀌었다. 모든 파일이 중앙 서버에 있고, 복사본은 **다른 곳의 저장소**로 간다(같은 업체의 다른 구역, 그리고 다른 회사의 한국 저장소). 매장에는 백업 장치가 없다. 가게에 드리는 말은 README '정한 것' D4, 자세한 것은 [deployment.md 6절](deployment.md#6-백업과-되살리기).

**되살리는 길은 둘이고 섞지 않는다**(셋째 검토에서 고침): ① **PITR**은 복제 도구가 직접 올린 자기 세대(스냅샷) + WAL로만 된다. 원본 파일의 WAL 프레임은 `VACUUM INTO`가 페이지를 새로 짠 다른 파일 위에 적용할 수 없기 때문이다. ② **`VACUUM INTO` 스냅샷**은 그 자체가 되살리는 지점이고, 그 뒤는 작업 기록 구간의 after-image로 이어 붙인다. 복제 도구의 스냅샷 간격과 보관(7일)은 `backup_policy`에 둔다. 연습은 두 길을 번갈아 잰다(10-3).

| 무엇 | 언제 | 어디 |
|---|---|---|
| 연결 설정 | 늘 | WAL, `synchronous = FULL`(정전 · 서버 멈춤에도 커밋한 돈이 남음), `busy_timeout = 5000`, `foreign_keys = ON`, `recursive_triggers = ON` |
| **WAL 복제**(모든 매장 파일 + control) | **커밋마다 몇 초 안**(복제 도구의 올림 간격; 영업 중 1초, 밤 10초 — 비용과 RPO 사이의 설정) | 같은 업체의 다른 구역 객체 저장소(도구의 세대 + WAL). 7일 동안 **아무 초로나** 되살릴 수 있다(PITR, 길 ①). 한국 안에 그 업체의 둘째 지역이 없으면 다른 회사의 한국 저장소에도 한 벌(deployment 4절). 감시는 '올리지 않은 커밋이 있는 동안의 시간'(deployment 8절) |
| **작업 기록 구간**(작업 기록 + `event_pii` + 명령 기록 + 바뀐 행의 after-image) | 1분마다(또는 500 rev마다) | **다른 회사의 한국 저장소**(필수, `journal_exports.target_key = 'second_store'`, 앞뒤 해시, epoch). 두 부분으로 나눠 쓴다: 개인정보 없는 부분(`part_key 'main'`: 작업 기록 · 명령 기록 · 개인정보 칸을 뺀 after-image, 시즌 + 지난 시즌)과 개인정보 부분(`part_key 'pii'`: `event_pii` · after-image의 개인정보 칸, 따로 된 객체에 35일 수명 규칙 `backup_policy.journal_pii_keep_days`, 매장 · 달마다 다른 데이터 키). 복제 도구가 틀리거나 지역 · 업체 사고일 때 되살리는 둘째 길 |
| control 파일의 복구 기록 | 같음 | WAL 복제에 더해 `control_changes`(바뀐 행의 after-image)를 같은 방식으로 내보냄(`control_journal_exports`). 계정 · PIN · 등록 번호 길 찾기(`enrollment_routes`)를 잃지 않음(기기 행 자체는 매장 파일에 있다) |
| 스냅샷(`VACUUM INTO`: 읽기 한 번의 스냅샷, 공개 키 암호화) | 날마다 새벽 4시(35일), 월요일 것은 손님 정보를 지운 사본(26주), 시즌 끝(손님 정보 지움, 5년 — 세무 확인). 가져오기 전(`pre_import`). 마이그레이션이 든 배포에서는 스냅샷 대신 '복제 지연 0 확인 + 그 순간의 복제 위치(시각 · rev)'를 되살림 지점으로 적는다(deployment 7절) | 다른 구역 저장소(객체 잠금). 그 자체가 되살리는 지점(길 ②) |
| 기기의 보낸 기록 | 늘(7일) | 각 기기. 복구 때 다시 보냄(10-2) |
| 되살리기 연습 | 개장 전 두 번(손으로, 7 · 10주차), 시즌 중 매주 월요일 04:30 자동 | **새 VM을 스크립트로 만들어** 매장마다 길 ①(도구의 세대 + WAL을 몇 분 전 시각까지)이나 길 ②(스냅샷 + 구간)로 되살림 → `integrity_check` → 검증기 → 사슬 · 장부 행 해시 비교(10-3) → `restore_drills`(길 · 저장소 · 도달한 rev, 걸린 시간 = 잰 되살리기 시간) → VM 지움. 그 스크립트가 곧 재해 절차다. 달마다 한 번은 다른 회사 저장소만으로 |

설정 값은 `backup_policy`(`wal_keep_days 7`, `daily_keep_days 35`, `journal_pii_keep_days 35`, `weekly_scrubbed_keep_weeks 26`, `season_scrubbed_keep_years 5`, 연습 월요일 04:30, 가게 보관용 내보내기 `owner_export_scrubbed`(손님 정보를 뺀 장부 사본, 기본 켬) · `owner_export`(손님 정보 포함, 사장님이 켬)). 백업 주기는 공급자가 정하고 가게가 바꾸는 것은 두 내보내기뿐이다.

`node:sqlite`의 `backup()`은 다른 연결이 쓰면 처음부터 다시 하므로 성수기에 끝나지 않을 수 있다. 그래서 `VACUUM INTO`(한 번의 읽기 스냅샷)를 작업 프로세스의 읽기 연결에서 한다. 모든 백업은 control의 `backups`에 sha256, epoch, `max_rev`, 그때 작업 기록 해시, 암호화에 쓴 매장 데이터 키(`key_id`)와 함께 목록으로 남고, `tenant_epochs.max_rev_seen`을 올린다. 복제 · 스냅샷 · 연습의 목록은 control `tenants`(활성)에서 저절로 만든다(손으로 목록에 더하는 단계가 없음, deployment 6-1).

**실제 복구 지점(RPO):** 서버 한 대가 통째로 망가져도 잃을 수 있는 것은 **아직 복제되지 않은 몇 초**(목표 5초 이하)뿐이다. 그 몇 초의 명령 중 기기(카운터 · 차량)가 보낸 것은 기기들이 보낸 기록에서 다시 보내므로 사실상 0이다 — **기기 안의 기록이 지워지지 않는 한**(브라우저 자료 지우기에 대비한 도우미의 한 벌, 8-5). 복제본까지 잃는 드문 경우에는 작업 기록 구간의 마지막 1분까지다. 카드는 단말 도우미의 로그와 VAN 정산으로 맞춘다. 되살리는 시간(RTO)은 **알림을 받은 때부터** 잰다: 서버 한 대 1시간(첫 매장 30분), 지역 · 업체 전체는 근거가 생길 때까지 '하루 안'이다(deployment 6-4). 그동안 기기는 오프라인으로 일한다(8절).

### 10-2. 복구 순서

1. 새 서버(또는 옆의 새 파일)에 되살린다(옛 파일은 건드리지 않고 옆에 둔다). 길 ①: **복제 도구의 자기 세대 + WAL을 목표 시각까지**(PITR). 길 ②(길 ①이 안 되거나 복제본 사고): **가장 최근의 확인된 `VACUUM INTO` 스냅샷**에서 시작한다. VM만 죽고 네트워크 볼륨이 멀쩡하면 그 볼륨을 새 VM에 붙이는 것이 가장 빠르다(deployment 6-2). 목표 시각은 보통 '망가지기 직전'이고, 잘못된 배포 · 명령을 되돌릴 때는 그 전 시각이다(그런 경우는 먼저 앞으로 고친다, deployment 6-4).
2. 길 ②이거나 WAL이 목표 시각까지 닿지 못하면 그 지점의 rev 뒤의 작업 기록 구간을 rev 순서로 이어 붙인다. 각 구간의 첫 `prev_hash`가 앞 구간의 마지막 `hash`와 같은지 확인한다(사슬이 끊기면 거기서 멈추고 관리자에게 알림). **적용은 구간에 담긴 after-image를 그대로 쓰는 것**이다: 같은 행이 같은 id · 같은 번호로 생기고, 처리기 코드가 그사이 바뀌었어도(핫픽스) 결과가 달라지지 않는다. 처리기를 다시 돌리는 것은 확인용이며 `events.handler_version`이 다르면 하지 않는다.
3. `shop_instance`와 control `tenant_epochs`에 새 epoch를 쓴다: `restored_up_to_rev`(이어 붙인 마지막 rev), `rev_floor` = **지금까지 이 매장에서 쓴 가장 큰 rev**(`tenant_epochs.max_rev_seen`, 모든 epoch의 `backups.max_rev` · `journal_exports.to_rev`, 기기가 알린 가장 큰 rev 중 최댓값) + 1,000,000. 복구를 두 번 하거나 더 옛 백업으로 돌아가도 이미 쓴 rev · 그 rev로 만든 옛 id가 다시 나오지 않는다.
4. 사람이 읽는 번호를 건너뛴다: 접수 번호 · 묶음 번호 계산기를 범위마다 +500 올린다(잃은 구간에서 이미 종이에 찍혔을 수 있는 번호를 다른 팀이 받지 않게). 기기 번호 계산기(`shop_counters('device_short_no')`)도 +10 올린다(잃은 구간에 등록된 기기의 번호가 다시 나와 임시 접수 번호가 겹치지 않게).
5. 복구 뒤 만들어지는(다시 적용 · 다시 보냄) outbox 행은 `replayed = 1`이고, 재시도 없는 채널(문자 · 카드)은 `unknown`에서 시작해 스스로 나가지 않는다. 사람이나 단말 조회가 정한다.
6. `platform_audit_log`에 복구를 적는다. 목표 시각 뒤에 있던 **손님 정보 지우기**(`customer.anonymize`)는 버리는 쪽의 작업 기록 구간에서 찾아 다시 적용한다(지운 이름 · 전화가 되살아나지 않게, deployment 10-5). 같은 구간에서 **목표 시각 뒤에 등록된 기기**의 `devices` 행과 공개 키도 다시 만든다: 되살린 파일에 없는 기기가 보낸 큐의 서명을 확인할 수 있게. 35일보다 오래된 지점으로 되살리면 `event_pii`와 구간의 개인정보 부분이 이미 없으므로 그 값이 비어 있는 것이 정상이다.
7. 서버를 켠다. 모든 응답에 새 epoch가 실린다. 다른 epoch의 basis를 가진 **온라인** intent는 '자료 복구 · 재확인 필요'를 받는다. **큐에서 온 명령은 epoch · basis를 보지 않는다**(8-12: 복구 전에 끊긴 채 쌓인 새 접수 · 품목 추가도 적어 두는 사실이다). 기기들은:
   - 캐시를 버리고 bootstrap을 받는다.
   - `sent` 기록(7일)에서 **서버가 준 rev가 `restored_up_to_rev`보다 큰 명령**을 같은 요청번호로, **`replay`에 그때 서버가 정한 값(`canonical`: 만든 id, 접수 번호, 묶음 번호, `posting_date`, 견적, 받은 rev)을 실어** 다시 보낸다. 카운터 포스도 같은 `sent` 기록을 가진다. 카드 · 인쇄 도우미도 자기 기록을 다시 알린다. 이름 · 전화 원문은 `sent`에 24시간만 있으므로(8-1) 그보다 오래된 명령은 참조로 바꾼 모양으로 가고, 그 칸은 비어 들어가며 `restore_replay`에 함께 적힌다(서버를 잃은 경우는 몇 초 전의 명령뿐이라 늘 원문이 있다).
   - 그다음 아직 못 보낸 큐를 보낸다.
8. 서버는 다시 보낸 명령을 짧은 창(기본 2분) 동안 모아 **원래 rev 순서로** 적용하고, `replay`의 값을 쓴다(2절). `restore_lost`(서버를 잃음)는 모든 값을 그대로 예약해 쓴다(같은 접수 번호, 같은 id). `restore_bad_deploy`(잘못된 배포로 값이 틀려 되돌림)는 이름 값(id · 접수 번호 · 묶음 번호 · 임시 번호)만 그대로 두고 계산 값(견적 · `posting_date`)은 고친 처리기로 다시 계산해, 달라진 것을 `recomputed_after_restore`로 올린다(틀린 견적을 다시 심지 않게). 이미 그 값을 다른 것이 가졌으면(다른 기기가 먼저 보낸 다른 팀) 새 값을 쓰고 `확인 필요`('복구 후 접수 번호 261226-041 중복 · 종이 접수증 확인', `receipt_no_clash`). 이미 들어간 것이면 `duplicate`, 잃어버린 것이면 새로 적용된다. 적용할 수 없는 것만 `확인 필요`('복구 후 재수신')로 간다.
9. 복구 기기의 기기 번호는 복구된 높은 물 표시 위의 것을 모두 받는다(구간에 없던 거절 · 충돌 행 때문에 빈 번호가 영원히 남지 않게).

### 10-3. 복구 시험이 확인하는 것

`PRAGMA integrity_check`, `foreign_key_check`, 검증기 전체(투영 · 현금 출처 · 해시 사슬 · 장부 행 해시). 운영과 견주는 것은 되살린 파일이 도달한 rev R에서 **할 수 있는 것만** 한다(SQLite에는 지난 rev 시점의 행 수를 볼 방법이 없다): ① 되살린 파일의 rev R 작업 기록 사슬 해시 = 운영 `events`의 rev R 행의 사슬 해시(작업 기록은 추가만 하므로 운영에 그대로 있다), ② 되살린 장부 행 해시를 다시 계산한 값 = events 결과의 해시, ③ 추가만 하는 장부 표의 `created_rev ≤ R` 행 수 = 운영의 같은 조건 행 수. 그리고 구간 이어 붙이기가 끝까지 되는지, 다시 보낸 명령이 같은 id · 번호로 들어가는지, **걸린 시간**(되살리기 목표 1시간의 절반을 넘으면 알림, PostgreSQL로 옮길 때를 알리는 숫자 — deployment 2-1). 실패하면 공급자의 휴대폰 · 관리자 콘솔 대시보드에 알림이 가고, 매장 관리 화면의 `백업` 카드와 머리줄 알림에 한 줄이 뜬다(매장 화면의 빨강은 늦은 것에만 쓰므로 빨강이 아닌 알림 표시). 통과하면 `백업` 카드에 `복구 점검 통과 · 월요일 04:30 · 12분`.

## 11. 여러 매장과 PostgreSQL

- 중앙 서버(시즌 1): 매장마다 SQLite 파일 하나, 파일마다 쓰기 하나(`BEGIN IMMEDIATE`), 매장끼리 서로 막지 않는다(옛 구조는 모든 매장이 쓰기 잠금 하나를 나눔). 한 건이 약 0.6 ms라는 값은 **macOS 노트북**에서 잰 것이다(macOS의 fsync는 디스크 캐시를 비우지 않는다). 운영 VM의 네트워크 볼륨에서는 커밋마다 fsync가 몇 ms이므로 1주차 스파이크에서 고른 VM으로 다시 재어 숫자를 고친다(deployment 2-1 · 2-2). 쓰기는 매장 해시로 나눈 Worker 스레드에서 돌려 HTTP · SSE의 이벤트 루프를 잡지 않는다. 한 매장의 명령이 쓰기 프로세스를 죽이면 처리 중 기록으로 격리해 다시 시작 때 되풀이하지 않는다(1절 0단계). 늘면 매장을 여러 프로세스 · 서버로 나눈다(deployment 2-2): 먼저 프로세스 나누기, 그다음 control을 공용 DB(또는 control 서비스)로, 그다음 매장 파일 서버를 여럿으로.
- 혼합 매장(나중): 그 매장 파일의 쓰는 쪽이 매장의 작은 PC이고 중앙은 복제본이다. 같은 파일에 쓰는 쪽이 둘이 되는 순간은 없다(deployment 1-3).
- SaaS PostgreSQL: 쓰기 트랜잭션마다 `SELECT value FROM shop_counters WHERE shop_id = $1 AND counter_key = 'rev' FOR UPDATE`. 매장별로만 줄을 세우고 커밋 순서 = rev 순서라 읽는 쪽이 rev를 건너뛰지 않는다. 행 보안 정책으로 `shop_id`를 한 번 더 막는다. 한 매장만 복구할 때는 새 스키마에 그 매장의 구간 after-image를 다시 적용해 만든 뒤 바꿔 끼운다(data-model 9절).
- 오래 걸리는 일: 검증기 · 보고서 · 백업 스냅샷은 별도 읽기 연결의 작업 스레드에서 한다(WAL이라 읽기가 쓰기를 막지 않음). **쓰는 긴 일**(시즌 보관의 지우기, 검증기의 고침)은 읽기 연결이 아니라 쓰기 경로로, 잘게 나눠서 한다: 지우기는 한 트랜잭션에 2,000줄씩 영업 시간 밖에, 사이마다 쓰기 잠금을 놓는다. 검증기의 고침은 정해진 요청번호의 시스템 명령(`verifier.repair`)이라 rev와 변경 목록이 남고 기기에도 간다. `SQLITE_BUSY`는 다시 해 볼 만한 거절이고 기기 번호를 쓰지 않는다.
