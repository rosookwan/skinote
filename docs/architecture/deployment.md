# 배치와 운영: 클라우드 중심

작성 2026-09-24(ADR-19). 스키노트를 **어디서 돌리고, 기기가 어떻게 붙고, 라이선스 · 백업 · 업데이트 · 감시 · 원격 지원 · 보안을 누가 어떻게 하는지** 정한다. 결정 기록은 [README ADR-19](README.md#adr-19-배치-클라우드-중심2026-09-24), 기기의 오프라인 규칙은 [sync-and-concurrency.md 8절](sync-and-concurrency.md#8-오프라인기사-기기와-카운터), 되살리는 순서(epoch · rev_floor)는 같은 문서 10절, 표는 [data-model.md](data-model.md)와 [`schema.sql`](../../packages/schema/schema.sql)이다. 표와 자료 구조는 그대로이고, 바뀐 것은 **그 파일이 어디에 있고 기기가 어떻게 붙는지**다. 같은 날 셋째 검토(끊김 · 보안 · 운영 · 일관성)를 반영했다: 가게 인터넷은 예비 회선 자동 넘어가기가 개장 조건이고 혼합은 시즌 1 대안이 아니다(1-3), 관리자 콘솔은 따로 된 주소(3절), 열쇠를 나눔(3 · 10-1절), 기기 등록은 두 단계(5-3), 백업의 두 길과 연습은 새 VM에(6절), 배포는 스키마와 코드를 나누고 되돌리기는 코드만(7절), 알림은 깨움과 아침 묶음(8절), 공급자의 자료 보기는 매장의 허락과 기록으로(9절), 매장 끝내기(6-7), 공급자가 멈출 때(12절).

## 0. 한눈에

- 모든 매장의 장부 원본은 **우리가 운영하는 중앙 서버(한국 안의 클라우드)**에 있다. 매장마다 SQLite 파일 하나(`shop-<id>.sqlite`), 모든 매장이 함께 쓰는 `control.sqlite` 하나. 매장 파일마다 쓰는 쪽은 하나다.
- 카운터 포스(설치한 PWA) · 기사 태블릿 · 휴대폰은 HTTPS로 중앙 서버에 붙고, 바뀐 것은 SSE 알림으로 받는다. 매장에는 서버 PC도, USB도, 랜선 복사도 없다. 대신 가게 인터넷은 **예비 회선(LTE)으로 저절로 넘어가는 공유기**를 둔다(첫 매장의 개장 조건, 11절).
- 인터넷이 끊기거나 우리 서버가 멈춰도 기기는 **자기 안의 사본과 보냄 대기**로 일한다. 기사 기기에 설계한 것과 같은 코드이고, 이제 카운터도 같다(sync 8절). 돈 · 반납은 어떤 경우에도 막지 않는다. 끊긴 채 쌓인 기록은 도착해서 돌려보내지 않는다(sync 8-12).
- 라이선스 확인 · 자동 백업 · 기사 기기 연결 · 업데이트 · 원격 지원은 모두 중앙에서 한다. 혼자 멀리서 일하는 개발자가 매장 하드웨어를 돌보지 않아도 된다. 대신 개발자 한 사람이 멈출 때의 대비를 둔다(12절).
- 백업은 커밋마다 몇 초 안에 **다른 구역의 저장소**로 복제되고, 1분마다 **다른 회사의 한국 저장소**로 작업 기록 구간이 가고, 날마다 스냅샷, 새 VM에 되살리는 연습을 한다. 서버가 망가져도 잃는 것은 몇 초이고, 그 몇 초도 기기들이 다시 보낸다.
- 인터넷이 정말 나쁜 매장은 **시즌 뒤에** 혼합(매장의 작은 PC가 그 매장의 쓰는 쪽, 중앙은 복제본 · 라이선스 · 기사 중계)을 고를 수 있다(1-3).

## 1. 무엇이 어디서 도나

### 1-1. 버린 것

| 안 | 버린 까닭 |
|---|---|
| **매장 PC 서버**(옛 ADR-02 · 12 · D4의 전제: 매장 PC에 두 파일, LAN 복사, USB, 매장 서버가 라이선스 확인) | 혼자 멀리서 일하는 개발자가 매장마다 PC · USB · 디스크 · 업데이트 · 백업을 돌볼 수 없다. 기사 휴대폰은 산에서 LTE로 붙으므로 NAT 뒤의 매장 PC에 닿으려면 어차피 중앙 중계가 필요했다. 불 · 도난 · 매장 PC 고장이 곧 자료 사고였다. 여러 매장에 팔 때 매장마다 설치 · 지원이 늘어난다 |
| **처음부터 혼합**(매장 PC가 쓰는 쪽, 중앙은 복제) | 두 곳을 오가는 쓰는 쪽 옮기기, 매장 하드웨어 · 설치 · 지원이 그대로 남는다. 첫 매장은 인터넷 + 예비 회선 자동 넘어가기 + 카운터 오프라인으로 버틴다(1-3) |
| **처음부터 공용 PostgreSQL** | 2-1 |

### 1-2. 기기와 서버 사이

- 모든 요청은 HTTPS 하나의 주소로 간다(3절). 쓰기는 `POST /api/v2/commands`(또는 `:batch`), 읽기는 `/api/v2/sync` · `/bootstrap` · 조회, 바뀜 알림은 SSE `/api/v2/stream`(2-4). 기기끼리는 직접 이야기하지 않는다(카운터 1과 카운터 2도 서버를 거친다). 그래서 매장 인터넷이 끊기면 카운터끼리도 서로의 기록을 보지 못한다(sync 8-7).
- 예외는 **같은 PC**뿐이다: 카운터 PC의 앱은 그 PC의 도우미와 `localhost`로 이야기한다(인쇄 · 돈통 열기 · 보냄 대기 한 벌, sync 8-5 · 9절). 도우미는 Chrome의 사설망 접근 확인 머리에 답하고, 요청은 그 PC 앱의 기기 키로 서명된 것만 받는다.
- **가게 LAN 중계(시즌 뒤):** 가장 흔한 고장(가게 인터넷만 끊김)에서 LAN은 멀쩡하다. 도우미가 LAN에서 각 카운터의 큐를 읽기 전용으로 받아 다른 카운터가 자기 사본에 겹쳐 그리게 하면 두 번 받기 · 두 번 지급이 줄어든다. 쓰는 쪽은 여전히 서버 하나라 혼합이 아니다. 시즌 1에는 만들지 않고, 예비 회선 자동 넘어가기와 가게 규칙(sync 8-7)으로 버틴다.
- 명령 봉투 · 멱등 · 충돌 · 사실은 거절하지 않음 · 요청번호는 그대로다(sync 1 · 2 · 4 · 6절). 달라진 것은 카운터도 기사처럼 **늦게 오는 사실과 보냄 대기**를 가진다는 것뿐이다.

### 1-3. 혼합(시즌 뒤)

- **무엇:** 그 매장의 작은 PC(미니 PC)가 그 매장 파일의 쓰는 쪽이 되고(옛 설계의 매장 서버), 중앙은 복제본 · 라이선스 · 기사 기기 중계 · 업데이트 · 원격 지원을 맡는다. 매장 PC는 작업 기록 구간과 WAL을 중앙으로 흘려 보내고(`journal_exports.target_key = 'edge_peer'`), `tenants.data_location`이 매장 PC를 가리킨다(`edge://<기기 id>`). 표 · 명령 · 화면은 같다.
- **작은 PC가 가질 것:** control을 쓰지 않는다. 끊긴 동안에도 로그인 · PIN · 라이선스를 확인하려고 **control의 그 매장 조각**(그 매장 직원의 비밀번호 · PIN 확인 값, 서명된 라이선스, 기기 공개 키)을 읽기 전용 사본으로 받는다. 중앙이 control의 유일한 쓰는 쪽이다(schema 머리말).
- **기사 기기 중계:** 기사 휴대폰은 산에서 LTE로 중앙에 붙는다. 작은 PC가 중앙으로 연결을 열어 두고(바깥으로 나가는 연결 하나), 중앙은 기사 명령을 그 연결로 넘긴다. 받은편지함도 작은 PC가 가져간다(pull).
- **아직 풀지 않은 것:** `https://app.<도메인>`에 설치된 PWA가 LAN의 작은 PC를 부르려면 혼합 콘텐츠 차단, 사설 · 로컬 네트워크 접근 규칙, LAN 주소용 신뢰된 인증서를 풀어야 하고, 출처가 다르면 OPFS와 보냄 대기가 따라오지 않는다. 쓰는 쪽을 옮기는 절차(쓰기를 잠깐 멈추고 마지막 구간까지 넘긴 뒤 쓰는 쪽을 바꿈)도 연습이 필요하다. 그래서 **시즌 1에는 만들지 않고 시즌 1의 대안도 아니다.** 시즌 1의 대안은 '예비 회선 자동 넘어가기 + 카운터 오프라인 + 끊긴 동안 결정을 적는 종이 양식'이다(migration 4절).
- **내놓는 때(시즌 뒤, 모두 만족):** ① 가게 인터넷을 성수기에 재어 보니(1주차부터 잰 기록, migration 6절) 영업 시간 중 30분 넘는 끊김이 한 주에 한 번 넘게 있거나, 짧은 끊김이 하루에도 여러 번이다. ② 예비 회선 자동 넘어가기로도 메워지지 않는다. ③ 카운터 오프라인으로도 모자라다고 사장님이 판단한다: 예를 들어 끊긴 동안 약속 바꾸기 · 마감 · 두 카운터가 서로의 수납을 봐야 하는 일이 잦다. ④ 매장이 작은 PC · 설치 · 지원 비용을 받아들인다. ⑤ 위의 '아직 풀지 않은 것'을 스파이크로 풀었다.
- 같은 매장 파일에 쓰는 쪽이 둘이 되는 순간은 없다(2-2의 잠금).

## 2. 서버와 매장 나누기

### 2-1. 매장마다 SQLite 파일 하나(시즌 1), PostgreSQL은 나중

**결정:** 중앙 서버의 로컬 디스크에 매장마다 SQLite 파일 하나와 `control.sqlite`를 두고, 각 파일의 WAL을 복제 도구(예: Litestream 같은 오픈 소스 SQLite 복제 도구)로 커밋마다 다른 구역의 객체 저장소에 이어 올린다. PostgreSQL은 아래 조건 중 하나가 오면 옮긴다.

| 기준 | 매장마다 SQLite 파일 | PostgreSQL(관리형) |
|---|---|---|
| 스키마 | 지금 그대로. 트리거 · STRICT · 실행기 · lint · 시험이 SQLite에서 돈다 | data-model 9절의 옮기기(plpgsql 트리거, `ALTER … ADD CONSTRAINT`, `COLLATE "C"`, 행 보안 또는 매장별 스키마)가 먼저 필요 |
| 오프라인 사본 | 서버와 브라우저(SQLite WASM)가 **같은 저장소 코드 · 같은 SQL**을 돈다(ADR-15) | 서버는 PostgreSQL, 브라우저는 SQLite라 `packages/store`가 처음부터 두 방언 |
| 혼자 하는 개발 | 서버 하나 · 파일 복사로 이해 · 복구가 된다 | DB 운영(연결 수, VACUUM, 판 올리기)이 더해진다 |
| 쓰기 | 파일마다 쓰기 하나. 한 건 약 0.6 ms는 **macOS 노트북** 값이고(data-model 10절, macOS의 fsync는 디스크 캐시를 비우지 않는다) 운영 VM의 네트워크 볼륨에서는 커밋마다 몇 ms일 수 있다: 1주차 스파이크에서 고른 VM으로 다시 재어 이 칸을 고친다. 매장끼리 서로 막지 않는다 | 매장별 `shop_counters` 행 잠금(sync 11절) |
| 매장 사이의 벽 | 파일이 다르다(한 쿼리가 다른 매장을 볼 수 없음) | 행 보안 정책 + 앱 검사 |
| 복구 | 매장 하나만 되살리기가 쉽다(파일 하나) | 매장 하나만은 after-image 논리 재구성(data-model 9절) |
| 비용 | 서버 한 대 + 저장소 | 관리형 DB는 이중화까지 더하면 서버 한 대보다 비싸다(4절) |
| 약한 곳 | 서버 한 대라 자동 절체가 없다(되살리기 목표 1시간, 6-4). 매장 사이 합계 쿼리는 파일마다 돈다 | 자동 절체 · 읽기 복제본이 쉽다 |

**PostgreSQL로 옮기는 때**(하나라도):
1. 되살리기 연습(6-3)에서 **모든 매장을 새 서버에 되살리는 시간**이 목표(1시간)의 절반을 넘는다. 매장 수 · 자료가 늘어 서버 한 대 복구가 느려졌다는 뜻이다(대략 수십 ~ 100 매장, 수십 GB쯤에서 올 것으로 본다. 재어서 정한다).
2. 중앙이 한 시간 멈추는 것도 받아들일 수 없을 만큼 매장이 늘어 **자동 절체(대기 서버)**가 필요하다.
3. 매장 사이를 잇는 기능(사업자 단위 공유 고객 · 적립, 매장 간 재고 조회)이 핵심이 된다(ADR-16 보류분).
4. 운영을 함께할 사람이나 관리형 DB 예산이 생긴다.
5. 쓰기 쪽 CPU가 성수기 저녁에 한 서버의 30%를 넘는다(운영 VM에서 잰 값).

옮길 때의 순서: ① 한 서버 안에서 매장을 매장 해시로 여러 쓰기 프로세스 · Worker로 나눈다(2-2). ② **control을 공용 DB(또는 control 서비스)로 옮긴다**: 명령마다 control(세션 · 계정 · 라이선스)을 읽고 로그인 · PIN · 세션은 control에 쓰는데, `control.sqlite`는 한 서버의 파일이라 둘째 서버가 열 수 없다(SQLite WAL은 네트워크 파일 시스템에서 안 된다). ③ 매장 파일 서버를 여럿으로(`tenants.data_location` = `sqlite://<host>/shop-<id>.sqlite`). ④ 그래도 모자라면 PostgreSQL(`pg://<cluster>/<schema>`). 브라우저의 오프라인 사본은 SQLite로 남는다.

### 2-2. 매장마다 쓰는 쪽 하나

- 시즌 1은 **쓰기 프로세스 하나**가 모든 매장의 명령을 받는다. 매장마다 명령 줄(비동기 잠금 하나)이 있어 한 매장의 명령은 하나씩, 다른 매장은 따로 간다. 한 명령 = 한 트랜잭션(`BEGIN IMMEDIATE`) = 한 rev(sync 1절). `node:sqlite` 호출은 동기라 커밋하는 동안 그 스레드의 이벤트 루프를 잡는다. 그래서 **쓰기는 매장 해시로 나눈 Worker 스레드에서** 돌리고 HTTP · SSE는 주 스레드에 둔다(복구 뒤나 가게 인터넷이 돌아온 뒤 여러 기기의 `:batch`가 몰려도 다른 매장의 요청과 SSE가 늦지 않게). 매장 · 기기마다 요청 수와 batch 크기를 제한한다.
- **독 명령:** 처리기가 JS 예외가 아니라 프로세스를 죽이는 명령(끝나지 않는 반복, 메모리 폭주)을 만나면, 다시 시작할 때 기기가 같은 요청번호로 다시 보내 또 죽고 그동안 모든 매장이 503을 받는다. 그래서 처리를 시작하기 전에 (매장, 요청번호)를 작은 '처리 중' 기록(서버 디스크의 파일)에 적고 끝나면 지운다. 시작할 때 남아 있는 기록의 요청은 격리하고(`command_log.status_key = 'held'`, 확인 필요 `command_held` '공급자 확인 중', 같은 요청번호가 와도 실행하지 않음) 개발자를 깨운다(8절). 명령마다 시간 제한(예: 2초 넘으면 알림)을 둔다.
- **두 쓰는 쪽을 막는 법:** 매장 파일마다 운영체제 파일 잠금을 쥔 프로세스만 연다. `tenants.data_location`이 이 서버를 가리키지 않는 매장(혼합 매장, 옮기는 중인 매장)은 쓰기로 열지 않는다. 잠금을 못 쥐면 시작을 거부한다.
- **읽기:** 매장마다 읽기 연결(WAL이라 쓰기를 막지 않음). 무거운 읽기(부트스트랩, 보고서)는 작업 스레드에서 한다.
- **긴 일:** 검증기 · 스냅샷(`VACUUM INTO`) · 시즌 보관은 따로 도는 작업 프로세스에서 읽기 연결로 한다. 고칠 것이 있으면 쓰기 프로세스에 시스템 명령(`verifier.repair`)을 보낸다(sync 11절). 되살리기 연습은 따로 된 VM에서 한다(6-3).
- 쓰기 연결은 요즘 쓴 매장만 열어 두고(최근 사용 순), 오래 안 쓴 매장은 닫는다.
- **두 번째 매장 전에** 매장 해시로 여러 쓰기 프로세스에 나누고 앞단이 요청을 그 프로세스로 보낸다. 규칙은 같다(파일마다 쓰는 쪽 하나). 이렇게 나눠야 한 매장의 문제가 모든 매장에 퍼지지 않고, 시험 매장 → 한 매장 → 전부 순서의 배포(7절)도 된다.

### 2-3. 명령 처리기가 도는 곳과 다시 시작

- 쓰기 순서는 sync 1절 그대로다. 11단계의 'LAN으로 흘려 보냄'이 '커밋한 WAL을 복제 도구가 몇 초 안에 다른 구역 저장소로'로 바뀌었다. 커밋을 복제가 기다리지 않는다(쓰기가 늦어지지 않게). 기다리지 않아서 생기는 몇 초의 틈은 기기의 보낸 기록이 메운다(6-4).
- **다시 시작(배포 · 고장):** 새 명령에 잠깐 `503`과 `Retry-After`를 주고(기기는 보냄 대기로 받음), 처리 중인 명령을 끝내고, 연결을 닫고, 새 판이 뜬다. 코드만 바뀐 배포는 몇 초 ~ 30초이고, 그동안 화면은 연결 띠만 잠깐 보인다(sync 8-1의 넘기기 지연 때문에 몇 초면 띠도 뜨지 않는다). **마이그레이션이 든 배포**는 매장 파일을 처음 열 때 하나씩 적용하므로(그 매장만 잠깐 503) 걸리는 시간이 매장 수 × 파일 크기에 비례한다: 그래서 새벽 예약 작업으로 한다(7절).

### 2-4. 바뀜 알림: SSE

- **SSE를 쓴다**(WebSocket이 아님). 쓰기는 모두 `POST`이고 서버가 알릴 것은 `{epoch, rev, configRev}` 한 줄뿐이라 한 방향이면 된다. HTTP/2 위에서 여러 창이 한 연결을 나눠 쓰고, 프록시 · 회사망을 잘 지나며, 끊기면 브라우저가 스스로 다시 붙는다.
- 25초마다 빈 줄(하트비트)을 보내 휴대폰 망과 앞단의 유휴 끊김을 막는다. 앞단의 유휴 시간은 그보다 길게 둔다. SSE는 세션 쿠키로 인증하고 주소에 토큰을 싣지 않는다(3절).
- SSE가 끊기면 포스는 5초, 기사 기기는 10초마다 `/sync`를 묻는다(sync 5절). 바뀐 것이 없으면 인덱스 한 번 보고 끝난다.
- 매장 하나에 기기 6~10대, 100 매장이면 연결 1,000개쯤이라 한 서버에 충분하다.

### 2-5. 매장 사이의 벽

- 매장 id는 요청 본문이 아니라 **세션 → 직원 → 매장**으로 정하고, 그 매장의 파일만 연다(data-model 2-3). 한 연결은 한 매장 파일만 안다. 앱 코드에서 여러 매장 파일을 한 쿼리로 묶는 일은 없다.
- **두 번째 막기:** 한 프로세스가 여러 매장 파일을 열어 두므로 '지금 매장' 전역 변수나 연결 캐시 키의 실수 하나로 다른 매장 파일에 쓸 수 있다. 그래서 파일을 열 때와 트랜잭션마다 그 파일의 `shops.id`가 세션의 매장인지 다시 보고(다르면 멈추고 알림), 저장소 계층의 모든 쿼리는 세션에서 온 `shop_id`를 바인딩한다(복합 키라 다른 파일이면 0행). 매장 핸들은 명시적으로 넘기고 전역 상태를 쓰지 않으며, 두 매장 명령을 섞어 돌리는 시험을 둔다.
- 공급자의 여러 매장 숫자(관리자 대시보드)는 작업 프로세스가 매장마다 하루 한 번 쓰는 `usage_daily`와 control 표에서만 본다.
- 매장 파일의 복제본 · 스냅샷 · 구간은 매장마다 따로 된 경로에 **매장마다 다른 데이터 키**로 암호화해 둔다(10-1). 매장 하나만 되살리고, 매장 하나만 지울 수 있다(6-7).

## 3. 환경 · 주소 · 암호화된 연결

| 환경 | 무엇 | 자료 |
|---|---|---|
| 운영(production) | 중앙 서버 한 대 + 다른 구역 저장소 + 다른 회사 저장소 | 실제 매장, 그리고 합성 명령을 돌리는 시험 매장 하나(`is_test = 1`, 7절) |
| 연습(staging) | 따로 작은 서버, 자기 저장소 | 시험 매장(`is_test = 1`)과 가짜 자료. **실제 손님 자료를 넣지 않는다**(옛 자료 가져오기 리허설도 이름 · 전화를 지운 사본으로) |
| 되살리기 연습 · 배포 전 확인(drill) | 스크립트로 새로 만드는 VM, 끝나면 지움 | 운영 복제본(암호화된 채 받아서 되살림). 바깥 연결 없음, 한국 안 |
| 체험판 | GitHub Pages | 예시 자료만, 서버 없음 |

- **주소:** 매장 앱 주소 하나(예: `app.<도메인>`), 연습 `staging.<도메인>`. 매장마다 하위 주소를 두지 않는다: 매장은 기기 등록과 로그인으로 정해지고, PWA 범위 · 인증서 · 서비스 워커가 하나라 간단하다. 도메인은 아직 정하지 않았다(열린 질문 21).
- **앱 출처는 바꾸지 않는다.** OPFS · IndexedDB는 출처마다 따로라, 주소를 바꾸면 옛 주소에 쌓인 보냄 대기 · 보낸 기록 · 기기 키가 새 주소의 앱에서 보이지 않는다. 바꿔야 하면 옛 출처에서 보냄 대기를 다 보내게 하는 절차를 먼저 한다. 도메인은 여러 해 자동 갱신, 등록 업체 잠금과 2단계 인증, 결제 수단 둘로 두고 만료 60일 · 30일 전에 알린다(8절). 도메인을 빼앗기면 모든 기기가 공격자 코드를 받는다.
- **TLS:** HTTPS만(HTTP는 HTTPS로 넘김), TLS 1.2 이상(1.3 우선), HSTS. 인증서는 앞단(예: Caddy · nginx + Let's Encrypt 자동 갱신, 또는 호스팅 업체의 인증서 관리)이 갱신하고, 만료 14일 전에 알림(8절). 새 서버로 되살릴 때 DNS가 바뀌기 전에도 받을 수 있게 DNS-01로 받거나 인증서를 비밀값과 함께 보관한다(6-2).
- **관리자 콘솔: 따로 된 주소의 따로 된 앱**(예: 다른 하위 도메인이 아니라 다른 도메인). 매장 앱과 출처가 같으면 쿠키 · IndexedDB · 서비스 워커 범위를 나눠 쓰므로, 매장이 넣은 글(손님 이름, 메모, 장소 메모, 화면 설정 · 인쇄 틀, 로고) 하나가 공급자 브라우저에서 스크립트로 돌면 모든 매장으로 번진다(여러 매장에 팔면 매장끼리는 서로 믿을 수 없는 고객이다). 그래서: 콘솔 앞단에 IP 허용 목록 · VPN · mTLS 중 하나, 공급자 계정은 하드웨어 키 2단계 인증, 매장 앱 주소에는 `/admin` 경로가 아예 없다(운영 빌드도 `check:dist`처럼 검사). 주소는 숨겨서 지키는 것이 아니라 **따로 된 주소 + 접근 제한**으로 지킨다(공개 저장소에 적혀 있어도 된다).
- **화면의 안전 규칙:** 매장 앱과 콘솔 모두 엄격한 CSP(`script-src 'self'`, 인라인 스크립트 없음, `object-src 'none'`, `frame-ancestors 'none'`)와 Trusted Types를 쓴다. 설정 · 인쇄 틀은 HTML이 아니라 형식 있는 값으로만 그린다(ui 7절). 세션은 HttpOnly · Secure · SameSite=Strict 쿠키이고 요청마다 기기 키 증명에 묶인다(sync 7절). CSRF는 SameSite와 기기 키 증명으로 막는다.
- **비밀값**(기기 표 서명 키, 백업 공개 키 · 저장소 접근 키, 문자 업체 키, PIN pepper, 지문 HMAC 키)은 데이터베이스와 저장소(git)에 두지 않는다. **업체의 KMS · 비밀 관리 기능**을 기본으로 하고 접근 기록을 켠다(안 되는 업체면 서버의 비밀 파일, 권한 제한). 운영 서버에 두지 않는 것: 라이선스 **루트 개인 키**(개발자의 하드웨어 키 · 금고), 백업을 **푸는 개인 키**(되살리기 절차와 연습 VM에만, 업체 KMS나 따로 된 계정), 저장소의 '지우기' 권한. 사본은 개발자의 비밀번호 관리자와 오프라인 봉투(금고), 그리고 12절의 둘째 사람 봉투에 둔다(10-1).

## 4. 호스팅(한국 안)

**조건(필수):** 한국 안의 데이터 센터, S3 호환 객체 저장소(버전 관리와 객체 잠금), 볼륨 · 저장소 암호화, 스냅샷, 콘솔 2단계 인증, 예약 공인 IP(또는 부하 분산기). 그리고 **서버가 있는 곳과 다른 곳에 복제본**: 같은 업체의 **한국 안 다른 지역**, 그 업체에 한국 지역이 하나뿐이면 **다른 회사의 한국 저장소**에 WAL 복제본(복제 도구는 두 곳에 올릴 수 있다)이나 적어도 작업 기록 구간을 둔다. 작업 기록 구간은 어느 경우든 다른 회사의 한국 저장소에 둔다(한 업체 계정 사고에 두 벌이 함께 사라지지 않게). 원화 청구 · 한국어 지원이면 더 좋다.

**후보(가격은 적지 않는다, 계약 전에 요금표로 확인):** 네이버 클라우드 플랫폼, NHN Cloud, KT Cloud, 카카오클라우드, 그리고 한국 지역이 있는 AWS(서울) · Google Cloud(서울) · Microsoft Azure(한국). 모두 한국 안에 자료를 둘 수 있다. 해외 업체 가운데는 한국 지역이 서울 하나뿐인 곳이 있어 '다른 지역'이 안 된다: 후보마다 한국 안 지역 수 · 구역 수를 1주차에 업체 문서로 확인해 이 줄에 적는다. 국내 업체는 원화 청구 · 한국어 지원이 쉽고, 해외 업체의 한국 지역은 도구가 많다.

**권하는 모양:** 한 업체에서 서버 한 대(시작은 2~4 vCPU · 4~8 GB 메모리 · SSD 수십 GB, 1주차 벤치로 고름) + 같은 업체의 **다른 지역 · 구역** 객체 저장소(WAL 복제본 · 스냅샷) + **다른 회사의 한국 저장소**(작업 기록 구간, 둘째 지역이 없으면 WAL 복제본도). 연습 서버는 가장 작은 것.

**비용(줄 항목, 값은 요금표와 첫 달 청구서로 채운다):**

| 항목 | 무엇이 늘리나 | 1주차에 잴 것 |
|---|---|---|
| 운영 VM · 볼륨 · 예약 IP | 매장 수(한동안은 그대로) | 고른 VM 종류의 쓰기 벤치(2-1) |
| 볼륨 스냅샷 | 날마다 · 보관 기간 | — |
| 저장 GB(복제본 · 스냅샷 · 구간) | 매장 수 × 쓰기 양 × 보관 | 한 매장 하루의 올린 바이트 |
| PUT 요청 | 복제 간격 × 활성 매장 파일 수(영업 12시간에 1초 간격이면 파일당 하루 약 4만 번) | 한 매장 하루의 PUT 수 → 매장당 한계 비용 |
| 구역 · 회사 사이 전송 | 복제 양 | 같음 |
| 둘째 회사 저장소(최소 요금 포함) | 구간 양 | — |
| 연습 서버 · 연습 VM 시간 | 연습 횟수 × 매장 수 | 되살리기 걸린 시간 |
| 가동 확인 · 전화 알림 서비스 | 고정 | — |
| 원격 화면 도움 도구 | 상업 사용 요금(무료판은 대개 상업 사용 불가) | — |
| 도메인 · 인증서 | 고정 | — |

복제 간격은 비용과 RPO 사이의 설정이다(예: 영업 중 1초, 밤 10초). '한 달 수만 원 ~ 10만 원 안팎'은 줄 항목을 채우기 전의 어림일 뿐이다. 관리형 PostgreSQL · 이중화 서버로 가면 그보다 몇 배가 될 수 있다.

업체 고르기는 1주차 일이다(열린 질문 20).

## 5. 라이선스와 기기

### 5-1. 세션을 열 때 중앙에서 확인

- 기기가 로그인(비밀번호) 하거나 등록된 카운터에서 PIN으로 사람을 바꿀 때, 중앙 서버가 계정 · 직원 · 기기 상태 · 매장 라이선스(`licences`: 상태, 기간, 기기 수, 기능)를 본다. 맞으면 세션과 함께 **기기 라이선스 표**를 준다.
- **열쇠는 두 층이다:** 매장 라이선스 증서(`licences.token`)와 '기기 표 서명 키'의 인증서는 **오프라인 루트 키**(개발자의 하드웨어 키 · 금고, `licence_signing_keys.purpose_key 'licence'`)가 서명한다. 운영 서버는 자주 바꾸는 **기기 표 서명 키**(`purpose_key 'device_token'`, `certified_by` = 루트, `not_after`)만 가진다. 앱에는 루트 공개 키만 들어 있고, 기기는 '루트 → 기기 표 키 인증서 → 표'를 확인한다. 서버가 뚫려도 아무 매장의 라이선스를 새로 서명할 수는 없고, 기기 표 키를 바꾸는 데 앱을 바꿀 필요가 없다(끊긴 기기는 옛 앱이다). 연습 서버는 루트가 시험 매장에만 허락한 전용 키(`test_only = 1`)를 쓴다(운영 키가 덜 지켜지는 연습 서버에 있을 까닭이 없다).
- 기기 라이선스 표(서명된 짧은 문서): 매장, 기기, 요금제 · 기능, 라이선스 끝날 날, 기간 끝 유예까지, **다시 받을 때까지(`refresh_by` = 받은 때 + `licences.offline_grace_days`)**, 받은 때. 기기는 IndexedDB에 둔다. 연결되어 있으면 동기화할 때마다 새로 받는다.
- 서버는 **온라인에서 새로 시작하는 일**(새 접수, 설정, 새 기기, 새 직원)마다 라이선스를 본다. 이미 일어난 오프라인 기록은 라이선스 때문에 거절하지 않는다(5-5, sync 8-12). 기기 쪽 확인은 화면 안내용이지 강제가 아니다(고친 앱은 넘을 수 있고, '유효했던 시각'도 기기가 보낸 `ageMs`로 정해지므로 막는 효과가 없다).
- **시즌 1(첫 매장, 시범):** 세션 때 중앙 확인과 기기 막기만 쓴다. 기기 표 · 오프라인 유예 · 기간 끝 제한의 강제는 설계대로 두고 **두 번째 매장 전에** 켠다(migration 6절).

### 5-2. 오프라인 유예는 14일

- 기기가 중앙에 닿지 못해도 마지막으로 표를 받은 뒤 **14일**(`licences.offline_grace_days` 기본값) 동안 그대로 쓴다. **14일이 지나면 그 기기에서 새 접수 · 품목 추가만 멈추고, 지급 · 반납 · 수납 · 보증금 · 인쇄는 계속된다**(sync 7 · 8-8, 5-5, 6-5와 같은 문장).
- **14일인 까닭:** 산 · 시골 인터넷의 긴 고장, 연휴, 우리 서버의 큰 사고를 넉넉히 덮는다. 기사 세션의 유휴 시간(14일, `session_idle_minutes.driver`)과 같아서 14일 동안 닿지 않은 기사 휴대폰은 어차피 다시 로그인해야 한다. 잃어버린 기기 · 계약이 끝난 매장의 기기가 오래 쓰이지 않게 할 만큼 짧다. 그리고 유예가 끝나도 **돈과 반납은 막지 않으므로**(5-5) 짧아서 생기는 피해가 작다.
- 기기 시계를 되돌려 유예를 늘리는 것은 마지막으로 본 서버 시각보다 벽시계가 뒤로 가면 '유예 끝'으로 보는 것으로 막는다. 완전한 막기는 아니다: 이 유예는 돈을 지키는 장치가 아니라 사용 조건이다.
- 7일(`offline_policy.max_backdate_hours` 168)이 지난 오프라인 기록은 날짜를 사람이 보게 `clock_suspect`가 붙는다(sync 2절). 유예(14일)와 다른 숫자인 것은 뜻이 달라서다: 7일은 기기 시계를 믿는 창, 14일은 라이선스 확인 없이 일하는 창.

### 5-3. 기기 등록은 중앙을 거치고 두 단계다

- 관리자가 `관리 → 기기 등록`에서 종류 · 이름 · 차량을 고르면 중앙이 일회용 번호(15분)를 준다: 헷갈리는 글자를 뺀 12자(`K7Q4-MX29-PRT3`)나 그 QR(새 기기의 카메라로). 해시는 매장 파일(`device_enrollment_codes`)과 control 길 찾기 표(`enrollment_routes`, 전역 유일)에 적는다. 새 기기는 앱 주소 하나에서 번호만 넣으므로 중앙은 이 표로 매장을 찾는다(모든 매장 파일을 뒤지지 않고, 두 매장에 같은 번호가 살아 있을 수 없다). 번호 넣기는 주소마다 · 전체로 시도 횟수를 제한하고 틀릴수록 늦춘다(`login_attempts`, 방법 `enrollment`).
- **두 단계:** 번호를 넣은 기기는 바로 붙지 않는다. 번호를 만든 관리 화면에 `새 기기(Windows · Chrome · 방금) 등록을 허락할까요?`가 뜨고 그 자리에서 눌러야 붙는다. '스키노트 점검입니다, 번호를 불러 주세요'라는 전화 한 통으로 남의 노트북이 카운터로 붙지 못한다. 번호 화면에는 `이 번호는 누구에게도 불러 주지 마세요. 공급자도 묻지 않습니다.`가 있다.
- 공급자가 콘솔에서 만든 번호(`origin_key 'supplier'`, 기기를 다시 받게 도울 때)는 **사장님이 매장 관리 화면에서 허락해야** 붙고, 기기 목록에 `공급자 기기`로 보인다(`devices.enrolled_by_supplier`).
- 붙으면 중앙이 라이선스 기기 수를 확인하고, `devices` 행과 **기기 번호**(`devices.short_no`: `shop_counters('device_short_no')`에서 1, 2, 3 …, 매장 안에서 한 번 쓴 번호는 다시 쓰지 않음, 되살리기도 건너뜀)를 만든다. 기기는 내보낼 수 없는 WebCrypto 키 쌍을 만들어 공개 키를 보내고 `navigator.storage.persist()`를 청한다(sync 7절). 사장님 알림 칸과 공급자에게 알리고, 기기 목록에 등록한 사람과 시각을 보인다.
- 기기 번호는 오프라인 카운터의 임시 접수 번호 앞자리다(`임시 1-12`, sync 8-6). 기기 이름표(`카운터 1`)와 같게 맞추기를 권한다.

### 5-4. 잃어버린 휴대폰 막기

1. 사장님(권한 `device.manage`)이나 공급자가 `관리 → 기기`에서 그 기기를 **사용 막기**. 중앙은 `devices.status_key = 'revoked'`, `revoked_at`을 쓰고 그 기기의 세션을 모두 끊는다.
2. 그 기기가 다시 연결되면 보낼 것을 받은 뒤 **기기 안의 사본 · 보낸 기록 · 라이선스 표를 지우라**는 답을 받는다.
3. **가르는 기준은 서버가 받은 때다:** `revoked_at` 전에 도착한 그 기기의 기록은 보통 기록이다. 그 뒤에 도착한 기록은 기기가 말한 시각과 상관없이 **적용하지 않고 보류**한다(장비 위치 · 잔액 · 돈통 예상 어디에도 넣지 않음). 관리자 목록 `revoked_device_record`('사용을 막은 기기(1호차 휴대폰)에서 기록 3건이 들어왔습니다. 넣지 않고 두었습니다. 맞는 기록이면 넣어 주세요.')에서 `넣기`를 눌러야 적용된다(고장 난 줄 알았던 태블릿의 정상 기록은 이 버튼으로 살린다). 돈도 명령 기록(서명된 봉투)은 남지만 수납 행과 돈통 예상에는 `넣기` 뒤에 들어간다.
4. 연결되지 않는 기기의 자료는 기기 스스로 지운다: 마지막 맞춤 뒤 기사 기기 24시간 · 카운터 72시간이 지나면 사본의 이름 · 전화 · 메모를 지우고 끝 4자리만 남긴다(sync 8-1). 끝난 업무의 작은 접수 카드는 그날 기준 시각에 지운다. 휴대폰은 뒤로 갔다가 5분 뒤 돌아오면 앱 잠금(PIN)이다(sync 7절). 그래도 기기 잠금(휴대폰 화면 잠금 · 윈도 로그인)을 꼭 켠다(10-3).

### 5-5. 라이선스 기간이 끝나면

| 때 | 되는 것 | 멈추는 것 | 화면 |
|---|---|---|---|
| 끝나기 30일 전부터 | 모두 | 없음 | 관리 화면과 머리줄 알림 칸에 `라이선스가 2월 14일에 끝납니다`(빨강 아님: 빨강은 늦음에만) |
| 끝난 뒤 유예(`expiry_grace_days`, 기본 14일) | 모두 | 없음 | `라이선스 기간이 끝났습니다 · 2월 28일까지 그대로 씁니다 · 공급자에게 연락해 주세요` |
| 유예가 끝난 뒤(제한) | **지급 · 반납 · 수납 · 환불 · 보증금 · 현장 수납 · 받음 · 매장 입고 · 현금 넘기기 · 마감 · 인쇄 · 자료 내보내기 · 조회** | 온라인에서 새로 시작하는 새 접수 · 품목 추가 · 설정 · 품목 · 요금 바꾸기 · 새 기기 등록 · 새 직원 | `새 접수`를 누르면 한 문장: `라이선스 기간이 끝나 새 접수를 받을 수 없습니다. 공급자에게 연락해 주세요.` |
| 기기가 14일 넘게 중앙에 닿지 못함 | 그 기기의 지급 · 반납 · 수납 · 보증금 · 현장 수납 · 받음 · 인쇄(연결이 필요한 일은 원래 안 됨) | 그 기기의 새 접수 · 품목 추가 | 연결 띠 `14일 동안 연결되지 않아 새 접수를 멈췄습니다 · 인터넷에 연결하면 바로 풀립니다` |

- **돈과 반납은 어떤 경우에도 막지 않는다.** 이미 빌려 간 장비를 돌려받고 돈을 받는 일은 손님과의 약속이고, 막으면 기록이 종이로 흩어진다.
- 공급자는 관리자 콘솔(그 전에는 명령줄 도구)에서 유예를 바로 늘릴 수 있다(사용 내역에 남음). 기기는 다음 동기화에서 새 표를 받는다. 공급자가 연락이 안 될 때를 위해 루트 키로 미리 서명한 '시즌 끝까지의 비상 연장'을 둘째 사람의 봉투에 둔다(12절).
- **끊긴 채 이미 받은 새 접수는 늘 받는다:** 라이선스가 끝난 뒤 시각에 만든 것이라도 접수 · 줄 · 돈을 모두 적고 `licence_lapsed_record`에 올려 청구 · 연락에 쓴다. 버리면 같은 팀의 돈이 가리킬 접수가 없어지고(수납 배분 · 보증금 FK), 종이 접수증만 남는다. 라이선스는 자료를 받는 조건이 아니라 온라인에서 새로 시작하는 일의 조건이다(sync 7 · 8-12).
- 시즌 1(첫 매장, 시범)에는 이 표의 제한을 강제로 켜지 않는다(5-1).

### 5-6. PIN과 오프라인 직원 바꾸기

- 등록된 카운터에서 4~6자리 PIN으로 사람을 바꾼다(sync 7절). 연결되어 있으면 중앙이 확인하고 `device_sign_ins`를 적는다. 중앙의 `accounts.pin_hash`는 서버 비밀(pepper)의 HMAC 위에 느린 해시라, control 백업이나 구간이 새도 4~6자리를 곧바로 풀 수 없다.
- **끊긴 동안의 PIN:** 그 매장의 **카운터 역할 직원 모두**의 PIN 확인 값(기기마다 다른 소금, 느린 해시)을 기기 키로 암호화해 매장의 모든 카운터에 둔다. 기기에서 확인하고, 5번 틀리면 그 기기에서 잠근다. **관리 권한을 가진 역할(사장님 · 관리자)의 확인 값은 기기에 두지 않는다**: 그런 승인(한도 넘는 할인, 마감 넘기기, 다시 열기)은 온라인에서 비밀번호나 휴대폰 확인으로 받는다. 계정 정지 · PIN 변경 · 역할 변경은 다음 동기화에서 확인 값을 지우고, 그 뒤 시각의 오프라인 로그인은 서버가 `unverified_sign_in`으로 올린다(sync 7절).
- PIN은 **편하게 사람을 바꾸는 장치이지 강한 잠금이 아니다.** 기록은 기기 기준이고, 켜진 PC의 확인 값은 그 브라우저의 스크립트가 쓸 수 있으므로 PC를 만질 수 있는 사람은 알아낼 수 있다고 본다. 기기 자체의 잠금이 필요하다(10-3). 끊긴 동안 나간 현금은 마감 미리 보기에 `끊긴 동안 나간 현금 · 누가`로 따로 보인다.

## 6. 백업과 되살리기

### 6-1. 무엇을 어디에

**되살리는 길은 둘이고 섞지 않는다**(sync 10-1): ① **PITR** = 복제 도구가 직접 올린 자기 세대(스냅샷) + WAL. ② **`VACUUM INTO` 스냅샷** = 그 자체가 되살리는 지점이고, 그 뒤는 작업 기록 구간의 after-image로 이어 붙인다. 원본 파일의 WAL 프레임은 `VACUUM INTO`가 페이지를 새로 짠 다른 파일 위에 적용할 수 없다.

| 무엇 | 언제 | 어디 | 얼마나 | 쓰임 |
|---|---|---|---|---|
| **WAL 복제본**(모든 매장 파일 + control; 도구의 세대 + WAL) | 커밋마다 몇 초 안(영업 중 1초, 밤 10초) | 같은 업체의 다른 구역 · 지역 객체 저장소(둘째 지역이 없으면 다른 회사에도) | 7일(`backup_policy.wal_keep_days`) | 7일 안의 **아무 초로나** 되살리기(PITR). 첫째 길 |
| **작업 기록 구간**(`journal_exports`) — 개인정보 없는 부분(`part_key 'main'`: 작업 기록 · 명령 기록 · 개인정보 칸을 뺀 after-image, 앞뒤 해시) | 1분마다(또는 500 rev마다) | **다른 회사의 한국 저장소**(객체 잠금) | 시즌 + 지난 시즌 | 스냅샷을 이어 붙이는 둘째 길, 지역 · 업체 사고, 해시 사슬 확인, 나중의 PostgreSQL · 혼합 옮기기(data-model 9절) |
| 작업 기록 구간 — 개인정보 부분(`part_key 'pii'`: `event_pii`, after-image의 개인정보 칸) | 같음 | 같은 곳의 따로 된 객체, 매장 · 달마다 다른 데이터 키 | **35일**(`journal_pii_keep_days`, 저장소 수명 규칙) | 되살리기에 개인정보를 채움. 35일보다 오래된 지점으로 되살리면 비어 있는 것이 정상 |
| 날마다 스냅샷(`VACUUM INTO`, 공개 키 암호화) | 새벽 4시. 가져오기 전(`pre_import`) | 다른 구역 저장소(객체 잠금) | 35일(`daily_keep_days`) | 그 자체가 되살리는 지점(길 ②) |
| 주 스냅샷 · 손님 정보 지움 | 월요일 새벽 4시 | 같은 곳 | 26주 | 오래전으로 되돌려야 할 때. 이름 · 전화를 지운 사본(10-5) |
| 시즌 끝 스냅샷 · 손님 정보 지움 | 시즌 마지막 마감 뒤 | 같은 곳 | 5년(세무 보관 의무 기간을 세무 담당과 확인, 열린 질문 13) | 장부 · 돈 · 마감 기록 보관(개인정보 칸 목록으로 지움, 10-5) |
| control 파일 | 매장 파일과 같이 | 같은 곳 | 같음 | 계정 · PIN · 등록 번호 길 찾기 · 라이선스 · 공급자 허락 |
| 기기의 보낸 기록 | 서버가 받았다고 답한 명령과 서버가 정한 값 | 각 기기(카운터는 도우미에도 한 벌) | 7일(`sent_log_days`, 이름 · 전화 원문은 24시간) | 복구 뒤 다시 보냄(sync 10-2) |
| 가게 보관용 내보내기 | 날마다 마감 뒤 | 카운터 PC의 폴더(6-6) | 14개 | 사장님이 가진 자기 자료. 손님 정보를 뺀 장부 사본은 기본 켬 |

- **암호화:** 모든 백업 파일은 우리 서버가 **올리기 전에 공개 키로 암호화**한다(예: age 수신자). 서버에는 매장마다의 공개 키만 있고, 푸는 개인 키는 되살리기 절차와 연습 VM에만 있다(3절). 저장소 회사는 열 수 없고, 서버가 뚫려도 백업을 읽을 수 없다. **올리기 전 암호화는 1주차 WAL 복제 스파이크의 통과 조건**이다: 도구가 지원하지 않으면 그 도구를 쓰지 않거나 암호화 층을 더한다(저장소 쪽 암호화만으로 대신하지 않는다: 가장 완전한 사본인 7일의 모든 쓰기가 저장소 회사가 열 수 있는 상태가 된다).
- **지울 수 없게:** 저장소 버킷은 버전 관리 + 객체 잠금(보관 기간 동안 지울 수 없음)을 켜고, 서버의 저장소 키에는 '이전 판 지우기' 권한을 주지 않는다. 다른 회사 저장소의 키는 쓰기만 된다. 서버가 뚫려 버킷을 비우려 해도 되살릴 길이 남는다(랜섬웨어).
- 모든 스냅샷 · 구간은 control `backups` · `journal_exports`에 sha256, epoch, `max_rev`, 데이터 키(`key_id`)와 함께 목록으로 남고 `tenant_epochs.max_rev_seen`을 올린다.
- 복제 도구가 WAL 체크포인트를 맡는 방식이면 앱 연결의 자동 체크포인트 설정을 그 도구의 안내대로 맞춘다(1주차 스파이크).
- **목록은 저절로:** 복제 설정과 스냅샷 · 연습 목록은 control `tenants`(활성)에서 만든다. 손으로 목록에 더하는 단계가 없다. `shop.provision`과 `data_location` 바꾸기(가져오기, 5-2)는 첫 스냅샷이 다른 구역에 올라가고 복제 위치가 확인될 때까지 그 매장의 기기 등록을 막는다(8절에 빠진 매장 알림).

### 6-2. 되살리기

- 순서는 sync 10-2 그대로다: 새 서버(또는 새 파일)에 길 ①이나 ②로 목표 시각까지 → **새 epoch, `rev_floor` = 지금까지 본 가장 큰 rev + 1,000,000** → 접수 번호 · 묶음 번호 +500, 기기 번호 +10 → 복구 뒤의 outbox는 `replayed`(문자 · 카드는 스스로 나가지 않음) → 서버를 켜면 기기들이 보낸 기록을 **서버가 정했던 값과 함께** 다시 보냄(같은 id · 같은 접수 번호).
- 오프라인 카운터의 임시 접수 번호는 기기가 매기고 기기 번호가 앞자리라 복구와 상관없이 겹치지 않는다. 최종 접수 번호는 +500 건너뛰기로 종이 접수증의 번호와 겹치지 않는다.
- **지운 손님 정보를 되살리지 않는다:** 되돌린 지점 뒤에 있었던 `customer.anonymize`는 버리는 쪽의 작업 기록 구간에서 찾아 다시 적용한다(10-5). 같은 구간에서 되돌린 지점 뒤에 등록된 기기의 `devices` 행 · 공개 키도 다시 만든다.
- **세 층으로 되살린다**(가장 흔한 것부터):
  1. **VM만 죽음**(네트워크 볼륨은 멀쩡함): 새 VM을 스크립트로 만들어 그 볼륨을 붙인다. 가장 빠르다.
  2. **디스크를 잃음:** 새 VM에 복제본을 되살린다(길 ①, 모자라면 ②).
  3. **지역 · 업체 사고:** 다른 회사(한국)에 같은 스크립트로 새 서버를 세우고 그 회사 저장소의 복제본 · 구간으로 되살린다.
- **주소를 바꾸지 않는다:** 앱 주소는 예약 공인 IP나 부하 분산기에 두어 새 VM에 IP를 옮기면 되게 한다(DNS 전파를 기다리지 않음). 업체를 옮기는 3층만 DNS를 바꾸며, 그래서 TTL은 60초로 둔다. 인증서는 DNS-01로 받거나 비밀값과 함께 보관한다(HTTP-01은 DNS가 먼저 바뀌어야 한다).
- **휴대폰에서 누르는 한 단계:** 되살리기는 개발자 휴대폰에서 누를 수 있는 작업 버튼 하나다(층과 목표 시각을 고르면 스크립트가 끝까지). 노트북 · 콘솔 로그인 · 설치 스크립트 · 비밀값 찾기를 사람이 차례로 하지 않는다.

### 6-3. 되살리기 연습

- **새 VM에 한다:** 연습은 스크립트로 새 VM을 만들고 → 되살리고 → 확인하고 → 시간을 재고 → VM을 지우는 자동 작업이다. 그 스크립트가 곧 재해 절차다(6-2의 층 1 · 2, 달마다 한 번은 층 3처럼 다른 회사 저장소만으로). 길 ①과 ②를 번갈아 잰다.
- **언제:** 개장 전에는 손으로(5주차에 절차서 첫 판, 7주차 · 10주차에 끝까지 두 번, migration 6절), 시즌 중에는 매주 월요일 새벽 4시 30분(`drill_weekday` · `drill_time`) 자동. 자동 연습은 시즌 첫 달 안에 켠다. 달 연습(층 3)을 빠뜨리면 개발자에게 알림이 간다.
- **확인하는 것**(sync 10-3): `integrity_check` · `foreign_key_check` · 검증기 전체. 운영과 견주는 것은 되살린 파일이 도달한 rev R에서 할 수 있는 것만: 작업 기록 사슬 해시 · 장부 행 해시 · 추가만 하는 장부 표의 `created_rev ≤ R` 행 수. 그리고 보낸 기록을 흉내 낸 다시 보내기가 같은 id · 번호로 들어가는지.
- 결과는 control `restore_drills`(길 · 저장소 · 도달한 rev, 통과 · 실패, 걸린 시간 = 잰 되살리기 시간, 보고서)에 적는다.
- **누가 보나:** 개발자는 관리자 콘솔 대시보드와 휴대폰 알림(실패 즉시). 매장은 `관리 → 백업` 카드 한 줄: `되살리기 연습 통과 · 월요일 04:30 · 12분`. 실패하면 머리줄 알림 칸에 `백업 확인 중 · 공급자가 고칩니다`(빨강 아님). 사장님은 월요일 아침에 한 번 본다.

### 6-4. 잃을 수 있는 것과 되살리는 시간(RPO · RTO)

RTO는 **알림을 받은 때부터** 잰다. 사람이 알아채는 시간은 따로 가정한다: 영업 시간에는 15분 안, 밤에는 다음 개장 1시간 전까지(깨움 알림, 8절).

| 일 | 잃는 것(RPO) | 다시 쓰기까지(RTO 목표) | 그동안 |
|---|---|---|---|
| 가게 인터넷 끊김 | 없음(기기 안의 기록이 지워지지 않는 한, sync 8-5) | — | 예비 회선으로 넘어가거나, 기기가 오프라인으로 일하고 연결되면 보냄 |
| 우리 서버 프로그램 멈춤 · 다시 시작 · 배포 | 없음(기기가 같은 요청번호로 다시 보냄) | 몇 초 ~ 몇 분 | 연결 띠 |
| VM만 죽음(볼륨 멀쩡) | 없음 | 30분(층 1) | 기기 오프라인 |
| 디스크 · 가상 서버 망가짐 | 서버 쪽 **5초 이하**(보통 1초 안팎). 기기에서 온 명령은 기기가 다시 보내 **0** | **1시간**(첫 매장 기준 30분 목표, 연습으로 잰다) | 기기 오프라인 |
| 지역 · 업체 전체 멈춤 | 다른 회사 저장소에 WAL 복제본이 있으면 몇 초, 구간만 있으면 1분 이하 + 기기 다시 보냄 | **하루 안**(층 3을 연습으로 재어 근거가 생기면 줄인다) | 기기 오프라인, 종이 대비(6-5) |
| 복제 도구 · 복제본 사고 | 없음(운영은 그대로). 되살려야 한다면 작업 기록 구간까지(1분 이하) + 기기 다시 보냄 | — | 개발자 알림, 새 스냅샷 곧바로 |

| 카드 | 카드 돈은 단말기 기록과 카드사 정산으로 맞춘다(sync 9절) | — | — |

### 6-5. 중앙 서버가 멈추면

- 기기는 연결이 끊긴 것과 똑같이 일한다(sync 8절): 카운터는 지급 · 반납 · 적재 · 권 주기 · 바꿔 드림 · 수납 · 보증금 · 새 현장 접수 · 품목 추가 · 인쇄, 기사는 받음 · 전달 · 현장 수납 · 권 추가 · 방문 결과 · 순서.
- **얼마나 오래:** 돈 · 반납은 끝없이(큐는 나이로 버리지 않음, sync 8-5). 라이선스 표를 마지막으로 받은 뒤 14일이 지나면 그 기기에서 **새 접수 · 품목 추가만** 멈추고, 지급 · 반납 · 수납 · 보증금 · 인쇄는 계속된다(5-2). 7일이 넘은 기록은 날짜 확인이 붙는다.
- 끊긴 동안 안 되는 일: 약속 바꾸기 · 취소 · 연장 · 할인 직접 입력 · 마감 · 매장 입고 · 현금 넘기기 · 빨리 확인 · 업무 옮기기 · 설정(sync 8-2). 서버가 1시간 안에 돌아오면 거의 느끼지 못하고, 밤까지 안 돌아오면 마감은 다음 날 아침에 한다(기준선이 늦은 기록을 맞는 날에 센다, data-model 3-3).
- **종이 대비:** 개장일과 성수기에는 아침마다 오늘 대여 장부와 수거 목록을 A4로 한 장씩 뽑아 둔다(인쇄는 오프라인에서도 기기가 그린다). 끊긴 동안 하지 못하는 결정(약속 바꾸기 · 취소 · 할인)은 **종이 양식**(`연결된 뒤 할 일`: 팀 · 끝 4자리 · 무엇을 · 누가)에 적고 연결되면 넣는다. 기기가 모두 꺼지는 일(정전)이 나면 종이에 적고 나중에 넣는다.

### 6-6. 가게 보관용 내보내기

- 둘이다. **손님 정보를 뺀 장부 사본**(`owner_export_scrubbed`, 기본 켬: 접수 번호 · 끝 4자리 · 품목 · 돈 · 마감)과 **손님 정보 포함**(`owner_export`, 사장님이 따로 켬). 날마다 마감 뒤 서버가 만든 파일을 카운터 PC가 받아 정한 폴더에 둔다(14개를 돌려 씀): 매장 파일의 사본과 읽기 쉬운 표(접수 · 수납 · 마감, 엑셀로 열 수 있는 모양).
- **공개 키로 잠근다:** 매장을 열 때 키 쌍을 만들어 개인 키는 사장님께 드리는 **복구 열쇠 종이**(QR, 금고)에만 두고, 서버와 PC에는 공개 키만 둔다. 서버가 공개 키로 파일을 만들어 내려 준다. 그래서 공급자도, 카운터 PC를 만지는 사람도 파일을 열 수 없고, 공급자가 없어져도 사장님이 자기 장부를 가진다(12절).
- 손님 정보 포함 파일을 켤지는 사장님이 정한다(열린 질문 22). 가게 PC에 둘 때의 안전 조치는 전문가 확인 목록(10-6)에 있다. 되살리기의 마지막 길로도 쓸 수 있다(epoch · `max_rev`가 들어 있다).

### 6-7. 매장 끝내기(계약이 끝날 때)

1. 사장님이 끝내겠다고 하면 `tenants.closing_requested_at`을 적고 5-5의 제한 모드로 N일(계약서에 적음) 둔다. 돈 · 반납 · 내보내기는 된다.
2. **전체 내보내기**(손님 정보 포함, 6-6의 공개 키로 잠금)를 드리고 받았다는 확인을 받는다.
3. 운영 파일을 지우고, 복제 목록에서 빼고(목록이 `tenants`에서 나오므로 상태를 바꾸면 빠짐), **그 매장의 데이터 키를 파기**한다: 복제본 · 스냅샷 · 구간 · 주 · 시즌 사본이 저장소 수명 규칙을 기다리지 않고 읽을 수 없게 된다. 되살리기 연습 흔적은 원래 남지 않는다(VM을 지움).
4. `tenants.data_destroyed_at`과 `platform_audit_log`에 적고 사장님께 파기 확인서를 드린다.
5. 세무 보관을 우리가 대신해야 한다면(전문가 확인, 10-6) 손님 정보를 지운 사본만 따로 된 키로 남긴다.

## 7. 업데이트

- **서버 먼저, 기기는 나중.** 서버는 바로 전 판 명령의 upcaster와, 오프라인 허용 명령은 큐 보관 기간보다 오래된 판까지 받는다(sync 2절).
- **스키마 배포와 코드 배포를 나눈다(되돌리기는 코드만).** 실행기는 이 앱이 모르는 마이그레이션이 적용된 파일을 **읽기 전용**으로 연다(data-model 7-3). 그래서 마이그레이션 N이 든 배포를 N−1로 되돌리면 모든 매장 · control이 읽기 전용이 된다. 순서:
  1. **스키마 배포 N:** 마이그레이션(열 · 표 · sys 행 더하기)과 그것을 아는 코드. 새 열을 쓰는 기능은 꺼 둔다(기능 설정 · 코드의 스위치). 동작이 거의 바뀌지 않으므로 되돌릴 일이 드물다.
  2. **코드 배포 N+1:** 그 열을 쓰는 기능을 켠다. 문제가 나면 **N으로 되돌린다**(N은 스키마 N을 알므로 읽고 쓴다).
  3. 한 매장 파일의 마이그레이션만 실패하면 그 파일만 읽기 전용이고 나머지는 그대로다. 앱을 되돌리지 않고 **앞으로 고친다**(고친 앱으로 다시 시작하면 남은 판부터 이어 적용).
  - 되돌리기 확인 목록의 첫 줄: '이 배포에 마이그레이션이 있었나' — 있었으면 되돌리지 않고 앞으로 고친다.
  - 실행기가 '모르는 판이지만 뒤로 호환'인 마이그레이션을 읽기 · 쓰기로 여는 표시(예: `compatible_from_app`)는 여러 판이 함께 도는 때(프로세스 나누기 · 카나리)에 1주차 실행기 마무리와 함께 정한다(roadmap).
- **두 종류의 배포:**
  - **코드만 바뀐 배포:** 영업 중 한가한 시간에도 한다(오프라인 설계 덕에 몇 초의 보냄 대기로 끝난다). 배포 뒤 합성 확인(아래)을 통과해야 끝이다. 12월 27일 11:00 확정 창에서 보증금이 두 번 더해지는 버그 같은 것을 하루 종일 두지 않는다.
  - **마이그레이션이 든 배포:** 저녁에 사람이 승인하면 **05:00에 자동으로 도는 예약 작업**이다(날마다 스냅샷 04:00, 연습은 따로 된 VM). 클라우드에서는 파일마다 `pre_migration` `VACUUM INTO`를 하지 않고 '복제 지연 0 확인 + 그 순간의 복제 위치(시각 · rev)'를 되살림 지점으로 적는다. `post_migration` 스냅샷은 쓰기를 연 뒤 작업 프로세스가 비동기로 올리고, 실행기가 쓰는 로컬 `backups/`는 올린 뒤 지운다(실행기에 백업 방식을 넘기는 자리를 1주차 실행기 마무리에서 더한다).
- **배포 길:** GitHub Actions에서 시험 · 검사 · 빌드 → 연습 서버에 자동 배포 → **배포 전 자동 확인**: 되살리기 연습 칸(한국 안, 바깥 연결 없음)에서 마지막으로 되살린 운영 매장 파일 전부에 새 판의 마이그레이션 + 검증기 + 기록한 명령 몇백 건 다시 넣기(모드 E)를 돌리고, 실패하면 배포를 막는다(가져온 옛 자료의 `legacy_*` 행과 NULL 조합에서만 실패하는 마이그레이션 · 계산을 잡는다) → 사람이 눌러 운영에 배포 → **배포 뒤 합성 확인**: 운영 안의 시험 매장(`is_test = 1`)에 합성 명령(새 접수 · 수납 · 반납 · 마감 미리 보기)을 돌려 금액을 기대값과 견준다. 두 번째 매장 전에 프로세스를 나누면(2-2) 시험 매장 → 한 매장 → 전부 순서의 카나리 배포를 한다.
- **배포 권한:** 운영 · 연습 배포는 GitHub `production` · `staging` 환경(Environments)에서만 돈다: 필수 승인자, `main`에서만, 대기 시간. 가능하면 OIDC로 짧은 자격 증명을 받고, 서버에는 서명된 빌드만 받아 배포 스크립트만 돌릴 수 있는 좁은 배포 계정을 둔다. 끌어오기 요청(포크 포함) 작업에는 비밀값을 주지 않고(`pull_request_target`를 쓰지 않음), 제3자 액션은 커밋 SHA로 고정하며, 비밀 스캔과 push protection을 켠다. 라이선스 루트 키 · 백업을 푸는 키는 Actions에 두지 않는다. `main`에 올리면 체험판(Pages)만 바로 바뀌고 운영 서버는 따로 누른다.
- **PWA 판이 바뀌는 때:** 서비스 워커가 새 판을 받아 두고 **열린 창이 없고 보냄 대기가 0일 때만** 바꾼다(ui 7절). 하루 종일 창을 닫지 않는 카운터 PC는 그런 때가 오지 않으므로, 카운터는 **마감 뒤나 05:00 ~ 06:00에 열린 창 · 초안 · 보냄 대기가 없으면 스스로 다시 연다**. 기사 기기는 앱을 켤 때 바뀐다. 머리줄 알림 칸에 `새 버전`. 오래 오프라인이던 기기는 옛 판 그대로 큐를 먼저 보내고(서버의 upcaster가 받음) 그다음 바뀐다.
- **판 차이:** 기기는 자기 계약 판(`devices.command_contract`)과 앱 판 · 스키마 판을 알리고, 서버는 동기화 답에 `minClientVersion`을 싣는다. `minClientVersion`은 **배포 창에서만** 올린다(영업 중 아무 때나 `새 버전으로 바꿉니다`가 떠 확정 창을 쓰던 직원 화면이 새로 고쳐지지 않게). 그보다 옛 기기는 큐를 다 보낸 뒤 `새 버전으로 바꿉니다` 한 문장과 함께 바뀐다. 서버는 그 기기가 모르는 표 · 열 · sys 키를 sync · bootstrap에서 빼고 준다(sync 5절: 서버가 열을 더해도 옛 기기가 reset을 받지 않음). 큐에 든 사실은 판 때문에 버리지 않는다. 감시에 '최소 판보다 옛 기기 · 3일 넘게 옛 판인 기기'를 둔다(8절).

## 8. 감시와 알림

알림은 두 등급이다. **깨움**은 전화 알림 서비스로 보내고 5분 안에 되받지 않으면 다시, 그다음 둘째 연락처(12절)로 올린다. **아침 묶음**은 아침 한 번 메시지로 모은다. 개장 1시간 전부터는 모든 것이 깨움이다.

| 무엇 | 기준 | 등급 |
|---|---|---|
| 바깥에서 본 서버 살아 있음(`/healthz`, 1분마다, 업체 밖의 가동 확인 서비스) | 2번 연속 실패 | 깨움 |
| WAL 복제 멈춤: **올리지 않은 커밋이 있는 동안의 시간**(로컬 WAL 위치 − 복제 위치) — 쓰기가 없는 밤에는 늘지 않는다 | 60초 넘음은 아침 묶음, 5분 넘음은 깨움 + 매장 `백업` 카드에 `백업 복사 늦음` | 아침 · 깨움 |
| 매장 명령 줄 멈춤: 매장마다 '줄에서 가장 오래 기다린 명령의 나이', 영업 시간 중 '마지막 커밋 뒤 지난 시간', 처리 중 기록이 남은 채 다시 시작(독 명령, 2-2) | 명령 나이 10초, 명령 시간 2초 넘음 | 깨움 |

| 스냅샷 · 작업 기록 구간 실패 | 한 번 | 아침(구간이 30분 넘게 밀리면 깨움) |
| 복제 · 스냅샷 · 연습이 없는 활성 매장 | 복제 상태 · 어제 스냅샷 · 지난주 연습 결과가 없음 | 깨움 |
| 되살리기 연습 | 실패 · 걸린 시간이 목표의 절반을 넘음 · 달 연습(층 3)을 빠뜨림 | 아침(실패는 영업 시간 전이면 깨움), 매장 `백업` 카드 |

| 기기(매장별 기기 목록) | 마지막 맞춤, 보냄 대기 수, 시계 차이, 앱 판 · 최소 판보다 옛 기기 · 3일 넘게 옛 판(`device_sync_cursors`) | 관리자 콘솔, 매장 마감 미리 보기(**보낼 기록이 남은 모든 기기**: 카운터 · 차량) |

- 시즌 중에는 밤에도 깨움이 온다. 개발자 휴대폰은 깨움 알림이 방해 금지 모드를 넘게 둔다.
- **기록(로그)에는 손님 이름 · 전화 · 자유 글을 넣지 않는다.** 요청 본문을 적지 않고 id와 결과만 적는다. 바깥 감시 · 오류 수집 서비스를 쓰면 개인정보가 나가지 않게 하고, 해외 서비스면 전문가 확인 목록(10-6)에 올린다.
- **운영 자료는 공개된 곳과 AI 도구에 넣지 않는다:** 운영 자료 · 화면 캡처는 GitHub(이슈 · 끌어오기 요청 · 커밋), AI 도구, 해외 서비스에 넣지 않는다(공개 저장소라 화면 캡처 속 손님 이름 · 번호가 그대로 공개된다). 지원 기록은 비공개 곳에 둔다. 가져오기 파일 · 가게 보관용 내보내기는 저장소 밖 폴더에서만 다루고(`.gitignore`가 `data/` · `exports/` · `*.csv` · `*.xlsx` · `*.age` · `*.enc`를 막음), 전화번호 · 키 모양 검사를 저장소 전체의 커밋 전 검사에도 건다(`check:dist`는 빌드만 본다). AGENTS.md에도 이 규칙을 적는다(README 열린 질문 30).
- 매장 화면에는 매장이 알아야 할 것만 쉬운 한 문장으로 보인다(`백업 복사 늦음`, `되살리기 연습 통과`). 빨강은 늦음에만 쓰므로 이 알림은 빨강이 아니다.

## 9. 원격 지원

- **시즌 1은 명령줄 도구로 지원한다**(관리자 콘솔 `apps/admin`은 시즌 뒤). 도구는 운영 파일을 직접 열지 않고 **서버 API**(가린 읽기 모델)를 거치며, 모든 호출을 `platform_audit_log`(분류 `support`)에 적는다. 매장마다: 기기 목록(마지막 맞춤 · 보냄 대기 · 앱 판 · 시계 차이), 열린 확인 필요 수, 최근 오류, 라이선스, 백업 · 되살리기 연습 결과.
- 할 수 있는 일(모두 `platform_audit_log`에 남음): 기기 등록 번호 만들기(사장님이 허락해야 붙음, 5-3), 기기 사용 막기, 라이선스 유예 늘리기, 기기 다시 받기(범위 reset), 검증기 다시 돌리기, 되살리기 연습 바로 하기, 보류된 명령 보기(`held`).
- **매장 자료 보기:** 기본은 손님 이름 · 전화를 가린 모양이다. 가리지 않은 자료를 봐야 하면 매장의 사장님 · 관리자가 `관리`에서 `공급자 도움 허락 · 2시간`을 눌러야 켜진다(control `support_access_grants`, 까닭과 끝 시각). 본 것은 사용 내역에 남고 매장 알림 칸에 보인다.
- **비상 접근(break-glass):** 운영 파일을 직접 여는 것(sqlite3, SSH)은 비상용 계정으로만 한다. 셸 기록은 서버 밖으로 보내고, 쓰면 그 매장 알림 칸에 `공급자가 자료를 직접 열었습니다 · 시각 · 까닭`을 띄운다. SSH는 하드웨어 키(FIDO2)나 짧은 인증서만 쓰고 비밀번호 로그인은 끈다.
- **화면 도움:** 카운터 PC의 화면을 함께 봐야 하면 원격 화면 도움 프로그램을 쓰되, **스키노트 관리 화면의 `원격 도움 받기` 버튼으로만 시작한다**: 앱이 1회용 확인 말(단어 두 개)을 보이고(`support_access_grants` 종류 `remote_screen`), 공급자가 그 말을 먼저 말해야 사장님이 도구를 켠다. 그 화면에 `공급자는 먼저 전화해 원격 연결을 요청하지 않습니다`를 적는다('스키노트 공급자입니다' 전화 사기에 원격 제어 앱이 그대로 쓰이지 않게). 무인 접속은 끄고, 세션마다 새 번호를 쓰고, 끝나면 도구를 닫는다. 시작 · 끝은 `platform_audit_log`에 적고 매장 알림 칸에 남긴다. 도구는 **한국 안 중계**를 쓰는 것을 고른다: 해외 회사 중계로 화면(손님 이름 · 전체 번호가 보이는 접수증)이 나가면 10-7과 다르다. 해외 도구라면 10-6 7번 · 처리방침 · 위탁 목록에 올린다.
- 체험판에는 관리자 콘솔 · 계정 · 실제 손님 자료가 없다(AGENTS.md).

## 10. 보안과 개인정보

### 10-1. 연결과 저장

- 연결: HTTPS만, TLS 1.2 이상, HSTS(3절). SSE도 같은 연결.
- 서버 디스크: 업체의 볼륨 암호화를 켠다. 매장 파일은 서버 안에서 권한을 좁힌 폴더에 둔다.
- **열쇠를 나눈다**(서버 한 대가 모든 열쇠를 쥐지 않게):
  - 백업: 올리기 전에 **매장마다의 공개 키로** 암호화(6-1). 서버에는 공개 키만. 푸는 개인 키는 되살리기 절차 · 연습 VM(업체 KMS나 따로 된 계정), 개발자의 비밀번호 관리자, 오프라인 봉투, 둘째 사람 봉투(12절). 매장 키를 파기하면 그 매장의 모든 사본을 읽을 수 없다(6-7).
  - 저장소: 버전 관리 + 객체 잠금, 서버 키에는 지우기 권한 없음, 다른 회사 저장소 키는 쓰기만(6-1).
  - 라이선스: 루트 키는 오프라인, 서버는 기기 표 서명 키만(5-1).
  - 키를 바꿀 때는 옛 키도 보관 기간이 끝날 때까지 둔다.
- 기기: 보냄 대기 · 보낸 기록 · PIN 확인 값은 등록 때 만든 내보낼 수 없는 기기 키로 암호화한다(sync 8-1). 오늘 일할 사본(OPFS의 SQLite)은 브라우저가 따로 암호화하지 않으므로, 암호화 SQLite WASM 빌드를 쓸 수 있는지 1주차에 확인한다. 암호화해도 켜진 브라우저는 키를 쓸 수 있으므로(잠금이 풀린 휴대폰에는 효과가 없음) 스스로 지우기 · 앱 잠금 · 꼭 필요한 것만 두기가 따로 있다(5-4, 10-5).

### 10-2. 매장 사이의 벽과 공급자의 접근

- 2-5 그대로: 세션이 정한 매장의 파일만 연다, 트랜잭션마다 매장을 다시 본다, 매장마다 파일 · 복제 경로 · 데이터 키가 따로다, 모든 매장 표는 `shop_id` 복합 FK다.
- 공급자(개발자)의 매장 자료 접근은 9절처럼 서버 API를 거친 가린 모양이 기본이고, 가리지 않은 보기는 매장의 허락(`support_access_grants`)과 사용 내역이 필요하다. 파일을 직접 여는 것은 비상 접근뿐이고 매장에 보인다.

### 10-3. 직원 계정 · PIN · 기기

- 계정은 control(`accounts`: 로그인 영역 + 이름, argon2id · scrypt 해시). 처음 로그인하면 비밀번호를 바꾼다. 매장 직원의 비밀번호 로그인은 **등록된 기기에서만**, 등록 안 된 곳에서는 사장님 · 관리자만 2단계 인증과 함께(sync 7절). 잠금은 (계정, 기기 또는 주소)마다 늘어나는 지연이다(남이 가게 계정을 잠글 수 없게).
- 세션은 기기 키에 묶인 HttpOnly 쿠키다(3절). 민감 동작은 비밀번호를 다시 묻고 사장님께 알린다.
- 카운터에서는 PIN으로 사람을 바꾼다(5-6). 기사 기기는 긴 세션(14일) + 앱 잠금.
- 기기는 등록 번호로만, 두 단계로 붙고(5-3), 잃어버리면 막는다(5-4). **카운터 PC는 윈도 로그인, 태블릿 · 휴대폰은 화면 잠금을 켠다**(설치 목록 11절). 카운터 PC는 Chrome 관리 정책으로 이 앱 원본의 사이트 자료 지우기를 막는다(sync 8-5).
- 권한은 역할(`roles` · `role_permissions`)과 범위(기사는 자기 차량)로 정하고 모든 명령에서 본다(sync 7절).

### 10-4. 사용 내역(감사)

- 매장: `events`(해시 사슬, 명령마다 한 줄, 개인정보 없음) + `config_changes`. 누가 어느 기기에서 무엇을 했는지 남는다.
- **읽기도 남긴다:** 개인정보를 본 것(전체 번호 보기, 끝 4자리 찾기, 목록 인쇄, 내보내기, 기기에 내려 준 오늘 일할 사본)은 `pii_access_log`에 한 줄(목록 조회는 묶어 한 줄). 서버가 준 읽기만 적고, 끊긴 기기가 자기 사본에서 본 것은 사본을 내려 준 한 줄로 갈음한다. 보관 기간(`retention.pii_access_days`, 시작 값 365일)은 전문가 확인 항목이다(10-6).
- 플랫폼: `platform_audit_log`(로그인, 라이선스, 기기 막기 · 등록, 백업 · 되살리기, 내보내기, 공급자의 매장 자료 보기 · 원격 화면 · 비상 접근). 해시 사슬.
- **사슬의 끝을 매장도 쥔다:** 매장 파일 · 사슬 · 구간을 모두 우리가 쥐면 우리(또는 서버를 뚫은 사람)가 사슬을 다시 계산할 수 있어 돈 다툼에서 증거가 되지 못한다. 그래서 날마다 **마감표(가게가 받아 인쇄하는 것)에 그날 마지막 사슬 해시와 rev를 짧게 찍고**, 구간은 객체 잠금(WORM) 저장소에 둔다(6-1).
- 주소(IP)는 `ip_hash`에 **키가 있는 HMAC**으로 두고 키를 바꾼다(IPv4의 sha256은 42억 개뿐이라 곧 풀린다). 조사할 때 원래 주소가 필요하면 보관 기간을 정해 원문을 따로 둔다(전문가 확인).
- 모두 추가만 하고(트리거; `pii_access_log`는 보관 기간이 지나면 지움), 백업에 함께 간다.

### 10-5. 손님 이름과 전화

- **모으는 것:** 대표자 이름과 전화(현장 대여는 전화가 설정에 따라 필수, `walk_in_phone_required`), 사이즈 미리 받기의 일행 이름 · 치수, 세금 문서의 신원(쓰는 매장만). 주민번호 같은 고유식별정보는 모으지 않는다. 기사 기기의 위치는 모으지 않는다(나중에 차량 위치를 더하면 위치정보 규칙을 따로 확인).
- **어디에(개인정보 칸 목록):** 개인정보가 들어갈 수 있는 칸을 **한 곳의 목록**으로 둔다(계약 패키지의 상수, 1주차). 지우기(`customer.anonymize`) · 보관 기간 · 손님 정보를 지운 사본 · 구간 나누기(6-1)가 모두 그 목록을 쓰고, 새 열이나 JSON 스키마에 개인정보 표시가 없으면 CI가 막는다. 목록: 고객 · 접수 대표자 스냅샷 · 일행 · `is_pii` 속성 · 문자 기록(`message_deliveries`)과 **문자 outbox의 `payload_json` · 업체 응답** · 인쇄 문서 · 세금 문서 신원 · `event_pii` · **확인 필요(`review_items`의 `message` · `message_params_json` · `detail_json`)와 알림(`notifications.params_json`)** · **control `inbound_events.payload_json`** · **옛 자료(`legacy_records` · `legacy_events`)** · 장부의 자유 글 칸. 장부 행과 작업 기록에는 없다(data-model 원칙 16).
  - 확인 필요 · 알림은 팀 이름 대신 **접수 id를 매개변수로** 저장하고 화면에서 그릴 때 이름을 붙인다(`{team}`은 대표자 이름이다). 이미 그려 둔 `message`는 지우기가 다시 그린다.
  - 문자 outbox의 수신 번호 · 본문은 결과가 난 뒤 30일(`retention.outbox_payload_days`), control `inbound_events`의 본문은 가져간 뒤 30일에 비운다.
  - 옛 자료는 가져올 때 마지막 이용이 1,095일(보관 기간)이 넘은 손님을 지운 채 넣고, 지우기가 `legacy_*` 행도 가린다(migration 5-2).
  - 명령 기록의 지문(`command_log.fingerprint`)은 개인정보를 참조로 바꾼 정본의 **매장 비밀 키 HMAC**이다(소금 없는 sha256이면 번호 1억 개를 대입해 되찾을 수 있다, sync 6절).
- **화면에서 가리기:** 목록(장부 · 수거 목록 · 한 번에 수납 · 끝 4자리 찾기)에는 이름과 **끝 4자리**만 보인다(`김민수 · 0025`). 전체 번호는 접수증과 기사 업무 판에서만 보인다(확인하고 걸려고; 볼 때마다 `pii_access_log`). 기사 목록 줄에는 번호를 적지 않고 `전화` 버튼으로 건다. 인쇄 수거 목록은 `010-…-0025`. 번호를 더 가려야 하는지(예: 접수증도 가운데를 가리고 누르면 보기)는 전문가 확인 목록(10-6)과 함께 정한다.
- **보관 기간:** 기본 3년(`retention.customer_pii_days` 1,095) 뒤 이름 · 전화를 지우고 `anonymized_at`을 적는다(행과 금액은 남음). 기간은 전문가와 확인한다(10-6, 열린 질문 3).
- **지워 달라는 요청:** 권한 `customer.anonymize`로 그 손님의 칸을 개인정보 칸 목록대로 지운다. 장부 자유 글에 이름이 있으면 `(지움)`으로 가린다. **백업 안의 옛 사본이 사라지는 때:** WAL 복제본 7일, 날마다 스냅샷 35일, 작업 기록 구간의 개인정보 부분 35일(개인정보 없는 부분은 시즌 + 지난 시즌 남지만 이름 · 전화가 없다), 주 · 시즌 스냅샷은 처음부터 손님 정보를 지운 사본. 그래서 **35일 안에 모든 사본에서 사라진다.** 되살리기를 하면 지우기를 다시 적용한다(6-2). 요청을 받은 날과 처리한 날은 사용 내역에 남는다.
- **기기 안의 사본:** 카운터는 오늘 일할 팀들의 이름 · 전화, 기사 기기는 자기 차량의 오늘 열린 업무의 작은 접수 카드뿐이다(sync 8-1). 로그아웃 · 기기 막기에서 지우고, 연결되지 않으면 기기가 스스로 지운다(5-4). 보낸 기록의 원문 이름 · 전화는 24시간만 둔다.
- **기사 휴대폰은 업무용 지급이 기본이다.** 개인 휴대폰이면 화면 잠금을 강제할 길이 없으므로, 쓰는 동안 화면 잠금을 켜고 퇴사 때 '기기 막기 + 앱 저장소 지우기'를 한다(절차는 11절, 가게의 의무는 10-6).

### 10-6. 전문가와 확인할 것(법률 자문이 아님)

아래는 개인정보 · 세무 전문가에게 확인할 **항목 목록**이다. 이 문서는 법률 판단을 하지 않는다.

1. 손님 이름 · 전화를 모으는 근거(대여 계약의 이행으로 충분한지, 따로 동의가 필요한지)와 가게에 붙일 안내문.
2. 가게(개인정보처리자)와 우리(처리를 맡은 곳)의 **처리 위탁 계약서**에 들어갈 것, 가게의 처리방침에 우리를 어떻게 적을지.
3. 안전성 확보 조치로 필요한 것: 접근 권한 · 접속 기록 보관 기간 · 암호화해야 하는 항목(전화번호 포함 여부) · 비밀번호 규칙이 이 설계로 충분한지.
4. 보관 기간(기본 3년으로 둔 값)과 파기 방법, 백업 안의 사본 처리(WAL 복제본 7일, 날마다 스냅샷 35일, 작업 기록 구간의 개인정보 부분 35일, 주 · 시즌 사본은 손님 정보를 지운 것)가 받아들여지는지.
5. 유출 사고가 나면 누구에게 언제까지 알려야 하는지(가게와 우리 중 누가).
6. 손님의 열람 · 정정 · 삭제 요청을 받는 창구와 처리 기한.
7. 감시 · 오류 수집 · 문자 업체 · 원격 화면 도움 도구가 해외 서비스일 때 국외 이전에 해당하는지(그래서 로그에 개인정보를 넣지 않는다, 8절).
8. 장부 · 증빙의 세무 보관 의무 기간(시즌 끝 스냅샷 5년으로 둔 값)과, 그 사본에서 손님 정보를 지워도 되는지.
9. 원격 지원 중 공급자가 매장 자료를 볼 때의 허락과 기록 방법(9절: 시즌 1은 서버 API를 거치는 명령줄 도구, 매장의 2시간 허락, 비상 접근은 매장에 보임)이 충분한지.
10. 나중에 차량 위치를 모으게 되면 위치정보 관련 의무.
11. 사이즈 미리 받기 · 일행 이름에 만 14세 미만 아이가 흔한데, 보호자 동의가 필요한지와 입력폼 안내.
12. 재위탁(하위 처리자): 호스팅 업체, 다른 회사의 둘째 저장소, 문자 업체, 가동 확인 · 알림 서비스, 원격 화면 도움 도구를 가게에 어떻게 알리고 동의받는지.
13. 계약이 끝날 때의 반환 · 파기(6-7)와 세무 보관을 누가 지는지.
14. 기사 개인 휴대폰에 손님 정보를 둘 때 가게의 의무와 퇴사 때 지우기(10-5).
15. 직원 개인정보(이름 · 전화 · 기기 로그인 기록처럼 누가 무엇을 했는지 남는 기록)를 모으는 근거, 보관 기간, 직원 안내.
16. 개인정보 읽기 접속 기록(`pii_access_log`)의 범위와 보관 기간(10-4).
17. 가게 보관용 내보내기 파일을 가게 PC에 둘 때의 안전 조치(6-6).
18. 주 · 시즌 '손님 정보를 지운 사본'이 접수 번호 · 금액 · 시각으로 사람을 다시 알아볼 수 있는지(가명정보에 해당하는지)와 5년 보관의 목적.

### 10-7. 자료는 한국 안에

- 운영 서버, 복제본, 스냅샷, 작업 기록 구간, 연습 서버, 되살리기 연습 칸 모두 **한국 안의 데이터 센터**에 둔다(4절). 해외 업체를 고르더라도 한국 지역만 쓴다.
- 기기 안의 사본은 그 기기(가게 · 기사)에 있다.
- 한국 밖으로 나갈 수 있는 것은 개인정보가 없는 것(코드, 빌드, 체험판, 개인정보 없는 감시 숫자)뿐이다. 원격 화면 도움의 화면 중계도 한국 안을 고른다(9절). 운영 자료 · 화면 캡처를 AI 도구 · 해외 서비스에 넣는 것도 국외 이전이라 하지 않는다(8절).

## 11. 첫 매장에 필요한 것

| 무엇 | 비고 |
|---|---|
| 카운터 PC 두 대(Chrome 또는 Edge, 설치한 PWA) | 윈도 로그인 켜기, 작업 표시줄 자동 숨김 권함(ui 3-7), Chrome 관리 정책으로 이 앱의 사이트 자료 지우기 막기(sync 8-5) |
| 가게 인터넷 + **예비 회선 자동 넘어가기**(듀얼 WAN 공유기 + LTE 요금제) | **개장 조건**(migration 6-1 G2): 선을 뽑으면 몇 초 안에 저절로 넘어가야 한다. 휴대폰 테더링처럼 사람이 바꾸는 것은 대신하지 못한다(열린 질문 23). 4~5주차에 설치 · 확인 |
| 카드 단말기 | 지금 쓰는 것 그대로(자기 회선). 포스에는 `카드`와 승인번호를 적는다(sync 8-10) |
| 영수증 · A4 프린터 | 인쇄 도우미는 카운터 PC의 작은 프로그램(기기로 등록, `localhost` 창구) |
| 기사 태블릿 · 휴대폰 | 업무용 지급이 기본. 화면 잠금 켜기, 등록 번호로 붙이기(두 단계). 개인 휴대폰이면 퇴사 때 기기 막기 + 앱 저장소 지우기 |
| 원격 화면 도움 프로그램 | 한국 안 중계, 무인 접속 끔, `원격 도움 받기` 버튼과 확인 말로만 시작(9절) |
| 복구 열쇠 종이 | 가게 보관용 내보내기의 개인 키(QR, 금고, 6-6) |
| 둘째 사람의 봉투 | 공급자가 멈출 때(12절) |
| **서버 PC · USB · 매장 랜선 복사** | **필요 없음**(옛 D4) |

**두 번째 매장부터의 개설 목록:** 라이선스(루트 키로 서명) → `shop.provision`(목록이 `tenants`에서 나오므로 복제 · 스냅샷 · 연습에 저절로 들어감) → 첫 스냅샷 · 복제 위치 확인(그 전에는 기기 등록이 막힘) → 가게 인터넷 측정 시작 · 예비 회선 자동 넘어가기 → 기기 등록(두 단계) · 원격 도움 도구 · 복구 열쇠 종이 → 교육(인터넷 선 뽑고 일해 보기). 두 번째 매장 전에 할 일: 쓰기 프로세스 나누기(2-2), 라이선스 강제 켜기(5-1), 관리자 콘솔(또는 명령줄 도구의 허락 기록 완성).

## 12. 공급자가 멈출 때(혼자인 개발자)

클라우드 중심은 '매장 하드웨어 사고'를 '공급자 한 사람 사고'로 옮겼다: 개발자가 아프거나 연락이 끊기면 라이선스가 갱신되지 않고, 서버 · 호스팅 요금 · 백업 키에 닿을 사람이 없다.

- **둘째 사람:** 봉투(백업을 푸는 개인 키, 호스팅 계정 복구 수단, 루트 키로 미리 서명한 시즌 끝까지의 비상 라이선스 연장, 한 쪽짜리 되살리기 절차)를 받을 사람을 정하고(신뢰할 수 있는 제3자 · 에스크로), 해마다 한 번 함께 되살리기를 연습한다. 쓰는 조건(개발자가 며칠 연락이 안 될 때)을 봉투에 적는다.
- **휴대폰에서 누르는 버튼:** 되살리기 · 유예 늘리기 · 기기 막기는 휴대폰에서 누를 수 있는 작업 버튼이다(6-2). 노트북 · 명령줄이 없어도 된다.
- **가게가 가진 것:** 가게 보관용 내보내기의 손님 정보를 뺀 장부 사본은 기본 켬이다(6-6). 연락 두절이 길 때 가게가 할 일을 한 장으로 드린다(종이 장부로 일하기, 둘째 사람 연락처, 복구 열쇠 종이의 쓰임).
- 이 의존을 사장님께 드리는 설명(README D4 · 열린 질문 19)에 한 줄로 적는다.
